# 角色档案字段设计深入探讨

> 版本：v1.0 · 状态：设计探讨（2026-11-25）  
> 项目：StoryForgeAI —— 专业小说 AI 写作软件  
> 类型：数据模型设计探讨  
> 关联：[知识库结构化字段详细定义](./知识库结构化字段详细定义.md)、[知识库条目分类规则](./知识库条目分类规则.md)、[知识库新类型完整定义](./知识库新类型完整定义.md)  
> 说明：本文档深入分析 `character` 类型的字段取舍、与产品模块的联动、边界情况与演进空间，供产品与研发对齐。

---

## 一、设计目标与约束

### 1.1 角色档案要解决什么问题

在 StoryForgeAI 中，角色不是静态设定，而是会被多次消费的核心资产：

| 消费场景 | 对字段的需求 |
|----------|--------------|
| **角色 Agent** | 需要稳定的人设、说话方式、关系，用于生成符合角色的对话与行为 |
| **角色版图** | 需要姓名、关系、阵营/身份，用于可视化连线 |
| **写作引用** | 需要快速扫视的性格、背景、弧光，避免写崩人设 |
| **剧情推衍** | 需要动机与关系，支持「这个角色会如何反应」的推理 |
| **知识库检索** | 需要可被灵感、设定、其他角色关联的结构化锚点 |

因此字段设计必须同时满足：**对人可读**、**对模型可注入**、**对图谱可连边**。

### 1.2 与现有类型的边界

| 对比类型 | 差异 |
|----------|------|
| `novel` 中的 characters[] | 小说拆文里的角色是「该文本中出现的角色快照」，字段较浅；`character` 是独立、可演进的权威人设 |
| `setting` | 设定集描述规则与世界；角色档案描述「具体的人」 |
| `inspiration` | 灵感是碎片想法；角色档案是相对完整、可维护的实体 |

**原则**：同一角色可以同时存在于小说拆文快照与独立 `character` 条目；长期应以 `character` 为权威源，小说中的角色信息可「提升」为独立档案。

## 二、当前字段方案回顾

当前定义（v1.1）：

```ts
interface CharacterStructured {
  name: string;                          // 主角色名（必填）
  aliases?: string[];                    // 别名/绰号
  identity: string;                      // 一句话身份定位（必填）
  personality: string[];                 // 性格关键词或描述（必填）
  background: string;                    // 背景故事摘要（必填）
  appearance?: string;                   // 外貌
  abilities?: string[];                  // 能力/特长
  arc?: string;                          // 人物弧光
  speech_style?: string;                 // 对白风格与用词习惯
  relationships: { target: string; relation: string }[];  // 必填，可为空数组
  key_quotes?: string[];                 // 代表性台词
  notes?: string;                        // 其他补充
}
```

## 三、逐字段设计分析

### 3.1 name（主角色名）— 必填

**为什么必填**  
- 检索、展示、Agent 注入、版图节点的主标识。  
- 没有稳定名称的角色难以被引用与关联。

**设计注意**  
- 允许笔名/化名写在 `aliases`，`name` 取作者最常用的称呼。  
- 群像或「某某等人」不适合作为单条 character；应拆成多条或归入 setting。  
- 重名角色：用 `identity` 或 `tags` 区分（如「少年林远」vs「晚年林远」），或在 title 层体现。

### 3.2 aliases（别名）— 可选

**价值**  
- 支持「真名 / 化名 / 外号 / 前世名」等多名并存。  
- 检索时可同时命中别名。

**建议**  
- 数组即可，无需再分子类型（真名/外号），除非产品明确要做「揭秘真名」玩法。  
- 数量建议上限 5–8，避免噪音。

### 3.3 identity（一句话身份）— 必填

**价值**  
- 列表卡片、版图节点、Agent 系统提示中的「第一眼定位」。  
- 例：「青云城少年，玄天体持有者」「前朝公主，现隐姓埋名」。

**设计原则**  
- 强制一句话，避免写成段落。  
- 前端展示优先于 `background` 的长文。

**替代方案讨论**  
- 有人主张用 `role`（主角/配角/反派）枚举。  
- 建议：**不替代 identity**，角色功能定位可用顶层 `tags`（主角、反派、导师）补充，identity 保留自由文本的丰富度。

### 3.4 personality（性格）— 必填，数组

**为什么用数组而非长文本**  
- 便于 Agent 注入时做「关键词约束」。  
- 便于卡片展示与筛选（如「所有坚毅的角色」）。  
- 降低模型把性格写成流水账的概率。

**粒度建议**  
- 3–8 个词条为宜。  
- 可以是词（「隐忍」）或短句（「对认定的人极度护短」）。  
- 避免把背景故事写进性格。

**进阶可能**  
- 后续可增加 `personality_conflicts[]`（性格内部矛盾），对复杂角色很有用，但 v1 可先放在 `notes` 或 `arc`。

### 3.5 background（背景）— 必填

**价值**  
- 动机与行为的根源，Agent 与推衍强依赖。  
- 与 `arc` 区分：background 是「过去已发生」，arc 是「变化路径」。

**长度**  
- 建议摘要级（100–400 字），细节仍以 `raw_content` 为准。  
- 超长背景应鼓励作者拆成「背景事件」时间线（可关联 `timeline` 类型）。

### 3.6 appearance（外貌）— 可选

**争议点**  
- 部分作者不重视外貌；部分类型（言情、影视化）非常重视。  
- 对纯文本 Agent 对话帮助有限，对封面/立绘/多模态未来有价值。

**结论**  
- 保持可选。  
- 若产品后续做「角色形象生成」，再考虑结构化五官字段；当前一段描述足够。

### 3.7 abilities（能力）— 可选数组

**价值**  
- 玄幻/科幻/系统文中高频。  
- 可与 setting 中的力量体系交叉引用。

**注意**  
- 不要与 setting 的「体系规则」重复：abilities 写「该角色具体会什么」，体系规则写在 setting。  
- 能力会随剧情变化时，可用 `notes` 或未来「版本快照」处理，v1 不强制版本化。

### 3.8 arc（人物弧光）— 可选

**价值**  
- 区分「静态人设」与「成长/堕落轨迹」。  
- 对长篇与角色驱动故事极关键。

**形式**  
- 一段话描述即可（「从隐忍复仇到学会信任」）。  
- 不强制三幕式结构，降低录入成本。

**与 plot_template 的关系**  
- 角色弧光是「这个人怎么变」；情节模板是「故事怎么走」。二者可互相参考，但字段独立。

### 3.9 speech_style（对白风格）— 可选，但对 Agent 极重要

**为什么单独成字段**  
- 角色 Agent 生成对话时，这是最直接的约束信号。  
- 例：「短句为主，很少比喻」「温言软语但暗藏机锋」「口头禅：有意思」。

**设计建议**  
- 保持自由文本，不要过早枚举「傲娇/高冷」等标签（可用 tags 补充）。  
- 鼓励作者写「怎么说」而不是「是什么性格」（性格已在 personality）。

### 3.10 relationships（关系）— 必填（可为空数组）

**结构**  
```ts
{ target: string; relation: string }
```

**为什么 target 用字符串而非 entry id**  
- 录入阶段对方可能尚未建档。  
- 允许写「神秘黑衣人」等未命名对象。  
- 后续可用「关系对齐」工具把 target 文本匹配到 character 条目并回写 link。

**演进方向**  
- v1：字符串 target + 自由 relation 文本。  
- v2：可选 `target_id`，以及 `relation_type` 枚举（敌对/亲情/师徒/恋人…）便于版图自动连线与筛选。  
- 双向关系：不在单条档案里强制对称；版图层做聚合展示。

### 3.11 key_quotes（代表性台词）— 可选

**价值**  
- 快速传达角色语气与价值观。  
- 可作为 Agent few-shot 或写作时的语气锚点。

**建议**  
- 上限 5 条左右。  
- 来自作品原文或作者设定均可，建议在 notes 中标注来源（可选）。

### 3.12 notes（补充）— 可选

**定位**  
- 垃圾桶与扩展槽：无法归入上述字段的信息、作者备注、待定设定。  
- 避免为小众需求不断加字段。

## 四、必填与可选的取舍原则

| 原则 | 应用 |
|------|------|
| 没有它就无法稳定引用/展示 | → 必填（name, identity） |
| 没有它 Agent 容易崩人设 | → 必填（personality, background） |
| 关系是版图与推衍的边 | → relationships 必填，但允许 `[]` |
| 强依赖题材或作者习惯 | → 可选（appearance, abilities, arc, speech_style, key_quotes） |
| 录入成本过高会降低建档率 | → 能选则选，用好的空态引导补全 |

**产品策略建议**：  
创建档案时只强制 name + identity + personality + background；其余在详情页用「完善人设」引导逐步补全，并显示完整度百分比。

## 五、与产品模块的数据流

```text
知识库 character 条目
        │
        ├──► 角色版图：name + identity + relationships → 节点与边
        ├──► 角色 Agent：personality + speech_style + background + key_quotes → 系统提示/约束
        ├──► 写作区引用：卡片展示 identity + personality + arc
        ├──► 剧情推衍：relationships + arc + background → 行为倾向
        └──► 小说拆文：可将 novel.characters[]「提升」为独立 character 条目
```

**权威源原则**：  
一旦某角色有了独立 `character` 条目，Agent 与版图优先读该条目；小说内快照仅作历史或章节局部状态。

## 六、边界与常见问题

| 问题 | 建议处理 |
|------|----------|
| 群像「三位一体反派」 | 拆成 3 条 character，用 relationships 互指；或一条 setting 描述组织 |
| 角色改名 | 旧名移入 aliases，name 更新；links 与版图需同步 |
| 同一角色不同时期（少年/老年） | 两条 character + tags（时期）；或一条 + arc 描述变化，按产品复杂度选择 |
| 只有一句话人设 | 允许建档，完整度低；用引导补全，不要拦截 |
| 关系对方不存在 | target 保持字符串；提供「一键创建对方档案」入口 |
| 与 setting 中的「种族模板」重复 | character 写个体差异；种族共性写在 setting，character 可 link 到该 setting |

## 七、可选演进（非 v1 范围）

1. **关系类型枚举 + target_id**  
   提升版图自动布局与筛选能力。

2. **人设版本 / 时间切片**  
   支持「第 10 章时的林远」与「结局时的林远」并存，服务长篇一致性检查。

3. **与剧情树节点绑定**  
   角色在某一情节节点的状态（受伤、黑化）作为临时覆盖，不污染主档案。

4. **对白样本库**  
   从 key_quotes 扩展为可增删的样本集，供 Agent 做 few-shot。

5. **完整度与质量分**  
   根据字段填充率与关联数给出「可注入 Agent」的就绪状态。

## 八、字段优先级小结（给实现与提示词）

| 优先级 | 字段 | 说明 |
|--------|------|------|
| P0 必填 | name, identity, personality, background, relationships | 最小可用人设 |
| P1 强烈建议 | speech_style, arc, abilities | Agent 与长篇质量关键 |
| P2 按需 | appearance, aliases, key_quotes, notes | 题材与作者习惯决定 |

**LLM 拆分提示词应**：  
- 强制产出 P0 字段；  
- 对 P1 尽量提取；  
- P2 有则写、无则省略；  
- 禁止编造原文未出现的能力、关系或台词。

## 九、结论与建议

1. **当前字段集总体合理**，覆盖了引用、Agent、版图三类核心消费场景，且录入负担可控。  
2. **relationships 用字符串 target 是务实选择**，降低冷启动成本；后续再用 target_id 增强。  
3. **speech_style 与 arc 虽为可选，但对产品差异化很重要**，应在 UI 上给予明确引导。  
4. **不要过早增加「阵营、数值、技能等级」等游戏化字段**，除非产品明确走向系统文/游戏化辅助；用 abilities + notes + tags 即可覆盖大多数网文需求。  
5. **下一步可落地**：  
   - 定稿本字段为 character 的权威 schema；  
   - 补全 character 专用 Few-shot 拆分提示词（已有骨架）；  
   - 设计「从小说角色快照提升为档案」的交互；  
   - 角色版图与 Agent 注入明确优先读 character 条目。
