## 一、问题定义

### 1.1 要解决什么

作者需要一张**可读、可交互**的角色关系图，用于：

| 场景 | 需求 |
|------|------|
| 写作中途查关系 | 快速看到「A 和谁有关、是什么关系」 |
| 长篇防崩 | 发现遗漏的对立/同盟、检查关系是否自洽 |
| 角色版图展示 | 阵营、主配角、感情线一目了然 |
| 与 Agent 联动 | 推衍时注入「当前相关人物子图」 |

### 1.2 与通用知识图谱的差异

| 维度 | 通用知识图谱 | 角色关系图谱 |
|------|--------------|--------------|
| 节点 | 条目、概念、事件混杂 | **几乎全是角色**（可少量组织/势力节点） |
| 边 | 多种语义、常很稀疏 | **关系类型有限但社交密度高**（群像戏） |
| 规模 | 可达上千 | 单部作品常见 **20–150 角色**，很少超过 300 |
| 审美 | 分析向 | **叙事向**：主配角层级、阵营、感情线要可读 |
| 动态 | 偏静态分析 | 随连载**演进**（反目、结盟、死亡） |

结论：不必上超大规模图引擎；应优先 **中小规模力导向 + 关系类型视觉编码 + 可选社区/层级**。

## 二、数据模型

### 2.1 节点（Node）

来源优先：知识库 `type = character` 的独立档案。

```ts
interface RelationGraphNode {
  id: string;                    // character entry id
  label: string;                 // name
  identity?: string;             // 一句话身份，作副标题
  tags?: string[];               // 主角/反派/配角等
  importance?: number;           // 0–1，用于节点大小（出现次数、关联度等）
  camp?: string;                 // 可选阵营（来自 tags 或后续字段）
  fixed?: boolean;               // 是否钉住位置
}
```

可选扩展节点：`setting` 中的组织（青云宗、丞相府），用不同形状区分。

### 2.2 边（Edge）

来源：`character.structured.relationships[]`。

当前字段为：

```ts
{ target: string; relation: string }  // target 多为名称字符串
```

图谱层建议归一为：

```ts
interface RelationGraphEdge {
  id: string;
  source: string;                // node id（解析后）
  target: string;                // node id
  relationLabel: string;         // 原始「师徒/敌对/…」文本
  relationType?: RelationType;   // 归一化枚举，便于颜色与布局
  weight?: number;               // 亲密度/戏份权重，默认 1
  directed?: boolean;            // 是否有向（师生 vs 互为宿敌）
}

type RelationType =
  | 'family'      // 亲情/血缘
  | 'romance'     // 恋慕/夫妻
  | 'mentor'      // 师徒
  | 'ally'        // 同盟/朋友
  | 'enemy'       // 敌对
  | 'faction'     // 同门/同组织
  | 'other';
```

### 2.3 名称 → id 解析（关键预处理）

因 `target` 允许未建档字符串，建图前需要 **实体对齐**：

1. 精确匹配 `name` / `aliases`  
2. 归一化（去空格、全半角、常见别名表）  
3. 仍无匹配 → **悬空节点**（虚线框占位）或丢弃边并记日志  
4. 提供「一键创建档案」把悬空点升级为 character  

双向边：若 A→B「师徒」与 B→A「徒弟」同时存在，可合并为一条边、双向标签，或保留两条有向边（产品二选一，建议 **合并 + 主标签**）。

## 三、布局算法选型

单部作品节点少，布局目标是 **叙事可读**，不是学术最优。

### 3.1 推荐主方案：力导向（Force-Directed）

适用：多数群像、关系网状、无严格层级。

| 算法族 | 适用 | 说明 |
|--------|------|------|
| **Fruchterman-Reingold / d3-force** | 默认首选 | 实现成熟，react-force-graph 开箱即用 |
| **ForceAtlas2 风格** | 有明显枢纽（主角） | 度加权排斥，主角更居中、配角铺开 |
| **带约束的力导向** | 需要分层 | 给「主角层」加 y 约束或环形半径约束 |

**角色图专用力建议：**

| 力 | 作用 |
|----|------|
| 排斥（charge） | 防重叠；枢纽可略强 |
| 边吸引力 | `weight` 大则理想长度更短（亲密关系更近） |
| 按 relationType 调 linkDistance | 敌对略长、亲情/恋人略短 |
| 重力 / center | 防止子图飞散 |
| 碰撞 | 为标签留空 |
| 可选：阵营质心引力 | 同 `camp` 节点互相吸引，形成阵营团块 |

### 3.2 辅助方案：径向 / 层级

| 布局 | 何时用 |
|------|--------|
| **径向（主角中心）** | 以某角色为中心的「自我中心图」（1–2 跳），写作时最常用 |
| **层级（Sugiyama 等）** | 师徒链、权力结构、家族树 |
| **环形分组** | 明确多阵营对峙（正派环 / 反派环） |

产品建议：

- **全局版图**：力导向 + 阵营着色  
- **点选某角色**：切到径向自我中心图（只显示 k 跳邻居）

### 3.3 自我中心图（Ego Graph）算法要点

1. 选定中心 `c`  
2. BFS / 受限 DFS 取距离 ≤ k 的节点（k=1 或 2）  
3. 中心固定在画布中心（`fx, fy`）  
4. 一层邻居铺在圆环上，二层再外环  
5. 仍可用轻微力导向微调，避免边交叉  

复杂度：O(|E_sub|) 级别，实时切换无压力。

## 四、关系类型与视觉编码

算法之外，**编码**决定「一眼能读」。

| 通道 | 建议 |
|------|------|
| 边颜色 | family=暖色, romance=红/粉, enemy=红暗/橙, ally=绿/青, mentor=蓝紫 |
| 边线型 | 敌对=虚线或闪电感；血缘=实线加粗；暧昧=点线 |
| 边粗细 | 由 `weight` 或同现次数 |
| 节点大小 | importance（出场章数、关联度、是否主角 tag） |
| 节点颜色 | 阵营 或 角色功能（主角/反派/配角） |
| 箭头 | 有向关系（师→徒）显示箭头；对称敌对可无箭头 |

`relation` 自由文本 → `relationType` 可用规则 + 轻量 LLM 分类（关键词：师/徒/父/敌/爱…），失败则 `other`。

## 五、社区与阵营发现（可选增强）

当角色 > 40 且阵营未标注时，可用图算法提示「可能的阵营」：

| 算法 | 特点 | 规模适配 |
|------|------|----------|
| **Louvain / Leiden** | 模块度社区发现，常用 | 百级节点极快 |
| **标签传播 Label Propagation** | 实现简单、速度快 | 适合在线粗分 |
| **连通分量** | 只分「是否有关系路径」 | 过粗，仅作基础 |

**注意**：小说里「敌对」边会把对立双方连在同一连通分量里。社区发现前可：

- 仅用 ally/family/faction/mentor 边做社区；或  
- 对 enemy 边采用 **负权** / 同步磁斥力（高级，非 v1 必需）

v1 更推荐：**作者用 tags/camp 手动标阵营**，算法只做布局与筛选。

## 六、增量与时序

### 6.1 增量布局

新增角色或关系时：

1. 旧节点保持当前位置为初始值  
2. 仅对新节点随机或按邻居质心初始化  
3. 短时间、小 `alpha` 力导向迭代，避免整图「爆炸重排」  

这与知识图谱实践一致：**位置稳定性 > 单次全局最优**。

### 6.2 时序版本（演进图谱）

长篇中关系会变（反目、成亲）。可选模型：

```ts
edge: {
  validFromChapter?: number;
  validToChapter?: number;
}
```

UI 用章节滑块过滤当前生效边；布局可在相邻章节间做插值，减少跳动。

v1 可不做时序，用 `notes` 或归档旧关系即可。

## 七、交互与查询算法

| 交互 | 算法/实现 |
|------|-----------|
| 点击节点 | 高亮邻居 + 一度边；侧栏展示 character 档案 |
| 搜索角色 | 名称/别名索引，定位并聚焦 |
| 按关系类型筛选 | 边过滤后可能需轻度重新布局或仅隐藏 |
| 最短关系链 | BFS 求 A 到 B 的路径（「他们怎么扯上关系的」） |
| 子图导出 | 诱导子图 + 当前坐标序列化 |

最短路径对作者很有用：解释配角如何通过中间人连到主角。

## 八、性能与实现栈建议

| 项目 | 建议 |
|------|------|
| 规模 | 按单作品 300 节点以内设计；超出则默认只渲染「核心角色」子图 |
| 库 | **react-force-graph-2d**（Canvas）或 reagraph；角色图不必一上来 WebGL |
| 布局计算 | 主线程可接受；>200 节点可考虑把 tick 放到 worker |
| 数据准备 | 服务端或客户端做 name→id 解析与 relationType 归一 |
| 缓存 | 按 `workId + 图谱版本` 缓存节点坐标 |

与现有「知识图谱可视化」结论一致：**本地/作品级子图优先，全库大图非角色版图目标**。

## 九、推荐落地路径

### Phase 1 — MVP（与 character 同步）

1. 从 character 档案构建无向边列表，完成 name→id 匹配  
2. 全局力导向 + 节点点选查看档案  
3. 边标签显示 `relation` 原文  
4. 位置本地缓存，避免每次重开乱跳  

### Phase 2 — 可读性

1. `relationType` 归一 + 颜色/线型编码  
2. 自我中心图（k=1/2）  
3. 按 tag 筛选主角/反派  
4. 悬空 target 引导创建档案  

### Phase 3 — 增强

1. 阵营手动标注 + 质心引力  
2. 最短关系链  
3. 章节时序边（可选）  
4. 与剧情树节点联动高亮

## 十、与 Agent / 推衍的接口

推衍或对话前，可截取：

```text
以「当前场景出场角色」为中心的 1 跳子图
→ 序列化为短文本：
  林远 —敌对→ 贺兰策
  林远 —师徒→ 陈墨
```

注入 Prompt，比丢整张全局图更稳、更省 token。

算法上即：**以集合 S 为种子的诱导子图 / 星型邻域**。

## 十一、风险与对策

| 风险 | 对策 |
|------|------|
| target 对不上号，图很碎 | 对齐工具 + 悬空节点 + 别名 |
| 敌对边造成「视觉上像一伙」 | 边颜色区分；社区只用正向边 |
| 每次打开布局大变 | 坐标持久化 + 增量布局 |
| 群像边太多交叉 | 自我中心视图；按类型过滤；适当增大排斥 |
| 关系文本极不规范 | 关键词规则 + 可选 LLM 归一到 relationType |

---

## 十二、结论

1. **数据**：以 character 为权威节点，relationships 为边；先做好 **名称对齐** 与可选 **关系类型归一**。  
2. **布局**：默认 **力导向（FR/d3-force 或 FA2 风格）**；写作场景叠加 **径向自我中心图**。  
3. **规模**：按单作品中小图设计，优先稳定与可读，而不是复杂社区算法。  
4. **演进**：MVP 先通「能看、能点、能缓存位置」；再加颜色编码与自我中心；时序与社区后置。  
5. **与创作链路**：子图抽取服务于 Agent 推衍，是关系图谱的第二价值，不仅是可视化。
