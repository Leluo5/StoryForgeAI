## 一、问题定义与约束

### 1.1 业务目标

知识库已具备：
- 五种条目类型（文章 / 论文 / 小说 / 灵感 / 设定集）
- 跨条目关联（`links` 字段，灵感默认最多自动关联 3 条）
- 小说内部结构化关系（角色关系、情节节点等）

可视化目标是让创作者：
1. **快速感知**条目之间的关联网络
2. **发现**被忽略的连接或孤立节点
3. **从关联出发**跳转到相关素材，辅助创作决策

### 1.2 规模与技术约束

| 约束项 | 当前预期 | 说明 |
|--------|----------|------|
| 节点规模 | 全局 ≤ 2000，单作品 ≤ 500 | 来自 M3c-3 验收口径 |
| 边密度 | 稀疏（灵感关联 ≤ 3，人工关联较少） | 非高密度社交网络 |
| 技术栈 | React 19 + TypeScript | 需良好 React 集成 |
| 交互设备 | 桌面优先（1024 / 1440） | 暂不考虑移动端复杂手势 |
| 视觉风格 | 墨韵科技风 + 知识库 cyan 语义色 | 需与现有 UI 规范一致 |
| 性能底线 | 初始渲染 < 1s，交互流畅（60fps 优先） | 与列表检索目标对齐 |

### 1.3 核心使用场景

1. **全局图谱**：查看整个知识库的关联全貌，按类型过滤。
2. **局部图谱（Local Graph）**：以当前条目为中心，展示 1–2 跳邻居（最常用）。
3. **小说内部关系图**：角色关系 + 情节节点（可作为图谱的特殊视图）。
4. **从图谱跳转详情**：点击节点打开右侧详情或抽屉预览。

## 二、可视化形态选型

### 2.1 推荐形态优先级

| 优先级 | 形态 | 适用场景 | 理由 |
|--------|------|----------|------|
| **P0** | **力导向图（Force-directed）** | 全局 + 局部关联探索 | 最符合「知识网络」心智模型，稀疏图效果好 |
| **P1** | **局部邻居图（Ego Graph）** | 条目详情页 / 抽屉 | 信息密度可控，性能极佳，创作时最实用 |
| **P2** | **层次 / 树状** | 小说四维大纲、设定层级 | 已有大纲树，可复用；不适合通用关联 |
| **P3** | **矩阵 / 表格** | 大量类型对比 | 辅助分析，非主视觉 |

**不推荐作为主方案**：
- 纯 3D 图谱（认知负担高，桌面写作场景收益低）
- 高密度边捆绑（当前边少，过度设计）

### 2.2 节点与边设计建议

**节点**
- 形状或颜色按类型区分（文章 / 论文 / 小说 / 灵感 / 设定集）
- 大小可映射「关联度」或「被引用次数」
- 标签默认显示标题（过长截断），悬停显示完整信息
- 选中 / 聚焦时高亮自身 + 直接邻居，其余降低透明度

**边**
- 默认细线，颜色中性或按关联类型（reference / inspiration / conflict）区分
- 支持箭头（有向）或无向
- 悬停显示关联说明（如有）

**交互最低集**
- 缩放 / 平移
- 拖拽节点（临时固定）
- 点击节点 → 打开详情
- 双击或「展开」→ 加载更多邻居（渐进式）
- 类型过滤、搜索定位节点

## 三、技术库选型对比（2026 现状）

针对 React 技术栈 + 中小规模知识图谱，主流选择如下：

| 库 | 渲染 | 适合规模 | React 友好度 | 布局能力 | 推荐指数 | 备注 |
|----|------|----------|--------------|----------|----------|------|
| **react-force-graph** | Canvas / WebGL | 500–2k（2D） | 极高（声明式） | 力导向为主 | ★★★★★ | 最简单上手，知识图谱常用 |
| **reagraph** | WebGL | ~1万 | 高（原生 React） | 15+ 内置布局 | ★★★★☆ | 性能更好，功能更全 |
| **Sigma.js + Graphology** | WebGL | 5万+ | 中（需包装） | 外部布局 | ★★★★ | 大规模首选 |
| **Cytoscape.js** | Canvas | ~5k | 中（官方 React 包装有） | 丰富 + 图算法 | ★★★★ | 需要路径分析、聚类时强 |
| **React Flow (xyflow)** | DOM + SVG | <500 推荐 | 极高 | 需外部布局 | ★★★ | 更适合「可编辑流程图」，非纯探索 |
| **AntV G6** | Canvas / SVG | 中大 | 中 | 强 | ★★★ | 国内生态好，但包体与学习成本较高 |
| **Cosmograph** | WebGL GPU | 百万级 | 高 | GPU 力导向 | ★★ | 当前规模过重 |

### 3.1 针对本项目的推荐路径

**阶段 1（MVP，推荐立即采用）**  
→ **react-force-graph** 或 **reagraph**

- 理由：规模匹配、React 集成成本最低、力导向效果直接满足「知识网络」需求。
- 实现重点：局部图（以当前条目为中心）优先，全局图作为次要入口。

**阶段 2（增强分析能力）**  
→ 引入 **Cytoscape.js** 或 Graphology 做后端/前端图算法（最短路径、社区发现），可视化层仍可用 reagraph / Sigma。

**阶段 3（规模增长 > 5k）**  
→ 迁移到 **Sigma.js** 或 **Cosmograph**。

## 四、产品方案建议（分阶段）

### 方案 A：轻量局部图谱（推荐作为第一个可交付版本）

**位置**：
- 知识库详情页右侧或底部
- 工作台抽屉展开详情时同步显示

**交互**：
- 默认展示当前条目 + 直接关联条目（1 跳）
- 提供「展开 2 跳」按钮
- 节点点击打开详情，边无复杂操作
- 类型颜色与列表页保持一致

**技术**：react-force-graph（2D Canvas）即可。  
**价值**：实现成本低，创作过程中「顺藤摸瓜」最频繁。

### 方案 B：全局知识图谱页

**位置**：知识库全局管理界面新增「图谱」视图切换（列表 / 图谱）。

**功能**：
- 力导向全图 + 类型过滤 + 搜索定位
- 支持框选、高亮路径
- 孤立节点提示（帮助清理无关联素材）

**技术**：reagraph 或 react-force-graph。  
**注意**：2000 节点需做好初始布局收敛与性能监控。

### 方案 C：小说专用关系视图

**位置**：小说条目详情内的「角色关系 / 情节关系」Tab。

**形态**：可切换力导向或层次布局，节点为角色/情节点，边为关系类型。  
**价值**：与现有四维大纲互补，强化「人物关系网」感知。

## 五、UX 与视觉原则（对齐墨韵科技风）

1. **克制**：图谱不是装饰，默认局部、按需展开，避免一打开就「星空爆炸」。
2. **类型可读**：五种类型必须用稳定的颜色/图标区分（建议沿用 cyan 系变体 + 形状）。
3. **焦点优先**：当前节点始终视觉中心，邻居高亮，其余降权。
4. **可恢复**：提供「重置布局」「适应画布」按钮。
5. **深色模式**：节点与边在深色背景下对比度达标，避免发光过度。
6. **无障碍**：键盘可聚焦节点，屏幕阅读器可读标签。

## 六、风险与决策建议

| 风险 | 说明 | 缓解 |
|------|------|------|
| 性能回退 | 力导向在节点增多时卡顿 | 优先局部图；全局图做分页/过滤；监控 FPS |
| 布局不稳定 | 每次打开位置跳动 | 缓存节点位置，或提供「固定布局」选项 |
| 信息过载 | 用户不知道看什么 | 默认局部 + 明确空态与引导 |
| 与现有列表重复 | 图谱变成鸡肋 | 图谱必须提供列表无法快速完成的「关联发现」价值 |
| 实现周期 | 完整全局图开发成本高 | 先做方案 A（局部图），验证价值后再做 B |

**建议决策顺序**：
1. 确认是否在下一 Phase 启动图谱能力。
2. 若启动，优先落地 **方案 A（局部图谱）**。
3. 收集真实使用数据后再决定是否投入全局图谱。

## 八、结论

| 问题 | 结论 |
|------|------|
| 是否值得做？ | 值得，但应作为**增强能力**，而非当前阻塞项 |
| 首选形态 | 力导向 + 局部优先 |
| 首选技术 | 阶段 1：react-force-graph 或 reagraph |
| 落地节奏 | 先局部图谱（详情/抽屉）→ 再全局视图 → 再图算法增强 |
| 与现有设计关系 | 完全兼容方案 C 全页与方案 D 抽屉，作为新增视图即可 |
