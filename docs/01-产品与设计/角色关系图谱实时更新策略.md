## 一、更新要解决的三类一致性

| 层级 | 对象 | 「实时」含义 |
|------|------|----------------|
| **L0** | DB 中 character + relationships | 写入后立即成为权威真相 |
| **L1** | 会话内 Snapshot | 是否、何时跟上 L0 |
| **UI** | 角色版图可视化 | 节点/边增删改的动画与布局 |
| **L2** | 后续 Agent 调用的子图块 | 是否用到新关系 |

实时更新策略必须分别回答：**写路径、失效路径、读路径、布局路径**。

---

## 二、变更事件模型

所有更新收敛为领域事件，便于串流水线：

```ts
type GraphChangeEvent =
  | { type: 'node_upsert'; characterId: string; workId: string }
  | { type: 'node_remove'; characterId: string; workId: string }
  | { type: 'edge_upsert'; characterId: string; /* 源角色档案内 relationships 变 */ workId: string }
  | { type: 'edge_rebuild'; workId: string }  // 全量重建
  | { type: 'alias_change'; characterId: string; workId: string }; // 影响对齐
```

**触发源**：

| 来源 | 典型事件 |
|------|----------|
| 用户编辑角色档案 | node_upsert / edge_upsert |
| 拆文「提升为档案」 | node_upsert |
| 删除角色 | node_remove（级联边） |
| 改名 / 别名 | alias_change → 可能需重对齐悬空边 |
| 批量导入 | edge_rebuild（防抖后一次） |
| 关系变更提案确认 | edge_upsert |

## 三、L0 写路径策略

### 3.1 单条保存（默认）

```text
用户保存 character
  → 事务写入 DB
  → 同步 normalize 该条 relationships 的 relationType（可异步）
  → 发布 GraphChangeEvent
  → 返回成功
```

**不必**在请求内重算全作品图；单作品百级节点，事件驱动增量即可。

### 3.2 批量导入

- 导入过程中抑制逐条事件  
- 结束后发 **一次** `edge_rebuild`  
- 避免 N 次缓存击穿与版图连闪  

### 3.3 对齐（name → id）时机

| 策略 | 说明 | 推荐 |
|------|------|------|
| 写时对齐 | 保存时解析 target | 主路径 |
| 读时对齐 | 构建 snapshot 时再解析 | 作补全 |
| 定时全量 | 夜间任务 | 可选修复悬空 |

**alias_change** 后：对该 work 做一次「悬空边重对齐」增量扫描（只扫 target 字符串命中旧名/新名的边）。

## 四、Snapshot（L1）更新策略

与《多 Agent 图谱共享》对齐，提供三档策略，产品可配置：

### 4.1 策略 S1：会话冻结（最稳）

- 会话开始加载 snapshot，**中途不自动变**  
- L0 变更只更新缓存中的「最新版」，不替换当前 session 引用  
- UI 提示：「关系已更新，可刷新版图 / 新消息将使用新关系」  

**适用**：长对话、多 Agent 群戏，避免中途关系突变导致前后对白立场分裂。

### 4.2 策略 S2：惰性刷新（推荐默认）

```text
L0 变更 → 使 work 级 cache 失效（version++）
下次 getSnapshot(workId) 或下次 Agent 调用前：
  if session.graphVersion !== latestVersion:
    可选：自动换成新 snapshot 或弹确认
```

- **Agent 调用边界**刷新：下一次续写/发言用新图  
- **同一次多 Agent 串行**：仍用进入编排时锁定的 version（编排级冻结）  

**适用**：平衡一致与实时；大多数写作场景。

### 4.3 策略 S3：热更新（强实时）

- 事件到达即替换 session.snapshot  
- 已在飞行中的 LLM 请求不打断；仅影响后续  

**风险**：同一场戏前半旧关系、后半新关系。需配合「关系变更声明」插入系统消息。

**建议**：仅在用户显式「保存并应用到当前会话」时启用热更新。

## 五、缓存失效设计

```text
RelationGraphCache
  key: workId
  value: { version, snapshot, builtAt }
```

| 事件 | 动作 |
|------|------|
| node_upsert / edge_upsert / alias_change / node_remove | `invalidate(workId)` 或增量 patch |
| edge_rebuild | `invalidate` + 异步 rebuild 预热 |
| 读取未命中 | 同步 build（百节点可接受）或返回旧版 + stale 标记 |

### 5.1 增量 patch vs 全量 rebuild

| 条件 | 策略 |
|------|------|
| 单节点人设字段变、边不变 | patch node 属性，**version 仍应增加**（人设注入要新） |
| 单角色 relationships 变 | 移除该 source 旧出边，重解析写入新边；重对齐相关悬空 |
| 节点删除 | 删节点 + 所有关联边 |
| 别名变更 | 出边不变；入边 target 重对齐 |
| 变更集合 > 阈值（如 20% 边） | 全量 rebuild 更简单 |

单作品规模下，**「失效 + 懒重建」** 往往比复杂增量更不易错；增量作为优化项。

## 六、前端版图（UI）实时更新

### 6.1 推送通道

| 方案 | 说明 |
|------|------|
| WebSocket / SSE | `graph_updated { workId, version }`，客户端拉取新 snapshot 或 diff |
| 保存响应内带 version | 单页编辑够用；多标签页需广播 |
| 轮询 version | 简单兜底（30s） |

### 6.2 局部更新与布局稳定

目标：**加边不要整图随机重排**。

```text
收到 diff:
  1. 合并 nodes/edges 到当前图数据
  2. 旧节点保留 fx/fy 或当前 x/y 作为初始位置
  3. 仅新节点：放在邻居质心或画布中心附近
  4. 短时力导向（低 alpha、少 ticks）微调
  5. 停止后写回位置缓存（localStorage / 服务端）
```

| 变更类型 | UI 行为 |
|----------|---------|
| 只改 relationLabel/type | 改色/线型，不重新布局 |
| 新增边 | 补边 + 轻量布局 |
| 新增节点 | 入场动画 + 轻量布局 |
| 删除节点 | 淡出；邻居略收缩 |
| 全量 rebuild | 可保留位置 map，按 id 回放坐标 |

### 6.3 防抖

用户连续改同一角色关系时：

- 输入中 **300–500ms debounce** 再发保存（若自动保存）  
- 版图订阅端 **200ms debounce** 合并多次 `graph_updated`

## 七、与 Agent 注入的衔接

```text
编排开始
  → lock graphVersion = session 选定版本（S2：可先 sync latest）
  → 本轮所有 Agent 共用该 version 的 snapshot
  → 编排结束
L0 若在编排中被改：不影响本轮；下一轮再读新 version
```

**用户侧反馈**：

- 保存关系成功后 toast：「已更新关系；下一次生成将生效」  
- 若策略 S3：系统插入不可见或可见约束刷新块  

**进行中的流式生成**：不中断、不热补关系块（避免半截答案前后矛盾）。

## 八、多标签页 / 多端

| 问题 | 策略 |
|------|------|
| 页 A 编辑，页 B 版图 | WS 广播 `graph_updated`；B 合并 diff |
| 页 A、B 同时编辑同一角色 | 乐观锁 `updated_at` 或 version；冲突提示后加载最新 |
| 离线编辑 | 暂不作为 MVP；上线后以服务端权威合并 |

## 九、推荐总体策略（组合）

| 环节 | 推荐 |
|------|------|
| L0 写入 | 事务保存 + 领域事件 |
| 关系类型 | 写时规则归一，失败标 other |
| 服务端缓存 | 失效优先，懒重建；热点作品可预热 |
| 会话 L1 | **S2 惰性刷新**（编排边界对齐 version） |
| 群戏长会话 | 可降级为 S1 + 手动「刷新关系」按钮 |
| 前端版图 | 事件驱动 diff + **位置保持** + 短时力导向 |
| Agent | 单轮编排锁定 version；不热改飞行中请求 |
| 批量导入 | 抑制中间事件，结束 rebuild 一次 |

## 十、状态机（单作品）

```text
        ┌──────────┐
        │  Clean   │ ← 缓存 version == DB
        └────┬─────┘
     变更事件 │
        ▼
        ┌──────────┐
        │  Dirty   │ ← cache 标记失效
        └────┬─────┘
     下次读取 │
        ▼
        ┌──────────┐
        │ Building │
        └────┬─────┘
       成功  │
        ▼
        ┌──────────┐
        │  Clean   │
        └──────────┘
```

Building 期间读请求：等待（短超时）或返回上一代 snapshot + `stale: true`（版图可先显示旧图角标「更新中」）。

## 十一、性能粗算

| 操作 | 规模假设 | 预期 |
|------|----------|------|
| 全量 build snapshot | 150 节点 / 400 边 | < 20ms 内存 |
| 增量 patch 一边 | — | < 1ms |
| 前端轻量布局 | 150 节点 | 数帧～十几帧 |
| WS 通知 | — | 可忽略 |

瓶颈通常在 **DB 读全角色**；故缓存与「仅读变更角色再 patch」有价值。

---

## 十二、失败与降级

| 情况 | 处理 |
|------|------|
| rebuild 失败 | 保留旧 cache，打错误日志；UI 提示「关系图暂时不完整」 |
| WS 断开 | 回退 version 轮询；保存响应仍带 version |
| 对齐大量悬空 | 不阻塞保存；后台任务 + 版图灰显未解析边 |
| 布局发散 | 限制 ticks；提供「重新整理布局」手动按钮 |

---

## 十三、MVP 范围

**必须：**

1. 保存后 cache invalidate  
2. 下次生成 / 打开版图时用新 snapshot  
3. 版图：整表刷新但尽量复用节点坐标  
4. Toast 说明「下次生成生效」  

**二期：**

1. WS diff 推送  
2. 真增量 patch  
3. S3 热更新 + 系统关系刷新提示  
4. 编排级 version 锁的显式 API  

---

## 十四、结论

角色关系图谱的「实时更新」不宜做成无节制的全局热重载，而应：

1. **L0 立即正确**  
2. **缓存快速失效、懒重建**  
3. **会话/编排边界对齐 version（S2）**，群戏可冻结（S1）  
4. **UI 保位置、轻布局、防抖**  
5. **Agent 不在生成中途偷换关系约束**  

这与三层图谱共享、子图注入流水线一致，能在实时性与叙事一致性之间取得稳妥平衡。
