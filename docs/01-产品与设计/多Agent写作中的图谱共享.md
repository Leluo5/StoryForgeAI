## 一、问题背景

### 1.1 多 Agent 典型分工（StoryForgeAI）

| Agent 角色 | 职责 | 对图谱的需求 |
|------------|------|--------------|
| **角色 Agent（多个）** | 以某角色口吻对话/行动 | 读：自我中心子图 + 本人人设 |
| **场景导演 Agent** | 调度谁说话、推进场面 | 读：出场诱导子图、对立/同盟结构 |
| **剧情推衍 Agent** | 分支、冲突升级 | 读：相关冲突子图；或提议改关系 |
| **一致性检查 Agent** | 审稿、抓人设/关系崩坏 | 读：全文相关边 vs 近文 |
| **设定/知识 Agent** | 查设定与档案 | 读：节点详情，少改边 |
| **用户代言 / 主笔 Agent** | 综合润色、定稿 | 读：当前场景子图 |

核心矛盾：

- **要一致**：所有 Agent 对「谁和谁是什么关系」必须同一事实源  
- **要隔离**：每个 Agent 上下文有限，不能共享整图全文  
- **要可控**：Agent 不应私自永久改写作者的关系设定

## 二、共享什么：三层状态模型

建议把「图谱相关状态」拆成三层，避免一个大泥球被所有人读写。

```text
┌──────────────────────────────────────────┐
│ L0 权威层 Authoritative Graph              │
│ character 条目 + relationships（作者资产）   │
│ 唯一写入口：用户编辑 / 明确的「应用提案」流水线 │
└──────────────────────────────────────────┘
                    ▲ 只读快照
┌──────────────────────────────────────────┐
│ L1 会话层 Session Graph Snapshot           │
│ 本轮写作会话的冻结快照（version 固定）        │
│ 所有 Agent 读同一 snapshot，保证回合内一致   │
└──────────────────────────────────────────┘
                    ▲ 按需切片
┌──────────────────────────────────────────┐
│ L2 视图层 Per-Agent Subgraph View          │
│ 各 Agent 的 promptBlock（策略 B/C/E…）      │
│ 只读；可带 agentId 水印日志                  │
└──────────────────────────────────────────┘
```

| 层级 | 可变性 | 共享范围 | 写权限 |
|------|--------|----------|--------|
| L0 | 持久、跨会话 | 全作品 | 用户 + 受控提案落地 |
| L1 | 单会话冻结 | 本会话全部 Agent | 会话开始时构建，中途默认不改 |
| L2 | 每次调用 | 单 Agent 单次调用 | 无（纯派生） |

**原则：Agent 之间不直接传「私有关系记忆」，只共享 L1 快照派生出的 L2。**

## 三、共享模式对比

### 3.1 模式 A：中心快照 + 分发切片（推荐默认）

```text
SessionStart → build L1 snapshot
Agent_i.run() → SubgraphInject(L1, agent_i context) → L2_i → LLM
```

**优点**：强一致、易审计、实现简单  
**缺点**：会话中途用户改关系，Agent 仍见旧图（可用「刷新快照」解决）

### 3.2 模式 B：黑板（Blackboard）共享工作区

多 Agent 把「本场临时事实」写到共享黑板（如：本章林远受伤、贺兰策暂离）：

```text
L1 关系图（稳定） + Blackboard（场景临时状态）
```

**黑板适合存**：位置、情绪、是否在场、本章临时盟约  
**黑板不适合存**：永久血缘/师徒（应回 L0）

### 3.3 模式 C：全量图塞进每个 Agent

反模式。Token 爆、互相矛盾时更难查、日志不可读。

### 3.4 模式 D：Agent 间聊天同步关系

反模式。关系在对话中漂移，无法与知识库对齐。

## 四、读路径：如何「共享」而不「复制真相」

### 4.1 会话级共享快照

```ts
interface SessionGraphContext {
  sessionId: string;
  workId: string;
  graphVersion: string;
  snapshot: RelationGraphSnapshot;  // nodes + edges + nameIndex
  createdAt: number;
}
```

- 会话创建时：`RelationGraphSnapshotService.getSnapshot(workId)`  
- 注入到 `AgentRuntime` 的共享依赖，**所有 Agent 构造器注入同一引用**  
- 各 Agent 只调用 `buildSubgraphInject({ snapshot, sceneIds, focusIds, taskType })`

### 4.2 按 Agent 类型绑定默认策略

| Agent | 默认策略 | focus / scene |
|-------|----------|----------------|
| 角色 Agent（林远） | B（ego） | focus=林远；scene=本场出场 |
| 角色 Agent（贺兰策） | B | focus=贺兰策；scene=同上 |
| 导演 Agent | E | scene=本场出场 |
| 推衍 Agent | E 或 C | 冲突双方 focus |
| 一致性 Agent | E 或全量边列表（截断提高） | 近文出现角色 |

同一 L1，不同 L2 → **事实同源、视角不同**。这是多 Agent 图谱共享的理想形态。

### 4.3 交叉出场时的一致性

林远 Agent 与贺兰策 Agent 必须看到**同一条**「宿敌/兄长」边：

- 来自同一 L1 edge id  
- 序列化时 `relationLabel` 原文一致  
- 硬禁止双方对称（或中心视角各写一句，但不许一个敌对一个兄弟情深除非 label 如此）

**测试点**：双 Agent 生成对白时，抽检关系描述是否同源。

## 五、写路径：谁能改图谱

### 5.1 默认禁止 Agent 直写 L0

Agent 输出中的关系变化（反目、成亲、拜师）视为 **叙事文本**，不是数据库更新。

### 5.2 受控「关系变更提案」流水线（可选二期）

```text
Agent / 用户 暗示关系变化
    → RelationChangeProposal {
        source, target, newLabel, evidence_span, confidence
      }
    → 展示给用户确认
    → 用户确认后写入 character.relationships（L0）
    → snapshot version++
    → 可选：刷新 L1
```

**自动落库**仅建议在明确产品开关「允许 AI 维护关系表」且高置信 + 用户模板同意时开启；默认关闭。

### 5.3 场景临时关系（黑板）

例如「本章假意结盟」：

```ts
BlackboardRelation {
  source, target, label, scope: 'chapter' | 'scene',
  expiresAtChapter?: number
}
```

- 注入时：**黑板边优先覆盖同名 L1 边的展示**（或并列：「设定上为宿敌；本章假意结盟」）  
- 过章后自动失效，不污染 L0  

适合多 Agent 共演「骗局、卧底、临时结盟」而不改作者永久设定。

## 六、并发与编排

### 6.1 串行编排（推荐 MVP）

```text
导演 Agent（读 L2_E）→ 决定发言顺序
  → 角色 Agent A（读 L2_B）→ 对白
  → 角色 Agent B（读 L2_B）→ 对白
  → 一致性 Agent（读 L2 + 近文）→ 批注
  → 主笔合并
```

同一 L1，无写冲突；实现简单。

### 6.2 并行角色 Agent

A、B 同时生成时：

- **只读共享 L1**（无锁）  
- 禁止并行写黑板同一 key（或用 merge 策略：last-write-wins + 日志）  
- 并行结果由导演/主笔合并，发现关系冲突则重跑或交用户  

### 6.3 会话中途刷新 L1

用户编辑了角色关系：

| 策略 | 行为 |
|------|------|
| 保守（默认） | 本会话继续旧 L1，提示「关系已更新，新开对话生效」 |
| 积极 | `refreshSnapshot()`，后续 Agent 调用用新 version |
| 混合 | 刷新 L1，但保留黑板场景临时边 |

## 七、上下文隔离 vs 世界共享

| 应共享（世界） | 应隔离（Agent 私有） |
|----------------|----------------------|
| L0/L1 关系与人设权威 | 该角色的内心独白计划 |
| 本场出场名单 | 作者给单 Agent 的私密指令 |
| 黑板公开场景状态 | 未向用户展示的中间推理 |
| graphVersion | 采样温度、style 偏好 |

**反模式**：把角色 Agent A 的完整对话历史塞给 Agent B 当「关系来源」——会导致关系从闲聊中漂移。B 只需 L2 关系块 + 必要的公开场面摘要。

## 九、Prompt 层约定（多 Agent 专用）

每个角色 Agent 的 system 中增加：

```text
你与其他角色由统一的「关系约束」知识库驱动。
你只能依据本提示中的【关系约束】理解人物关系，
不要根据猜测或其他角色可能说出的内容修改这些关系。
若场面需要与约束冲突的行为，用演技与张力表达冲突，而不是默默改写关系。
```

导演 Agent：

```text
调度时尊重【关系约束】中的敌对/师徒/亲缘；
不要安排逻辑上越界的亲密互动，除非用户明确要求戏剧反转。
```

## 十、风险与对策

| 风险 | 对策 |
|------|------|
| 两 Agent 关系认知不一致 | 强制同一 L1；禁止用对方私有历史当关系源 |
| 临时剧情污染永久设定 | 黑板 scope=scene/chapter；默认不写 L0 |
| 会话过长 L1 过期 | 显示 graphVersion；提供刷新 |
| Token 乘以 Agent 数爆炸 | 严格 L2 切片；并行时仍各自小块 |
| 提案刷屏 | 关系变更提案合并去重，批量确认 |
| 检查 Agent 与生成 Agent 争辩 | 检查只读；结果以批注形式给用户，不直接改文除非用户点应用 |

## 十一、落地阶段建议

### Phase 1（MVP）

- 会话绑定只读 L1 快照  
- 多 Agent 均经 `SubgraphInjectFacade` 取 L2  
- 角色 Agent 用策略 B，导演用 E  
- 无写回、无黑板  

### Phase 2

- 场景黑板（在场、临时盟约）  
- 用户确认式关系变更提案  
- 会话内刷新快照  

### Phase 3

- 一致性 Agent 自动扫关系违反  
- 提案与剧情树/章节绑定  
- 多作品/多线图谱命名空间  

---

## 十二、结论

多 Agent 写作中的图谱共享，本质不是「把一张大图复制给每个人」，而是：

1. **L0 作者权威、单一写入口**  
2. **L1 会话级冻结快照，全员只读共享**  
3. **L2 按 Agent 职责切片，同源不同视角**  
4. **场景临时事实走黑板，不污染永久关系**  
5. **关系变更必须用户可见、可确认**  

这样既保证群戏关系一致，又控制 token 与幻觉，并与现有子图注入流水线自然衔接。
