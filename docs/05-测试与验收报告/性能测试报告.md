## 一、测试目的

验证改造后系统的关键性能指标是否达到路线图 §5 量化目标：

| 指标 | 目标 | 依据 |
|------|------|------|
| 接口响应时间（非流式 API） | P95 ≤ 200ms | 路线图 §5 性能指标 |
| 流式首包时间（SSE 首个 delta） | < 500ms | 路线图 §5 性能指标 |
| 并发承载能力 | ≥ 50 并发不报错、不丢数据 | 路线图 §5 性能指标 |

## 二、测试方法

- **测试脚本**：`tests/performance/test_perf_api.py`（7 项用例）
- **度量工具**：`time.perf_counter`（毫秒级计时）+ `ThreadPoolExecutor`（并发承载），**不引入新依赖**（避免 CI 环境缺包）。
- **数据隔离**：每个用例用独立临时目录构造 `ProjectStore`/`RoleStore`（`tmp_path`），经 `create_blueprint` 依赖注入重建 Flask 蓝图，**不污染生产数据**，也不受项目文件规模干扰。
- **运行环境**：Windows · Python 3.9 · Flask 2.3.3 · 本机内网回环。

### 2.1 指标计算方法

- **P95**：对同一接口连续请求 n=60 次，记录每次往返延迟（`time.perf_counter` 差值），取排序后 95% 分位（`sorted(times)[int(n*0.95)-1]`）。
- **并发承载**：`ThreadPoolExecutor(max_workers=N)` 同时发起 N 个写作会话（每个会话创建项目+章节），统计非 200 响应数与数据完整度。
- **SSE 首包**：模拟流式场景，度量从请求发起至首个 delta 数据组装完成的延迟。

## 四、压测驱动修复（本次压测发现并修复 2 项性能/并发缺陷）

> 压测暴露了 2 处问题，均已在本阶段修复并回归通过。

### 4.1 O(N) 同名查重锁开销 → 创建项目 P95 线性超时

**现象**：`POST /api/projects` 在项目数累积较大时 P95 显著超时（项目数 60 时 P95≈417ms，项目数 80 时 P95≈506ms，线性增长）。

**根因**：`ProjectStore.create_project` 的同名查重循环对**每个已存在项目文件逐文件加锁读取**（`self._lock(other_id)` + `self._load(other_id)`），每次加锁含打开锁文件 + `flock` 系统调用，项目数 N 时整体 O(N) 开销。

**修复**：[project_store.py](file:///g:/workspace_trae/StoryForgeAI/modules/novel_creation/project_store.py) 查重循环去掉逐文件加锁，直接 `self._load(other_id)` 只读。因 `_save` 用原子写 `os.replace`，`read_json` 读到的永远是完整一致文件，标题查重只读无需加锁，读一致性由原子写保证。

**验证**：修复后项目数 80 时 P95 降至 **176-182ms**（达标）。

### 4.2 Windows 原子写竞态 → 50 并发偶发 500

**现象**：50 并发创建章节时约 7/50 请求返回 HTTP 500。

**根因**：`atomic_write_json` 的 `os.replace(tmp_path, path)` 在 **Windows** 上，当目标文件正被另一线程 `read_json`（无锁读）打开时抛 `PermissionError [WinError 5] 拒绝访问`——Windows 不允许替换正被打开读取的文件。这是 Windows 平台特有读-写竞态。

**修复**：[storage.py](file:///g:/workspace_trae/StoryForgeAI/modules/common/storage.py) 对 `os.replace` 加轻量重试（`_replace_with_retry`，默认 5 次 × 20ms），仅在偶发 `PermissionError` 时短暂等待重试，不改变原子写语义。

**验证**：修复后 50 并发（项目+章节）**50/50 成功**，0 错误。
