# P5-T5a 版图角色详情体验优化设计

> 版本：v1.0
> 日期：2026-11-14
> 状态：已确认设计，待书面审阅
> 分支：`feature/p5-t5-experience-optimization`

## 1. 背景

路线图将 P5-T5 定义为前端交互与性能体验优化，原始目标包括“命令面板渲染 <100ms”和“角色切换无闪烁、状态同步”。现状调研确认：

- 规划中的 `static/js/tool_panel.js` 尚未落地，不能把新增命令面板混入体验优化。
- 版图角色详情由 `_openRoleDetail()`、`_closeRoleDetail()`、`_loadGrowth()` 和 `_renderGrowthTimeline()` 组成。
- 详情当前存在先删除再创建 DOM 的结构，成长线响应缺少角色 ID 与请求代次校验；可见闪烁和实际竞态频率仍需运行时基线验证。
- 对话页没有独立的同作品 `role_id` 切换控件。同作品多 Agent 切换属于新增功能，不纳入本轮体验优化。

## 2. 已确认范围

### 2.1 本轮范围

仅实施 **P5-T5a：版图角色详情体验优化**：

1. 消除角色详情同步渲染过程中的空白帧和旧角色闪帧。
2. 防止成长线旧响应覆盖当前角色。
3. 保证角色名称、头像、关系和成长线最终属于同一角色。
4. 对基础详情与成长线的本地渲染分别建立 P95 `<100ms` 的量化验收。
5. 保持既有版图性能、主题、响应式和浏览器兼容性不回退。

### 2.2 非本轮范围

- 命令面板及其 `<100ms` 指标：另立前置功能任务。
- 同作品多 Agent 切换：P5-T5a 完成后独立走需求、技术方案和任务规划。
- 作品卡片切换对话室的既有问题：本轮不修改。
- 剧情树、Admin、后端 API、数据结构、D3 布局与拖拽协议：本轮不修改。
- Firefox、Safari 的新增兼容性认证：不作为本轮验收门槛。

## 3. 方案选择

采用**分链路定向优化**，先在现有功能上采集基线，再做最小修复：

- 沿用 ES6、IIFE、CustomEvent、D3 和 `requestAnimationFrame`。
- 不引入前端框架、构建链、共享状态库或统一调度器。
- 不采用单纯骨架屏、动画或缓存掩盖旧响应竞态。
- 首版不增加数据缓存；只有测量证明本地渲染不达标时才重新评估。

## 4. 组件与数据流设计

### 4.1 同步详情渲染

`_openRoleDetail()` 负责一次完整详情提交：

1. 读取当前选中角色的本地数据。
2. 构建包含新角色基础信息、头像、关系区域和异步加载态的完整 `DocumentFragment`。
3. 通过一次 `replaceChildren()` 替换详情内容，避免先删后建产生空白帧。
4. 在下一帧确认 DOM 已提交，作为本地同步渲染测量终点。

切换后不得展示上一角色的名称、头像、关系或成长线。加载态必须属于新角色，不得先清空容器再等待重建。

### 4.2 请求代次隔离

在现有角色图板闭包内维护单调递增的详情请求代次：

- 每次 `_openRoleDetail(role)` 增加代次，并记录当前 `roleId`。
- `_closeRoleDetail()` 增加代次，使关闭前的请求全部失效。
- `_loadGrowth(roleId, generation)` 捕获调用时的角色 ID 和代次。
- 响应返回后以及 `_renderGrowthTimeline()` 执行前，同时校验：
  - 响应 `roleId` 等于当前角色 ID；
  - 响应代次等于当前代次；
  - 详情面板仍处于打开状态。
- 任一校验失败均忽略响应，不写 DOM、不改当前状态、不显示错误提示。

请求代次是唯一事实来源；即使旧请求已经无法取消，也不能覆盖当前角色。无需为该校验引入全局状态管理。

### 4.3 成长线渲染

只有通过有效性校验的响应可以进入 `_renderGrowthTimeline()`：

1. 在当前详情的成长线区域内一次性提交新内容。
2. 使用 `requestAnimationFrame` 确认稳定帧并记录本地渲染耗时。
3. 空数据渲染标准空状态，不回退到上一角色内容。
4. 网络等待不计入本地渲染 P95，但最终状态一致性单独验收。

## 5. 异常处理

- **旧响应成功**：直接忽略，不产生界面变化。
- **旧响应失败**：直接忽略，不弹窗、不写控制台未捕获错误。
- **当前请求失败**：保留新角色基础信息，仅在成长线区域显示明确错误态。
- **当前请求返回空数据**：显示标准空状态。
- **快速关闭或连续切换**：立即使旧代次失效，后续响应不得重新打开或修改详情。
- **局部数据缺失**：沿用项目既有占位和转义规则，不展示其他角色数据。

## 6. 测量与验收设计

### 6.1 基准场景

- 使用隔离测试数据：100 个角色、150 条关系边。
- 冷打开：角色首次展开详情。
- 热打开：角色重复展开详情。
- 基础详情与成长线分别采集冷、热各 30 次样本，并分别计算 P95。
- 使用 Performance API 和 `requestAnimationFrame` 测量函数入口到 DOM 稳定帧的本地耗时，不增加持久化遥测。

### 6.2 性能验收

| 指标 | 验收标准 |
|---|---|
| 基础详情本地渲染 | 冷、热分别计算 P95，两组结果均 `<100ms` |
| 成长线本地渲染 | 冷、热分别计算 P95，两组结果均 `<100ms` |
| 版图 FPS | 同设备、同数据下，优化后相对基线下降不超过 5%，且不低于既有强制验收门槛 |
| 控制台 | 未捕获错误为 0 |

网络等待、模型生成耗时均不计入上述本地渲染指标。

### 6.3 乱序与视觉验收

通过受控延迟和乱序响应执行 30 轮 `A → B → A`：

- 最终角色、头像、关系和成长线一致率 100%。
- 旧响应覆盖当前详情 0 次。
- 空白帧 0 次，旧角色闪帧 0 次。
- 控制台未捕获错误 0 次。

补充覆盖：加载、失败、空数据、关闭后响应返回、关闭重开、快速连续点击。

### 6.4 兼容与项目回归

- Chrome、Edge 验证浅色和深色主题。
- 验证 500、768、1024、1440 四档宽度。
- 保持主题切换、ARIA、角色头像、连线配色和既有交互不回退。
- 全量 Python 测试通过。
- Node.js 18.20.8 下后端、前端、安全、依赖四脚本检查均为 0 违规。
- 语法编译与 `git diff --check` 通过。

## 7. 测试策略

1. 在实施前建立可复现的延迟、乱序响应回归场景，并确认现有实现会失败。
2. 先验证请求代次与角色一致性，再验证一次性 DOM 提交和视觉表现。
3. 运行时证据至少包括响应顺序、最终角色状态、性能样本数、P95 和控制台结果。
4. 性能报告同时保留优化前后基线，避免只报告优化后的单次结果。
5. 后端契约未改变，现有接口和数据测试必须全部保留。

## 8. 完成定义

只有同时满足以下条件，P5-T5a 才可标记完成：

- 同步详情和异步成长线的状态一致性测试通过。
- 冷、热渲染样本数量完整，基础详情与成长线的四组 P95 结果均达标。
- 乱序、视觉、主题、响应式和浏览器验收全部通过。
- 既有版图性能相对基线下降不超过 5%，且不低于既有强制验收门槛。
- 全量测试、四脚本检查、编译和差异格式检查全部通过。
- 文档、验证结果与代码实际行为一致。
