## 一、背景与目标

### 1.1 背景

当前系统以 Flask、Jinja2 和原生 JavaScript 实现，主界面由作品大厅、Coze 体验页、管理后台和独立创作面板组成。剧情树、角色版图、知识库与命令面板已经具备局部能力，但缺少以正文为中心的持续工作上下文。

本规格定义目标系统，不描述当前实现已经具备这些能力。目标系统完成切换后，旧 Flask UI、`chat`、`form`、`mixed` 体验视图和双后端运行方式退场。

### 1.2 产品目标

1. 建立作品首页、卷章节管理和正文写作的一体化工作流。
2. 让作者与 AI 的所有正文变更都可查看、接受、拒绝、追溯和回滚。
3. 将划词评论、待办、指派、@ 和通知纳入同一创作上下文。
4. 将剧情树、角色版图、知识库和 Agent 变成工作台上下文能力，而非孤立页面。
5. 保证自动保存、崩溃恢复、冲突处理和任务重试不静默丢失或重复数据。

### 1.3 技术目标

- 前端采用 React + TypeScript，正文采用 Tiptap/ProseMirror。
- 后端采用 NestJS 模块化单体，使用 PostgreSQL + TypeORM 保存权威数据。
- 使用 Redis + BullMQ 执行长耗时 AI 任务，使用 SSE 推送进度。
- 使用共享 Zod 契约校验前后端 API 边界。
- 以可测试、可迁移、可回滚的里程碑替代一次性大爆炸上线。

### 1.4 用户与协作边界

目标用户是独立小说作者。AI 是创作参与者，可生成候选修订、评论和待办结果。

评论、待办、指派和 @ 用于组织作者与 AI 的变更工作流，不代表本期实现多人同时编辑同一文档。通知以应用内通知中心为准，不扩展邮件、短信或公共社区。

## 二、范围与非目标

### 2.1 本期范围

- 作品库首页、作品设置、卷与章节树。
- 富文本与 Markdown 双模式正文编辑。
- 自动保存、离线恢复、崩溃恢复和版本冲突处理。
- 全量修订、不可变版本、差异比较和非破坏回滚。
- 划词评论、待办、指派、@、通知中心和审计记录。
- AI 写作工具、Agent 配置、任务队列和执行状态。
- 剧情树、角色版图、作品知识库及命令面板。
- 旧小说项目、Coze 配置、角色、Agent 和知识数据迁移。

### 2.2 非目标

- 多人实时协同编辑和公开作者社区。
- 长期保留 Flask 与 NestJS 两套线上写入后端。
- 长期保留独立聊天、表单或混合体验页面。
- 在新系统中建立第二份独立 Markdown 正文数据库。
- 通过自动合并覆盖人工未确认的 AI 结果或版本冲突。

## 三、设计原则

1. **正文优先**：三栏布局围绕正文组织，创作工具不得迫使作者丢失章节上下文。
2. **单一事实来源**：ProseMirror JSON 是唯一正文源，服务端数据库是跨设备权威源，本地 WAL 是崩溃恢复源。
3. **所有变更可追踪**：作者、AI、导入和回滚都通过变更记录进入正文。
4. **AI 不直接覆盖**：AI 只生成待审修订，接受和拒绝由作者决定。
5. **失败不伪装**：保存、离线、冲突、解析和 AI 失败均显示真实状态。
6. **迁移不双写**：新旧系统短期并行只用于验证，切换点之后只有一个写入方。
7. **阶段可验收**：每个里程碑独立设计、实施和验证，不以总设计替代详细任务计划。

## 四、目标系统架构

### 4.1 架构分层

```text
React Web
  ├─ 作品库与设置
  ├─ 三栏工作台
  ├─ ProseMirror 编辑器
  └─ 本地快照与 WAL（IndexedDB）
             │ HTTPS / SSE
             ▼
NestJS 模块化单体
  ├─ 作品 / 卷 / 章节
  ├─ 正文 / 修订 / 版本
  ├─ 评论 / 待办 / 通知
  ├─ Agent / 创作工具 / 知识库
  └─ 鉴权 / 审计 / 迁移
             │
       ┌─────┴──────────┐
       ▼                ▼
PostgreSQL          Redis + BullMQ
权威业务数据          AI 任务与事件
                            │
                            ▼
                      Coze / 模型服务
```

### 4.2 模块边界

| 模块 | 核心职责 | 不得承担的职责 |
| --- | --- | --- |
| 作品模块 | 作品、卷、章节、排序、设置 | 直接修改正文修订 |
| 正文模块 | 文档、版本号、保存、并发检查 | 执行 AI 业务逻辑 |
| 修订模块 | 操作集、接受、拒绝、差异 | 静默覆盖冲突版本 |
| 版本模块 | 不可变快照、比较、回滚 | 删除历史版本 |
| 评论模块 | 锚点、回复、解决、失联 | 将评论写入正文 JSON |
| 待办模块 | 创建、指派、状态、关联对象 | 替代通知记录 |
| 通知模块 | @、指派、任务结果、已读状态 | 作为业务状态唯一来源 |
| AI 模块 | Agent 解析、工具调用、任务状态 | 直接接受生成的修订 |
| 知识模块 | 作品知识、角色、剧情和检索 | 跨作品读取私有上下文 |
| 迁移模块 | 分类、映射、校验、幂等导入 | 迁移期间双写 |

### 4.3 工程组织

目标采用 Monorepo，逻辑边界如下：

```text
apps/
  web/                 React 工作台
  api/                 NestJS HTTP、SSE 与 Worker 入口
packages/
  contracts/           Zod API 契约和错误模型
  editor-schema/       ProseMirror Schema 与 Markdown 转换
  design-tokens/       主题和设计令牌
```

Worker 与 API 共用领域模块，但任务执行和 HTTP 请求生命周期分离。数据库迁移只由明确的部署步骤执行，不在应用启动时隐式修改生产结构。

## 五、信息架构与组件设计

### 5.1 页面与路由

| 页面 | 目标路由 | 核心内容 |
| --- | --- | --- |
| 作品库 | `/works` | 作品列表、搜索、创建、归档和设置入口 |
| 写作工作台 | `/works/:workId/write/:chapterId` | 三栏写作主界面 |
| 作品设置 | `/works/:workId/settings` | 基本信息、权限、Agent 和数据管理 |
| 通知中心 | `/notifications` | @、指派、AI 结果和系统异常 |
| 迁移管理 | `/settings/migration` | dry-run、映射报告、校验和切换状态 |

工作台使用查询参数表达中央页签和右侧上下文，例如 `?tab=manuscript&panel=comments`。作品、章节、中央页签和右侧面板均可深链；草稿正文本身不写入 URL。

> 路由壳更新（2026-11-22）：`/works`（作品库）、`/works/:workId/write/:chapterId`（写作工作台）等模块页共用同一 `ModuleLayout` 布局壳——左侧共享导航工具栏（`SideNav`：作品库/知识库/智能体/工作流/模型/后台六个入口）常驻各模块页，内容区经 `<Outlet/>` 注入。写作工作台由此**纳入共享壳**，侧边栏在工作台页面正常显示；「作品库」入口经 `NavLink` 父路径规则在工作台路由下自动保持高亮，指向 `/works`。作品设置 `/works/:workId/settings`、通知中心、迁移管理等规划路由如与六个模块入口不一致，仍按独立模块页接入共享壳或按需调整。

### 5.2 三栏布局

| 区域 | 桌面行为 | 窄屏行为 |
| --- | --- | --- |
| 左侧导航 | 卷章节树、剧情树、角色版图、知识库 | 单栏抽屉，打开后隔离背景 |
| 中央工作区 | 正文、修订、版本及大型工具页签 | 始终保留当前任务和返回路径 |
| 右侧上下文 | 角色、剧情、知识、评论、待办、AI | 全高抽屉或底部面板 |

宽屏持续显示三栏，中屏允许折叠左右栏，窄屏只显示一个主区域。面板宽度与折叠状态按作品保存在本地；章节、页签和面板选择保存在 URL。

> 布局壳并存说明（2026-11-22）：写作工作台纳入 `ModuleLayout` 壳后，内容区预留 64px 安全边距（共享侧边栏收起态宽度），工作台三栏在内容区内正常布局——左侧卷章节树等面板紧邻共享侧边栏右侧，中央工作区与右侧上下文不变。共享侧边栏展开时为 224px 浮层覆盖内容区左缘，不挤压工作台布局；工作台内点击/输入/滚动会触发共享侧边栏自动收缩。

### 5.3 顶部全局状态

顶部栏持续显示：

- 当前作品与章节。
- 当前角色或 AI 上下文。
- 保存状态：`本地保存中`、`本地已保存`、`云端同步中`、`已同步`、`离线待同步`、`版本冲突`、`保存失败`。
- AI 任务入口和通知未读数。
- 命令面板入口、主题切换和作品设置。

保存状态必须由实际持久化状态驱动，不得用固定延时模拟成功。

### 5.4 编辑器与中央页签

- `manuscript`：正文编辑与阅读。
- `revisions`：待审修订、逐条接受或拒绝、批量操作。
- `versions`：版本列表、差异比较和回滚。
- `plot`：剧情树及其与章节的关联。
- `roles`：角色版图、角色详情和成长线。

切换页签不得清空未保存正文。剧情树和角色版图等复杂任务使用独立中央页签，避免全屏弹层遮蔽正文和保存状态。

### 5.5 评论、待办和通知

- 划词创建评论，记录选区、原文、章节版本和作者。
- 评论可回复、解决、重新打开，也可转为待办。
- 待办支持标题、说明、负责人、关联章节/评论/修订和状态。
- 待办状态为 `open → in_progress → done`，另有 `cancelled`；状态变化产生通知和审计记录。
- @ 与指派只创建应用内通知，不隐式修改业务对象权限。
- 通知记录关联对象和已读时间，业务对象被删除时保留可读的历史说明。

## 六、正文与修订模型

### 6.1 唯一正文源

正文权威格式是符合共享 Schema 的 ProseMirror JSON。Markdown 是同一文档的编辑和导出视图，不建立第二份独立正文。

评论、待办、修订和通知保存在独立关系模型中，不将业务元数据混入正文 JSON。

**唯一例外：块级排版标识 `pid`**（见 [ADR-0003](../../02-技术与架构/架构决策记录/0003-正文块级pid与业务元数据边界.md)）。为使「关联角色已归档」提示能定位到具体段落，正文块级文本节点允许携带稳定属性 `pid`。该属性仅为排版身份：

- 不携带角色、关系、归档、归属等任何业务语义；
- 不参与 `content_hash` 与 `canonicalizeDocument` 计算；
- 归档与恢复操作不写入正文；
- 除该属性外，业务元数据一律不得混入正文 JSON。

### 6.2 双模式转换

- 富文本模式和 Markdown 模式共用 `editor-schema` 包。
- Markdown 提交前必须解析并转换为合法 ProseMirror JSON。
- 不支持的 Markdown 结构显示行、列和原因，保留源码草稿，不覆盖当前正文。
- 模式切换通过同一转换链路重定位评论和修订锚点。
- 锚点无法可靠重定位时标记失联并保留原文，不静默删除评论或修订。
- 序列化必须执行往返测试，禁止无提示丢弃节点、标记或文本。

### 6.3 修订集

一次连续输入、一次粘贴、一次 AI 生成或一次回滚可形成一个修订集。修订集包含多个有序操作，每个操作独立记录接受或拒绝结果。

| 字段 | 含义 |
| --- | --- |
| `revision_set_id` | 修订集标识 |
| `chapter_id` | 所属章节 |
| `base_version` | 生成时的章节版本 |
| `actor_type` | `author`、`ai`、`import`、`rollback` |
| `actor_id` | 作者、Agent 或系统任务标识 |
| `operations` | 有序插入、删除和格式操作 |
| `status` | `pending`、`partially_resolved`、`resolved` |
| `created_at` | 创建时间 |

连续输入可按时间、段落和操作类型合并；AI 结果不得与作者手工输入合并。接受或拒绝本身也产生可审计变更。

### 6.4 版本与回滚

自动保存只推进章节版本号，不自动创建命名版本。以下操作创建不可变快照：

- 作者主动创建版本。
- 首次接受任一 AI 修订集前；同一修订集只创建一个自动快照。
- 执行回滚前。
- 数据迁移或批量导入前。

回滚不是删除后续历史，而是以目标快照为基准生成新的回滚修订集。作者确认后才成为当前正文。

## 七、自动保存与崩溃恢复

### 7.1 本地 WAL

IndexedDB 保存本地快照和预写式操作日志（Write-Ahead Log，WAL）。每个日志项至少包含：

| 字段 | 含义 |
| --- | --- |
| `change_id` | 全局唯一变更标识 |
| `work_id`、`chapter_id` | 所属作品和章节 |
| `client_id`、`sequence` | 客户端标识和严格递增序号 |
| `base_version` | 基于的服务端版本 |
| `operations` | ProseMirror 操作 |
| `created_at` | 本地事务时间 |
| `sync_state` | `pending`、`acknowledged` |

编辑事务先提交到 IndexedDB，再更新界面为“本地已保存”。定期生成快照以限制回放长度，但快照不得跳过未确认日志。

### 7.2 服务端保存

- 本地变更按 `client_id + sequence` 排序同步。
- 服务端按 `change_id` 去重，数据库事务同时写入文档、变更记录和新版本号。
- 保存确认返回 `change_id`、`server_version` 和内容摘要；摘要使用规范化文档 JSON 的 SHA-256。
- 只有收到服务端确认后，本地日志才标记为已确认。
- 页面隐藏、章节切换和离开前触发同步，但正确性不依赖 `beforeunload`。

### 7.3 崩溃恢复

浏览器或设备进程崩溃后：

1. 打开作品时读取最近本地快照。
2. 按客户端和序号回放未确认日志。
3. 比较本地 `base_version` 与服务端版本。
4. 版本一致则继续同步，冲突则保留本地和服务端双份并进入三方差异合并。
5. 恢复完成前显示真实恢复状态，禁止显示“已同步”。

恢复目标是恢复到最后一次成功提交到 IndexedDB 的事务。用户主动清除浏览器存储、浏览器自行清除站点数据或设备物理损坏不在该保证范围内；这些场景依赖服务端最近确认版本和导出备份。

### 7.4 多标签页

同一浏览器内，同一章节只允许一个标签页持有写入权。其他标签页进入只读模式，可显式接管。

接管前必须确认旧写入页已释放租约；租约超时后仍需比较版本，防止旧页面恢复后覆盖新页面。跨设备不强行限制单写，统一通过服务端版本检查和三方合并处理冲突。

### 7.5 本地异常

- WAL 写入失败或配额不足：立即显示“保存失败”，提供恢复数据导出，不再宣称自动保存有效。
- 本地数据损坏：保留原始恢复数据，不自动清除；提供服务端版本恢复入口。
- 快照压缩失败：继续使用日志，不阻塞正文编辑，但持续显示本地性能或容量风险。

## 八、评论锚点与冲突处理

### 8.1 评论锚点

评论锚点记录起止位置、原文、前后文、章节版本和锚点状态。正文变更时通过 ProseMirror 映射更新位置。

原文被删除或无法定位时，`anchor_status = orphaned`。界面显示“评论已失联”和原始引用，允许手动重新关联，不自动删除评论。

### 8.2 保存冲突

服务端版本与 `base_version` 不一致时返回 `409`，响应包含当前服务端版本和请求 ID。

客户端必须保留：

- 共同基准版本。
- 本地未确认版本。
- 服务端当前版本。

三方合并只提供操作建议，不静默覆盖。作者确认合并结果后，以最新服务端版本重新提交。

### 8.3 其他冲突

- 同一修订被重复接受或拒绝：按操作当前状态返回幂等结果或明确冲突，不重复应用。
- 同一待办被重复完成：保持最终状态和单次审计语义。
- 同一 AI 任务重复回调：按任务和结果序号去重，不生成重复修订。

## 九、AI 任务与上下文

### 9.1 任务生命周期

AI 任务状态为 `queued → running → succeeded / failed / cancelled`。长任务由 BullMQ 执行，SSE 只负责推送，数据库中的任务状态是恢复和重连依据。

每次任务包含 `task_id`、`idempotency_key`、作品、章节、Agent、输入摘要和事件序号。客户端重连后先读取当前任务状态，再按序号补取遗漏事件。

### 9.2 AI 正文结果

AI 生成正文时：

1. Worker 获取明确的基准章节版本和上下文。
2. 生成结果先保存为候选输出。
3. 服务端将候选输出转换为独立修订集。
4. 作者逐条或批量接受、拒绝。
5. 基准版本已变化时标记“基于旧版本”，通过差异界面处理，不直接套用。

任务超时、Worker 崩溃或服务重启可以重试。外部模型调用采用至少一次语义，系统不承诺外部服务恰好执行一次；相同幂等键最多产生一个有效结果修订集，重复调用结果必须去重。

### 9.3 创作工具上下文

命令面板、剧情树、角色版图、知识库和 Agent 共用 `work_id`，按需附加 `chapter_id`、`role_id` 和选区上下文。

工具不得读取其他作品的私有知识或角色绑定。当前角色和默认 Agent 可在顶部切换，切换动作写入审计记录。

## 十、数据模型与 API 契约

### 10.1 核心实体

| 实体 | 关键关系 |
| --- | --- |
| `Work` | 包含多个 `Volume`、`Chapter`、`Agent` 和知识资产 |
| `Volume` | 属于一个作品，包含有序章节 |
| `Chapter` | 保存当前文档、版本号和卷内顺序 |
| `ChapterChange` | 保存每次已确认变更及幂等标识 |
| `RevisionSet` | 保存作者或 AI 的待审操作集 |
| `VersionSnapshot` | 保存不可变正文快照和来源 |
| `CommentThread` | 关联章节、锚点、回复和解决状态 |
| `Todo` | 关联作品、章节、评论或修订及负责人 |
| `Notification` | 关联作者或 Agent 接收对象、事件和已读时间 |
| `Agent` | 关联作品、类型、配置版本和归档状态 |
| `AITask` | 关联工具、Agent、上下文、状态和结果 |

所有正文保存、修订操作和任务结果使用 UTC 时间存储，界面按 `Asia/Shanghai` 显示。标识使用不可猜解的 UUID，金额字段不适用于本系统。

### 10.2 API 规范

- 新接口使用 `/api/v1` 前缀，按作品、章节、修订、评论、待办、通知、Agent 和任务分资源。
- React 与 NestJS 从 `packages/contracts` 复用 Zod Schema。
- 写请求携带身份、作品上下文和必要的幂等键。
- 响应统一包含 `request_id`；错误包含稳定 `code`、可读 `message` 和结构化 `details`。
- 校验失败返回 `422`，字段错误内联展示并聚焦首个错误。
- 未认证返回 `401`，无权限返回 `403`，版本冲突返回 `409`，限流返回 `429` 和重试时间。
- 外部模型失败使用 `502` 或可重试的 `503`，不得包装成成功响应。

### 10.3 鉴权与安全

- 作品库公开内容只读；正文写作、修订、评论、待办和 AI 操作必须验证作者身份与作品权限。
- 作品访问码只控制允许访问的只读内容，不直接授予写作权限。
- 会话 Cookie 使用 `HttpOnly`、`Secure`、适当的 `SameSite` 和 CSRF 防护。
- 访问码只保存摘要，PAT Token 和 API Key 只存在服务端环境或密钥管理设施。
- API 响应、SSE、浏览器存储和日志不得包含 PAT Token、API Key 或会话秘密。
- Markdown、AI 输出和富文本粘贴统一执行 Schema 校验与 XSS 清理。
- 修订处理、版本回滚、Agent 配置、权限和迁移操作写入审计日志。

## 十一、异常处理与反馈

| 场景 | 系统行为 | 用户反馈 |
| --- | --- | --- |
| 离线 | 正文写 WAL，AI 不伪装成功 | 显示离线待同步 |
| 保存冲突 | 保留三方版本，等待合并 | 显示 409 和差异入口 |
| Markdown 失败 | 保留源码和当前正文 | 显示行列和原因 |
| WAL 失败 | 停止宣称自动保存有效 | 提供导出和服务端恢复 |
| AI 失败 | 保留任务上下文和错误 | 允许按原幂等键重试 |
| 未知服务端错误 | 记录请求链路和脱敏上下文 | 显示请求 ID 和重试 |
| 评论失联 | 保留原评论与引用 | 提供重新关联 |
| 无权限 | 禁止写操作，不泄露私有内容 | 显示权限说明 |

所有异步按钮必须有执行中、成功、失败和防重复提交状态。网络请求取消只取消客户端等待，不得错误宣称服务端任务已取消。

## 十二、视觉、响应式与无障碍

### 12.1 视觉规则

沿用墨韵科技风、靛蓝主色、8px 间距和现有设计令牌，将令牌迁移到 `design-tokens` 包。明暗主题同步设置 `color-scheme`，不为新工作台另建一套冲突颜色体系。

动画只使用明确的属性和短时反馈，尊重 `prefers-reduced-motion`，不使用全局 `transition: all` 掩盖布局问题。

### 12.2 无障碍要求

- 章节树使用树语义和方向键操作，章节重命名可通过键盘完成。
- 编辑器、修订、评论和待办均可脱离鼠标完成关键流程。
- 弹窗和抽屉具备标题关联、焦点陷阱、背景隔离和关闭后焦点恢复。
- Toast 和保存状态使用适当的 `aria-live`，但不逐字朗读流式正文。
- Canvas 剧情树和 SVG 角色版图提供等价的列表、搜索和键盘操作入口。
- 正文、修订颜色和评论锚点不能只依赖颜色表达状态。
- 目标为 WCAG 2.2 AA，覆盖 375、768、1024、1440px 布局。

## 十三、迁移与切换

### 13.1 数据分类

迁移模块必须先分类，再映射。禁止将旧 Coze 展示作品与小说项目仅按名称合并。

| 旧数据类型 | 目标映射 |
| --- | --- |
| 小说项目及章节 | `Work`、`Volume`、`Chapter` 和初始版本 |
| 角色与角色绑定 | 角色实体、Agent 绑定和流程配置 |
| Coze bot / workflow | Agent 或工具连接配置 |
| dataset / 知识文件 | 作品知识资产及来源记录 |
| 剧情树与版图 | 剧情节点、关系、角色节点和布局 |
| 全局模型配置 | 服务端环境引用或非敏感设置 |
| 无法分类的数据 | 隔离清单，人工确认后再导入 |

PAT Token 和 API Key 不通过业务数据导出文件迁移。迁移报告必须指出需要重新配置的秘密引用，但不得输出秘密值。

### 13.2 迁移流程

1. 对源数据建立只读快照和摘要。
2. 执行 dry-run，生成实体分类、字段映射、数量和错误报告。
3. 修正映射后以同一批次键重跑，保证幂等。
4. 校验作品、章节、角色、Agent、知识和剧情数量及内容摘要。
5. 在维护窗口停止旧系统写入，执行最终增量迁移。
6. 切换唯一写入方到 NestJS，完成冒烟验证后开放使用。
7. 按备份策略保留源数据，不在验证完成前删除。

### 13.3 回滚边界

- 切换前回滚：继续以旧系统为唯一写入方，废弃未生效导入批次。
- 切换后代码回滚：仅在数据库结构兼容时回滚应用版本，不直接重新开放旧系统写入。
- 切换后数据恢复：使用数据库备份、时间点恢复或前向修复，避免新旧库各自产生新写入。

## 十四、测试与质量门槛

### 14.1 自动化分层

- 单元测试：双模式转换、修订分组、接受/拒绝、锚点重定位、WAL 回放、权限和幂等。
- 集成测试：PostgreSQL 原子保存、409 冲突、队列重试、重复回调、迁移和审计。
- 组件测试：章节树、编辑器、修订、评论待办、保存状态和错误提示。
- Playwright：作品库到正文、双模式、AI 修订、评论待办、通知、版本回滚和创作工具联动。

### 14.2 故障注入

必须覆盖以下场景：

1. 本地已落盘、服务端未确认时杀死浏览器并恢复。
2. 保存事务中停止数据库或服务端，验证无半条数据。
3. AI Worker 执行中及结果写入前崩溃，验证不重复修订。
4. 模拟断网、重复回调、WAL 损坏、配额不足和多标签页。
5. 模拟非法 Markdown、评论失联和本地/服务端版本冲突。

### 14.3 非功能门槛

- 千级章节导航虚拟化；常规章节按 1 万汉字正文计，输入响应 P95 < 50ms，打开章节 P95 < 2 秒。
- 性能验收报告必须记录硬件、浏览器、数据集和是否包含网络；缺少环境信息的结果不作为达标证据。
- Chrome、Edge、Firefox、Safari 最新两个主版本完成关键流程验证。
- 375、768、1024、1440px 无阻断性溢出或不可达操作。
- 键盘、读屏、焦点和对比度达到本规格无障碍要求。
- 每次提交前通过类型检查、Lint、单元测试、集成测试、E2E、构建及相关迁移检查。

核心底线是：不静默丢稿、不静默覆盖、不重复产生有效 AI 结果或正文修订、不伪造保存成功。

## 十五、分阶段交付

| 里程碑 | 范围 | 验收门槛 |
| --- | --- | --- |
| M0 工程基座 | Monorepo、数据库、契约、鉴权、CI | 应用可启动，迁移可重复，密钥不入前端 |
| M1 写作基座 | 作品库、三栏壳、卷章节、双模式、WAL | 完成一章写作，恢复和冲突场景通过 |
| M2 变更协作 | 修订、版本、评论、待办、通知、审计 | 全部变更可追踪，评论和回滚边界通过 |
| M3 AI 创作 | Agent、工具、队列、SSE、剧情、角色、知识 | AI 只生成待审修订，任务重试不重复 |
| M4 迁移切换 | 分类映射、dry-run、校验、唯一写入方切换 | 迁移报告通过，旧 UI 与旧后端退场 |
| M5 发布加固 | 兼容、性能、无障碍、安全、备份恢复 | 质量门槛和发布回滚演练通过 |

每个里程碑必须在实施前形成独立任务拆解和验收证据。本规格不授权跳过 M0/M1 直接建设全部外围功能。

## 十六、风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 总范围过大 | 按 M0–M5 分阶段评审，每阶段独立验收 |
| 双模式转换丢内容 | 共享 Schema、往返测试、失败不覆盖 |
| 自动保存造成虚假安全感 | 区分本地和云端状态，执行真实故障注入 |
| AI 重复或覆盖正文 | 幂等结果、候选修订、人工接受 |
| 评论随编辑丢失 | 位置映射、原文指纹、失联状态 |
| 迁移错误合并 | 先分类后映射，dry-run 和摘要校验 |
| 新旧系统数据分叉 | 维护窗口、单写入方、禁止双写 |
| 原型变成长期演示 | 每个里程碑必须通过真实数据库和浏览器验收 |

## 十七、文档与实施衔接

实施过程中必须同步更新项目概述、技术栈、目录结构、API 契约、开发规范、测试报告和上线手册。现有文档描述的是当前 Flask 系统；只有对应里程碑完成后，才能将其更新为已落地状态。

后续实施计划应从 M0 开始，M1 的工作台壳和正文基础优先于外围工具美化。任何需求变化先修订本规格或对应里程碑规格，再进入编码。
