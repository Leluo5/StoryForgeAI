> 版本：v1.0 · 状态：生效（2026-11-19）
> 适用范围：StoryForgeAI 开发环境搭建、依赖安装、数据库初始化、生产构建与部署验收
> 维护：07-上线与运维｜关联：[技术栈](../02-技术与架构/技术栈.md)、[目录结构](../02-技术与架构/目录结构.md)、[开发规范](../02-技术与架构/开发规范/README.md)、[文档中心](../README.md)
> 执行约定：除特别说明外，命令均在仓库根目录 `StoryForgeAI/` 执行；Windows 使用 PowerShell 5.1 及以上，Linux/macOS 使用 bash

## 一、总览与部署模式

本章说明项目由哪两套系统组成、各自依赖什么，以及三种部署模式的选择标准。

### 1.1 结论先行

项目当前是**双栈并存**：旧版 Flask 展示平台（Python）与新版写作工作台（NestJS + React）在同一仓库内独立运行、独立存储、互不双写。完整部署需要 Node.js、pnpm、Python、PostgreSQL 16、Redis 7 五类运行时；只部署旧版展示平台时仅需 Python。

部署是否成功，以第八章的验收清单全部通过为准，不以“进程已启动”为准。

### 1.2 双栈运行边界

下表列出两套子系统的运行边界，部署时不得混用端口、数据库与数据目录。

| 子系统 | 技术栈 | 入口 | 监听地址 | 存储 |
| --- | --- | --- | --- | --- |
| 新版写作工作台 | NestJS 11 + React 19 + Vite 6 | `apps/api`、`apps/web` | `127.0.0.1:3001`、`127.0.0.1:5173` | PostgreSQL 16 + Redis 7 |
| 旧版展示平台 | Flask 2.3 + 原生 JS | `app.py` | `0.0.0.0:5000` | `data/*.json` |

> 【必读】新版 API 只读写 PostgreSQL 中的作者、作品、章节、修订、AI 任务、Agent 与剧情数据；旧版 Flask 只读写 `data/` 下的 JSON。两者不共享数据，也不存在自动迁移。

### 1.3 三种部署模式

按用途选择模式，避免安装无关组件。

| 模式 | 适用场景 | 必需组件 | 可选组件 |
| --- | --- | --- | --- |
| A 完整开发 | 本地开发、联调、验收 | Node 22.16.0、pnpm 10.12.4、Python 3.9+、PostgreSQL 16、Redis 7 | Docker、Playwright |
| B 仅新版工作台 | 生产部署写作系统 | Node 22.16.0、pnpm 10.12.4、PostgreSQL 16、Redis 7、Nginx | Docker |
| C 仅旧版展示 | 仅展示 Coze 作品 | Python 3.9+ | Nginx、Gunicorn |

> 【注意】模式 B 与模式 C 可以同机部署，但必须使用不同端口并分别维护数据备份；不要将旧版 `data/` 导入 PostgreSQL。

### 1.4 生产拓扑硬约束

`apps/api/src/main.ts` 中 API 固定监听 `127.0.0.1`，不接受外部直连。对外提供服务时，必须由同机 Nginx 反向代理 `/api/` 到 `127.0.0.1:3001`，或经评审后修改监听地址。

> 【禁止】不要通过端口映射或防火墙把 `3001` 直接暴露到公网；该端口没有 TLS，且会话 Cookie 的 `Secure` 行为依赖部署协议。

## 二、软件环境要求

本章给出唯一的版本口径、硬件下限与网络前提；版本不符时先修正环境再继续。

### 2.1 版本矩阵

下表为唯一版本口径，来源于 `package.json`、`.nvmrc`、`infra/docker-compose.yml` 与 CI 配置。

| 组件 | 版本要求 | 用途 | 是否必需 | 校验命令 |
| --- | --- | --- | --- | --- |
| 操作系统 | Windows 10/11 x64、Ubuntu 22.04、macOS 13+ | 运行环境 | 是 | `uname -a` 或 `winver` |
| Node.js | 22.16.0（精确版本） | API、Web、脚本 | 是 | `node --version` |
| pnpm | 10.12.4（精确版本） | 工作区依赖管理 | 是 | `pnpm --version` |
| Python | 3.9 及以上，推荐 3.10–3.12 | 旧版 Flask、测试脚本 | 模式 A/C 必需 | `python --version` |
| PostgreSQL | 16.x（容器使用 `pgvector/pgvector:pg16` 镜像，含 `vector`/`pg_trgm` 扩展） | 新版业务数据库 | 模式 A/B 必需 | `psql --version` |
| Redis | 7.x | BullMQ 任务队列 | 模式 A/B 必需 | `redis-server --version` |
| Docker | Engine 24+ 或 Desktop 4.x | 中间件容器化 | 推荐 | `docker --version` |
| Docker Compose | v2（`docker compose` 子命令） | 编排 PostgreSQL/Redis | 推荐 | `docker compose version` |
| Nginx | 1.24 及以上 | 生产静态托管与反代 | 模式 B 生产必需 | `nginx -v` |
| Playwright Chromium | 1.51.x | 浏览器验收 | 仅验收 | `pnpm exec playwright --version` |
| 浏览器 | Chrome 120+ 或 Edge 120+ | 工作台运行 | 是 | 浏览器“关于”页 |

> 【注意】仓库 `engines` 与 `.nvmrc` 均锁定 `22.16.0`，`packageManager` 锁定 `pnpm@10.12.4`。使用其他 Node 主版本可能在安装或构建阶段被拦截。

> 【禁止】项目只支持 pnpm。`npm install` 与 `yarn install` 无法正确解析 `workspace:*`，不得替代。数据库只使用 PostgreSQL 16，不使用 MySQL 或 MongoDB。

### 2.2 操作系统与硬件

- 最小配置：2 核 CPU、8 GB 内存、10 GB 可用磁盘；同时运行 PostgreSQL、Redis、Node 与浏览器时建议 16 GB 内存。
- Windows 需启用 PowerShell 执行策略以运行 pnpm 脚本：`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`。
- Linux 需具备 `build-essential`、`python3-dev`（`argon2` 无预编译包时用于本地编译）。
- 文件系统需支持符号链接；Windows 建议开启“开发者模式”，否则 pnpm 工作区链接可能退化为复制。

### 2.3 网络与外部服务

- 包源：npm Registry、PyPI、Docker Hub、Playwright 浏览器下载源。
- 旧版展示平台需访问 Coze Open API `https://api.coze.cn`，并在管理后台配置 PAT Token。
- 新版工作台当前使用内置 Mock 模型 Provider，不依赖外部大模型；接入外部模型前无需额外网络配置。
- 生产环境如果启用 HTTPS，需准备证书；`NODE_ENV=production` 时会话 Cookie 带 `Secure` 标记，纯 HTTP 下登录态不会生效。

### 2.4 工具链校验

安装完成后先执行一次版本校验，输出必须与 2.1 一致。

```powershell
node --version
pnpm --version
python --version
docker --version
docker compose version
```

预期输出依次为 `v22.16.0`、`10.12.4`、`Python 3.9` 以上、Docker 版本号、Compose 版本号。任一不符时先修正运行时，不要继续安装依赖。

### 3.9 版本锁定与完整性

`pnpm-lock.yaml` 是唯一锁文件，CI 使用 `pnpm install --frozen-lockfile`。修改 `package.json` 后必须同步更新锁文件并提交，否则 CI 直接失败。

`requirements.txt` 中 `flask`、`requests`、`flask-cors`、`markdown` 为精确版本，`cryptography` 为下限约束；升级需同步 `技术栈.md`。

安装后执行以下命令确认依赖树完整。

```powershell
pnpm install --frozen-lockfile
node scripts/repair-workspace-links.mjs
pip check
pnpm exec playwright --version
```

`repair-workspace-links.mjs` 会检查并修复失效的工作区软链接；输出 `repaired 0 broken link(s)` 表示无需修复。

## 四、部署前准备

本章完成数据目录、端口、环境变量与密钥的准备，任何一项缺失都会导致后续步骤失败。

### 4.1 目录与运行时数据

旧版 Flask 首次启动会自动创建 `data/`，其中包含不得提交到 Git 的运行时数据。

| 路径 | 内容 | 备份要求 |
| --- | --- | --- |
| `data/global_config.json` | 站点名、主题、管理密码哈希 | 必须备份 |
| `data/works/*.json` | 作品配置与加密后的 PAT Token | 必须备份 |
| `data/projects/*.json` | 小说项目、角色、章节 | 必须备份 |
| `data/knowledge/*.json` | 知识库条目 | 必须备份 |
| `data/agents/`、`data/flows/` | Agent 配置与流程进度 | 建议备份 |
| `data/sessions.json` | 管理员与访问码会话 | 可不备份 |
| `data/.master.key` | PAT Token 加密主密钥 | 必须备份 |

> 【禁止】丢失 `data/.master.key` 且未配置 `STORYFORGE_MASTER_KEY` 时，已加密的 PAT Token 无法解密，只能重新导入作品。

### 4.2 端口清单

| 端口 | 服务 | 绑定地址 | 冲突处理 |
| --- | --- | --- | --- |
| `3001` | 新版 API | `127.0.0.1` | 修改 `.env` 的 `PORT`，同步 Nginx |
| `5173` | Vite 开发服务器 | `127.0.0.1` | 需改 `vite.config.ts` 的 `port` |
| `5433` | PostgreSQL 容器映射 | `0.0.0.0` | 修改 `infra/docker-compose.yml` 端口映射 |
| `6380` | Redis 容器映射 | `0.0.0.0` | 修改 `infra/docker-compose.yml` 端口映射 |
| `5000` | 旧版 Flask | `0.0.0.0` | 端口在 `app.py` 内硬编码 |
| `80`、`443` | Nginx | `0.0.0.0` | 由系统服务管理 |

> 【注意】PostgreSQL 使用 `5433` 而非默认 `5432`，Redis 使用 `6380` 而非 `6379`，目的是避免与本机既有实例冲突。连接串必须与 `infra/docker-compose.yml` 保持一致。

### 4.3 环境变量

新版 API 通过 `apps/api/src/config/env.ts` 读取仓库根目录 `.env`，变量缺失时使用默认值，格式非法时启动即失败。

| 变量 | 必填 | 默认值 | 用途 | 使用方 |
| --- | --- | --- | --- | --- |
| `NODE_ENV` | 否 | `development` | 运行模式，决定 Cookie 是否 `Secure` | API |
| `PORT` | 否 | `3001` | API 监听端口 | API |
| `WEB_ORIGIN` | 否 | `http://127.0.0.1:5173` | CORS 允许来源 | API |
| `DATABASE_URL` | 否 | `postgresql://storyforge:storyforge@127.0.0.1:5433/storyforge` | 开发库连接串 | API、迁移 |
| `TEST_DATABASE_URL` | 验收必填 | `postgresql://storyforge:storyforge@127.0.0.1:5433/storyforge_test` | 测试库连接串 | 测试、E2E |
| `REDIS_URL` | 否 | `redis://127.0.0.1:6380` | 队列连接串 | API |
| `SESSION_TTL_SECONDS` | 否 | `604800` | 会话有效期，上限 `2592000` | API |
| `AUTHOR_EMAIL` | 引导时必填 | 无 | 初始作者邮箱 | 引导脚本、E2E |
| `AUTHOR_DISPLAY_NAME` | 引导时必填 | 无 | 初始作者显示名 | 引导脚本、E2E |
| `AUTHOR_PASSWORD` | 引导时必填 | 无 | 初始作者密码，长度 8–128 | 引导脚本、E2E |
| `STORYFORGE_MASTER_KEY` | 否 | 无 | 旧版 PAT Token 加密主密钥 | Flask |

以 `.env.example` 为模板创建 `.env`。以下示例中的尖括号内容必须替换为实际值，不得原样提交。

#### 4.3.1 开发环境示例

开发环境连接本机容器化中间件，开发库与测试库共用同一实例。

```bash
NODE_ENV=development
PORT=3001
WEB_ORIGIN=http://127.0.0.1:5173
DATABASE_URL=postgresql://storyforge:storyforge@127.0.0.1:5433/storyforge
TEST_DATABASE_URL=postgresql://storyforge:storyforge@127.0.0.1:5433/storyforge_test
REDIS_URL=redis://127.0.0.1:6380
SESSION_TTL_SECONDS=604800
AUTHOR_EMAIL=author@example.com
AUTHOR_DISPLAY_NAME=Author
AUTHOR_PASSWORD=<PASSWORD>
```

`AUTHOR_*` 只在执行 `bootstrap:author` 与浏览器验收时读取，API 日常运行不依赖它们。

#### 4.3.2 生产环境示例

生产环境必须显式设置 `NODE_ENV=production`，并把域名、密码替换为真实值。

```bash
NODE_ENV=production
PORT=3001
WEB_ORIGIN=https://writer.example.com
DATABASE_URL=postgresql://storyforge:<PASSWORD>@127.0.0.1:5433/storyforge
REDIS_URL=redis://127.0.0.1:6380
SESSION_TTL_SECONDS=604800
```

> 【注意】`NODE_ENV=production` 时会话 Cookie 带 `Secure` 标记，只能通过 HTTPS 登录；`WEB_ORIGIN` 必须与浏览器实际访问的协议、域名、端口完全一致。

#### 4.3.3 验收场景变量覆盖

验收脚本从进程环境读取变量。为避免污染开发库，执行前将数据库指向 `_test` 库。

```powershell
$env:DATABASE_URL = "postgresql://storyforge:<PASSWORD>@127.0.0.1:5433/storyforge_test"
$env:TEST_DATABASE_URL = "postgresql://storyforge:<PASSWORD>@127.0.0.1:5433/storyforge_test"
$env:AUTHOR_EMAIL = "author@example.com"
$env:AUTHOR_DISPLAY_NAME = "Author"
$env:AUTHOR_PASSWORD = "<PASSWORD>"
$env:M1_ALLOW_DATABASE_RESTART = "1"
```

验收库名不以 `_test` 结尾时，测试与 E2E 脚本会直接拒绝执行，这是防止误清开发库的保护。

> 【禁止】不要将真实的 `.env`、PAT Token、管理密码或主密钥提交到 Git；`.gitignore` 已忽略 `.env` 与 `.env.*`，仅保留 `.env.example`。

### 4.4 账号与密钥准备

1. 准备一个作者邮箱与 8–128 位密码，用于 `bootstrap:author`。
2. 旧版展示平台需要一个 Coze PAT Token，由管理员在后台录入，落盘时自动加密。
3. 生产环境建议显式设置 `STORYFORGE_MASTER_KEY`，避免密钥随 `data/` 目录迁移；生成命令如下：

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

### 4.5 备份基线

部署或升级前先完成一次基线备份，至少包含 `.env`、`data/` 与 PostgreSQL 数据库。

```powershell
docker compose -f infra/docker-compose.yml exec -T postgres pg_dump -U storyforge -Fc storyforge > backup-storyforge.dump
Compress-Archive -Path data -DestinationPath backup-data.zip -Force
Copy-Item .env backup.env
```

## 五、开发环境部署步骤

以下步骤按顺序执行，每一步都有校验点；上一步未通过不要进入下一步。

### 5.1 步骤 1：准备运行时

使用版本管理器切换 Node，并通过 Corepack 启用指定 pnpm 版本。

```powershell
nvm install 22.16.0
nvm use 22.16.0
corepack enable
corepack prepare pnpm@10.12.4 --activate
node --version
pnpm --version
```

预期输出为 `v22.16.0` 与 `10.12.4`。Linux/macOS 可使用 `fnm use` 或 `nvm use`，命令等价。

### 5.2 步骤 2：安装依赖

先安装 Node 工作区依赖，再在虚拟环境中安装 Python 依赖。

```powershell
pnpm install --frozen-lockfile
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install pytest
```

Linux/macOS 将虚拟环境激活命令替换为 `source .venv/bin/activate`。

校验点：`pnpm install` 退出码为 `0`，`.venv` 已创建，`pip check` 输出 `No broken requirements found.`。

### 5.3 步骤 3：启动 PostgreSQL 与 Redis

`infra/docker-compose.yml` 将 PostgreSQL 数据卷声明为外部卷 `infra_storyforge_pg`，首次部署必须先创建，否则启动失败。数据库镜像为 `pgvector/pgvector:pg16`（含 `vector` 与 `pg_trgm` 扩展，知识库依赖），数据卷可直接复用既有 `infra_storyforge_pg`，扩展由迁移创建。

```powershell
docker volume create infra_storyforge_pg
docker compose -f infra/docker-compose.yml up -d postgres redis --wait
docker compose -f infra/docker-compose.yml ps
```

校验点：`ps` 输出中 `postgres` 与 `redis` 状态均为 `running (healthy)`。

> 【注意】`docker compose down -v` 会删除 Redis 数据卷；删除外部卷会丢失全部业务数据，生产环境禁止执行。

### 5.4 步骤 4：初始化数据库

数据库初始化分两层：SQL 脚本只创建角色与空库，业务表一律由 TypeORM 迁移创建。`synchronize` 已关闭，手工建表会与迁移冲突。

#### 5.4.1 Docker 方式

compose 已通过 `POSTGRES_DB=storyforge` 自动创建开发库，只需补充测试库并执行迁移。

```powershell
docker compose -f infra/docker-compose.yml exec -T postgres psql -U storyforge -d postgres -c "CREATE DATABASE storyforge_test OWNER storyforge"
pnpm --filter @storyforge/api migration:run
```

测试库已存在时 `psql` 返回 `database "storyforge_test" already exists`，忽略该提示即可；迁移命令可重复执行。

#### 5.4.2 非 Docker 方式完整 SQL

在 PostgreSQL 16 超级用户下通过 `psql` 执行以下脚本，执行前替换 `<PASSWORD>`。

```text
-- 1. 创建业务角色（幂等）
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'storyforge') THEN
    CREATE ROLE storyforge LOGIN PASSWORD '<PASSWORD>';
  END IF;
END
$$;

-- 2. 创建开发库与测试库（UTF8，独立模板）
CREATE DATABASE storyforge OWNER storyforge ENCODING 'UTF8' TEMPLATE template0;
CREATE DATABASE storyforge_test OWNER storyforge ENCODING 'UTF8' TEMPLATE template0;

-- 3. 授予 public schema 权限（PostgreSQL 15+ 已收紧默认权限）
\connect storyforge
GRANT ALL ON SCHEMA public TO storyforge;
\connect storyforge_test
GRANT ALL ON SCHEMA public TO storyforge;
```

`CREATE DATABASE` 不支持 `IF NOT EXISTS`，也不能放在事务块或 `DO` 块内；`\connect` 与 `\dt` 为 `psql` 元命令，在图形客户端中需手工切换连接。执行前用以下查询确认库是否已存在，已存在时跳过对应建库语句；角色已存在时脚本不会重置其密码。

```text
SELECT datname FROM pg_database WHERE datname IN ('storyforge', 'storyforge_test');
```

#### 5.4.3 迁移与校验

业务表由迁移创建，执行后核对版本表与关键表是否存在。

```powershell
pnpm --filter @storyforge/api migration:run
docker compose -f infra/docker-compose.yml exec -T postgres psql -U storyforge -d storyforge -c "SELECT name FROM migrations ORDER BY id;"
docker compose -f infra/docker-compose.yml exec -T postgres psql -U storyforge -d storyforge -c "\dt"
```

首次执行输出 `migrations complete: ...`，再次执行输出 `No migrations are pending`，说明迁移幂等。校验点为：`migrations` 表返回 8 条记录，`\dt` 可见 `authors`、`works`、`chapters`、`ai_tasks`、`plot_trees` 等表。

> 【禁止】不要手工创建 `authors`、`works` 等业务表，也不要直接修改 `migrations` 表；表结构变更必须新增迁移文件并走评审。

### 5.5 步骤 5：引导作者账号

引导脚本使用根目录 `.env` 中的 `AUTHOR_*` 变量写入作者表；重复执行会更新同名邮箱的显示名与密码。

```powershell
pnpm --filter @storyforge/api bootstrap:author
```

校验点：输出 `bootstrap complete: <AUTHOR_EMAIL>`。输出 `bootstrap failed` 时先检查 `DATABASE_URL` 与 `AUTHOR_PASSWORD` 长度。

### 5.6 步骤 6：构建共享契约包

API 与 Web 在运行时读取 `packages/contracts/dist`，启动前必须构建。

```powershell
pnpm --filter @storyforge/contracts build
```

校验点：`packages/contracts/dist/index.js` 与 `index.d.ts` 存在。

### 5.7 步骤 7：启动 API 与 Web

分别在两个终端启动，保持进程前台运行便于观察日志。

```powershell
pnpm --filter @storyforge/api start:dev
```

```powershell
pnpm --filter @storyforge/web dev
```

校验点：API 日志出现监听 `3001`，Web 日志出现 `http://127.0.0.1:5173/`；访问 `http://127.0.0.1:5173` 能看到登录页。

> 【注意】`vite.config.ts` 设置了 `strictPort: true`，`5173` 被占用时 Web 会直接退出而不是换端口。

### 5.8 步骤 8：启动旧版 Flask

仅在使用 Coze 展示、知识库、角色版图等旧功能时需要。

```powershell
python app.py
```

或双击 `start.bat`（Windows）、执行 `./start.sh`（Linux/macOS）。访问 `http://localhost:5000`。

首次启动前若 `data/global_config.json` 不存在，系统会随机生成管理密码并只保存哈希，明文不回显。需要可控密码时，可在首次启动前手工创建该文件并写入明文密码，加载时会自动转为哈希。

```json
{
  "version": "2.0.0",
  "admin_password": "<PASSWORD>",
  "site_name": "StoryForgeAI",
  "site_description": "AI 作品展示平台",
  "theme": "light"
}
```

### 5.9 步骤 9：快速冒烟

依次执行健康检查、登录与作品列表查询，全部返回成功后再进入功能验收。

```powershell
curl.exe -s http://127.0.0.1:3001/api/v1/health
curl.exe -s -c cookies.txt -H "Content-Type: application/json" -d "{\"email\":\"author@example.com\",\"password\":\"<PASSWORD>\"}" http://127.0.0.1:3001/api/v1/auth/login
curl.exe -s -b cookies.txt http://127.0.0.1:3001/api/v1/works
```

预期：健康检查返回 `{"data":{"status":"ok"},"request_id":"..."}`；登录返回作者信息与 `csrf_token`；作品列表返回 `data` 数组。

## 六、生产部署步骤

生产部署以“锁定依赖、显式迁移、静态托管、反向代理”为原则，不引入仓库未声明的运行时。

### 6.1 构建与产物

生产环境只安装锁定依赖，按“契约包 → API → Web”的顺序构建。

```powershell
pnpm install --frozen-lockfile
pnpm --filter @storyforge/contracts build
pnpm --filter @storyforge/api build
pnpm --filter @storyforge/web build
```

产物路径为 `apps/api/dist/main.js` 与 `apps/web/dist/index.html`。Web 产物是纯静态文件，不包含 Node 运行时。

### 6.2 启动 API

生产模式必须显式设置 `NODE_ENV=production`，否则 Cookie 不带 `Secure`，与预期安全策略不一致。

```powershell
$env:NODE_ENV = "production"
pnpm --filter @storyforge/api start:prod
```

Linux 使用 systemd 托管时，`WorkingDirectory` 指向 `apps/api`，`EnvironmentFile` 指向仓库根 `.env`。

```text
[Unit]
Description=StoryForge API
After=network.target postgresql.service redis.service

[Service]
Type=simple
WorkingDirectory=/opt/storyforge/apps/api
EnvironmentFile=/opt/storyforge/.env
Environment=NODE_ENV=production
ExecStart=/usr/bin/node dist/main.js
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

> 【注意】systemd 不加载 shell 的 nvm 环境，`ExecStart` 必须写 Node 绝对路径；用 `which node` 查询实际路径。

### 6.3 Web 静态托管与反向代理

将 `apps/web/dist` 发布到 Nginx 站点根目录，并把 `/api/` 反代到 API。前端使用 `BrowserRouter`，必须配置 SPA 回退。

```text
server {
  listen 80;
  server_name example.com;
  root /var/www/storyforge;
  index index.html;

  location /api/ {
    proxy_pass http://127.0.0.1:3001;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_read_timeout 3600s;
  }

  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

`proxy_buffering off` 与长 `proxy_read_timeout` 用于 AI 任务进度与剧情推衍的 SSE 长连接。启用 HTTPS 后，将 `listen` 改为 `443 ssl` 并配置证书，同时把 `WEB_ORIGIN` 改为对外域名并重启 API。

### 6.4 停止、重启与优雅退出

API 收到 `SIGINT` 或 `SIGTERM` 时先关闭 BullMQ Worker，再关闭 HTTP 服务，最后退出进程。

```powershell
Get-NetTCPConnection -LocalPort 3001 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess }
```

```bash
kill -TERM "$(pgrep -f 'apps/api/dist/main.js')"
```

中间件停止与重启：

```powershell
docker compose -f infra/docker-compose.yml stop
docker compose -f infra/docker-compose.yml start
```

生产重启顺序为：中间件 → API → Nginx。Nginx 配置变更后先 `nginx -t` 再 `nginx -s reload`。

### 6.5 升级与回滚

升级步骤固定为：备份 → 拉取代码 → 安装锁定依赖 → 执行迁移 → 构建 → 重启 → 验收。迁移只按版本前向执行，回滚不依赖迁移的 `down`，而是恢复数据库备份。

回滚步骤：停止 API → 恢复数据库 dump → 恢复 `data/` 与 `.env` → 切回上一版本代码 → 重新构建契约包与 API → 启动 → 复跑验收清单。

## 七、常见问题排查

本章按“现象、原因、处理”组织，覆盖端口、版本、依赖、数据库、缓存、鉴权与浏览器七类高频问题。

### 7.1 端口被占用

现象：API 启动报 `EADDRINUSE`，Vite 直接退出，或容器启动失败。

```powershell
Get-NetTCPConnection -State Listen -LocalPort 3001,5173,5433,6380,5000
```

Linux 使用 `ss -lntp | grep -E ':(3001|5173|5433|6380|5000)'`。处理方式为停止占用进程，或修改 `.env` 的 `PORT` 并同步 Nginx；`5173` 与 `5433`、`6380` 的修改还会影响 `vite.config.ts` 与 `docker-compose.yml`，修改后需同步文档。

### 7.2 Node 或 pnpm 版本不符

现象：安装阶段提示 `Unsupported engine`，或构建产物异常、脚本无法执行。

处理：严格切换到 `22.16.0` 与 `pnpm 10.12.4`，不要使用 Node 24/26 兼容替代。执行 `corepack disable` 后再 `corepack enable` 可修复 Corepack 缓存错乱。

### 7.3 依赖安装失败

现象：`pnpm install` 在 `argon2`、`esbuild` 或网络阶段失败。

- 网络问题：设置可访问的 npm Registry 后重试，不要跳过校验。
- 原生模块：Windows 安装 Visual Studio Build Tools 与 Python，Linux 安装 `build-essential`。
- 锁文件冲突：确认 `pnpm-lock.yaml` 已提交且与 `package.json` 一致，禁止用 `--no-frozen-lockfile` 掩盖问题。
- 缓存损坏：执行 `pnpm store prune` 后重装。

### 7.4 工作区软链接损坏

现象：启动时报 `Cannot find module '@storyforge/contracts'`，或 `dist` 内容缺失。

```powershell
node scripts/repair-workspace-links.mjs
pnpm --filter @storyforge/contracts build
```

该脚本是 `postinstall` 钩子，会重建失效的 `workspace:*` 链接；输出 `repaired N broken link(s)` 后重启开发服务器。

### 7.5 PostgreSQL 连接失败

现象：API 启动报 `ECONNREFUSED 127.0.0.1:5433` 或 `password authentication failed`。

按顺序检查容器状态、健康检查与连接串；连接串中的库名、用户、端口必须与 compose 文件一致。

```powershell
docker compose -f infra/docker-compose.yml ps
docker compose -f infra/docker-compose.yml exec -T postgres pg_isready -U storyforge -d storyforge
```

如果本机已有 PostgreSQL 占用 `5432`，不要改容器到 `5432`，继续使用 `5433` 映射。

### 7.6 外部数据卷缺失

现象：`docker compose up` 报 `external volume "infra_storyforge_pg" not found`。

```powershell
docker volume create infra_storyforge_pg
docker compose -f infra/docker-compose.yml up -d postgres redis --wait
```

> 【禁止】不要为绕过报错而删除 `external: true` 后重建同名卷；这会让新容器挂载空卷，表现为“数据全部丢失”。

### 7.7 迁移未执行导致表不存在

现象：接口返回 500，日志出现 `relation "works" does not exist`。

```powershell
pnpm --filter @storyforge/api migration:run
```

不要在开发库开启 `synchronize`，也不要手工建表；显式迁移是唯一建表路径。测试库重建使用 `pnpm --filter @storyforge/api test:prepare`，该命令会删表，仅允许库名以 `_test` 结尾。

### 7.8 Redis 连接失败或 AI 任务卡住

现象：AI 任务长期停留在 `queued`，日志出现 `ECONNREFUSED 127.0.0.1:6380`。

```powershell
docker compose -f infra/docker-compose.yml up -d redis --wait
docker compose -f infra/docker-compose.yml exec -T redis redis-cli ping
```

预期返回 `PONG`。若 Redis 正常但任务仍不推进，检查 API 启动日志是否成功创建 Worker；Worker 与 HTTP 在同一进程内启动，API 未启动时任务不会被消费。

### 7.9 登录后仍 401 或 403

- `401`：会话 Cookie 未携带。确认访问地址统一使用 `127.0.0.1`，不要混用 `localhost`。
- `403`：写操作缺少 CSRF。请求头 `x-csrf-token` 必须等于 `storyforge_csrf` Cookie 值。
- 生产环境登录成功但立即失效：`NODE_ENV=production` 时 Cookie 带 `Secure`，必须通过 HTTPS 访问。
- 跨域失败：`WEB_ORIGIN` 必须与浏览器地址完全一致，协议、域名、端口任一不同都会被 CORS 拒绝。

### 7.10 浏览器端页面空白或深链 404

开发环境由 Vite 处理回退；生产环境缺少 `try_files $uri $uri/ /index.html` 时，直接访问 `/works/...` 会 404。补齐 Nginx 配置后重载。

页面空白且控制台报模块导出缺失时，多为契约包未构建或未预构建，执行契约包构建后清空浏览器缓存再试。

### 7.11 Playwright 浏览器缺失

现象：`pnpm test:e2e` 报 `Executable doesn't exist`。

```powershell
pnpm exec playwright install --with-deps chromium
```

Linux 无 root 权限时去掉 `--with-deps`，由系统管理员预装依赖库。

### 7.12 Python 依赖或权限问题

- `cryptography` 编译失败：升级 pip 后重试，Linux 先安装 `build-essential` 与 `python3-dev`。
- `Permission denied`：确认虚拟环境已激活，且不要把包装到系统 Python。
- 旧版写入 `data/` 失败：确认运行用户对仓库目录有写权限，Windows 不要放在受控目录（如 `Program Files`）。
- Flask 启动后 500：查看控制台 traceback，重点检查 `data/global_config.json` 是否为合法 JSON。

### 7.13 旧版作品 PAT 解密失败

现象：作品详情、对话或工作流执行报“未配置 PAT Token”或鉴权失败，日志无明文密钥。

原因通常是主密钥变更或丢失。恢复原 `data/.master.key`，或使用原 `STORYFORGE_MASTER_KEY` 重启；无法恢复时只能删除该作品并重新导入。

## 九、风险、边界与回滚

本章明确当前架构的已知限制、必须提前备份的数据，以及升级失败时的回滚路径。

### 9.1 已知风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| API 固定监听 `127.0.0.1` | 无法被外部直接访问 | 同机 Nginx 反代，或评审后修改监听地址 |
| SSE 事件总线为进程内实现 | 多实例部署时订阅者收不到其他实例事件 | 单实例部署，或改造为跨进程广播 |
| 外部数据卷 `infra_storyforge_pg` | 卷缺失时容器无法启动 | 首次部署先创建卷，禁止重建空卷 |
| 旧版 JSON 与新库不互通 | 旧数据不会出现在新工作台 | 明确迁移不在本手册范围，禁止双写 |
| `.env` 与主密钥不入库 | 丢失后无法恢复会话或解密 | 独立备份 `.env` 与 `data/.master.key` |
| 迁移只前向执行 | 升级失败不能靠回滚迁移恢复 | 升级前做数据库 dump，回滚用备份 |

### 9.2 回滚步骤

1. 停止 API 与 Nginx 流量入口。
2. 恢复最近一次 PostgreSQL dump，恢复 `data/` 与 `.env`。
3. 切换到上一版本代码并重新执行 `pnpm install --frozen-lockfile`。
4. 重新构建契约包与 API，启动并按第八章复验。
5. 在验收报告中记录回滚原因、时间与数据恢复点。

### 9.3 不在本文范围

- 旧版 JSON 数据迁移到 PostgreSQL 的方案与脚本。
- 多实例水平扩展、跨进程 SSE 广播与队列独立 Worker。
- 云厂商负载均衡、对象存储与证书自动续期。
- Coze 平台侧的智能体、工作流与知识库配置。
