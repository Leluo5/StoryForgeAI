## 四、根因

### 4.1 根因机制（核心）

`RevisionService.resolveOperation`（M2 变更协作实现，M3a 复用）原设计**只标记 `revision_set` 状态**（`pending → accepted/rejected → resolved`），**从不写回章节正文**。M2 的正文写回只在 `confirmRollback`（回滚时）发生。

M3a 技术方案 §八 D4 明确要求「接受 AI 修订写入正文、版本推进、版本快照（复用 M2 resolveOperation）」——但 M2 `resolveOperation` 从未实现写正文，因此 M3a 直接复用该函数导致 D4 未落地。

### 4.2 辅助根因：占位 step 破坏 M2 链路

前端「创建 AI 修订集」按钮（`revision-panel.tsx`）传入**占位 step** `{type:'placeholder', text:'AI 修订占位'}`，非合法 ProseMirror step。若对占位 step 调 `applyOperations` 会抛错，导致 M2 完整链路「接受 → 已解决」失败。这是修复写正文时引入的连带问题，需在写正文分支容忍占位 step。

---

## 五、修复方案（最小改动）

### 5.1 接受 AI 修订写回正文

`apps/api/src/revision/revision.service.ts` 的 `resolveOperation` 接受分支新增 AI 写正文逻辑（`ai_set && decision === 'accept'` 时）：

```ts
// 接受 AI 修订：把该条 step 应用到章节正文（版本+1、content_hash）。
// 与 M2 手工修订不同（仅标记状态），M3a D4 要求接受 AI 修订即真正写入正文。
// 自动快照已在上面 ensureAutoSnapshot 完成（记录的是接受前的正文，作为回滚基准）。
if (revisionSet.ai_set && decision === 'accept') {
  const chapter = await manager.getRepository(ChapterEntity).findOneBy({ id: revisionSet.chapter_id });
  if (chapter) {
    try {
      const nextDoc = applyOperations(chapter.document, [toSteps([target.step])[0]!]);
      chapter.document = nextDoc.toJSON();
      chapter.version = chapter.version + 1;
      chapter.content_hash = createHash('sha256').update(canonicalizeDocument(nextDoc.toJSON())).digest('hex');
      await manager.save(chapter);
    } catch {
      // 占位/非法 step（前端「创建 AI 修订集」占位操作、或测试构造的假 step）无法应用为真实正文变更：
      // 仅推进修订集状态，不写正文、不改版本。真实 AI replace step 才走上方写入分支。
    }
  }
}
```

**要点**：
- 仅 `ai_set && accept` 分支生效，M2 手工修订行为不变（只标记状态）；
- 版本快照已由既有 `ensureAutoSnapshot` 在写入前完成（记录接受前正文，作为回滚基准）；
- 占位/非法 step 在 `catch` 中容忍（跳过写正文，仅推进修订集状态），不破坏 M2 完整链路。

### 5.2 import 调整

新增 `applyOperations`、`canonicalizeDocument`（来自 `@storyforge/editor-schema`）；移除不再使用的 `BadRequestException`。

### 5.3 相关改动（同批）

- `apps/api/src/main.ts`：恢复 `AiTaskProcessor` Worker 启动（`createWorker()`）——M3a-A5 实现的 Worker 无调用方，导致队列任务不被消费；
- `playwright.config.ts`：webServer env 补 `REDIS_URL`（`redis://127.0.0.1:6380`），E2E 可连通 Redis；
- `tests/e2e/m3a-ai-creation.spec.ts`：新增 7 项 E2E 用例（鉴权/全链路/幂等/状态机/取消/契约审计/断线重连补取）。

## 八、同类问题排查指引

### 8.1 快速定位（三问）

1. **接受后正文是否更新？** → 读章节 `GET /works/:workId/chapters/:chapterId`，看 `document`/`version`；
2. **是否 `ai_set=true`？** → 读修订集 `revision_sets`，确认 `actor_type='ai'`；
3. **是否占位 step？** → 读修订集 `operations[].step.type`，若为 `placeholder` 则走容忍分支。

### 8.2 标准排查命令

```powershell
# 查修订集与章节（psql）
docker exec -it storyforge-postgres psql -U postgres -d storyforge -c "SELECT id, ai_set, status FROM revision_sets ORDER BY created_at DESC LIMIT 5;"
docker exec -it storyforge-postgres psql -U postgres -d storyforge -c "SELECT id, version, content_hash FROM chapters WHERE id = '<chapter_id>';"
```

## 九、预防措施

1. **跨里程碑复用函数的验收标准核对**：M3a 方案 D4 明确「复用 M2 resolveOperation」，但 M2 实现从未写正文，需在方案层标注「M2 原语义 + M3a 增强」差异，避免静默复用；
2. **占位 step 与真实 step 区分**：前端占位操作不应进入后端应用逻辑，建议后续在契约层用 `z.discriminatedUnion` 校验 step 类型，或前端改用真实 step；
3. **E2E 全链路覆盖**：任何「接受 → 正文写入」闭环必须有全链路 E2E 断言正文，而非仅断言修订集状态。

## 十、注意事项

- **M2 语义不变**：本次仅对 `ai_set && accept` 分支新增写正文，M2 手工修订（`ai_set=false`）仍只标记状态，不写正文；
- **版本快照顺序**：自动快照（`ensureAutoSnapshot`）必须在写入正文**之前**完成，记录接受前正文作为回滚基准；
- **占位 step 容忍**：`catch` 只跳过写正文，不吞掉修订集状态推进（状态仍正确进入 resolved）。
