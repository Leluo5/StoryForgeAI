## 一、变更总览

本文档记录「新增文档口径」与「M3c-3 已定稿实现」之间的差异，以及经用户裁决后的增量设计。

### 1.1 四项用户裁决（2026-11-25）

| 决策点 | 结论 | 影响面 |
| --- | --- | --- |
| 条目类型范围 | **全部 11 类**一次性扩满 | DB CHECK、contracts 枚举、前端渲染模板 |
| 既有四类字段改名 | **就地改名 + 存量降级** | 契约重写；旧数据不迁移，遇旧结构回退原文展示 |
| 类型识别机制 | **LLM 判定 + 规则兜底** | 判定链路改造；复用 M3b 已接入的 `RealKnowledgeLlmProvider` |
| 长文拆分多条 | **不纳入**，标注为文档空白 | 不做条目拆分模型 |

### 1.2 变更分级

| 级别 | 内容 | 判定 |
| --- | --- | --- |
| 纯新增扩展 | 6 个新类型（`character` / `plot_template` / `reference_work` / `technique` / `reader_feedback` / `timeline`）的判定规则、structured schema、渲染模板；方案 C 的批量多选 / 排序 / 时间范围 / 标签云；方案 D 抽屉宽度可配 | 低：不动既有语义 |
| **语义变更** | `article` / `paper` / `novel` / `inspiration` 四类 structured 字段整体改名重构 | **高**：现有 `.strict()` 契约与存量数据直接失效 |
| **机制变更** | 类型识别从纯函数规则改为 LLM Few-shot 判定（数值置信度三段阈值）；`setting` 由「仅手选」放开为可自动判定 | 中 |
| **口径冲突** | `outline` 归属：现有为独立列，新文档并入 novel 的 `structured` 内 | 中，本文档 §4.3 裁决 |

### 1.3 明确不做

- 不删除任何类型，只允许标记废弃（分类规则 v1.1 禁止事项）。
- 不做「一条原文拆多条条目」：无条数上限、无父子关系模型、无去重口径，属**文档空白**，不在本期。
- 不做存量数据迁移脚本（裁决二已选就地改名 + 存量降级）。
- 不新增未在分类规则 v1.1 中定义的类型；流派等细分仍用 `tags`。

## 二、类型体系（11 类）

### 2.1 类型清单

顺序：核心 5 类在前，扩展 6 类按优先级排列。

| # | 枚举值 | 中文名 | 优先级 | 判定特征（满足任意 2 项即可倾向判定） | 排除特征 |
| --- | --- | --- | --- | --- | --- |
| 1 | `article` | 文章 | 核心 | 传递信息 / 观点 / 事实为主，非完整虚构故事，有段落结构（现象→分析→结论） | 出现完整虚构人物弧光与情节冲突 → 小说 |
| 2 | `paper` | 论文 | 核心 | 具摘要 / 关键词 / 引言 / 方法 / 结果 / 讨论 / 参考文献等学术结构，明确提出研究问题并给出方法与结论 | 仅科普转述且无研究过程 → 文章 |
| 3 | `novel` | 小说 | 核心 | 虚构人物、情节、冲突为主线，有叙事视角 / 时间线 / 场景描写与故事推进 | 纯设定罗列且无情节推进 → 设定集 |
| 4 | `inspiration` | 灵感 | 核心 | 碎片化、未完成、口语化跳跃，通常 <500 字，缺乏完整结构 | 已形成完整段落与逻辑闭环 → 文章 |
| 5 | `setting` | 设定集 | 核心 | 以「设定」为目的（世界观 / 力量体系 / 地理 / 历史 / 种族 / 组织），条目化列表化，本身不是完整故事 | 有完整情节与人物弧光 → 小说 |
| 6 | `character` | 角色档案 | **P0** | 以单一或少数角色为描述中心，重点在性格 / 背景 / 外貌 / 能力 / 说话方式 / 弧光 | 有完整情节推进与多场景叙事 → 小说 |
| 7 | `plot_template` | 情节模板 | **P0** | 描述情节结构 / 节拍 / 套路 / 冲突升级路径而非具体故事，具抽象性与可复用性 | 具体人物 + 具体事件推进 → 小说 |
| 8 | `reference_work` | 对标作品 | P1 | 主体是对另一部已有作品（小说 / 影视 / 游戏）的分析、拆解、优缺点总结 | 作品原文或大量引用原文叙事 → 小说 |
| 9 | `technique` | 写作技法 | P1 | 核心是「如何写」的具体方法、步骤、示范，可直接指导某类段落练习 | 宏观结构套路 → 情节模板 |
| 10 | `reader_feedback` | 读者反馈 | P2 | 来源为读者评论汇总、数据报告、追更 / 弃坑分析 | — |
| 11 | `timeline` | 时间线 | P2 | 以时间顺序排列的事件序列（故事内或创作相关） | — |

> 权威源：[知识库条目分类规则](../../01-产品与设计/知识库条目分类规则.md) §二（v1.1）、`KNOWLEDGE_ENTRY_TYPES`（`docs/02-技术与架构/knowledge-prompts/types.ts`）。

### 2.2 现有实现的差异点

| 差异 | 现状 | 本期结论 |
| --- | --- | --- |
| 类型枚举来源 | `knowledge-enums.ts` 与 `contracts/knowledge.ts` 各自硬编码 5 类，且与 `KNOWLEDGE_ORIGINS` 存在漂移（enums 已含 `coze_import`，contracts 的 `knowledgeOriginSchema` 未含） | 11 类清单单一来源化；顺带补齐 `coze_import` 漂移 |
| `setting` 可判定性 | 永不自动识别，仅手选 | 放开为 LLM 可判（排除特征法）；判定来源记 `user_override` / `auto` |
| 类型变更 | 改判调用 `restructure`，成功前保留旧结构化结果 | 不变，补充判定来源写入 |
| 权威源规则 | 无 | 新增：独立 `character` 条目 > 小说拆文 `characters[]` 快照 |

## 三、structured 字段重构

### 3.1 通用约束（新增文档 §十三口径）

| 约束 | 规则 |
| --- | --- |
| 必填缺失降级 | 必填字段结构化失败时**降级为仅保存 `raw_content` + 类型**：条目以原文入库，`structure_status='failed'`，仍可检索 / 编辑 / 重试 |
| 空集表示 | **空集合用 `[]`，不用 `null`**（`character.relationships` 即「P0 必填但允许空数组」范例） |
| 关系 target | `relationships[].target` 使用**字符串而非 entry id**，允许对方尚未建档；后续对齐工具回写 `target_id` |
| 长度建议 | 摘要 100–300 字；单条观点 / 要点 ≤100 字；超长内容保留在 `raw_content` |
| 版本兼容 | 新增字段向后兼容；**禁止删除或重命名已有字段**（本期四类改名为一次性例外，见 §3.4） |
| 禁止编造 | 结构化只能来源于 `raw_content`，**禁止编造原文未出现的能力、关系或台词** |
| 与顶层关系 | `tags` 可由各类型 `tag_list` 初始化；`inspiration.related_ids` 与顶层 `links` 保持同步 |
| 存储 | `structured` 使用 PostgreSQL `jsonb` |

### 3.2 既有四类字段改名映射

**`article`**（原：`sections` / `key_points` / `tags`）

| 新字段 | 类型 | 必填 | 上限 | 旧字段去向 |
| --- | --- | --- | --- | --- |
| `paragraphs` | `Paragraph[]` | 是 | — | `sections` → 改名；`{heading, content}` → `{order, content, summary?}` |
| `key_points` | `string[]` | 是 | 3–8 条 | 保留，新增数量口径 |
| `summary` | `string` | 是 | 100–300 字 | 新增 |
| `tag_list` | `string[]` | 是 | — | `tags` → 改名 |

`Paragraph`：`order: number`（必填）、`content: string`（必填）、`summary?: string`（选填）。

**`paper`**（原：五要素 + `keywords`）

| 新字段 | 类型 | 必填 | 旧字段去向 |
| --- | --- | --- | --- |
| `research_question` | `string` | 是 | 保留 |
| `research_method` | `string` | 是 | `method` → 改名 |
| `core_conclusion` | `string` | 是 | `findings` + `contributions` → 合并 |
| `limitation` | `string` | 是 | `limitations` → 改名 |
| `design_insight` | `string` | 是 | 新增（对创作 / 产品的可落地启发） |
| ~~`keywords`~~ | — | — | **删除**（改用顶层 `tags` 承载） |

**`novel`**（原：`characters` / `plot_summary` / `narrative_style` / `worldview`）

| 新字段 | 类型 | 必填 | 旧字段去向 |
| --- | --- | --- | --- |
| `characters` | `Character[]` | 是 | 保留；`{name, role, description}` → `{name, description, relationships?}`，**移除 `role`**，新增字符串数组 `relationships` |
| `plot_lines` | `PlotLine[]` | 是 | `plot_summary` → 升级为结构化数组 |
| `narrative_style` | `string[]` | 是 | 由 `string` 改为**数组** |
| `world_setting` | `string` | 是 | `worldview` → 改名 |
| `outline` | `NovelOutline` | 是 | 见 §4.3 口径裁决 |

`PlotLine`：`type: 'main' | 'branch' | 'hidden'`（必填枚举）、`summary: string`（必填）、`key_events?: string[]`（选填）。

**`inspiration`**（原：`completion` / `matched_entry_ids` / `independent`）

| 新字段 | 类型 | 必填 | 上限 | 旧字段去向 |
| --- | --- | --- | --- | --- |
| `raw_text` | `string` | 是 | — | 新增（碎片原样保留） |
| `enriched_text` | `string` | 是 | — | `completion` → 改名 |
| `related_ids` | `string[]` | 是 | 默认最多 3 条 | `matched_entry_ids` → 改名；**`independent` 字段删除**（改由 `related_ids` 为空数组表达） |

**`setting`**：同 `article` 四字段，另加选填 `setting_items?: {name: string; content: string; category?: string}[]`。

### 3.3 六个新类型的 schema

**`character`**（P0，字段优先级口径最完整；`CHARACTER_P0_FIELDS = ['name','identity','personality','background','relationships']`）

| 字段 | 类型 | 必填 | 级别 | 上限 |
| --- | --- | --- | --- | --- |
| `name` | `string` | 是 | P0 | 检索与版图主标识 |
| `identity` | `string` | 是 | P0 | 一句话身份 |
| `personality` | `string[]` | 是 | P0 | 建议 3–8 条 |
| `background` | `string` | 是 | P0 | 建议 100–400 字；与 `arc` 区分 |
| `relationships` | `{target: string; relation: string}[]` | 是（允许 `[]`） | P0 | `target` 允许未建档字符串 |
| `speech_style` | `string` | 否 | P1 | 对白风格与用词习惯 |
| `arc` | `string` | 否 | P1 | 成长 / 堕落路径 |
| `abilities` | `string[]` | 否 | P1 | 体系规则仍归 `setting` |
| `appearance` | `string` | 否 | P2 | — |
| `aliases` | `string[]` | 否 | P2 | — |
| `key_quotes` | `string[]` | 否 | P2 | 建议 ≤5 条 |
| `notes` | `string` | 否 | P2 | — |

> 判定特征写「单一**或少数**角色」，但 schema 只建模**单一主角**（`name` 为单值 `string`）：少数角色场景需拆为多条 `character` 条目，不做多主角数组。

**`plot_template`**（P0）：`structure_name: string`（必填）、`description: string`（必填）、`beats: Beat[]`（必填，**至少 1 个**）、`applicable_genres?: string[]`、`conflict_pattern?: string`、`example_usage?: string`。
`Beat`：`name`（必填）、`order: number`（必填）、`description`（必填，该节拍的叙事任务）、`purpose?: string`（选填，悬念 / 爽感 / 转折等）。

**`reference_work`**（P1）：`work_title: string`（必填）、`genre?: string[]`、`strengths: string[]`（必填）、`weaknesses: string[]`（必填）、`key_techniques: string[]`（必填）、`takeaways: string[]`（必填）、`target_audience?: string`、`notes?: string`。
口径：`work_title` / `strengths` / `weaknesses` / `takeaways` 建议各有实质内容。

**`technique`**（P1）：`technique_name: string`、`description: string`、`steps: string[]`、`examples: string[]`、`common_mistakes: string[]`（以上必填）；`applicable_scenes?: string[]`。

**`reader_feedback`**（P2）：`source: string`、`positive_points: string[]`、`negative_points: string[]`、`action_suggestions: string[]`（以上必填）；`data_insights?: string[]`。

**`timeline`**（P2）：`title: string`（必填）、`events: Event[]`（必填）、`scope: 'story_world' | 'creation' | 'other'`（必填）。
`Event`：`date_or_order: string`（必填）、`event: string`（必填）、`importance?: 'high' | 'medium' | 'low'`。

### 3.4 存量降级策略（裁决二）

**不写数据迁移脚本**，契约一次性切到新字段名，存量按以下顺序降级：

| 条件 | 行为 |
| --- | --- |
| 存量 `structured` 通过新 schema 校验 | 正常渲染 |
| 存量含旧字段（`sections` / `method` / `plot_summary` / `completion` 等） | 契约侧**不拒绝**该条目本身，`structured` 按新 schema 校验失败即视为「无有效结构」，详情页**回退原文展示**，`structure_status` 保持原值 |
| 作者在详情页触发「重新整理」（`restructure`） | 走新管线，用新 schema 覆盖旧结构 |
| 前端渲染 | 模板按字段存在性判断，缺失关键必填字段时渲染降级占位，不抛错 |

> 说明：现有 `structured` 列为 `jsonb NULL`，列本身兼容；仅内部结构不兼容。契约侧需为 `knowledgeStructuredSchema` 增加一条**只读宽类型**分支（`z.record(z.unknown())`）用于响应体，避免旧数据导致详情接口 422；**请求体**仍严格走新 schema。

## 四、关键口径裁决

### 4.1 outline 归属

| 方案 | 结论 |
| --- | --- |
| 独立列 `outline`（现有实现，含 `knowledgeOutlineSchema` 与 `outline_status`） | **保留，本期不变** |
| 并入 novel 的 `structured.outline`（新文档口径） | 不采纳 |

理由：独立列已有 `outline_status` 状态机、独立失败路径（`no_chapters`）与 PATCH 字段，迁移成本高且无收益。新文档中 novel 的 `structured.outline` 在本期**不落地为结构化字段**，novel 的 `structured` 只含 `characters` / `plot_lines` / `narrative_style` / `world_setting`。此处作为**已记录的设计差异**，在本文档中显式声明，避免后续实现者照抄新文档。

> 注意：新文档的 `NovelOutline` 子表字段（`chapters[].order/level`、`plot_nodes[].type: main|branch|turn`、`character_relations[].camp`、`core_storylines`）与现有 `knowledgeOutlineSchema`（`chapters[{title,summary}]`、`plot_nodes[{title,summary,chapter_index}]`、`character_relations[{source,target,relation}]`、`story_lines[]`）**字段名不同**。本期不改 `outline` 契约，仅在此记录差异；若后续需要，走新一轮 C1 变更。

### 4.2 两套 plot 枚举不得混用

| 枚举 | 取值 | 用途 |
| --- | --- | --- |
| `structured.plot_lines[].type` | `main` / `branch` / `hidden` | 情节脉络（正文事实） |
| `outline.plot_nodes[].type` | `main` / `branch` / `turn`（新文档） | 大纲节点（派生结构） |

两者不可互相校验或复用。

### 4.3 character 权威源

- 独立 `character` 条目为角色权威数据源；小说拆文的 `characters[]` 仅为文本内快照。
- 同一角色并存时，Agent 与角色版图**优先读独立 `character` 条目**。
- 本期不实现自动对齐工具（`target_id` 回写）；`relationships[].target` 只写字符串。

## 五、类型识别机制（LLM 判定 + 规则兜底）

### 5.1 目标链路

```
录入原文
   │
   ▼
判定入口（新增 KnowledgeTypeDetection 端口）
   │
   ├─ 有 LLM 凭据 ──► Few-shot 判定
   │                    │
   │                    ▼
   │              { type, confidence, reason }
   │                    │
   │     ┌──────────────┼───────────────┐
   │     ▼              ▼               ▼
   │  ≥0.75 采用    0.5–0.75 确认框   <0.5 强制手选
   │  (auto)        (auto→user_override) (manual)
   │
   └─ 无凭据 / 调用失败 ──► 现有纯函数规则（classify.ts）
                              │
                              ▼
                        映射为数值置信度，走同一阈值分流
```

### 5.2 判定输出契约

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | 11 值枚举联合 | 判定出的类型 |
| `confidence` | `number`（0–1） | 置信度 |
| `reason` | `string` | 一句话判定依据，用于确认框展示 |

system / user 两段式：system 取 `TYPE_DETECTION_SYSTEM_PROMPT`，user 为「标题：X / 正文：raw_content」（`buildTypeDetectionUserPrompt`）。与现有 `knowledge-llm.real.ts` 的调用约定（system + user 两条消息、响应解析为结构化类型）一致。

### 5.3 阈值分流与来源写入

| 条件 | 行为 | 判定来源 |
| --- | --- | --- |
| 用户手动指定 | 最高优先级，直接采用 | `manual` |
| `confidence ≥ 0.75` | 直接采用自动结果 | `auto` |
| `0.5 ≤ confidence < 0.75` | 弹确认框，展示推荐类型与 `reason`，允许修改 | 用户接受 → `auto`；用户改判 → `user_override` |
| `confidence < 0.5` 或无法判定 | 强制手动选择 | `manual` |
| 改判（详情中改类型） | 调用 `restructure`，成功前保留旧结构化结果并显示「重新整理中」 | `user_override` |

**规则兜底映射**（`classify.ts` 现返回 `'high' | 'medium' | 'low'`）：

| 现值 | 映射 confidence | 结果 |
| --- | --- | --- |
| `high` | `0.9` | 直接采用（`auto`） |
| `medium` | `0.6` | 落确认框区间 |
| `low` | `0.3` | 强制手选 |

规则兜底时仍保留 `KNOWLEDGE_TYPE_UNCERTAIN` 提示，语义与 F2 一致。

### 5.4 存储与契约影响

| 项 | 现状 | 本期 |
| --- | --- | --- |
| 判定来源字段 | 无 | 新增列 `type_source varchar(16)`（`auto` / `manual` / `user_override`），非空默认 `manual` |
| 判定置信度 | 无 | 新增列 `type_confidence numeric(3,2)`（可空），仅记录判定时刻值，供确认框与审计展示 |
| 结构化管线 | `structure_status` + `structure_error` | 不变 |

> 现有 `entry_type` 列已非空且无来源信息；新增两列为**纯增量**，不改动既有列语义。

### 5.5 setting 可判定性变更

F2 原文：「设定集永不自动识别，只能由作者在录入时或详情中手动指定。」（02-技术方案.md §5.2）

本期改为：**setting 可被 LLM 自动判定**（分类规则 v1.1 已给出其判定与排除特征）。当 LLM 判定为 `setting` 且 `confidence ≥ 0.75` 时直接采用并记 `auto`。规则兜底路径下 setting 仍**不会**被自动识别（规则表无 setting 分支），落强制手选。

## 七、风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 旧数据详情接口 422 | 存量条目打不开 | §3.4 响应体宽类型分支；详情接口对 `structured` 校验失败只降级不报错 |
| 前端模板漏分支 | 6 个新类型白屏 | 模板按字段存在性渲染；缺必填字段走降级占位，禁抛错 |
| LLM 判定不稳定 | 确认框频繁弹出 | 阈值 0.75 留有余量；`reason` 随响应返回便于用户判断；失败即回退规则 |
| 无凭据环境 | 判定降级为纯函数 | 规则映射表保证阈值分流链路不空转，CI 与本地不炸 |
| CHECK 扩容失败 | 迁移中断 | 单条 ALTER，可回滚（重建旧 CHECK）；`type_source` 有 `DEFAULT`，回滚不影响既有读写 |
| 提示词真源漂移 | 文档与常量不一致 | 修改提示词时 **文档 + `knowledge-prompts` 常量同步更新**（既有约定，沿用） |

回滚路径：新增迁移单独成文件 → 反向迁移恢复 `varchar(16)` 与 5 值 CHECK、删除两新增列；contracts 回退枚举；前端模板回退。语义变更（字段改名）**不回滚**，靠 §3.4 降级兜底。
