## 一、方案概览与范围边界

### 1.1 设计目标

在现有 TS Monorepo（`apps/api` NestJS + TypeORM + PostgreSQL、`apps/web` React + Vite、`packages/contracts` Zod）上新增「知识库」能力，逐条满足 F1 v1.1 的 D01~D30，并保证：

1. **双层隔离**：全局素材库按作者长期沉淀，作品内只保存引用与副本；两个库的列表、计数、检索、收藏与置顶互不串数据。
2. **引用只读**：作品引用始终读取全局条目最新内容，禁止在作品内直接改写；需要独立维护时另存为作品副本。
3. **录入即入库**：粘贴文本同步写入条目，文件上传异步解析；结构化在后台完成并回填，不阻塞界面。
4. **失败不丢内容**：解析或结构化失败时保留原文或失败原因，条目可检索、可编辑、可重试，不静默丢弃。
5. **素材成网**：灵感录入后基于向量相似度自动建立最多 3 条关联并生成补全文本；作者可手动增删。
6. **可迁移可恢复**：Markdown 单条/批量导入导出；整库备份采用版本化 JSON + gzip，恢复采用合并策略并返回统计。
7. **工作台内完成**：所有操作在左侧知识库抽屉内完成，正文编辑器保持挂载，保存状态与光标位置不受影响。
8. **桌面两档**：只覆盖 `1024` 与 `1440` 视口，键盘可完成核心操作。

### 1.2 范围边界

**包含**：双层素材库与作品引用、五种条目类型与类型改判、粘贴与 `docx`/`pdf`/`txt`/`md` 上传（单文件 ≤20 MB）、自动结构化与小说四维大纲、分块进度与失败重试、原文/结构化双视图、关键词/类型/标签/时间四维检索、标签增删改、收藏与置顶、灵感向量关联与补全、跨条目手动关联、引用与另存副本、回收站恢复与彻底删除、Markdown 导入导出、整库备份与合并恢复、关键操作审计。

**明确不包含**：

| 不包含项 | 原因 / 归属 |
| --- | --- |
| 图片 OCR 与扫描件文字识别 | F1 §2.2-1、D28；上传接口与界面均不暴露 OCR 入口，扫描件 PDF 以解析失败提示 |
| 条目注入角色上下文、拆文角色导入角色版图 | F1 §2.2-2、D28；角色域不读取知识库，知识库不写角色表 |

| 跨用户共享、协作编辑、权限分配 | F1 §2.2-5；全局库按作者隔离，作品库按作品归属隔离 |
| 网页抓取、RSS、自动订阅 | F1 §2.2-6；素材只能由作者主动录入或导入 |
| PDF/Word 等其他格式导出 | F1 §2.2-7；导出只支持 Markdown 与整库 JSON 备份 |
| 移动端与平板适配 | F1 §2.2-8；不承诺 375/768 视口可用性 |
| 旧 F5 数据迁移与旧代码复用 | F1 §2.2-9；仍归 M4，不读写 `data/projects/*.json` |
| 回收站批量彻底删除与定时自动清理 | F1 §2.2-10；只提供逐条恢复与逐条彻底删除 |

### 1.3 核心技术决策

| 决策 | 方案 | 理由 |
| --- | --- | --- |
| 双层存储模型 | 单表 `knowledge_entries` 以 `library_scope` 区分 `global` / `work`；作品引用单独存 `knowledge_work_refs` | 全局与副本共用一套条目结构；引用不复制内容，避免多副本漂移 |
| 作品引用只读 | 引用行只存指针 + 有界快照；读取时 JOIN 全局条目取最新内容 | D14 要求引用随全局更新；直接改引用一律 409 |
| 另存副本 | 复制为 `library_scope='work'` 的新条目，`origin='ref_copy'` | D15 要求副本与全局互不影响；复制后走普通条目编辑链路 |
| 收藏与置顶 | 条目行存 `favorite/pinned`；引用行单独存 `favorite/pinned` | D11 要求收藏置顶只在当前库生效；同一全局条目在全局库与作品库可有不同标记 |
| 录入与结构化 | 粘贴同步建条目；上传异步解析；结构化统一走 `knowledge_jobs` 队列 + SSE，原文先行入库 | D03/D07 要求失败不丢内容；大文件不阻塞界面 |
| 结构化执行 | 独立 BullMQ 队列 `knowledge-jobs`，独立 `knowledge_job_events` 事件表 | 全局库无 `work_id`，复用 `ai_tasks` 需改核心表与鉴权；独立队列影响面最小 |
| 类型识别 | 纯函数启发式识别文章/论文/小说/灵感，无法判断默认文章；设定集只由作者手动指定 | 识别可解释、可测试；F1 §4.1 已确认「不确定按文章并提示改判」 |
| 小说大纲 | `structured.outline` 四维 JSON + `outline_status`；失败保留拆文结果 | D17/D18 要求可编辑、可重试、失败不丢拆文 |
| 大纲质量 | 结构化/大纲 Provider 同时提供 Mock 与真实文本模型实现；验收环境抽样 10 条 ≥8 条作为上线门禁 | D19 要求可量化；CI 不依赖外部模型，验收环境验证真实质量 |
| 相似度检索 | `pgvector` 扩展 + `vector(1024)` 余弦距离；Mock 嵌入 Provider 保证测试确定性 | 用户 2026-11-21 确认采用向量方案；2000 条规模无需 ANN 索引 |
| 关键词检索 | `pg_trgm` GIN 索引 + `search_text` 聚合列 | 中文无分词依赖；`ILIKE` 走 trigram 索引，2000 条稳定在毫秒级 |
| 备份格式 | 版本化 JSON（`schema_version=1`）→ gzip，扩展名 `.sfkb.json.gz` | 用户确认；可无损表达条目、结构化、标签、关联与收藏，版本可演进 |
| 导入导出 | Markdown + YAML front matter；批量导出打包 zip | 人类可读、可外部编辑；批量与分类导出满足 D23 |
| 异步任务边界 | 解析、结构化、大纲、导入、导出、备份恢复均为作业；CRUD 与检索为同步请求 | 写操作可幂等重试；读操作保持 1 秒预算 |
| 上传文件 | multipart 内存接收，单文件 ≤20 MB；解析后只存文本，不保存原始二进制 | 满足 F1 体积上限；避免二进制存储与备份膨胀 |
| 并发控制 | 条目编辑使用 `expected_version` 乐观锁；收藏/置顶与引用关系以唯一键幂等 | 与 M3c-2 语义一致；多人协同不在本期 |
| 删除语义 | 软删除进回收站；彻底删除需二次确认，引用行保留快照并标记失效 | D20~D22；不提供自动清理与批量清理 |
| 检索执行位置 | 服务端检索 + 分页（默认 50 条），前端只在当前页做轻量排序修正 | 2000 条规模下服务端索引检索更稳地满足 1 秒指标，避免一次拉全量 |
| 时间检索 | `time_field` 支持 `created_at` / `updated_at`，半开区间，默认创建时间 | 兼顾收集时间与最近编辑；两种字段各有索引覆盖 |
| 前端入口 | 原生 `<dialog>` 实现左侧浮层抽屉，`showModal` 打开，不改变三栏宽度 | D01/D27；正文编辑器保持挂载，关闭后焦点归还原位 |

## 二、数据模型设计

### 2.1 迁移清单

### 2.2 表定义

#### 2.2.1 knowledge_entries（素材条目）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `owner_id` | uuid | NOT NULL，FK `authors(id)` ON DELETE CASCADE |
| `library_scope` | varchar(8) | NOT NULL，CHECK `global/work` |
| `work_id` | uuid | NULL，FK `works(id)` ON DELETE CASCADE |
| `entry_type` | varchar(16) | NOT NULL，CHECK `article/paper/novel/inspiration/setting` |

> ⚠️ **本节已变更**（见 [06-设计更新](./06-设计更新-11类扩展与判定重构.md) §6.3）：`entry_type` 扩为 `varchar(32)` + 11 值 CHECK；新增 `type_source varchar(16) NOT NULL DEFAULT 'manual'`（`auto/manual/user_override`）与 `type_confidence numeric(3,2)` 两列。存量行 `type_source` 由默认值兜底，判定来源不可追溯，为已知信息损失。
| `title` | varchar(200) | NOT NULL |
| `title_key` | varchar(200) | NOT NULL（归一化标题，用于导入判重与展示排序） |
| `original_text` | text | NOT NULL（原文，唯一事实来源） |
| `content_hash` | char(64) | NOT NULL（归一化原文 SHA-256） |
| `search_text` | text | NOT NULL DEFAULT `''`（标题 + 标签 + 结构化摘要 + 原文前 2000 字） |
| `structured` | jsonb | NULL（按类型受控结构，见 §3.5） |
| `structure_status` | varchar(16) | NOT NULL DEFAULT `'pending'`，CHECK `pending/structuring/ready/failed` |
| `structure_error` | jsonb | NULL |
| `outline_status` | varchar(16) | NULL，CHECK `pending/ready/failed`（仅小说） |
| `outline` | jsonb | NULL（四维大纲，见 §3.5） |
| `favorite` | boolean | NOT NULL DEFAULT false |
| `pinned` | boolean | NOT NULL DEFAULT false |
| `pinned_at` | timestamptz | NULL |
| `origin` | varchar(16) | NOT NULL DEFAULT `'manual'`，CHECK `manual/upload/markdown_import/backup/ref_copy` |
| `source_entry_id` | uuid | NULL（副本来源，弱引用，不建 FK） |
| `version` | integer | NOT NULL DEFAULT 1（编辑乐观锁） |
| `deleted_at` / `deleted_by` | timestamptz / uuid | NULL（软删除） |
| `created_at` / `updated_at` | timestamptz | NOT NULL DEFAULT now() |

约束与索引：

- `CHECK ((library_scope = 'global' AND work_id IS NULL) OR (library_scope = 'work' AND work_id IS NOT NULL))`；
- 全局库按作者唯一内容：`CREATE UNIQUE INDEX uq_knowledge_global_hash ON knowledge_entries (owner_id, content_hash) WHERE library_scope = 'global' AND deleted_at IS NULL`；
- 作品库按作品唯一内容：`CREATE UNIQUE INDEX uq_knowledge_work_hash ON knowledge_entries (work_id, content_hash) WHERE library_scope = 'work' AND deleted_at IS NULL`；
- `idx_knowledge_global_list (owner_id, updated_at DESC) WHERE library_scope='global' AND deleted_at IS NULL`；
- `idx_knowledge_work_list (work_id, updated_at DESC) WHERE library_scope='work' AND deleted_at IS NULL`；
- `idx_knowledge_global_type (owner_id, entry_type, updated_at DESC) WHERE library_scope='global' AND deleted_at IS NULL`；
- `idx_knowledge_work_type (work_id, entry_type, updated_at DESC) WHERE library_scope='work' AND deleted_at IS NULL`；
- `idx_knowledge_global_created (owner_id, created_at DESC) WHERE library_scope='global' AND deleted_at IS NULL`；
- `idx_knowledge_work_created (work_id, created_at DESC) WHERE library_scope='work' AND deleted_at IS NULL`；
- `idx_knowledge_trash (owner_id, deleted_at DESC) WHERE deleted_at IS NOT NULL`；
- `CREATE INDEX idx_knowledge_search_trgm ON knowledge_entries USING gin (search_text gin_trgm_ops)`。

> `content_hash` 由服务端计算：原文做 NFKC → 统一换行 → 去首尾空白后取 SHA-256。重复提交返回 409 `KNOWLEDGE_ENTRY_DUPLICATE` 与既有条目 id，不静默新增。
>
> `search_text` 在创建、标题变更、结构化完成、标签变更、原文编辑后重算；只取原文前 2000 字，避免大文本进入索引。

#### 2.2.2 knowledge_work_refs（作品引用）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `owner_id` | uuid | NOT NULL，FK `authors(id)` ON DELETE CASCADE |
| `work_id` | uuid | NOT NULL，FK `works(id)` ON DELETE CASCADE |
| `entry_id` | uuid | NULL，FK `knowledge_entries(id)` ON DELETE SET NULL |
| `snapshot_title` | varchar(200) | NOT NULL |
| `snapshot_type` | varchar(16) | NOT NULL |
| `snapshot_tags` | jsonb | NOT NULL DEFAULT `'[]'`（只存名称数组） |
| `snapshot_excerpt` | varchar(2000) | NOT NULL DEFAULT `''` |
| `snapshot_structured` | jsonb | NULL（有界结构化摘要，≤ 16 KB） |
| `favorite` | boolean | NOT NULL DEFAULT false |
| `pinned` | boolean | NOT NULL DEFAULT false |
| `pinned_at` | timestamptz | NULL |
| `added_by` | uuid | NOT NULL |
| `created_at` / `updated_at` | timestamptz | NOT NULL DEFAULT now() |

约束与索引：

- `CREATE UNIQUE INDEX uq_knowledge_ref ON knowledge_work_refs (work_id, entry_id) WHERE entry_id IS NOT NULL`（同一作品同一全局条目仅一条引用）；
- `idx_knowledge_refs_work (work_id, updated_at DESC)`；
- `idx_knowledge_refs_entry (entry_id)`（全局条目删除前统计引用作品）。

**引用状态（读取期派生，不落库）**：

```text
active          : entry_id IS NOT NULL AND 全局条目 deleted_at IS NULL
source_deleted  : entry_id IS NOT NULL AND 全局条目 deleted_at IS NOT NULL
invalid         : entry_id IS NULL（全局条目已彻底删除）
```

> 快照只作失效兜底与删除提示，不作为读路径数据源。全局条目软删除时，在同一事务内刷新其全部引用的快照；正常读取始终 JOIN 全局条目，保证 D14「引用随全局更新」。

### 2.3 双层库与引用语义

| 场景 | 数据行为 |
| --- | --- |
| 在全局库录入 | 新建 `library_scope='global'`、`work_id=NULL` 的条目 |
| 在作品库直接录入 | 新建 `library_scope='work'`、`work_id=当前作品` 的条目（独立条目） |
| 从全局库引用到作品 | 仅插入 `knowledge_work_refs`，不复制条目 |
| 引用随全局更新 | 作品库列表与详情读取时 JOIN 全局条目，展示最新标题、类型、结构化与标签 |
| 直接编辑引用 | 拒绝，409 `KNOWLEDGE_REF_READONLY`，提示另存副本 |
| 另存副本 | 复制全局条目内容与结构化，创建 `origin='ref_copy'` 的作品条目；可同时删除原引用或保留 |
| 移除引用 | 删除 `knowledge_work_refs` 行，不删除全局条目 |
| 删除被引用的全局条目 | 软删除；返回引用作品列表；引用显示「来源已删除，可从回收站恢复」 |
| 彻底删除全局条目 | `entry_id` 置 NULL（FK SET NULL）；引用显示「来源已失效」，保留快照 |
| 作品之间隔离 | 所有作品库查询强制 `work_id`，副本与引用不跨作品可见 |

> 作品库的「条目」由两部分组成：作品自有条目（含副本）与全局引用。列表接口返回统一 `kind: 'entry' | 'reference'` 视图模型，`D02` 的列表、计数与检索均按此模型计算。

### 2.4 状态机与派生状态

**条目结构化状态**：

```text
pending → structuring → ready
                     ↘ failed
failed / ready → structuring（重试或改判类型）
```

- `pending`：条目已创建（粘贴）或占位，尚未开始结构化；
- `structuring`：作业执行中，界面显示「整理中」；
- `ready`：结构化完成，可编辑；
- `failed`：解析或结构化失败，保留原文，界面显示「待整理」与重试入口；
- 同一 `entry_id` 同时最多一个 `structure` 作业运行。

**小说大纲状态**：`outline_status = pending → ready | failed`；`ready` 下可编辑，`failed` 保留拆文结果并可重试。

**作业状态**：`queued → running → succeeded | failed | cancelled`；进程重启时把遗留 `running` 置 `failed`（可重试），不假装完成。

**引用状态**：`active / source_deleted / invalid` 读取期派生，不落库、不写状态。

**软删除状态**：`active → deleted（deleted_at 非空）→ active（恢复）| purged（物理删除，终态）`。

### 2.5 与既有域的边界

| 域 | 边界 |
| --- | --- |
| `works` | 作品库条目与引用通过 `work_id` 归属；作品删除级联删除其条目、引用、标签、关联与作业 |

### 2.6 事务边界与级联策略

| 操作 | 事务范围 |
| --- | --- |
| 创建条目（粘贴） | 条目 + 标签关联 + 作业（structure）入队记录同事务；入队提交后执行 |
| 上传解析成功建条目 | 作业状态推进 + 条目 + 标签 + 后续 structure 作业同事务 |
| 结构化完成 | 条目的 `structured/outline/status` + `search_text` + 向量 upsert + 作业成功 + 事件同事务；向量写入失败不回滚结构化，作业标 `failed` 并可重试 |
| 编辑条目 | 条目 + 标签差异 + `search_text` + 向量 `source_hash` 标记同事务；向量重算异步 |
| 软删除全局条目 | 条目 `deleted_at` + 全部引用快照刷新同事务 |
| 彻底删除 | 条目物理删除（级联标签/关联/向量）+ 引用 `entry_id` SET NULL + 审计同事务 |
| 备份恢复 | 按条分批事务；每批 ≤ 50 条；失败批次回滚并计入统计，不整体回滚已成功批次 |
| 删除作品 | FK `ON DELETE CASCADE` 清理作品库全部数据；全局库不受影响 |

### 2.7 为什么使用独立作业队列

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 独立 `knowledge-jobs` 队列 + 独立事件表（选定） | 全局库无 `work_id` 也可运行；不动 `ai_tasks` 表与鉴权；任务类型与知识库语义一致 | 新增一套队列/Worker/SSE，代码量增加 |
| B. 扩展 `ai_tasks` 为 `scope='knowledge'` 且允许 `work_id` 为空 | 复用现有 Worker 与 SSE | 需改核心表、`assertOwnedTask`、SSE 鉴权与 scope CHECK；回归面覆盖 M3a/M3b/M3c-1/M3c-2 |
| C. 同步请求内执行 | 无队列 | 20 MB 文件与长文阻塞请求，无法满足「界面不阻塞」与失败重试 |

**决策 A**。代价通过复用 `ai-task.queue.ts` / `ai-task.sse.ts` 的代码结构与 Redis 配置来控制；`ai_tasks` 与既有链路零改动。

> ⚠️ **本节已变更**（见 [06-设计更新](./06-设计更新-11类扩展与判定重构.md) §2–§4）：类型扩至 11 类；`article`（`sections→paragraphs`、`tags→tag_list`、新增必填 `summary`）、`paper`（五要素改名、删 `keywords`）、`novel`（`plot_summary→plot_lines[]`、`worldview→world_setting`、`narrative_style` 变数组、移除 `characters[].role`）、`inspiration`（`completion→enriched_text`、`matched_entry_ids→related_ids`、删 `independent`）四类字段**就地改名，不做数据迁移**，存量遇旧结构回退原文展示。新增 6 类（`character` / `plot_template` / `reference_work` / `technique` / `reader_feedback` / `timeline`）完整 schema 见 06 §3.3。`outline` 仍为独立列，不并入 `structured`（06 §4.1）。

| 类型 | 结构字段 | 说明 |

所有结构字段 `.strict()`；未知字段拒绝；文本长度上限在契约与前端计数器保持一致（标题 ≤200、分段内容 ≤20000、观点/标签 ≤200）。

### 3.6 Markdown 导入导出格式

- front matter 使用 YAML 子集（字符串、字符串数组、布尔、ISO 时间）；`type` 必须是五类之一。

- `refs` 仅作品库备份携带；恢复时按 `entry_content_hash` 在当前全局库中尝试重新关联，找不到则恢复为 `invalid` 引用（保留快照）。
- 文件为 UTF-8 JSON 经 gzip 压缩，扩展名 `.sfkb.json.gz`；解压后上限 500 MB，条目 ≤2000，标签 ≤1000，关联 ≤5000。
- 备份只含知识库数据，不含正文、角色、剧情与账号信息。

## 五、核心逻辑与算法

### 5.1 归属校验与读取模型

- 统一 `assertOwnedLibrary(manager, authorId, scope, workId?)`：`global` 校验条目 `owner_id`；`work` 校验 `works.author_id` 且条目 `work_id` 一致。
- 列表只返回摘要（不含原文全文）；详情才返回 `original_text`，避免 20 MB 文本进入列表响应。
- 作品库列表使用 CTE 合并「作品自有条目」与「全局引用条目」，统一排序字段为 `pinned DESC, COALESCE(pinned_at, updated_at) DESC, id`。
- 引用条目读取时 JOIN `knowledge_entries`；若 `entry_id IS NULL` 或全局条目 `deleted_at` 非空，按 §2.2.2 派生状态返回，不抛 404。

### 5.2 类型识别（纯函数）

> ⚠️ **本节已变更**（见 [06-设计更新](./06-设计更新-11类扩展与判定重构.md) §5）：改为「LLM Few-shot 判定 + 规则兜底」。LLM 输出 `{type, confidence, reason}`，按 `≥0.75` 直接采用（`auto`）/ `0.5–0.75` 弹确认框 / `<0.5` 强制手选 三段分流；无凭据或调用失败时回退下表纯函数规则，`high/medium/low` 映射为 `0.9/0.6/0.3` 走同一阈值分流。`setting` 放开为可自动判定（LLM 路径），规则路径下仍不会自动识别。新增 `type_source`（`auto/manual/user_override`）与 `type_confidence` 两列。

| 信号 | 判定倾向 |
| --- | --- |
| 文件名含 `论文`/`paper`/`abstract`，或正文含「摘要」「关键词」「参考文献」≥2 个 | 论文 |
| 含「第 X 章」「Chapter X」≥2 处，或对话引号比例高且长度 >5000 字 | 小说 |
| 长度 <800 字且含「灵感」「想法」「突然想到」等标记，或仅一段短文本 | 灵感 |
| 其他（默认） | 文章 |

- 设定集永不自动识别，只能由作者在录入时或详情中手动指定。
- 识别结果写入条目，作者可在详情中改判；改判调用 `restructure`，成功前保留旧结构化结果并显示「重新整理中」。
- 识别不确定时按文章处理，并在创建响应中返回 `warnings: ['KNOWLEDGE_TYPE_UNCERTAIN']`，前端提示可改判。

### 5.3 结构化管线（异步 + 分块 + 合并）

1. **原文先行**：粘贴创建条目时写入 `original_text` 与 `content_hash`，`structure_status='pending'`；上传解析成功后同样先建条目再结构化。
2. **分块**：按空行/段落切分，单块 ≤6000 字符，相邻块重叠 200 字符；小说按章节标题优先切分。
3. **逐块结构化**：调用 `KnowledgeStructureProvider`（端口 + Mock 实现 + 真实文本模型实现），每块产出该类型的局部结构；每完成一块写一次 `progress` 事件（`processed/total/percent`）。
4. **合并**：分段按顺序拼接并去重标题；核心观点按文本归一化去重；标签取并集并限制 ≤20；论文五要素按块合并取信息量最大者；小说角色按名称合并。
5. **大纲**：小说类型在结构化后调用 `KnowledgeOutlineService`，提取四维大纲；失败只把 `outline_status='failed'`，不影响 `structured`。
6. **向量**：结构化完成后计算嵌入并 upsert `knowledge_entry_embeddings`；嵌入失败不回滚结构化，作业 `failed`，作者可重试。
7. **落库**：`structured/outline/structure_status='ready'/search_text` 与作业成功、事件在同一事务；失败则 `structure_status='failed'` + `structure_error`，保留原文。
8. **重试**：`restructure` 复用同一管线；成功后覆盖结构化字段，不新增条目（D07）。

> 大篇幅文本分块处理、进度可见、界面不阻塞（F1 §4.1）；单次作业最多处理 8,000,000 字符，超出返回 `KNOWLEDGE_TEXT_TOO_LARGE`，在解析阶段直接失败并保留原因。

### 5.4 小说大纲提取

- **章节结构**：按「第 X 章 / Chapter X / 卷一」等标题切分；无章节结构时 `outline_status='failed'`，`error.reason='no_chapters'`，前端提示手动补充（D18）。
- **情节节点**：以章节摘要 + 关键事件句生成，记录 `chapter_index`；不写剧情树。
- **人物关系**：从角色名共现与显式关系词（师/父/敌/盟等）提取，输出 `{source,target,relation}`；无法确定关系时只记录共现，`relation='同场'`。
- **故事线**：按章节主题聚类为 1~5 条线，记录章节索引。
- 大纲可编辑保存，保存走条目 PATCH 的 `outline` 字段与 `expected_version`；本期不建树、不联动角色版图。

### 5.5 向量嵌入与灵感关联

**嵌入生成**：

- `KnowledgeEmbeddingProvider` 端口，方法 `embed(texts: string[]): Promise<number[][]>`；默认 `MockEmbeddingProvider` 输出 1024 维、L2 归一化的确定性向量（字符 bigram 哈希），保证单测与 E2E 可复现。
- 真实 Provider 接入时只替换实现，不改表与接口；模型标识写入 `model`，维度固定 1024。
- 重算触发：条目创建、结构化完成、标题变更、标签变更、原文编辑、副本创建；以 `source_hash` 判断是否需要重算，未变化则跳过。

**灵感自动关联**（最多 3 条）：

```sql
SELECT e.id, 1 - (emb.embedding <=> $1) AS score
FROM knowledge_entry_embeddings emb
JOIN knowledge_entries e ON e.id = emb.entry_id
WHERE emb.owner_id = $2
  AND e.library_scope = $3
  AND ($4::uuid IS NULL OR e.work_id = $4)
  AND e.deleted_at IS NULL
  AND e.id <> $5
ORDER BY emb.embedding <=> $1
LIMIT 10;
```

1. 先按同库、未删除、排除自身取前 10 条候选；
2. 过滤 `score < 0.35` 的弱相关项，按分数降序取前 3；
3. 在 `knowledge_entry_links` 写入 `kind='inspiration_auto'`，`score` 保留 4 位小数；重复执行先删除该灵感的旧自动关联，再写新关联，手动关联不受影响；
4. 调用结构化 Provider 基于命中条目生成 `structured.completion`；无命中时 `independent=true`、`completion=''`，前端提示存为独立灵感（D12）；
5. 作者可删除自动关联、补充手动关联；删除后不再自动恢复，直到下一次 `restructure`。

> 2000 条规模下顺序扫描余弦距离在毫秒级；不建 ANN 索引。相似度阈值与候选数写入服务常量，便于后续按真实模型调参。

### 5.6 四维检索

| 维度 | 实现 |
| --- | --- |
| 关键词 | `search_text ILIKE '%kw%'`，走 `gin_trgm_ops`；同时匹配标题与标签名称 |
| 类型 | `entry_type = ANY($types)`；引用条目按全局条目类型过滤 |
| 标签 | `EXISTS (SELECT 1 FROM knowledge_entry_tags ... tag_id = ANY($tagIds))`；作品库同时匹配引用条目的全局标签 |
| 时间 | `time_field` 取 `created_at` 或 `updated_at`；`时间字段 >= time_from AND 时间字段 < time_to`（半开区间，ISO 时间） |
| 收藏/置顶 | 条目使用自身列，引用使用 `knowledge_work_refs` 列 |
| 回收站 | `deleted=true` 时只查 `deleted_at IS NOT NULL`，并强制同库 |

- 排序：`pinned DESC, COALESCE(pinned_at, updated_at) DESC, id ASC`；
- 时间字段：`time_field=created_at` 走 `idx_knowledge_*_created`，`time_field=updated_at` 走列表索引；默认 `created_at`，前端提供近 7 天/30 天/自定义；
- 分页：游标编码 `updated_at + id`，避免深分页 `OFFSET`；
- 计数：`summary` 与列表 `total` 使用同一 WHERE 条件，不把回收站计入常规计数；
- 空结果返回 `{ items: [], total: 0, next_cursor: null }`，前端展示空状态与放宽提示（D09）。

### 5.7 引用、副本与失效

| 操作 | 逻辑 |
| --- | --- |
| 建立引用 | 校验全局条目属于当前作者且未删除；`ON CONFLICT DO NOTHING` 后返回既有引用 |
| 读取引用 | JOIN 全局条目；派生 `active/source_deleted/invalid`；`source_deleted` 显示「来源已删除，可从回收站恢复」 |
| 直接编辑引用 | 条目 PATCH 前检查是否存在引用关系；引用 id 一律 409 `KNOWLEDGE_REF_READONLY` |
| 另存副本 | 事务内复制原文、结构化、大纲、标签（作品库按名称查找或新建）；`source_entry_id` 指向全局条目；`keep_ref` 决定是否保留引用 |
| 移除引用 | 删除引用行；若有收藏/置顶一并丢弃；不影响全局条目 |
| 软删除全局条目 | 条目 `deleted_at` + 刷新全部引用快照（标题、类型、标签、≤2000 字摘录、≤16 KB 结构化摘要） |
| 彻底删除全局条目 | 物理删除条目；FK `ON DELETE SET NULL` 使引用 `entry_id` 为空；引用保留快照，状态变为 `invalid` |

> **失效引用的「另存已有内容」**：彻底删除前，删除确认弹层展示引用作品并允许逐条「另存副本」（内容仍完整）；彻底删除后，失效引用只能「移除」或「按快照另存为摘录条目」（截断内容，标题追加「（失效引用摘录）」）。该口径已于 2026-11-21 确认（见 §12.4 P1）。
>
> **引用只读的服务端强制**：作品库中的引用条目对作者呈现为只读，但不能只靠前端隐藏按钮。条目 PATCH、flags、DELETE 在收到 `context_work_id` 时，先查 `knowledge_work_refs (work_id, entry_id)`：存在引用则 PATCH 与 flags 返回 409 `KNOWLEDGE_REF_READONLY`，DELETE 返回 409 `KNOWLEDGE_REF_SOURCE_DELETE` 并提示「移除引用」或「前往全局库删除源条目」。从全局库上下文（不带 `context_work_id`）删除源条目仍允许，并按 §5.7 处理引用状态。

### 5.8 回收站与彻底删除

- 软删除只对条目生效；引用不是条目，移除引用不走回收站。
- 恢复条目：`deleted_at=NULL`，标签、关联、收藏、置顶原样保留；若内容与库内现有条目冲突（恢复期间新建了同内容条目），返回 409 `KNOWLEDGE_ENTRY_DUPLICATE` 并提示先处理冲突。
- 彻底删除：必须 `confirm=true`；同事务物理删除条目，级联删除标签关联、跨条目关联、向量与相关作业；引用 `entry_id` 置 NULL；写审计 `knowledge_entry_purged`。
- 不提供批量彻底删除、不设定时清理；回收站条目不计入常规列表与检索。

### 5.9 导入导出与备份恢复

**Markdown 导出**：按 §3.6 生成；单条直接返回流；多条用 `archiver` 流式打包 zip，文件名 `knowledge-<scope>-<yyyyMMddHHmm>.zip`。

**Markdown 导入**：

1. 逐文件读取、去 BOM、编码回退，解析 front matter；
2. 以 `title_key + 原文哈希` 计算预览统计与冲突；
3. 同名同内容 → 重复；同名不同内容 → 待确认；不同名 → 新增；
4. 提交按文件级 `overwrite/rename/skip` 执行；`rename` 标题追加「(导入 N)」；逐文件返回成功/失败/跳过；
5. 导入条目 `origin='markdown_import'`，默认触发结构化作业（与粘贴一致）。

**整库备份**：

1. 导出：按库读取条目、标签、关联、收藏置顶；作品库额外读取引用；写 JSON → gzip → 产物文件；作业记录统计与体积；
2. 预览：校验版本/类型/体积/数量；按 `title_key + content_hash` 分类；返回冲突列表与 `preview_id`；
3. 提交：按 `policy` 与逐条 `resolutions` 分批写入（每批 ≤50），失败批次回滚并累计统计；标签按名称复用或新建；关联仅在两端都成功写入时恢复；作品引用按 `entry_content_hash` 尝试重连全局条目；
4. 恢复完成后刷新受影响条目的 `search_text` 与向量（异步补齐，不阻塞统计返回）。

### 5.10 审计清单

| 事件 | `action` | `detail` 要点 |
| --- | --- | --- |
| 条目创建 | `knowledge_entry_created` | scope、type、origin、字符数；不含原文 |
| 条目编辑 | `knowledge_entry_updated` | 变更字段名、版本号；不含原文与结构化全文 |
| 结构化完成/失败 | `knowledge_structure_succeeded/failed` | entry_id、耗时、错误码、分块数 |
| 删除/恢复/彻底删除 | `knowledge_entry_deleted/restored/purged` | scope、引用作品数 |
| 引用/副本 | `knowledge_ref_added/removed`、`knowledge_copy_created` | 作品 id、全局条目 id |
| 导入/导出/备份/恢复 | `knowledge_imported/exported/backup_exported/backup_restored` | 作业 id、策略、成功/失败/跳过统计 |
| 标签变更 | `knowledge_tag_created/renamed/deleted` | 标签 id、影响条目数 |

`detail` 不含正文全文、向量值、模型密钥；错误信息不回显 SQL/堆栈。

### 6.3 状态管理

- `KnowledgeStoreProvider` 持有 `scope/workId/keyword/types/tagIds/timeField/timeRange/favorite/pinned/items/nextCursor/selectedEntry/jobs`；
- 进入抽屉或切换库时才加载，`enabled` 标志避免影响正文首屏；
- 检索条件变化后 250 ms 防抖，取消上一次未完成请求（`AbortController`），只渲染最新响应；
- 写操作先调用 API，成功后局部更新列表与详情；409 版本冲突提示「条目已被更新」并提供「刷新并重试」，不静默覆盖；
- 上传/结构化/导入/导出/备份恢复通过 `GET /knowledge/jobs/:jobId/events` 订阅 SSE，断线按 `event_seq` 重放；作业失败显示原因与重试。

### 6.4 与正文编辑器并存

- 抽屉是浮层，不改变三栏布局宽度、不触碰正文滚动容器；
- 打开/关闭抽屉、切换素材库、执行检索都不调用保存控制器，不重置编辑器状态；

### 6.5 检索与列表性能

| 手段 | 说明 |
| --- | --- |
| 服务端检索 | 四维条件 + 游标分页，默认 50 条；不在前端拉全量 |

## 八、幂等与一致性

### 8.1 幂等键与重复提交

| 操作 | 幂等机制 | 重复调用结果 |
| --- | --- | --- |
| 条目创建 | 库内 `content_hash` 唯一索引 | 409 `KNOWLEDGE_ENTRY_DUPLICATE` + 既有 id |
| 条目编辑 | `expected_version` 乐观锁 | 版本一致才写；不一致 409 |
| 收藏/置顶 | 覆盖写布尔值，天然幂等 | 200 当前状态 |
| 引用创建 | `UNIQUE (work_id, entry_id)` + `ON CONFLICT DO NOTHING` | 200 + 既有引用 |
| 引用移除 | 状态判断 | 已不存在 200 当前状态 |
| 标签创建 | 同库 `name_key` 唯一 | 409 + 既有标签 |
| 标签删除 | 级联删除关联 | 已不存在 404 |
| 关联创建 | `UNIQUE (source,target,kind)` | 409 + 既有 id |
| 关联删除 | 状态判断 | 已不存在 200 当前状态 |
| 结构化/导入/导出/备份作业 | 作业 `idempotency_key` 唯一 + 同条目唯一运行索引 | 同键返回既有作业；运行中 409 `KNOWLEDGE_JOB_RUNNING` |
| 恢复条目 | `deleted_at` 状态机 | 已恢复 200 `{ changed: false }` |
| 彻底删除 | 物理删除 + 事务 | 已删除 404；引用 SET NULL 只执行一次 |
| 备份恢复提交 | 作业幂等键 + `preview_id` 绑定 | 重放返回首次统计，不重复写入 |

### 8.2 并发编辑冲突

- 条目编辑：`expected_version` 与 `knowledge_entries.version` 不等 → 409 `KNOWLEDGE_VERSION_CONFLICT`（`details.current_version`）。
- 结构化回填与作者编辑并发：回填事务先锁条目行；若作者在回填前已改过 `structured`（`version` 变化），回填仍以作业结果覆盖，但审计记录 `overwritten_by_structure=true`；前端提示「整理结果已更新」。
- 标签重命名与条目编辑并发：同一事务内更新标签与受影响条目 `search_text`；批量 ≤2000 条，超时则分批并在作业中完成。
- 引用与全局删除并发：全局软删除先锁条目，再锁其引用；引用创建先校验条目未删除；冲突时以先到者为准，后到者返回 409 或 200 既有状态。
- 上传/结构化与回收站：作业开始前检查条目未删除；条目在作业中被删除时，作业结束不复活条目，标记 `cancelled`。

### 8.3 数据一致性不变量

1. 全局条目 `work_id` 必为 NULL；作品条目 `work_id` 必非 NULL。
2. 同一库内未删除条目的 `content_hash` 唯一；不同库可存在相同内容。
3. 引用 `entry_id` 非空时必指向 `library_scope='global'` 的条目。
4. 引用 `entry_id` 为空时，快照必须完整（标题、类型、摘录）。
5. 关联两端必须同库且不同条目；自动关联最多 3 条/灵感，手动关联最多 20 条/端。
6. 标签与条目同库；删除标签不删除条目。
7. `structure_status='ready'` 时 `structured` 非空；`'failed'` 时 `structure_error` 非空。
8. `outline_status='ready'` 时 `outline` 四维字段齐全。
9. 向量行与条目一一对应；`source_hash` 变化必须重算。
10. 软删除条目不出现在常规列表与检索；恢复后重新出现。
11. 彻底删除后不存在指向该条目的关联；引用 `entry_id` 为 NULL。
12. 作业事件 `event_seq` 单调递增且唯一；SSE 重放不重复。

## 十一、技术选型与权衡

### 11.1 结构化执行方式

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 异步作业 + SSE（选定） | 20 MB 文件与长文不阻塞；进度可见；失败可重试；原文先行不丢内容 | 新增队列/Worker/SSE；前端需处理作业状态 |
| B. 同步请求内完成 | 实现最简单 | 长文/大文件占用请求，超时与重试困难，违背「界面不阻塞」 |
| C. 小文本同步 + 大文本异步 | 短文本即时 | 两套路径、两套错误处理与测试，状态一致性成本高 |

**决策 A**（用户 2026-11-21 确认）。代价通过独立队列与统一作业契约控制。

### 11.2 相似度检索方案

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 向量嵌入 + pgvector（选定） | 语义相似度好；2000 条顺序扫描毫秒级；可平滑接入真实嵌入模型 | 需切换 Postgres 镜像、创建扩展、维护向量表与重算逻辑；模型维度需固定 |
| B. `pg_trgm` 词面相似度 | 无模型依赖、可解释、实现最轻 | 只能匹配字面相近，改写/近义表达召回差 |
| C. LLM 逐条判断 | 语义最强 | 成本与延迟不可控，2000 条无法在录入时实时完成 |

**决策 A**（用户 2026-11-21 确认）。关键词检索仍使用 `pg_trgm`；向量只用于灵感自动关联，两者并存，互不替代。

**基础设施影响**：`postgres:16` 不含 pgvector，必须切换为 `pgvector/pgvector:pg16`；旧数据卷可直接挂载，扩展由迁移创建。实施时同步 CI 与部署手册，并在 API 启动时检查 `vector` 扩展，缺失则拒绝启动并输出明确错误。

### 11.3 备份格式

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 版本化 JSON + gzip（选定） | 无损表达条目/结构化/标签/关联/收藏；版本可演进；校验清晰 | 非技术作者不可直接编辑；文件较大 |
| B. Markdown ZIP + 清单 | 人类可读、可外部编辑 | 关联、收藏与结构化字段表达受限，恢复语义丢失 |
| C. CSV/SQL 多文件 | 便于数据工具处理 | 与业务模型耦合，引用/约束难保证，恢复风险高 |

**决策 A**（用户 2026-11-21 确认）。Markdown 导出仍保留，用于人类阅读与单条迁移；两者职责分离。

### 11.4 文件解析依赖

| 依赖 | 用途 | 说明 |
| --- | --- | --- |
| `multer`（`@nestjs/platform-express` FileInterceptor） | multipart 接收 | 内存存储，`limits.fileSize=20 MB`；不落原始文件 |
| `mammoth` | `.docx` → 纯文本 | 只取文本，不保留样式；解析失败抛业务错误 |
| `unpdf` | `.pdf` → 纯文本 | 纯 JS、无原生依赖；扫描件无文本层时返回空并提示 |
| `iconv-lite` | `.txt/.md` 编码回退 | UTF-8 优先，失败尝试 GB18030；仍失败逐文件报错 |
| `yaml` | Markdown front matter | 只解析受控子集，拒绝复杂锚点/标签 |
| `archiver` | 批量导出 zip | 流式打包，避免一次性占用内存 |
| `gzip`（Node `zlib`） | 备份压缩 | 不引入额外依赖 |

> 不引入 OCR、PDF 渲染或图片处理依赖（F1 §2.2-1）。

### 11.5 其他取舍

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 全局库与作品库：单表 vs 双表 | 单表 + `library_scope` | 查询需带 scope 条件；换来统一结构与迁移成本低 |
| 引用：复制 vs 指针 | 指针 + 有界快照 | 读取需 JOIN；换来 D14 同步与 D15 副本语义清晰 |
| 收藏置顶：条目列 vs 独立表 | 条目列 + 引用列 | 两处维护；换来「按库生效」与查询简单 |
| 检索：前端全量 vs 服务端分页 | 服务端分页 | 每次请求有网络开销；换来 2000 条稳定 1 秒与索引可控 |
| 向量索引：无 vs HNSW | 本期无索引 | 超过 10000 条需评估；换来迁移简单、2000 条性能足够 |
| 备份恢复：整体替换 vs 合并 | 合并（按策略） | 冲突处理复杂；换来不丢现有数据，符合 F1 §3.9-5 |
| 导入执行：同步 vs 异步 | 预览同步 + 提交异步 | 多一层作业；换来大量文件不阻塞、统计可追踪 |

### 11.6 大纲质量验收方式

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 接入真实文本模型并作为上线门禁（选定） | 唯一能验证 D19「10 条 ≥8 条可用」的方案；质量可量化 | 需模型凭据与调用预算；验收环境增加外部依赖 |
| B. 仅 Mock/规则，D19 顺延 | 无外部依赖，交付最快 | D19 无法在本期成立，须回写 F1 标记延期，不能声称覆盖 |
| C. 接入真实模型但不门禁 | 有质量数据，不阻塞上线 | 质量不达标仍可上线，与 D19 的验收语义冲突 |

**决策 A**（用户 2026-11-21 确认）。CI 使用 Mock 验证结构与链路；验收环境使用真实模型抽样 10 条，≥8 条可直接使用作为上线门禁。Provider 保持可插拔，不绑定具体厂商；凭据只从环境变量读取，不写入审计与日志。

> 现状说明：`apps/api` 当前只有 `MockAiModelProvider` / `MockPlotModelProvider`，尚无真实文本模型实现；旧 Flask 的 `coze_client.py` 不复用。F3 需明确真实 Provider 的厂商与凭据来源（Coze Open API 或 OpenAI 兼容协议均可），并以独立适配器实现，避免知识库逻辑绑定厂商 SDK。

### 12.2 技术风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Postgres 镜像不含 pgvector | 迁移失败、启动失败 | 切换 `pgvector/pgvector:pg16`；迁移 `CREATE EXTENSION`；启动检查；CI 与部署手册同步；旧数据卷可复用 |
| 扩展创建权限不足 | 生产迁移失败 | 生产库由 DBA 预装 `vector`/`pg_trgm` 或授予建扩展权限；迁移使用 `IF NOT EXISTS`，无权限时输出明确错误 |
| 真实大纲模型凭据/配额缺失 | D19 门禁无法执行 | 验收环境预配置 Provider 凭据与调用预算；CI 使用 Mock；凭据不写入审计与日志 |
| 真实模型接入路径未定 | F3 无法拆出可执行任务 | F3 明确厂商与协议（Coze Open API 或 OpenAI 兼容），以独立适配器实现；不复用旧 Flask `coze_client.py`；未定前不进入 F4 |
| 真实大纲质量不达标 | 阻塞上线 | 抽样 10 条 ≥8 条为门禁；不达标时调整提示词、分块策略或更换 Provider 后复测，不带缺陷上线 |
| 嵌入维度与模型漂移 | 换模型需重建向量 | 维度固定 1024；`model` 与 `source_hash` 记录；提供离线重建脚本（F4 实现），不阻塞业务 |
| Mock 嵌入与真实模型差异 | 关联质量在 Mock 下不可代表 | E2E 用共享关键词样本验证链路；真实模型接入后单独评估召回与阈值 |
| PDF 扫描件无文本层 | 解析为空 | 返回 `KNOWLEDGE_PARSE_FAILED` 并提示「疑似扫描件，暂不支持 OCR」；不建条目 |
| 20 MB 文件解析内存/CPU | 请求或 Worker 峰值高 | 内存接收上限 20 MB；Worker 并发 2；解析后立即释放；文本上限 8,000,000 字符 |
| 中文关键词检索 | `pg_trgm` 对中文按字符 trigram | 2000 条规模足够；实测命中率不足时再评估分词或 `zhparser`（本期不引入） |
| 作业进程重启 | `running` 作业悬挂 | 启动时把遗留 `running` 置 `failed`，可重试；不假装完成 |
| 全局库 SSE 鉴权 | 无 `work_id` 可绕过作品校验 | SSE 与作业接口统一校验 `jobs.owner_id`；订阅前验证作业归属 |
| 引用快照截断 | 失效后内容不完整 | 删除前提示并支持逐条另存副本；快照只作兜底，界面明确标注「摘录」 |
| 备份体积与恢复耗时 | 大库导出/恢复慢 | 异步作业 + 分批事务 + 进度；解压上限 500 MB；失败批次回滚并统计 |
| 同名标签跨库 | 误用全局标签改作品标签 | 标签按库隔离；切换库时重新加载标签；接口强制 scope/work_id |
| 时间筛选时区 | 用户预期与 UTC 不一致 | 存 `timestamptz`；前端按本地时区生成 ISO 区间；预设按本地自然日计算 |
| 回收站长期增长 | 数据库体积上升 | F1 明确不做自动清理；提供逐条彻底删除；监控行数与体积 |
| 桌面限定 | 小屏不可用 | `1024` 以下不承诺；抽屉在两档内自适应；不做移动布局 |
| 结构化覆盖作者编辑 | 作业回填覆盖手工修改 | 回填前锁行并记录 `overwritten_by_structure`；前端提示；作者可再次编辑 |
| 大量引用导致删除变慢 | 全局条目引用很多时刷新快照耗时 | 引用数量按作品 500 条上限；删除事务内批量更新，超时则排队异步刷新（F4 兜底） |

### 12.3 明确不做的设计

- 不引入图数据库、知识图谱渲染库或协同编辑框架；
- 不做 OCR、PDF 渲染、图片处理；
- 不做向量 ANN 索引（本期 2000 条顺序扫描）；
- 不做知识库 Agent 工具、角色上下文注入、剧情树生成；
- 不做旧 F5 数据迁移与双写；
- 不做回收站自动清理、批量彻底删除；
- 不做移动/平板专用布局；
- 不把知识库数据写入正文、角色表或剧情表。
