## 一、编号约定

- 本轮变更任务使用 **R01\~R16**（R = Revision），**不复用** T01\~T42 编号，避免与已实施完成的 F3 任务混淆。
- R 编号按依赖分层排列，层内可并行。
- 每项任务的「方案依据」统一指向 06 的章节号，实现层面以 06 为真源。

## 二、任务总览

```
L0 契约层        R01  11 类枚举单一来源 + 契约重写
                 R02  响应体只读宽类型分支（存量降级）

L1 数据层        R03  迁移：entry_type 扩容 + 11 值 CHECK + 2 新增列
                 R04  实体与 data-source 装配

L2 服务层        R05  结构化管线：11 类 schema 归并与合并规则
                 R06  判定端口：LLM Few-shot 判定实现
                 R07  判定端口：规则兜底与置信度映射
                 R08  判定分流与 type_source 写入

L3 接口层        R09  创建/改判/检索端点契约接线
                 R10  批量操作端点（多选导出/删除/收藏）

L4 前端层        R11  类型选择器 11 类分组
                 R12  6 个新类型渲染模板 + 存量降级占位
                 R13  确认框（0.5–0.75 区间）
                 R14  方案 C 补强：计数徽章/排序/时间范围/标签云/收藏置顶/批量多选
                 R15  方案 D 补强：抽屉宽度可配 + 筛选状态记忆

L5 集成回归      R16  回归验证（D01\~D30 重跑）+ 迁移双跑 + 存量降级专项
```

### 6.2 交付门禁

1. **11 类矩阵**：创建 / 详情 / 检索 / 备份导出导入 四类操作 × 11 类型全部通过，否则阻塞交付。
2. **存量降级**：含旧字段样本详情接口必须 200 且渲染原文降级，任一类 422 即 FAIL。
3. **D19 门禁沿用**：真实模型抽样 10 条 ≥8 条结构化结果可用。
4. **判定溯源**：`type_source` 五场景写入正确，缺一项即 FAIL。
5. **迁移双跑**：全新库与存量快照库各 up + down 通过。

### 6.3 CI 门禁

1. **`pnpm run ci`** 全量通过（单测 + API E2E + 浏览器 E2E）。
2. **迁移双跑**：R03 新增迁移在全新库与存量快照库各执行 up（含 down 验证）。
3. **提示词真源一致性**：`apps/api` 不得硬编码类型判定提示词文本；`docs/02-技术与架构/knowledge-prompts/` 与文档同步更新（既有约定）。
4. **枚举单一来源**：`git grep` 断言 `KNOWLEDGE_ENTRY_TYPES` 不在 `apps/api` 中重复硬编码。

## 八、明确不做（与 06 §1.3 一致）

1. 不做「一条原文拆多条条目」：无条数上限、无父子关系模型、无去重口径，属**文档空白**，本轮不落地、不占编号。
2. 不写存量数据迁移脚本：旧字段就地改名，存量靠降级与用户触发「重新整理」自然收敛。
3. 不改动 `outline` 归属：仍为独立列，不并入 `structured`（06 §4.1）。
4. 不实现 `relationships[].target_id` 自动对齐回写：`target` 只写字符串。
5. 不新增未在分类规则 v1.1 中定义的类型；不删除任何既有类型。
6. 不落地新文档 `NovelOutline` 字段名变更：`outline` 契约本期不动，差异已在 06 §4.1 记录。
