## 一、方案概览与范围边界

### 1.1 设计目标

在现有 TS Monorepo（`apps/api` NestJS + TypeORM + PostgreSQL、`apps/web` React + Vite、`packages/contracts` Zod）上新增「角色版图」能力，逐条满足 F1 v1.3 的 D01~D31，并保证：

1. 角色资料按作品隔离、多视图共用一份，视图只保存布局与成员，不复制角色。
2. 手动建图与 AI 候选并存；AI 结果只进入草稿与候选条目，作者确认后才落正式数据，绝不静默覆盖。
3. 关系、成长线、头像、归档的写入均可校验、可回滚、可幂等重试。
4. 复用 M3a/M3b 的 AI 任务队列、SSE、Agent 工具解析、M2 审计与统一错误包络，不新增第二套异步通道。
5. 前端在中央「角色」页签内完成，正文编辑器保持挂载、保存状态不受影响。
6. 归档不改写正文文字；仅为块级文本节点补充稳定 `pid` 排版标识，标记以编辑器装饰层呈现，正文内容与保存链路保持可编辑（见 §3.6、§5.5）。

### 1.2 范围边界

**包含**：角色资料（含 13 项随机资料生成与人工修改）、关系类型与关系实例（5 组 23 类默认值）、多视图与布局、六维筛选、疑似重复候选与合并、成长线与剧情节点/章节跳转、**剧情节点归属与专属标记（归档时仅隐藏专属节点本身）**、AI 角色/关系候选、AI 成长事件候选、头像生成与采用、关系独立配色与冗余表达、归档与恢复、**段落级正文锚点（pid + 归档扫描 + 剔除 + 漂移降级）**、导入导出（含角色/关系/类型与可选锚点元数据）、关键变更审计。

**明确不包含**：

| 不包含项 | 原因 / 归属 |
| --- | --- |
| 角色专属 AI 扮演者（Agent）的配置、调整、绑定、启停 | F1 §2.2-1、D21；不新增任何 Agent 相关入口 |
| 真人实时共同编辑、在线状态、协作者消息 | F1 §2.2-2；不做 WebSocket/CRDT |
| 归档角色与关联内容的永久清理 | F1 §2.2-3、D16；不提供 purge 端点 |
| 旧 Flask 角色/关系/头像/成长线数据迁移 | F1 §2.2-4、D22；仍归 M4，本期不双写、不读取 `data/projects/*.json` |
| 同名/别名自动合并 | F1 §2.2-6、D07；只出候选，合并必须由作者显式选择 |
| 逐词/句法级锚点、语义推断、外貌识别 | F1 §3.5-3 明确只按姓名/别名精确匹配；本期锚点粒度固定为段落 |
| 实时监听归档后新增段落 | F1 §4.1 已知限制；仅在重新扫描（手动刷新或下次归档影响说明）时更新 |
| 正文内容导出与跨作品正文迁移 | 本段导入导出只覆盖角色域；锚点元数据仅用于同作品备份恢复，跨作品一律不还原 |
| 共享剧情节点随角色归档隐藏 | F1 §3.5-3 明确共享节点不属于任何单一角色，永不隐藏；仅 `is_exclusive` 节点参与过滤 |
| 通过正文文本推断节点归属 | F1 §2.1-12、§3.5-3；归属只能由作者显式设置，不做单关联或语义自动推断 |
| 关系类型的逐字冻结 | F1 §2.2-7；5 组 23 类是本期默认清单（见 §2.2.3），作品内可改名/停用 |

### 1.3 核心技术决策

| 决策 | 方案 | 理由 |
| --- | --- | --- |
| 角色资料模型 | 单表 `characters` + 别名子表，视图不持有资料副本 | 满足 D02「多视图共用同一资料」；避免多副本漂移 |
| 视图与成员 | `character_views`（视图元数据）+ `character_view_nodes`（显式成员 + 每视图坐标） | 版图是作者挑选的呈现；显式成员才能让「本视图布局」稳定，新增角色不会突然挤进每张图 |
| 关系不可变方向 | `character_relation_types.directed` 定义方向能力，实例保存 `directed` 快照 + `pair_key` 归一化 | 同一对角色可并存多类型；无向关系 A-B 与 B-A 视为同一条，避免重复 |
| 禁止自我关联 | 应用层 409 + DB `CHECK (source_id <> target_id)` 双保险 | 与 M3c-1 `PLOT_LINK_SELF` 保持一致的可读错误 |
| 关系样式 | 颜色 + 线型 + 标签三者同时落库，标签必填默认取关系名 | D12 要求「隐藏颜色仍可辨认」，不能只存颜色 |
| AI 候选 | 复用 `ai_tasks` 队列与 SSE，新增 `scope='character'`；草稿表 + 可逐条确认的条目表 | 与 M3c-1 草稿/候选范式一致；逐条状态机天然满足 D06/D08/D10 |
| 锚点定位 | 正文块节点新增稳定 `pid` 属性；锚点表按 `(角色, 章节, pid)` 定位 | 段落移动/重排仍可命中；不建独立指纹表、不做实时扫描（F2 前已确认） |
| 锚点生成 | 归档时异步扫描全书正文，按姓名/别名精确匹配后批量生成，作者可剔除误报 | 修复「仅按成长事件章节」的漏标；扫描进度可见，未完成不假装完成 |
| 编辑漂移 | 读取时校验 pid 与段落文本哈希；不匹配则锚点失效，整章提示并标注「原文已修改」 | 不误标新段落、不静默丢失（D25）；失效为可审计状态 |
| 正文契约 | `paragraph`/`heading` 增加可选 `pid`；保存时补齐并校验唯一，`content_hash` 忽略 pid | pid 只作排版稳定性标识，不改变正文文字与版本语义（§3.6） |
| 归档语义 | `characters.status` 三态（active/archived/merged），关系与成长线按状态派生隐藏 | 避免关系表反复改状态导致漂移；恢复只需改角色状态 |
| 专属剧情节点 | 节点级归属表 `plot_node_character_owners`（`is_exclusive`）；归档仅隐藏**全部专属归属者均已归档**的节点 | 不改 `plot_nodes` 行与层级/连线；共享节点永不隐藏；多角色同标专属时不误藏 |
| 剧情隐藏方式 | 读取期过滤（`includeArchivedOwner`，默认 false），不做删除/重建 | 恢复后节点原样复现；零写入、可逆、幂等（D29~D31） |
| 关系类型 | 5 组 23 类默认种子，作品内可改名/停用 | F1 v1.3 已确认；不逐字冻结，自定义类型仍开放 |
| 合并语义 | 保留被合并角色行（status='merged' + `merged_into_id`），转移关系/成长线/别名/节点归属 | 禁止物理删除、可追溯；不提供「恢复被合并角色」入口 |
| 头像存储 | 本地文件目录 + 元数据表，内容哈希命名，鉴权后流式读取 | 不引入对象存储；避免 base64 撑大数据库；失败不清除旧头像 |
| 导入导出 | 版本化 JSON（`schema_version=2`）+ preview/commit 两阶段 | 关系与视图无法用 CSV 无损表达；先预览冲突再提交，避免「同名自动合并」 |
| 并发控制 | 角色/关系/成长线写操作使用 `expected_version` 乐观锁；布局坐标不做版本控制 | 与 M3c-1 剧情树语义一致；拖拽不应因版本冲突失败 |
| 筛选 | 前端内存过滤为主，服务端参数为兼容与深链兜底 | 100 角色/150 关系规模下单次读全量最快，也最稳地满足 1 秒指标 |

### 1.5 与 M3c-1 的复用关系

| 复用项 | 用法 |
| --- | --- |
| `ZodValidationPipe` | 全部写接口入参校验，失败即 422 并回传 `details.field_errors` |
| `SessionGuard` / `CsrfGuard` | 读接口仅会话；写接口追加 CSRF（与剧情接口一致） |
| 作品归属校验范式 | 统一 `works.author_id = 当前作者`，不属于一律 404，不泄露存在性 |
| `AuditService.record` | 全部关键变更写审计，`detail` 不含正文与模型密钥 |
| `ai_tasks` + BullMQ + `AiTaskEventBus` | 角色/关系候选、成长事件候选、头像生成共用同一队列与 SSE 端点 |
| 乐观锁 + 行锁 | `SELECT ... FOR UPDATE` + `expected_version`，冲突返回 409 |
| 草稿/候选分离 | 与 `plot_generation_drafts` / `derivation_candidates` 同构，降低认知成本 |
| `editor-schema` | 复用 `parseDocument/canonicalizeDocument/applyOperations`；新增 pid 工具与内容哈希（忽略 pid），不另起一套文档模型 |
| `PlotModule` | 导出只读 `PlotOwnerService`（归属列表、归档隐藏集合、影响计数）；`CharacterModule` 注入使用，不直接写 `plot_nodes` |

## 二、数据模型设计

### 2.1 迁移清单

| 迁移 | 内容 | 可回滚要点 |
| --- | --- | --- |
| `1760500000000-character-base.ts` | 11 张角色域表 + 索引 + 约束 | down 按依赖逆序删表 |

> 迁移全部显式注册到 [data-source.ts](../../../apps/api/src/database/data-source.ts) 的 `migrations` 与 `entities`；禁止 `synchronize: true`。
>
> **正文 pid 不建迁移**：`pid` 存放在既有 `chapters.document` 的 JSONB 内，无列变更。历史正文采用「读取时惰性补齐 + 保存/归档扫描时固化」（§3.6），不运行批量改写脚本，不新增 `version_snapshots` 记录。

### 2.2 表定义

#### 2.2.1 characters（角色）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `work_id` | uuid | NOT NULL，FK `works(id)` ON DELETE CASCADE |
| `name` | varchar(60) | NOT NULL |
| `name_key` | varchar(60) | NOT NULL（归一化名，仅用于疑似重复检索，非唯一） |
| `identity` | varchar(80) | NULL（身份） |
| `age` | integer | NULL，CHECK `age IS NULL OR (age >= 0 AND age <= 10000)` |
| `gender` | varchar(16) | NULL |
| `personality` | varchar(2000) | NOT NULL DEFAULT ''（性格） |
| `experience` | text | NOT NULL DEFAULT ''（经历） |
| `country_region` | varchar(80) | NULL（国家/地域，筛选维） |
| `faith` | varchar(80) | NULL（信仰，筛选维） |
| `faction` | varchar(80) | NULL（阵营，筛选维） |
| `race` | varchar(80) | NULL（种族，筛选维） |
| `occupation` | varchar(80) | NULL（职业，筛选维） |
| `age_band` | varchar(40) | NULL（年龄段，筛选维） |
| `attributes` | jsonb | NOT NULL DEFAULT `'[]'`，受控数组 `[{key,value}]` ≤ 20 项 |
| `avatar_asset_id` | uuid | NULL，FK `character_avatar_assets(id)` ON DELETE SET NULL |
| `status` | varchar(16) | NOT NULL DEFAULT `'active'`，CHECK `active/archived/merged` |
| `merged_into_id` | uuid | NULL，FK `characters(id)` ON DELETE SET NULL，CHECK `merged_into_id <> id` |
| `archived_at` / `archived_by` | timestamptz / uuid | NULL |
| `origin` | varchar(16) | NOT NULL DEFAULT `'manual'`，CHECK `manual/random/ai/import` |
| `version` | integer | NOT NULL DEFAULT 1（资料乐观锁） |
| `created_at` / `updated_at` | timestamptz | NOT NULL DEFAULT now() |

索引与约束：

- `idx_characters_work_status (work_id, status, updated_at DESC)`；
- `idx_characters_work_name_key (work_id, name_key)`（非唯一：同名允许存在，只用于提示候选）；
- `idx_characters_work_filters (work_id, country_region, faith, faction, race, occupation, age_band)`（六维组合的兜底索引，实际以内存过滤为主）；
- `CHECK (status <> 'merged' OR merged_into_id IS NOT NULL)`；
- `CHECK (status <> 'archived' OR archived_at IS NOT NULL)`。

> `name_key` 由服务端在写入时计算（NFKC → trim → 小写 → 去空白与常见间隔符），不对外开放修改。
>
> **循环外键处理**：`characters.avatar_asset_id → character_avatar_assets.id` 与 `character_avatar_assets.character_id → characters.id` 互为引用。迁移顺序为：先建 `characters`（不建该外键）→ 建 `character_avatar_assets` → `ALTER TABLE characters ADD CONSTRAINT ... ON DELETE SET NULL`；down 逆序先删外键再删表。

#### 2.2.2 character_aliases（别名）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `work_id` | uuid | NOT NULL（冗余，便于按作品索引；与角色归属一致由服务层保证） |
| `character_id` | uuid | NOT NULL，FK `characters(id)` ON DELETE CASCADE |
| `alias` | varchar(60) | NOT NULL |
| `alias_key` | varchar(60) | NOT NULL |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |

约束与索引：

- `UNIQUE (character_id, alias_key)`（同一角色不重复别名）；
- `idx_character_aliases_work_key (work_id, alias_key)`（疑似重复检索）；
- 别名数量上限 10，由 Zod 与业务层双重限制。

#### 2.2.3 character_relation_types（关系类型定义）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `work_id` | uuid | NOT NULL，FK `works(id)` ON DELETE CASCADE |
| `code` | varchar(40) | NOT NULL（稳定标识，如 `kinship`、`master_apprentice`） |
| `label` | varchar(40) | NOT NULL（正向称谓） |

- `idx_character_avatar_character (character_id, created_at DESC)`；

> **补充约定（v1.4，Q3）**：头像资产完整状态机为 `pending → active → superseded`，`pending → failed` 为失败终态；不允许 `active → pending`、`superseded → active`、`failed → active`。
>
> - `pending → active`：仅由作者调用「采用」触发；目标资产属于该角色、未超时、未失败；同事务把旧 `active` 置 `superseded`、更新 `characters.avatar_asset_id` 并 `version + 1`。
> - `pending` 超时：生成成功后 7 天内未被采用视为过期，后台将其置 `failed`（`error.reason='adopt_timeout'`），作者可重新生成；过期不删除文件与行，保留审计。
> - 失败降级：生成失败直接写 `failed`（若需要留痕）或直接不建行；无论哪种，旧 `active` 资产保持原样，不清除、不降级。
> - 合并角色（§5.4）：被合并角色的 `active` 资产先复制为**新的 `pending` 资产行**（复用同一 `storage_path/content_hash`，新 id），再把原 `active` 置 `superseded`；若保留角色无 `active`，新 `pending` 在同事务直接晋级为 `active`，否则保持 `pending` 等待作者采用。由此避免非法的 `active → pending` 迁移。影响任务：T33、T38。

#### 2.2.14 plot_node_character_owners（剧情节点归属与专属）

| 列 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | PK |
| `work_id` | uuid | NOT NULL，FK `works(id)` ON DELETE CASCADE |
| `node_id` | uuid | NOT NULL，FK `plot_nodes(id)` ON DELETE CASCADE |
| `character_id` | uuid | NOT NULL，FK `characters(id)` ON DELETE CASCADE |
| `is_exclusive` | boolean | NOT NULL DEFAULT false（作者显式标记的专属归属） |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |

约束与索引：

- `UNIQUE (node_id, character_id)`（同一节点对同一角色只有一条归属）；
- `idx_plot_owner_character (work_id, character_id, is_exclusive)`（归档影响统计、恢复检查）；
- `idx_plot_owner_node (node_id)`（节点详情/批量读取归属）；
- 只存归属关系，**不复制任何剧情内容**（标题、正文、坐标仍在 `plot_nodes`）。

**归属语义与隐藏判定**：

1. 专属是**节点级**属性，不是角色级：同一节点可被多个角色标记归属，其中部分或全部可设 `is_exclusive=true`。
2. 共享节点（无 `is_exclusive=true` 的归属，或仅普通归属）**永不隐藏**，即使该角色是唯一关联者。
3. 隐藏判定（读取期计算，不写 `plot_nodes`）：

```text
exclusiveOwners(node) = owners where is_exclusive = true
hidden(node) = exclusiveOwners.length > 0
               AND 所有 exclusiveOwners 对应角色 status = 'archived'
```

4. **多角色同标专属不误藏**：若节点同时被 A、B 标为专属，A 归档、B 仍 active，则 `hidden=false`；只有 A、B 都归档时才隐藏。理由：专属是「共同归属」，任一角色仍在正式使用该节点就不应把它从正式树拿走；宁可多显示，不可误藏作者仍在用的结构。
5. 隐藏只作用于节点本身：`parent_id`、`sibling_order`、`plot_links` 全部保持原值，不级联隐藏子节点，不删除、不重建任何行。恢复只是让判定重新变为 `hidden=false`。

**模块边界**：

- 表与实体、归属读写、隐藏集合计算归**剧情模块**（`plot`），由 `PlotModule` 导出只读 `PlotOwnerService`；`CharacterModule` 仅注入该服务做归档影响统计与恢复校验，不直接操作 `plot_nodes`。
- 迁移文件 `1760500004000-plot-node-character-owners.ts` 依赖 `characters` 与 `plot_nodes`，必须排在角色基础迁移之后。
- 剧情导出/导入不携带归属（跨作品 character id 无意义）；导入产生的新节点默认无归属，因此永不因归档隐藏。

### 2.3 自我关联与关系去重的约束落地

**禁止自我关联**（D05）：

1. 契约层 `createCharacterRelationRequestSchema.refine(v => v.source_id !== v.target_id)`；
2. 服务层提前拦截，返回 409 `{ details: { code: 'CHARACTER_RELATION_SELF' } }`；
3. 数据库 `CHECK (source_id <> target_id)` 兜底，防止绕过接口的写入。

**关系对归一化 `pair_key`**（D05「同对角色多种关系并存」且不产生无意义重复）：

```text
directed = true   → pair_key = `${source_id}>${target_id}`
directed = false  → pair_key = [source_id, target_id].sort().join('~')
```

- `directed` 创建时从 `character_relation_types.directed` 快照，之后不随类型修改而变（类型方向被锁）。
- A→B 与 B→A 的有方向关系视为两条不同关系（允许「互为师徒」这类表达）；无方向关系 A-B 与 B-A 归一为同一条。
- `UNIQUE (work_id, pair_key, type_id)` 保证「同对角色同类型」不重复，但不同 `type_id` 可并存，满足多关系并存。

### 2.4 状态机与归档语义

角色状态：

```text
active ──archive──▶ archived ──restore──▶ active
active ──merge───▶ merged（终态，仅保留 merged_into_id）
```

| 状态 | 出现在正式版图 | 出现在归档视图 | 关系可见 | 成长事件状态 | 专属剧情节点 | 正文标记 | 可恢复 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `active` | 是（若属于该视图） | 否 | 是 | `active` | 正常显示 | 无 | — |
| `archived` | 否 | 是 | 否（派生隐藏） | `archived` | 仅隐藏「全部专属归属者均已归档」的节点本身 | 段落锚点（`active`）+ 失效时整章兜底 | 是 |
| `merged` | 否 | 否（无法单列恢复） | 指向被合并角色 | 已转移至保留角色 | 归属转移至保留角色，按保留角色状态判定 | 无（按保留角色计算） | 否 |

- `archive` 只改 `characters.status/archived_at/archived_by` 与该角色成长事件 `status='archived'`；**不删除**关系、不改正文文字，仅创建一次归档扫描并在正文中补齐 `pid`。
- `restore` 反向操作并把成长事件恢复 `active`；恢复前返回疑似重复候选，由作者决定（D07/D15），不自动合并；同时把该角色 `active` 锚点置 `invalid`（`character_restored`），标记全消失；专属节点因判定恢复而原样复现。
- 关系隐藏不落库：读取时按 `characters.status='active'` 过滤；这样恢复后关系必然重新可见，不存在双写漂移。
- 专属剧情节点隐藏同样不落库：`plot_nodes` 行、`parent_id`、`sibling_order`、`plot_links` 均不改；恢复不需要重建任何节点（D29~D31）。
- 归档后关系数据仍保留，因此「恢复」没有丢失风险；同时满足 D16「不提供永久清理」。

### 2.5 与 work / chapter / plot_node 的边界

| 关联 | 方式 | 理由 |
| --- | --- | --- |
| `works` | 强 FK + 级联删除 | 作品是聚合根；删作品即删角色域数据 |
| `chapters` | 成长事件 `chapter_id` 强 FK + `ON DELETE SET NULL`；锚点 `chapter_id` 强 FK + `ON DELETE CASCADE` | 章节是正文权威；章节删除时成长事件保留但失去跳转目标，锚点随章节消失（无正文可标记） |
| `plot_nodes` | 成长事件弱引用（`plot_node_id` 无 FK + 快照）；归属表 `plot_node_character_owners.node_id` 强 FK + `ON DELETE CASCADE` | 剧情节点可被作者删除；成长事件历史不应随节点消失而丢；归属随节点删除而清理，不会悬空 |
| `plot_links` / `parent_id` | **不读写、不修改** | 归档只过滤节点呈现，层级与连线结构保持原值（D29/D30） |
| `ai_tasks` | `character_ai_drafts.task_id` 弱引用 | 与 M3c-1 一致：任务表不承载业务外键，上下文写 `input_summary` |
| 正文文档 | **仅 `attrs.pid` 排版标识**；文字与结构不变 | 锚点需要跨编辑稳定定位（§3.6）；业务状态仍存锚点表，不写入正文属性 |

Future M4 迁移边界：

- 本套表不读取旧 Flask `data/projects/*.json`、不写旧目录、不做双写。
- 旧 `role_agent_bindings.role_id` / `flow_progress.role_id` 属于 M3b 既有 Agent 领域，与本表 `characters.id` **不建立外键**，避免把「角色资料」与「角色扮演者」耦合（F1 明确排除 Agent）；未来若需要关联，由 M4/后续里程碑单独设计映射表。

### 2.6 事务边界与级联策略

| 操作 | 事务范围 | 锁 | 级联/派生 |
| --- | --- | --- | --- |
| 创建/修改角色 | characters + aliases + 审计 | `SELECT ... FOR UPDATE` 角色行 | — |
| 归档角色 | characters + 成长事件状态 + 扫描作业行 + 审计 | 锁角色行 | 关系/节点归属不写（读取期派生）；扫描在事务外分批 |
| 归档扫描 | 每批：章节 pid 补齐 + 锚点 upsert + 进度 | 无长事务；按扫描行更新 | 批次失败可重试；不阻塞正文保存与节点隐藏 |
| 恢复角色 | characters + 成长事件状态 + 锚点批量失效 + 审计 | 锁角色行 | 节点归属不改；重复候选只读计算；正文零写入 |
| 设置节点归属 | plot_node_character_owners（整组替换/单条删除）+ 审计 | 锁节点行 | 不改 `plot_nodes` 内容、位置、父子与连线 |
| 合并角色 | 目标/来源两行 + 关系转移 + 别名 + 成长事件 + 视图成员 + 节点归属转移 + 审计 | 按 id 排序锁两行（防死锁） | 冲突关系去重后跳过；归属唯一键冲突按 `is_exclusive` 合并 |
| 建/改/删关系 | character_relations + 审计 | 锁作品下关系唯一键（靠唯一索引） | 类型删除受 RESTRICT 限制 |
| 视图布局 | character_view_nodes（批量 upsert） | 无版本锁 | 不推进视图/角色版本 |
| 确认 AI 条目 | item 行 + 目标实体 + 草稿状态 + 审计 | 锁 item 与草稿 | 依赖未确认则 409 |
| 导入 commit | 全部角色域表 + 作业行 + 审计 | 锁作品下相关行/表级顺序一致 | 失败整体回滚 |
| 头像采用 | asset 两行 + character 指针 + 审计 | 锁 asset 行 | 旧 active → superseded |

统一原则：

1. 所有跨表写操作在**单个** `dataSource.transaction` 内完成，中途失败整体回滚。
2. 审计写入复用 `AuditService.record(..., manager)`，与业务写入同事务（与 M3c-1 `plot_generation_commit` 一致）。
3. 外部 I/O（头像文件写盘、模型调用）不在事务内：先落临时文件/拿到结果，再开短事务写元数据；文件写失败则不写元数据。
4. 级联删除只发生在 `works` 删除与显式 `character` 删除（本期不提供角色物理删除），其余一律软状态。

| 冲突 | preview 表现 | commit 规则 |
| --- | --- | --- |
| 同名 / 别名重叠（归一化后相同） | `conflicts[]`：`{ type:'character_duplicate', local_id, matches:[{character_id,name,matched_on}] }`，`matched_on` 取 `name` 或 `alias` | 该 `local_id` 必须提供 `resolution`：`create`（新建独立）/`merge`（并入指定 `character_id`）/`keep_independent`（等价 create）；缺失则 409 `CHARACTER_IMPORT_NEEDS_RESOLUTION` |
| 关系悬空 | `type:'dangling_relation'` | 直接 422 整单回滚（不自动丢弃） |
| 关系重复 | `type:'duplicate_relation'` | 跳过并计入 `summary.skipped_relations` |
| 类型缺失 | `type:'unknown_relation_type'` | 422 整单回滚 |
| 视图重名 | `type:'view_name_conflict'` | `merge` 模式下改名为「原名 (导入)」；`replace` 模式整体替换 |

### 3.6 正文契约变更：块级 `pid`

> 本节是 v1.1 的核心契约变更。现网 `packages/editor-schema/src/schema.ts` 的 `paragraph`/`heading` **没有 attrs**（仅列表节点有 `tight/order`），`proseMirrorNodeSchema` 的 `attrs` 为 `z.record(z.unknown())`，因此新增属性不破坏既有解析，但所有正文生产/消费方必须按本节口径处理。

#### 3.6.1 属性定义

| 项 | 规则 |
| --- | --- |
| 挂载节点 | `paragraph`、`heading`；`blockquote`/`list_item` 不带，其子 `paragraph` 携带；`code_block`/`fence`/`hr` 不带（不参与姓名扫描） |
| 字段 | `attrs.pid: string` |
| 格式 | 小写 UUID v4（36 字符），与项目现有 `z.string().uuid()` 风格一致；不用 nanoid，避免与既有 id 风格分叉 |
| 必填性 | **契约层可选**（兼容历史文档与旧快照）；**保存/扫描落库前必须补齐**，新写入文档必须全部具备 |
| 唯一性 | 同一章节文档内唯一；重复即拒绝（见 §3.6.4） |
| 语义 | 仅表示「同一段落身份」，用于排版与锚点定位；**不含任何业务语义，不做跨作品引用，不参与哈希与 diff** |

> **Schema 必改**：`packages/editor-schema/src/schema.ts` 必须为 `paragraph` 与 `heading` 的 `attrs` 显式声明 `pid: { default: null }`（`heading` 保留 `level`）。ProseMirror 的 `Node.fromJSON` 只按 `type.attrs` 读取属性，未声明的属性会被丢弃，仅在契约层加字段不足以让 pid 存活。
>
> **补充约定（v1.4，Q1）**：`pid` 一律使用 **UUID v4（随机生成）**，存量惰性补齐同样生成 v4；不使用 v5、不引入命名空间或任何基于文本内容的派生输入。`uuid` 校验只要求「UUID 格式 + 小写 + 章内唯一」，不锁定版本号，但生成实现统一 `newPid()`（v4）。理由：v5 依赖命名空间与文本/序号派生，会让 pid 间接承载内容语义，与「pid 不承载语义、不做内容派生」的边界冲突。影响任务：T01、T02。

#### 3.6.2 生成与保留规则

| 场景 | 规则 |
| --- | --- |
| 新建空段落 / 回车拆分 / 粘贴 | 前端 ProseMirror 插件 `appendTransaction`：事务产生新块后，对 `pid` 缺失或为 `null` 的 `paragraph/heading` 通过 `tr.setNodeAttribute(pos, 'pid', newPid())` 在同一事务内补齐；拆分时前半段保留原 `pid`，后半段分配新 `pid`。因为 pid 随步骤上行，服务端只需对缺失补齐，避免两端 pid 不一致 |
| 合并段落 | 保留目标（前半）段落 `pid`，被合并段落的 `pid` 消失；不回收、不复用 |
| 撤销 / 重做 | `pid` 随历史步骤恢复，不重新生成；历史中若出现重复（理论上不会），保存时校验拦截 |
| 历史正文（无 pid） | 读取时惰性补齐并随响应返回；生成算法 `pid = uuidv5(chapter_id, sha256(归一化段落文本) + ':' + 同文本出现序号)`，同一文档同一内容多次读取结果一致；首次保存或归档扫描时固化写入 |
| AI 写正文（整篇替换） | 服务端在 `replaceDocumentOperations` 前执行 `preservePids(base, candidate)`：候选段落与基准段落在「类型 + 文本 + 标记 + 子结构」上完全一致时复用基准 `pid`，其余分配新 `pid`；AI 改写过的段落因此换新 `pid`，旧锚点自然失效 |
| Markdown 导入 | `markdownToDocument` 后统一 `ensurePids()` 分配新 `pid`；Markdown 本身不承载 `pid` |
| 角色导入导出还原 | 同作品备份可携带 `anchors.paragraph_pid` 并原样写回；跨作品导入**丢弃锚点，且任何导入的 pid 都不写入目标正文**，确需落正文时一律调用 `newPid()` 重新分配 |
| 版本回滚 | `replaceDocumentOperations(current, targetSnapshot)` 前对快照执行 `preservePids(current, target)`；旧快照无 pid 仍可读 |

> **补充约定（v1.4，Q1）**：上表「历史正文」行中的 `uuidv5(chapter_id, sha256(文本)+序号)` 算法**作废**，不再实施。存量补齐与新建段落统一调用 `newPid()` 生成 v4 随机 UUID；惰性补齐不保证跨请求稳定，锚点只在保存或归档扫描固化 pid 后建立。由于 `canonicalizeContent` 忽略 pid，跨请求 pid 差异不会触发编辑器重置或无意义保存。该差异以本约定为准。

#### 3.6.3 与哈希、快照、diff 的关系

| 依赖点 | 影响 | 处理 |
| --- | --- | --- |
| `canonicalizeDocument`（editor-schema） | 目前参与 `content_hash` 与文档相等判断；pid 进入后会误判「纯 pid 变化」为正文变化 | 新增 `canonicalizeContent(document)`：规范化时剔除 `attrs.pid`（含 `null/undefined`），并删除因剔除而变空的 `attrs` 与空数组，使「无 pid 的旧文档」「pid 为 null 的解析结果」与「仅有 pid 的新文档」得到相同字符串；`content_hash`、AI 无变更判断、编辑器外部同步判断改用 `canonicalizeContent`；结构测试仍可用 `canonicalizeDocument` |
| `chapter.content_hash` | 定义改为「正文内容哈希（不含 pid）」 | 纯 pid 补齐不改变 `content_hash`；`ChapterSaveService` 用 `canonicalizeContent` 计算 |
| `chapter.version` | 纯 pid 补齐不构成作者可见内容变更 | 若 `applyOperations` 后仅 pid 变化：持久化 `document`、不递增 `version`、不建快照、不进入修订；仍写 `chapter_changes` 以保证 `change_id` 幂等重放，`server_version` 保持当前值。归档扫描的 pid 固化同此规则 |
| `version_snapshots` | 历史快照无 pid；新快照含 pid | 旧快照保持原样可读；`compareNodes/flattenText` 只读 `type/text`，天然不受 pid 影响，无需改 diff 算法 |
| `revision` 操作集 | 路径定位不依赖 attrs | `applyOperations` 不受影响；接受/拒绝与回滚前后的锚点失效由 §5.5 的读取校验兜底 |
| `replaceDocumentOperations` | 内部用 `canonicalizeDocument` 校验「应用后 == 候选」，pid 补齐会导致比较失败 | 改为 `canonicalizeContent` 比较；调用前先 `preservePids(base, replacement)`（AI 写正文、回滚、整篇替换共用） |
| 编辑器外部同步 | `prosemirror-editor.tsx` 用 `canonicalizeDocument` 判断是否重置文档，pid 差异会导致无意义重置 | 改用 `canonicalizeContent`；`initialDocument` 变更时只比较内容 |
| 契约校验 | `proseMirrorNodeSchema` 允许任意 `attrs` | 新增 `validateDocumentPids(document)`：仅检查 `paragraph/heading` 的 `pid` 格式与唯一性；接入 `parseDocument`（开发/测试强校验）与保存/导入入口（生产强校验） |

#### 3.6.4 校验点与错误码

| 位置 | 行为 |
| --- | --- |
| `parseDocument` | 出现非法 `pid` 格式 → 抛错（`Unsafe/invalid document`） |
| `POST /chapters/:id/changes`（保存） | 补齐后若重复 → 422 `DUPLICATE_PARAGRAPH_PID`（`details.duplicated_pids`） |
| AI 修订集创建 / 回滚 | 生成候选后同样执行补齐与唯一性校验；失败不创建修订集 |
| 归档扫描 | 补齐后若仍有重复（异常数据），保留首个并写审计 `character_scan_pid_conflict`，不中断扫描 |
| 角色导入 commit | 携带锚点时校验 pid 存在与唯一；非法锚点丢弃并计 `summary.discarded_anchors` |
| Markdown 导入 | 解析后统一分配，不校验来源 pid（来源不存在） |

#### 3.6.5 架构冲突记录（必须保留）

系统设计 §6.1 要求「业务元数据不入正文」。本方案把 `pid` 写入正文属性，属于**有意的例外**：

- 理由：段落级锚点必须在作者编辑、重排、AI 改写后仍能定位；独立指纹表无法在「段落删除后仍区分是删除还是改写」时不依赖正文派生信息，实时扫描又无法满足打开 1 秒与不打扰输入。
- 边界：`pid` 只是排版身份，不含角色、关系、归档等任何业务语义；归档状态全部在 `character_text_anchors`，恢复时正文零写入。
- 代价：正文 JSON 每段增加约 50 字节；所有正文生产方需遵循补齐/保留规则；`content_hash` 必须显式忽略 pid。风险与回归面见 §10.2、§12.2。

## 四、API 设计

统一前缀 `/api/v1`（`app.setGlobalPrefix('api/v1')`）；全部走 `SessionGuard`，写操作追加 `CsrfGuard`，入参 `ZodValidationPipe`；成功响应 `ok(request, data)` → `{ data, request_id }`；错误响应 `{ error: { code, message, details? }, request_id }`，业务码写入 `details.code`（与 M3c-1 一致）。作品归属不匹配一律 404。

- 读取时做**惰性失效判定**（短事务、幂等）：锚点段落 `pid` 不存在 → `invalid(pid_missing)`；`pid` 存在但段落文本哈希 ≠ `excerpt_hash` → `invalid(text_changed)`；角色已恢复 → `invalid(character_restored)`。失效锚点不返回为 `paragraph_marks`，而是聚合成 `chapter_marks` 兜底。
- `scan.status` 为 `pending/running` 时返回当前进度，前端显示「扫描中」；`failed` 时提供重试按钮，不展示「已归档」结论。
- 剔除 body：`{ reason?: string }`；批量 body：`{ anchor_ids: uuid[] (1~100) }`。重复剔返回 200 当前状态，不报错。
- 重新扫描仅允许 `archived` 角色；已有 `pending/running` 扫描时返回 409 `CHARACTER_SCAN_RUNNING`。

### 4.8 导入导出（4 个）

| 方法 | 路径 | 说明 | 成功 | 主要错误 |
| --- | --- | --- | --- | --- |
| GET | `/works/:workId/character-portability/export?include_archived=true&include_anchors=true` | 导出 JSON（`Content-Disposition` 附件），默认含归档角色与锚点、不含 merged | 200 | 401/404 |
| POST | `/works/:workId/character-portability/import/preview` | 校验 + 冲突预览（不写业务表） | 200 | 422 |
| POST | `/works/:workId/character-portability/import/commit` | 按预览与 resolutions 提交 | 200 | 409/422 |
| GET | `/works/:workId/character-portability/jobs/:jobId` | 作业结果摘要 | 200 | 404 |

- `preview` 请求即导入文件本身（`schema_version` 顶层，接受 1/2）；返回 `{ preview_job_id, summary, conflicts, resolved_preview }`，作业 `kind='import_preview'`；校验失败直接 422，不创建作业行。

## 五、核心逻辑与算法

### 5.1 读取模型与归属校验

- 角色域所有接口统一走 `assertOwnedWork(manager, authorId, workId)`：`works.id = :workId AND works.author_id = :authorId`，不满足即 404（不泄露存在性）。
- 版图读取采用「一次读全」：`board` 单次查询视图、成员 JOIN 角色、成员间关系、关系类型、布局行；不做 N+1。
- 列表读取只返回角色摘要（不含关系与成长线），详情页再按需拉取，避免首屏负载过大。

### 5.2 版图布局与视图持久化

**成员模型（明确取舍）**：视图成员 = `character_view_nodes` 行；角色资料永远只有一份。新建视图时默认把「当前全部 active 角色」批量加入（默认视图同样处理），之后新增角色只自动加入默认视图，其余视图由作者手动加入或「按当前筛选一键加入」。这样既满足 D02（多视图共用资料），又避免所有视图被自动塞满。

**布局算法（前端纯函数 `character-layout.ts`）**：

```text
输入：members[]（含 arranged/x/y）、relations[]、当前筛选结果
1. arranged=true 的成员使用已保存坐标；
2. arranged=false 的成员按稳定顺序（sort_index, name, id）排入网格：
   columns = ceil(sqrt(未排布数量))，cell = 220 × 160，起点 (80, 80)
3. 避让：未排布坐标若与已排布坐标重合，向下顺延一行
4. 关系端点用成员中心点；有方向关系加箭头 marker，无方向关系无箭头
输出：{ character_id: { x, y } }（不落库）
```

- 拖拽结束（`pointerup`）只提交被移动成员的坐标；`PUT layout` 批量 upsert，已存在的行更新、缺失的行插入，未知成员忽略并返回 `updated` 计数（幂等）。
- **撤销自动布局**：前端保存一次坐标快照，撤销时用快照反向调用 `PUT layout`（与 M3c-1 一致）。
- 布局与坐标不推进任何版本号；视图筛选/改名推进 `character_views.version`。

#### 5.2.1 随机资料生成（13 项）

```text
POST /characters/random { seed? }
  → 服务端纯函数 character-random.ts：以 seed（缺省随机）构造可复现序列
  → 返回 { seed, dossier: { name, identity, age, gender, personality, experience,
       country_region, faith, faction, race, occupation, age_band, attributes[] } }
  → 不落库；作者确认/修改后走 POST/PATCH characters 保存
```

- 13 项与 F1 一一对应：姓名、身份、年龄、性别、性格、经历、国家/地域、信仰、阵营、种族、职业、年龄段、属性。
- 一致性校验：`age_band` 由 `age` 推导（幼年/少年/青年/中年/老年）或从词表取值时保持区间一致；`attributes` 生成 2~5 项受控键值，避免空壳角色。
- 同一 `seed` 必须得到同一套资料（D03 与单测可复现）；作者修改任何字段后以保存结果为准，不再受 seed 影响。
- 生成逻辑放在服务端而非前端：规则集中、可单测、导入导出与后续 AI 候选可复用同一词表。

### 5.3 关系去重与多关系并存

新建关系流程（单事务）：

1. 校验作品归属、两端角色属于该作品且均为 `active`（归档角色不可新增关系 → 409 `CHARACTER_ARCHIVED_TARGET`）。
2. 自我关联拦截 → 409 `CHARACTER_RELATION_SELF`。
3. 校验 `type_id` 属于该作品；取类型 `directed/reverse_label/label` 作为默认值。
4. 计算 `pair_key`；`INSERT` 冲突（`UNIQUE(work_id, pair_key, type_id)`）→ 409 `CHARACTER_RELATION_EXISTS`，附 `details.existing_id`，前端提示「关系已存在」而非静默覆盖。
5. 颜色：作者未指定时从调色板按 `sort_order` 轮转分配（保证相邻关系不同色）；`tag` 默认等于 `label`，`line_style` 默认 `solid`。
6. 写审计 `character_relation_create`。

**反向称谓展示**：仅在 `directed=true` 时展示；查看方向为 target → source 时显示 `reverse_label ?? label`，不修改存储方向。无方向关系统一按「角色 A – 角色 B」展示，`reverse_label` 必须为空（契约与 DB 双重约束）。

**冗余表达**：前端始终渲染「线型 + 标签 chip」；`color` 只作为第三重提示。深色/浅色主题下线型宽度与标签对比度按 design-tokens 取值（不新增硬编码色值）。

### 5.4 疑似重复检测（只出候选，禁止自动合并）

归一化函数 `normalizeNameKey`（服务端与导入共用）：

```text
1. Unicode NFKC；
2. 去首尾空白；
3. 小写；
4. 删除所有空白（含全角空格）与间隔符：· ・ - _ . ~ ；
5. 长度截断 60。
```

检测方式：

| 场景 | 查询 | 输出 |
| --- | --- | --- |
| 全作品疑似重复 | 按 `(work_id, name_key)` 分组，`HAVING count(*) > 1`；别名同理按 `alias_key` 分组后回查角色 | `[{ key, matched_on, character_ids }]` |
| 恢复角色前 | 用该角色 `name_key` 与全部 `alias_key` 查 `characters(status='active')` 与 `character_aliases` | 恢复响应内 `duplicate_candidates` |
| AI 候选条目 | 每个角色候选的 `name/aliases` 归一后与现有角色比对 | 条目 `suspected_duplicates` |

**合并流程**（显式调用，单事务）：

1. 锁「保留角色」与「被合并角色」两行（按 id 排序加锁，防死锁）；校验不同、非 merged。
2. 关系转移：把 `source_id/target_id = 被合并 id` 的关系改为保留角色，重算 `pair_key`；若目标唯一键冲突（保留角色已存在同类型关系），跳过该条并计入 `skipped_relations`。
3. 别名合并：把被合并角色别名并入保留角色；冲突别名跳过。
4. 成长事件转移：`character_id` 改为保留角色（`plot_node_id/chapter_id` 不变）。
5. 节点归属转移：`plot_node_character_owners.character_id` 改为保留角色；与保留角色既有归属冲突时合并为一条，`is_exclusive = 原两条取 OR`；不改变节点内容与层级。
6. 视图成员：保留角色所在视图保留原坐标；被合并角色的成员行删除；若保留角色不在该视图，则把被合并角色的坐标转给保留角色（尽量保持视觉位置）。
7. 头像：仅当保留角色无 active 头像时，把被合并角色的 active 资产改为 `pending` 并提示作者另行采用；不自动覆盖。
8. 被合并角色：`status='merged'`、`merged_into_id=保留角色`、`avatar_asset_id=NULL`；**不删除**行与文件。
9. 写审计 `character_merge`，`detail` 记录转移/跳过数量。

> **补充约定（v1.4，Q3）**：第 7 步「把被合并角色的 active 资产改为 pending」与 §2.2.8 状态机冲突（不允许 `active → pending`）。实际执行改为：复制该资产为一条新的 `pending` 资产行（同 `storage_path/content_hash`，新 id），原 `active` 置 `superseded`；若保留角色无 `active`，新行在同事务晋级 `active`，否则等待作者采用。以本约定为准。

> 拒绝自动合并的硬线：`POST duplicates` 只读；恢复与 AI 确认流程在无显式 `mode` 时一律 409；导入无 `resolution` 时一律 409。

### 5.5 归档 / 恢复状态机：专属剧情节点与段落锚点

**归档**（`POST .../archive`）：

1. 锁角色行；已 `archived` → 若有扫描则返回 `{ changed:false, character, scan }`；若历史归档没有扫描（v1.1 前数据），补建一次扫描后返回（幂等，不重复扫描）。
2. `status='merged'` → 409 `CHARACTER_MERGED`。
3. 统计影响：关系数（两端涉及该角色）、成长事件数、**全书章节数**（扫描范围是全书正文，不再局限于成长事件关联章节）、**将隐藏的专属剧情节点数**（`exclusive_plot_nodes`，按 §2.2.14 判定预计算）。
4. 写 `status='archived'`、`archived_at/archived_by`；成长事件 `status='archived'`。
5. 插入 `character_archive_scans(status='pending', total_chapters, requested_by)`；唯一索引保证同角色同时只有一次扫描。
6. 提交事务后触发异步扫描（不阻塞归档响应），写审计 `character_archive`。

**专属剧情节点（独立于正文扫描）**：

- 归档**不写** `plot_nodes`、`plot_node_character_owners`、`plot_links`：专属节点隐藏完全由 §2.2.14 的读取期判定产生，条件为「该节点存在 `is_exclusive=true` 归属，且这些归属者全部为 `archived`」。
- 共享节点（无专属归属，或仅普通归属）永不隐藏；即使该角色是唯一关联者也一样。
- 多角色同标专属时，任一归属者仍 active 就不隐藏，避免误藏。
- 只隐藏节点本身，不级联子节点；子节点 `parent_id` 指向隐藏父节点时仍原样返回，前端按父节点隐藏做缩进兜底与弱提示（§6.5）。
- 正文扫描与节点隐藏是两条独立链路：扫描失败不影响节点隐藏，节点归属写入失败也不影响扫描；两者都不阻塞归档响应。
- 重复归档/恢复不产生节点写操作，天然幂等。
- 归档响应中的 `exclusive_plot_nodes` 只统计「归档后将变为 hidden」的节点；已有多角色共享的专属节点不计入。

**扫描（异步、分批、可重试）**：

```text
for 每批 50 章（按 volume/position 顺序）:
  1. 读章节 document → ensurePids() → 若发生 pid 变化则原地固化（不递增 version、不建快照）
  2. 提取 paragraph/heading 的 (pid, 纯文本)
  3. 文本与姓名/别名做精确匹配（归一化后 indexOf；不做语义/外貌判断）
  4. 每段每角色最多 1 条锚点：matched_name 取最长的命中名称，excerpt 截取命中附近 ≤120 字
  5. upsert character_text_anchors（唯一键 work+character+chapter+pid）：
     active → 刷新 excerpt/hash/scan_id
     dismissed → 保持 dismissed（不复活作者剔除的决定）
     invalid → 置回 active 并刷新 hash（重新命中）
  6. 更新 scanned_chapters / matched_paragraphs
失败：扫描置 failed + error，已写入锚点保留；前端显示失败与重试。
进程重启：启动时把遗留 pending/running 置 failed（可重试）。
```

性能预算：单章匹配 ≤ 20 ms（100 角色名 × 段落数的一次线性扫描），批间让出事件循环；扫描期间正文保存不受影响。扫描读到的是章节快照，若作者同时保存，读取时哈希校验会把失配锚点降级（见下）。

匹配与哈希口径（必须读写一致）：

- 匹配文本：对段落纯文本与姓名/别名统一做 `NFKC → 转小写 → 去空白与间隔符`（复用 `normalizeNameKey`），再做 `indexOf`；`excerpt` 仍从原始文本截取，保留作者可读的标点与大小写。
- `excerpt_hash`：对段落纯文本做 `NFKC → trim → 空白折叠` 后的 SHA-256；**不转小写、不去标点**，保证「改一个字」也能判定为 `text_changed`。
- 只做精确包含匹配，不做分词、拼音、同义词、性别/外貌推断；单字名可能产生较多误报，由作者在影响说明中剔除（见 §12.2）。

**剔除误报**（单条 / 批量）：

- 仅 `active` → `dismissed`，记录 `dismissed_at/dismissed_by`，**保留行**以便审计与后续扫描不复活。
- 重复剔除 → 200 当前状态（幂等）；对 `invalid` 锚点剔除 → 409 `CHARACTER_ANCHOR_NOT_DISMISSABLE`（不重复写、不伪造成功）。
- 写审计 `character_anchor_dismiss`（单条与批量分别记录数量）。

**编辑漂移与标记读取**：

```text
GET /chapters/:chapterId/role-marks
  1. 读该章 active 锚点（走 idx_character_anchors_chapter）与章节 document
  2. 建立 pid → 归一化段落文本 的映射
  3. 逐条校验：
     pid 不存在                → invalid(pid_missing)
     sha256(段落文本) ≠ hash   → invalid(text_changed)
     角色已恢复                → invalid(character_restored)
  4. 失效结果短事务持久化（幂等、best-effort，不阻塞响应）
  5. 输出：有效锚点 → paragraph_marks；
          该角色在本章存在失效锚点 → chapter_marks（label「关联角色已归档（原文已修改）」）
```

- 编辑失配只影响该段：同章其他仍命中的段落继续显示段落标记；失效段落不重新锚定、不误标新段落（D25）。
- 段落被删除 → `pid_missing`；段落被拆分 → 前半段 pid 保留但文本变化 → `text_changed`；后半段无锚点，不误标。
- 归档后新增的、再次提到角色的段落：本期不实时监听，不产生锚点；仅在手动重新扫描（`POST archive-scans`，归档影响说明中的「刷新命中」按钮）时更新。重复归档不自动重扫（幂等），F1 所述「下次归档影响说明」通过该刷新入口落地（F1 已知限制）。
- 标记只表达状态，不降低正文可编辑性（D14/D27）；不改文字、不产生章节版本、不进入修订集。

**恢复**（`POST .../restore`）：

1. 锁角色行；已 `active` → 幂等返回 `{ changed:false, character }`。
2. `status='merged'` → 409（不提供反向合并）。
3. 计算疑似重复候选（§5.4），**不合并**。
4. `status='active'`、清空归档字段；成长事件恢复 `active`。
5. 该角色 `active` 锚点批量置 `invalid(character_restored)`；`dismissed` 保持 `dismissed`（保留作者剔除决定，重新归档也不复活）；若有 `pending/running` 扫描，置 `failed` 并通知批次中止（批次写入前复查角色状态）。
6. 专属剧情节点归属不改；判定重新满足「存在 active 归属者」，读取时原样复现，不重建、不删除（D31）。
7. 写审计 `character_restore`；**正文零写入**，标记查询因角色非归档而返回空（D15/D26）。

**幂等与并发**：

| 场景 | 行为 |
| --- | --- |
| 重复归档 | 返回既有扫描与影响摘要，`changed:false`，不新增扫描行 |
| 归档与恢复并发 | 锁角色行串行化；后到者看到新状态并按幂等返回或 409 |
| 重复剔除 | 200，不重复写审计 |
| 重复恢复 | 200 `{ changed:false }` |
| 扫描中恢复 | 扫描置 failed（`character_restored`），后续批次跳过 |
| 扫描中再次归档 | 唯一运行索引冲突 → 返回既有扫描，不重复 |

**「个人剧情」定义（F1 v1.3 已确认）**：个人剧情 = 该角色的 `character_growth_events`（含关联的剧情节点与章节引用）＋ 作者显式标记为专属的剧情节点（`plot_node_character_owners.is_exclusive=true`）。专属节点在归档时仅从正式剧情树读取结果中过滤掉节点本身，`plot_nodes` 行、`parent_id`、`sibling_order`、`plot_links` 一律不变，不级联隐藏子节点；共享节点（无专属归属）永不隐藏。该口径已写入 §2.2.14 与 §5.5，不再作为待确认项。

### 5.6 头像生成与同步

**链路**：

```text
POST avatar/generations
  → 校验作品/角色归属、工具 character_avatar_generate 启用
  → 同一角色已有 running 任务 → 409 CHARACTER_AVATAR_BUSY
  → 插入 ai_tasks(scope='character', tool='character_avatar_generate',
       input_summary={character_id, name, identity, personality, race})
  → 入队，返回 202 + task

worker (scope='character' + 该 tool)
  → CharacterModelProvider.generateAvatar(ctx) → { mime, bytes, width, height }
  → 校验 mime 白名单与 ≤ 1MB → 计算 sha256 → 写文件（临时文件 + rename）
  → 事务：插入 asset(status='pending', task_id) + succeeded 事件 + 审计
  → 失败：任务 failed，不写 asset；旧 active 资产原样保留
```

**幂等**：`ai_tasks.idempotency_key = character-avatar-${character_id}-${request_nonce}`；处理器写 asset 前按 `task_id` 查重，重复回调直接返回既有 asset。

> **补充约定（v1.4，Q3）**：状态机与超时口径以 §2.2.8 补充约定为准；本节「生成任务」不再有 `active → pending` 的隐式回退，合并场景的资产复制见 §5.4 补充约定。影响任务：T33、T38。

**采用**（`POST avatar/adopt`）：

1. 锁角色与目标资产；资产必须属于该角色且 `status='pending'`，否则 409 `CHARACTER_AVATAR_NOT_ADOPTABLE`。
2. 旧 `active` → `superseded`；目标 `pending` → `active`；`characters.avatar_asset_id` 指向目标；`characters.version + 1`。
3. 写审计 `character_avatar_adopt`。

**同步**：版图节点、列表、详情、归档视图都只读 `characters.avatar_asset_id` 与资产元数据，因此天然一致（D11）；前端 `<img>` 使用 `content_url` + `ETag`，更新后 URL 带 asset_id 以避免缓存旧图。

**多端呈现**：节点头像 48×48、列表 32×32、详情 160×160；加载失败显示姓名首字占位（不显示虚假成功）。

### 5.7 AI 角色 / 关系候选生成与合并

**发起**（`POST character-ai/drafts`）：

1. 校验作品归属、草稿唯一性（同作品同 `kind` 不得有 `pending`）。
2. 构造上下文：
   - `source=chapter`：读取章节，`documentToMarkdown(chapter.document)` 截断至 8,000 字；
   - `source=work`：按 `position` 拼接章节 Markdown，单章 ≤ 4,000 字、总量 ≤ 40,000 字，超出部分记录 `summary.truncated=true`；
   - 附带现有角色名册（`name + aliases`，最多 100 条）用于模型避重与疑似重复提示。
3. 插入草稿（`status='pending'`）与 `ai_tasks(scope='character', tool='character_extract')`；`input_summary` 只放 `draft_id/kind/source/chapter_id/字符数`，不放正文全文。
4. 入队，返回 202。

**任务完成**（`CharacterTaskHandler`，单事务）：

1. 锁草稿与任务；任务必须 `running` 且 `draft.task_id` 匹配，否则跳过（幂等）。
2. 校验模型输出 → 归一化为条目：
   - 角色条目：`payload` 为 13 项资料；计算 `name_key` 与 `suspected_duplicates`；
   - 关系条目：两端 `ref` 必须为该草稿的已产出角色条目或现有角色；类型按 `type_code` 映射，未知类型落到「其他」并在 `summary` 提示；
   - 成长条目：`character_ref` + 事件内容；`plot_node_id/chapter_id` 必须存在（否则置空并记 warning）。
3. 写 `raw_payload`（可选）、`summary`（数量、重复数、丢弃数）、items（`pending`）、草稿 `succeeded`。
4. 若候选为空：草稿 `succeeded` + `summary.empty=true`，不创建任何正式数据。

**确认单条**（`confirm`，幂等）：

1. 锁 item 与草稿；草稿必须 `succeeded`（`committed` 时已确认条目仍可幂等返回）。
2. item 已 `confirmed` → 返回 `resolved_entity_id`（200，不重复写入）；已 `rejected/skipped` → 409 `CHARACTER_AI_ITEM_RESOLVED`。
3. 依赖检查：`dependencies` 中的条目必须已确认或已映射现有实体，否则 409 `CHARACTER_AI_DEPENDENCY_UNRESOLVED`。
4. 重复决策：`suspected_duplicates` 非空且未给 `mode` → 409 `CHARACTER_DUPLICATE_DECISION_REQUIRED`；`mode='merge'` 必须给 `target_character_id` 且属于该作品。
5. 写入：
   - `create`：新建角色（`origin='ai'`）/关系（`origin='ai'`）/成长事件；
   - `merge`：把候选字段并入目标角色（仅填充空字段，不覆盖作者已填内容；别名追加），**不修改正文**；
   - 关系确认时如唯一键冲突 → 视为已存在，返回既有关系 id（幂等）。
6. item → `confirmed`、`resolved_entity_id`、`resolved_at`；写审计 `character_ai_item_confirm`。
7. 全部条目非 `pending` 时草稿自动 `committed`。

**拒绝 / 丢弃**：拒绝只改 item 状态；丢弃只改草稿状态，已确认条目**不回滚**（F1 无回滚要求，且避免误删作者已确认内容）。

### 5.8 成长线 AI 候选

- 工具 `character_growth_extract`，上下文 = 选定章节文本（或最近 N 章）+ 选中角色的资料摘要 + 已有成长事件标题列表（用于避重）。
- 输出条目 `kind='growth'`，`character_ref` 可为：
  - `existing`：角色 id（作者在发起时选定的角色，优先）；
  - `item`：同草稿内角色条目（若同时生成角色）。
- 确认规则与 §5.7 一致；确认后写 `character_growth_events`（`origin='ai'`），返回 `chapter_id/plot_node_id` 以便前端立即跳转。
- 拒绝的候选不进入成长线；生成失败保留既有成长线与正文（F1 §4.1）。

### 5.9 导入 / 导出流程

**导出**：

1. 校验作品归属；按 `characters(status IN active, archived)` 导出（`include_archived` 默认 true），`merged` 不导出。
2. 关系类型只导出被使用/自定义的类型；关系只导出两端均在导出集合内的（悬空关系在结构上不可能出现）。
3. 成长事件导出 `plot_node_title` 与 `chapter_title` 作为人类可读线索（导入时按标题无法可靠匹配，故导入**忽略**这两个字段，仅保留文本）。
4. 视图导出名称、筛选与已排布坐标（未排布不导出）。
5. 同作品备份（`include_anchors=true`，默认 true）导出 `anchors`：只含 `active/dismissed` 锚点，且只覆盖本次导出的角色；字段为 `character_local_id/chapter_id/paragraph_pid/excerpt/status`；不含 `excerpt_hash`，不含正文全文。`include_archived=false` 时归档角色的锚点同步不导出。
6. 响应 `Content-Disposition: attachment; filename="character-board-<workId>.json"`；写作业 `kind='export'`，`summary` 记录角色/关系/锚点数量。

**导入**：

1. `preview`：校验 schema/体积/数量/引用/自关联/类型/锚点 → 归一化比对现有角色 → 返回 `conflicts` 与 `preview_job_id`；不写任何业务表。`work.id` 与目标不一致时，`summary.cross_work=true`，并预告锚点将全部丢弃。
2. `commit`：
   - 校验 `preview_job_id` 存在且属于该作品、`idempotency_key` 未重放（重放返回首次作业结果）；
   - `mode='merge'`：保留现有数据，按 local_id 新建/合并；`mode='replace'`：要求 `confirm_overwrite=true`，事务内清空该作品角色域数据（角色/别名/关系/成长事件/视图/锚点；头像资产与文件保留但解除指针），再写入文件内容；
   - 每个重复角色按 `resolutions` 执行；缺失 resolution → 409（不猜）；
   - 关系去重：按目标 id + `pair_key` + `type_id` 判重，重复跳过并计数；
   - 视图重名：merge 模式改名「原名 (导入)」；
   - **锚点**：仅同作品、`chapter_id` 存在、`paragraph_pid` 在目标章节正文中存在时还原；跨作品或 pid 不存在一律丢弃（`summary.discarded_anchors`）。**跨作品导入不把任何来源 pid 写入正文**，需要生成正文片段时一律 `newPid()`；
   - 完成后写作业 `kind='import_commit'`、`status='succeeded'`、`summary`；写审计 `character_import_commit`。
3. 任意一步失败 → 事务回滚，作业记 `failed` + `error`，现有数据不变。

### 6.3 状态管理

- 采用与 `plot-state.ts` 相同的 Provider + Context 模式：`CharacterStoreProvider` 持有 `view/characters/relations/relationTypes/layout/version`；
- 读：进入 `roles` 页签时才加载（`enabled` 标志），不影响正文首屏；
- 写：先调用 API，成功后局部合并；409 版本冲突时提示「资料已被更新」并提供「刷新并重试」，不静默覆盖；
- 筛选：前端内存过滤（`useMemo`），URL 只保存 `viewId` 与选中角色，不保存草稿级状态；
- 布局：拖拽中只改本地坐标，`pointerup` 后批量提交；失败回滚到提交前快照。

### 6.4 与正文编辑器并存

- 角色页签与正文页签共用同一三栏壳；切换页签不卸载编辑器、不重置滚动位置、不打断自动保存；
- 成长线跳转章节：`navigate('/works/:workId/write/:chapterId?tab=roles&panel=role&characterId=...')`，返回时仍回到角色页签与同一角色；
- 角色面板不监听全局快捷键；所有快捷键仅在画布/列表容器聚焦时生效，避免抢占正文输入（D20）；
- 正文编辑器只叠加**装饰层**：不插入、不删除、不改写文档节点，不触发 `onDocument`，不参与保存队列。

#### 6.4.1 编辑器内段落标记

| 项 | 方案 |
| --- | --- |
| 渲染机制 | ProseMirror `Decoration.node(pid 对应段落, { class: 'role-archived-mark' })` + `Decoration.widget(段落起始, 标签)`；装饰只影响 DOM，不进入 `editor.state.doc`，因此不产生事务、不触发保存 |
| 数据来源 | `ProseMirrorEditor` 新增 `roleMarks?: { pid, label }[]` prop；内部插件按 `pid` 从 `state.doc` 解析位置，用 `setProps({ decorations })` 更新；文档变更后插件从 `state.doc` 重新解析，不重建 EditorState |
| 只读/编辑态 | `editable=false` 与 `editable=true` 均显示装饰；编辑态下装饰随段落移动自动跟随，输入不中断 |
| 失效兜底 | `chapter_marks`（整章兜底）显示在编辑器顶部状态条，使用 `role="status"`，文案「关联角色已归档（原文已修改）」；不覆盖正文、不遮挡输入区 |
| Markdown 模式 | `markdown-editor.tsx` 为 textarea，无法逐段装饰；在编辑器上方渲染「本章命中段落」列表（含摘录与剔除按钮），作为等价路径 |
| 性能 | 装饰集合只在 `roleMarks` 变化或文档变化时重算；100 段以内 O(n) 匹配，输入路径零额外请求 |

#### 6.4.2 归档影响说明（可剔除列表）

- 归档确认弹层分三段：关系/成长事件影响摘要 → 扫描进度（进行中/失败可重试，不显示「已完成」）→ 命中段落列表；
- 列表每条展示「章节名 + 段落摘录 + 命中名称」，提供复选框、全选、批量剔除；键盘可达（Tab/空格/Enter），不依赖颜色；
- 剔除后立即从列表移除并显示「已剔除 N 条」；失败提示可重试，不假装成功；
- 同一角色重新扫描后，已剔除条目不会复活；新命中条目追加到列表顶部并高亮「新增」。

### 6.5 版图渲染与交互

- 容器 `transform: translate(pan) scale(zoom)`，只作用于内层；拖拽/缩放不触发角色卡重渲染（与 M3c-1 一致）；
- 角色卡：`React.memo`，依赖 `id/name/avatar/status/selected`；
- 连线：父级一次计算所有路径，有方向加 `marker-end`，无方向不加；线型来自 `line_style`；
- 着色：`color` 仅用于描边；标签 chip 始终显示 `tag`；选中/归档使用图标 + 文案 + 边框，不只靠颜色；
- 拖拽边界钳制 ±1,000,000；缩放 0.25~2，提供「适应视图/复位」；
- 触屏：Pointer Events 统一处理，移动端提供列表为主视图（见 §6.6）。

#### 6.5.1 剧情树的「显示归档角色剧情」开关

- 位置：剧情页签工具栏；原生 `<input type="checkbox" role="switch">` + 可见文字标签「显示归档角色剧情」，支持 Space/Enter，状态不只靠颜色（开启时文字变「隐藏归档角色剧情」）。
- 数据：开关切换时请求 `GET /plot-tree?includeArchivedOwner=true|false`；关闭为默认行为。开关状态按作品写入本地偏好（`localStorage: sf:plot:includeArchivedOwner:<workId>`），不写服务端、不写入作品文档；深链可用 `?includeArchivedOwner=1` 覆盖并同步本地偏好。
- 节点：关闭时隐藏节点不渲染；其子节点仍渲染（不级联隐藏），若 `parent_id` 属于隐藏集合，在列表/画布上标注「父节点属于归档角色剧情」并退化为顶层缩进，不改变真实 `parent_id`。
- 连线：两端都隐藏 → 不渲染；仅一端隐藏 → 保留连线，用虚线 + 标签「归档角色剧情」指向 `archived_owner_nodes` 提供的坐标 stub，避免结构突然消失；开关打开后恢复实体节点与实线。
- 恢复角色后重新拉取（或开关切换）即恢复原样；不在前端本地重建节点。
- 归属设置入口：节点详情抽屉内「归属角色」多选 + 「专属」复选框；保存调用 §4.9 `PUT owners`，失败回滚本地选择并提示错误。

### 6.6 可访问性

- 画布节点使用 `<button>` 语义，可访问名 = 「姓名，身份，状态」；关系用 `<g role="img" aria-label="{label}，{有方向/无方向}">`；
- 列表视图 `role="grid"`（或 `table`）承载全部角色与关系，支持方向键移动、`Enter` 打开详情、`Delete` 触发确认；作为读屏与纯键盘用户的主路径；
- 归档标记 `role="status"`，文字为「关联角色已归档」，可被读屏播报；段落标记同时提供 `aria-describedby` 指向段落摘录，避免只靠视觉样式；
- 归档影响说明的段落列表使用 `role="group"` + 复选语义，支持全选/反选/批量剔除的键盘操作；
- 「显示归档角色剧情」开关使用 `role="switch"` + 可见文字，键盘 Space/Enter 可切换；隐藏节点/父节点归档提示均带文字与图标，不只靠颜色或线型；
- 弹层使用原生 `<dialog>` + 焦点陷阱 + 关闭后焦点归还；
- 四档视口（375/768/1024/1440）：窄屏画布折叠为列表 + 抽屉详情，页面不出现横向滚动；
- 浅色/深色主题下角色卡、连线、标签、归档标记均需通过对比度检查（design-tokens 提供语义色）。

### 6.7 性能手段（100 角色 / 150 关系）

| 手段 | 说明 |
| --- | --- |
| 一次读全 | `board` 单请求返回成员/关系/类型/布局，避免串行请求 |
| 内存筛选 | 关键词 + 六维在 `useMemo` 中完成，100 条过滤 < 5 ms |
| 渲染隔离 | 角色卡 memo、连线父级一次计算、拖拽只改 transform |
| 批量写 | 拖拽结束一次 `PUT layout`，不逐节点请求 |
| 头像懒加载 | 列表使用 `loading="lazy"` + `decoding="async"` |
| 无虚拟化 | 100 节点不引入虚拟列表；列表视图超过 300 行再评估 |
| 锚点查询 | `role-marks` 单章查询走 `(work_id, chapter_id, status)` 复合索引，只返回有效锚点与兜底摘要；与章节加载并行发起，不阻塞首帧 |
| 剧情过滤 | 隐藏集合按作品一次查询归属索引（`work_id, character_id, is_exclusive`）后内存求交，100 节点/23 类规模下 O(n)；不逐节点查库；作品无归档角色时跳过归属查询（快速路径），默认响应零额外开销 |
| 扫描分批 | 每批 50 章、批间让出事件循环；单章匹配目标 ≤ 20 ms；扫描进度独立轮询，不挂在正文保存链路上 |
| 标记装饰 | 装饰集合按 `pid` 预索引为 `Map`，文档事务内查找 O(1)；不在输入路径发请求 |
| 预算测量 | 前端用 `performance.mark/measure` 记录「进入页签 → 首帧」「筛选 → 首帧」「章节打开 → 正文可编辑」与「标记渲染完成」，E2E 断言正文可编辑 < 1000 ms |

## 七、安全与权限

| 风险 | 措施 |
| --- | --- |
| 未登录访问 | 全部端点挂 `SessionGuard`；SSE 沿用既有任务流鉴权（`work_id` 归属） |
| CSRF | 所有写操作挂 `CsrfGuard`；前端 `apiRequest` 自动带 `x-csrf-token` |
| 越权读取/写入 | 每个接口先 `assertOwnedWork`；角色/关系/视图/成长事件/草稿再校验 `work_id` 一致；跨作品一律 404 |
| 跨作品引用 | 关系两端、成长事件章节/剧情节点、节点归属角色、AI 目标角色、导入 `target_character_id` 均校验同作品 |
| 节点归属越权 | 归属接口继承剧情模块 `assertOwnedWork`；节点必须属于该作品剧情树、角色必须属于同一作品且 active；不允许通过归属接口修改 `plot_nodes` 内容或层级 |
| 批量接口放大 | 成员/布局/批量确认限制数量（500/50），超出 422 |
| 注入 | Zod `.strict()` + 受控字段；所有文本按纯文本处理，前端用文本节点渲染，不注入 HTML |
| 头像文件 | 路径由服务端生成（哈希命名），不接受客户端路径；读取前校验归属；`nosniff` + CSP `sandbox`；前端只用 `<img>`，不用内联 SVG |
| 导入内容 | 体积 ≤ 2 MB、数量上限、未知字段拒绝；导入文本永不写入正文文档；导入的 pid/锚点不跨作品复用 |
| 锚点内容 | 只存 ≤120 字摘录，不存段落全文；接口不返回 `excerpt_hash` 与 `matched_name` 之外的正文信息；审计不记录正文 |
| pid 完整性 | 保存/AI 修订/回滚/导入入口统一 `validateDocumentPids`；非法格式与重复一律 422，防止恶意步骤制造重复锚点 |
| 扫描放大 | 单角色同时仅一次扫描（唯一运行索引）；扫描只读、分批；重新扫描仅限已归档角色，避免高频触发 |
| 审计泄露 | `detail` 不含正文全文、头像二进制、模型密钥；错误信息不回显 SQL/堆栈 |
| 限流 | 复用全局策略；AI 发起类接口额外按作品去重（同作品同 kind 仅一份 pending 草稿） |
| 归档安全性 | 归档不产生删除；不提供 purge 端点；`merged` 为终态且不可恢复，避免误操作 |

头像 MIME 白名单：`image/png`、`image/svg+xml`。SVG 仅允许作为 `<img>` 资源加载，响应头固定 `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` 与 `X-Content-Type-Options: nosniff`；若后续接入真实图像模型，优先产出 PNG。

## 八、幂等与一致性

### 8.1 幂等键与重复提交

| 操作 | 幂等机制 | 重复调用结果 |
| --- | --- | --- |
| AI 草稿发起 | `UNIQUE (work_id, idempotency_key)` + 同作品同 kind 仅一份 `pending` | 409 `CHARACTER_AI_DRAFT_RUNNING`，不重复入队 |
| AI 条目确认 | item 行锁 + `status` 状态机 + `resolved_entity_id` | 已确认 → 200 返回首次实体 id |
| AI 条目拒绝 | 状态机 | 已拒绝 → 200 返回当前状态 |
| 关系创建 | `UNIQUE (work_id, pair_key, type_id)` | 409 + `existing_id`（不静默覆盖） |
| 归档 / 恢复 | 状态判断 + 行锁 | 已是目标状态 → 200 `{ changed:false }`，不重复写审计 |
| 归档扫描 | `(character_id) WHERE status IN ('pending','running')` 唯一索引 | 已有进行中扫描 → 返回既有扫描（手动发起为 409 `CHARACTER_SCAN_RUNNING`） |
| 剔除锚点 | `status='dismissed'` 状态机 | 重复剔除 → 200 当前状态，不重复写审计 |
| 节点归属设置 | `UNIQUE (node_id, character_id)` + 整组替换 | 重复 PUT 同一组结果一致；DELETE 不存在 → 404 |
| 视图布局 | 按 `character_id` upsert，未知成员忽略 | 200 `{ updated }` |
| 导入 commit | 作业表 `(work_id, kind, idempotency_key)` 唯一 | 重放返回首次作业摘要，不重复写入 |
| 头像生成 | `ai_tasks.idempotency_key` + 处理器按 `task_id` 查重 | 重复回调返回既有资产 |
| 头像采用 | 资产状态机 | 已 active → 200；非 pending/superseded → 409 |

> **补充约定（v1.4，Q4）**：节点归属的「整组替换」以 §4.9 补充约定为准——差异更新，归档角色归属行不因 PUT 省略而删除。影响任务：T30、T44。

### 8.2 并发编辑冲突

- 角色资料：`expected_version` 与 `characters.version` 不等 → 409 `CHARACTER_VERSION_CONFLICT`（`details.current_version`）。
- 视图设置：`expected_version` 与 `character_views.version` 不等 → 409。
- 关系：以唯一键为准；并发创建同一关系时数据库冲突 → 409 + 既有 id。
- 布局：按行最后写入生效（`updated_at` 更新），不返回冲突；多个客户端同时拖拽同一角色时以最后一次为准（本期无多人协同，F1 §2.2-2）。
- 合并与归档并发：两行按 id 排序加锁；先到者生效，后到者看到新状态并按幂等规则返回或 409。
- **补充约定（v1.4，Q6）**：AI 候选确认的 `expected_version` 只校验「该角色记录的 `characters.version`」，不校验作品或章节版本。仅 `mode='merge'` 且提供 `target_character_id` 时生效：不一致 → 409 `CHARACTER_VERSION_CONFLICT`（`details.current_version`），提示刷新后重试，不静默覆盖；`create` / `keep_independent` 无目标角色，携带 `expected_version` → 422 `CHARACTER_VERSION_NOT_APPLICABLE`。影响任务：T29、T42。

### 8.3 数据一致性不变量

1. `characters.avatar_asset_id` 指向的资产必须是同角色、`status='active'`（同事务维护）。
2. 每个角色至多一条 `active` 资产（部分唯一索引保证）。
3. 关系两端必须属于同一作品且 `source_id <> target_id`。
4. 同一对角色同一类型至多一条关系（`pair_key + type_id`）。
5. 归档角色的成长事件必须全为 `archived`；恢复后必须全为 `active`（同事务）。
6. `merged` 角色不得再出现在任何视图成员、关系端点或成长事件归属中（合并事务转移）。
7. AI 草稿的 items 只有在草稿 `succeeded` 后才可确认；确认幂等。
8. 角色域操作不改变正文文字；归档扫描只允许补齐 `pid`，且补齐前后 `canonicalizeContent` 完全一致、`chapter.version` 与 `content_hash` 不变。
9. 同一章节内 `pid` 唯一；锚点 `(work_id, character_id, chapter_id, paragraph_pid)` 唯一。
10. 锚点 `status='active'` 的必要条件：角色为 `archived`、段落 pid 存在、段落文本哈希等于 `excerpt_hash`；任一不满足即失效。
11. 恢复角色后，该角色不存在 `active` 锚点，标记查询必为空。
12. 专属节点隐藏仅由读取期判定产生；`plot_nodes.parent_id/sibling_order`、`plot_links` 不因归档改变。
13. 节点的 `is_exclusive` 归属若存在任一 active 角色，则该节点永不被归档过滤隐藏。

### 10.2 跨模块回归面（正文契约 + 剧情归属）

`pid` 进入正文后，所有读写 `chapters.document` 或依赖 `content_hash` 的已交付模块都必须回归；节点归属扩展后，剧情树的读取/写入/导入/连线渲染也必须回归。现有代码事实：`content_hash = sha256(canonicalizeDocument(document))`（[chapter-save.service.ts](../../../apps/api/src/writing/chapter-save.service.ts)），`version_snapshots.document` 为完整 JSONB，`version.service` 的 diff 只比较 `type/text`，`ai-result.mapper.ts` 用整篇 `ReplaceStep`，`plot-generation.service.ts` 用 `documentToMarkdown` 读取正文，[plot-tree.service.ts](../../../apps/api/src/plot/plot-tree.service.ts) 的 `getTree` 一次返回 nodes/links/groups。

| 模块 | 依赖点 | 为何需要回归 | 验证点 |
| --- | --- | --- | --- |
| M1 章节保存 | `applyOperations` + `canonicalizeDocument` + `content_hash` | pid 会改变规范化字符串；若哈希不忽略 pid，会误判正文变化 | 纯 pid 补齐保存后 `version`/`content_hash` 不变；正文编辑仍正常递增；重复 pid 422 |
| M1 版本快照 | `version_snapshots.document` 全量 JSONB | 旧快照无 pid，新快照有 pid，回滚必须兼容 | 读取旧快照不报错；回滚应用后 pid 齐全；快照数量不因 pid 补齐增加 |
| M2 变更协作 / 审批 diff | 操作集应用、`compareNodes/flattenText` | diff 若把 attrs 计入会产生噪声；接受/拒绝后的锚点可能失效 | 审批预览无 pid 差异；接受/拒绝/回滚后锚点按哈希降级；操作集仍可重放 |
| M3a AI 写正文 | `replaceDocumentOperations` 整篇替换 | 整篇替换会丢弃所有 pid，导致全章锚点失效 | `preservePids` 保留未改段落 pid；改写段落换新 pid 并降级；AI 修订集幂等 |
| M3c-1 剧情自动建树 / 读正文 | `documentToMarkdown(chapter.document)` | Markdown 转换必须忽略 attrs，且不因 pid 改变输出 | 同一正文加 pid 前后 Markdown 完全一致；剧情候选生成不受影响 |
| 剧情导入 / 正文导入 | `markdownToDocument` | 导入必须补齐 pid，且不重复 | 导入后每段有唯一 pid；再次导入不产生重复 pid |
| 角色导入导出 | 锚点与 pid 跨作品 | 来源 pid 不可写入目标作品 | 跨作品导入锚点丢弃；目标正文 pid 全部由本作品生成 |
| Markdown 双向编辑 | `documentToMarkdown` / `markdownToDocument` | 往返不得丢文字或把 pid 写进 Markdown | 往返文本逐字一致；Markdown 中无 pid；切回富文本后重新分配 pid |
| 撤销 / 重做 | ProseMirror history | 历史栈中的 pid 必须随步骤恢复，不能重复 | 撤销拆分后 pid 唯一；重做后锚点仍能按哈希命中或正确降级 |
| 编辑器同步 | `prosemirror-editor.tsx` 的 `canonicalizeDocument` 比较 | pid 差异会导致无意义重置、光标丢失 | 仅 pid 变化不重置 EditorState；正文变更正常同步 |
| M3c-1 剧情树读取 | `plot-tree.service.getTree` + `plotTreeResponseSchema` | 新增 `includeArchivedOwner`、`owners`、`archived_owner_nodes` 不得改变默认响应 | 默认查询的 nodes/links/groups 与改造前逐字段一致；显式 true 才返回全部节点 |
| 剧情节点增删改 / 移动 | `plot_nodes` CRUD、`moveNode`、`assignGroup` | 归属与隐藏不得写入或篡改层级/排序；删除节点需级联清理归属 | 增删改移动行为不变；删除节点后归属行同步消失；隐藏节点仍可被 API 编辑 |
| 剧情导入 | `importPlotTreeRequestSchema` + `importTree` | 导入格式不携带归属，不得因旧数据产生悬空归属 | 导入后新节点 `owners=[]`；导入前后归属行数不变（除节点删除级联） |
| `plot_links` 渲染 | 前端 links 过滤 + 隐藏集合 | 连线隐藏规则错误会破坏结构或误连 | 两端隐藏才隐藏；单端隐藏显示 stub；开关打开后连线完全恢复 |

## 十一、技术选型与权衡

### 11.1 版图渲染方案

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. SVG 连线 + 绝对定位 DOM 卡片（推荐） | 与 M3c-1 剧情画布一致；卡片可直接承载头像/文本/按钮，天然可访问；100 节点性能足够 | 需自行实现布局、命中测试、连线路径 |
| B. Canvas 2D 绘制 | 大量节点更快；绘制自由 | 无障碍与文本选择差；需维护命中检测与 DPR 缩放；无法直接使用 DOM 组件 |
| C. 图库（React Flow / Cytoscape） | 内置拖拽、缩放、布局、边路由 | 新增依赖与样式体系；与现有工作台视觉/交互不一致；包体积与可访问性需额外适配 |

**决策 A**。理由：验收规模仅 100/150，瓶颈在数据加载而非绘制；DOM 卡片对 D12/D20 的可访问性与冗余表达最直接。代价通过「memo + transform + 批量坐标」控制。

### 11.2 头像生成与存储方案

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 本地文件目录 + 元数据表（推荐） | 二进制不膨胀数据库；可用 ETag/immutable 缓存；备份=目录 + 数据库 | 部署需持久化卷；多实例需共享存储（本期单实例） |
| B. 数据库 `bytea`/base64 | 部署最简单，备份一体 | 行体积大、查询与备份变慢；100 张×数百 KB 即明显；连接池压力 |
| C. 对象存储（S3/OSS） | 可扩展、CDN 友好 | 本期无云资源与凭据管理；增加环境依赖与测试复杂度 |

**决策 A**，存储根通过 `CHARACTER_AVATAR_DIR`（默认 `apps/api/var/character-avatars`）配置，内容哈希命名，文件写入用「临时文件 + rename」。失败降级：不写元数据、旧 active 保留。代价：部署文档需说明目录持久化；本地开发自动创建目录。

### 11.3 导入导出格式

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 版本化 JSON（推荐） | 可无损表达关系、视图、别名与布局；与 `packages/contracts` 共用校验；版本可演进 | 非技术作者不可直接编辑；文件较大 |
| B. CSV 多文件包 | 可用 Excel 编辑 | 关系/视图/多值字段需多文件与自定义编码；易产生悬空引用；校验成本高 |
| C. Markdown + Front-matter | 人类可读 | 无法稳定表达关系图与视图布局；解析歧义大 |

**决策 A**。代价通过「preview 冲突报告 + 人类可读 summary + 导出文件名含作品」缓解；不承诺与旧 Flask 格式互通（M4 另行设计）。

### 11.4 其他取舍

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 视图成员：显式 vs 按筛选动态 | 显式成员 + 可选筛选辅助批量加入 | 新角色不会自动进入所有视图，需要「一键加入」；换来布局稳定与可预期的版图 |
| 关系隐藏：落库 vs 派生 | 派生（按角色状态过滤） | 读取多一个 join 条件；换来无需双写与恢复零漂移 |
| 专属节点隐藏：读取期过滤 vs 写 `plot_nodes` 状态 | 读取期过滤 | 查询多一次归属集合计算；换来不改层级/连线、恢复零写入且节点不重建 |
| 疑似重复：持久化 vs 实时计算 | 实时计算 + AI 条目内快照 | 每次全量分组查询；100 角色规模可忽略 |
| 导入执行：同步 vs 队列 | 同步事务 + 作业表 | 大文件会占用请求；用 2 MB/500 条上限约束 |

### 11.5 段落锚点方案

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| A. 正文块节点 `pid` + 归档扫描锚点表（选定） | 段落移动/重排仍可定位；删除与改写可区分；读取一次即可判定；不依赖正文外挂扫描结果 | 改动正文契约；所有正文生产方需补齐/保留 pid；`content_hash` 必须忽略 pid；约 +50 字节/段 |
| B. 独立指纹表（存文本哈希 + 上下文指纹） | 正文零改动 | 排版重排即失配；重复段落与短句误配；编辑后无法区分「改写」与「移动」；仍需全量扫描 |
| C. 读取时实时扫描正文 | 无存储、无契约改动 | 每次打开章节全量匹配，100 角色 × 全书正文不可控；无法保留作者剔除决定；无法表达「原文已修改」 |

**决策 A**（F2 前已确认）：`pid` 是唯一能同时满足「段落级精度、编辑后不误标、恢复零写入、打开 1 秒」的方案。代价集中在契约与回归面（§3.6、§10.2）：通过 `canonicalizeContent` 忽略 pid、保存时补齐、Markdown 丢弃/重建、跨作品重分配来隔离影响。B/C 不作为主方案，仅在风险节保留为未采用备选。

| 开关状态跨设备不一致 | 用户疑惑 | 开关是本地偏好（按作品 localStorage），不写作品数据；深链 `includeArchivedOwner` 可显式覆盖；界面文案说明「仅本机」 |

### 12.3 明确不做的设计

- 不引入图数据库、图算法库或协同编辑框架；
- 不做 WebSocket，AI 进度继续用 SSE；
- 不做角色级权限、多人实时协同、在线状态；
- 不做旧 Flask 角色数据映射与双写；
- 不做归档角色的永久清理与回收站；
- **不把角色/关系/归档状态写入正文**；正文只增加无业务语义的 `pid`，标记由锚点表 + 编辑器装饰层表达，且不新增章节版本来承载标记；
- 不做实时监听正文新增段落、语义/外貌识别、基于向量或指纹的模糊匹配；
- 不在本期接真实 Coze/图像模型 Provider。
