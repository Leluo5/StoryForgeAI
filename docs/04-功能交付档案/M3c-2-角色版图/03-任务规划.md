层间硬约束：

1. **L0 未冻结，L1 不动手**：字段、枚举、错误码与文件格式先定，避免迁移返工。
2. **L1 未回滚验证，L2 不写事务**：迁移必须同时验证 up 与 down，空库与存量库各一遍。
3. **L2 未通过真实库集成，L3 不接 controller**：尤其是归档、合并、扫描、导入四类多表事务。
4. **L3 未闭环，L4 不做真实联调**：前端可先用契约类型与 mock 推进 T31/T32，但 T33 之后依赖真实 board / role-marks 响应。
5. **L5 不替代各层自测**：回归任务验证的是「跨模块影响」，不能用来补做本层单测。

| 职责 | 让内容哈希与文档比较忽略 pid，并在 Markdown 双向转换与整篇替换中落实「导出丢弃、导入重建、未改段落保留」。 |

## 九、待澄清

> 以下仅为 F3 在任务拆解中发现的**实现层面无法自洽**之处，登记备查；不修改 F1 需求结论与 F2 技术方案结论，不在本阶段自行拍板。

### Q1 pid 版本形态冲突

- **位置**：F2 §3.6.1 规定 pid 为「小写 UUID v4」；§3.6.2 规定历史正文惰性补齐使用 `uuidv5(chapter_id, ...)`。
- **冲突**：格式规则锁定 v4，但存量补齐算法产出 v5；若校验强制 v4，旧文档惰性补齐会被拒绝。
- **影响任务**：T01、T02、T18、T48。
- **建议处理**：F4 前确认校验口径为「UUID 格式 + 小写 + 唯一」，不锁定版本号；或把 §3.6.1 的 v4 表述改为「UUID v4 或 v5」。
- **状态**：已澄清（F2 v1.4 附录 A / §3.6.1、§3.6.2）——统一 UUID v4 随机生成，v5 算法作废。

### Q2 新作品的关系类型种子时机未定义

- **位置**：F2 §2.1 迁移 `1760500002000` 只为**已有作品**补默认关系类型；§4.2 读取「全部类型」。
- **冲突**：迁移之后新建的作品不会自动获得 23 类种子，GET 关系类型可能为空，关系创建找不到 `type_code`。
- **影响任务**：T08、T12、T13、T22、T48。
- **建议处理**：明确新作品创建时写入 23 类，或在首次读取 / 首次建关系时按需补种；两种方式的幂等与并发需在 F2 中补一句口径。
- **状态**：已澄清（F2 v1.4 附录 A / §2.2.3）——作品创建时写入，存量作品首次访问角色页签时幂等补种。

### Q3 头像 `active` → `pending` 的迁移路径与状态机不一致

- **位置**：F2 §2.2.8 只定义「采用」时 `pending` → `active`、旧 `active` → `superseded`；§5.4 合并第 7 步要求把被合并角色的 `active` 资产改为 `pending`。
- **冲突**：`active` → `pending` 不在已定义状态机内，且会让旧资产重新进入可被采用状态。
- **影响任务**：T12、T16、T25。
- **建议处理**：确认合并时是改为 `pending` 还是 `superseded`；若保留 `pending`，需在 F2 状态机中显式增加该迁移与约束说明。
- **状态**：已澄清（F2 v1.4 附录 A / §2.2.8、§5.4、§5.6）——状态机为 `pending → active → superseded`、`pending → failed`；合并改为复制新 pending 行，旧 active 置 superseded。

### Q4 节点归属整组替换与归档角色归属冲突

- **位置**：F2 §4.9 要求 PUT 为整组替换，且 owners 中的角色必须同作品且 `status='active'`；§2.2.14 允许节点保留归档角色的 exclusive 归属用于恢复判定。
- **冲突**：节点已有归档角色 exclusive 归属时，任何一次整组 PUT 都必须省略该归档角色；省略即删除其归属，恢复后专属判定丢失。
- **影响任务**：T11、T29、T40、T46。
- **建议处理**：明确 PUT 是「只增删 active 角色行、保留归档角色行」，还是「整组替换但允许归档角色原样保留」；需补一条与恢复语义一致的口径。
- **状态**：已澄清（F2 v1.4 附录 A / §4.9、§8.1）——差异更新：只增删 active 行，归档角色归属保留，省略视为不变更。

### Q5 归档角色成长事件的读写权限未定义

- **位置**：F2 §4.4 的成长线路由挂在 `/characters/:characterId/growth-events` 下；§2.4 只说归档时成长事件 `status='archived'`，未说 GET / PATCH / DELETE 是否允许。
- **冲突**：归档视图需要读取成长事件，但编辑 / 删除归档角色的事件是否允许没有口径，容易出现「能看不能改」或「能改但不应改」两种实现。
- **影响任务**：T15、T24、T38、T48。
- **建议处理**：明确归档角色成长事件为只读，或允许编辑但禁止新增；在 F2 §4.4 补一行状态说明。
- **状态**：已澄清（F2 v1.4 附录 A / §4.4）——归档角色成长事件只读，写操作 409 `CHARACTER_ARCHIVED_READONLY`，恢复后自动可写。

### Q6 AI 单条确认的 `expected_version` 语义未定义

- **位置**：F2 §4.6 确认 body 可带 `expected_version`；同节又允许 `create` / `merge` / `keep_independent` 三种模式。
- **冲突**：`create` 没有目标实体可校验版本；`merge` 的目标角色才有版本；`keep_independent` 等价 `create`。当前未说明 `expected_version` 作用于草稿、条目还是目标角色。
- **影响任务**：T17、T26、T37、T48。
- **建议处理**：明确仅在 `merge` 且提供 `target_character_id` 时校验目标角色版本，其余模式忽略；或从确认请求中移除该字段，避免误用。
- **状态**：已澄清（F2 v1.4 附录 A / §4.6、§8.2）——校验对象为 `characters.version`，仅 merge 生效；其余模式携带即 422。
