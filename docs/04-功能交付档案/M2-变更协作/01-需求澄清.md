## 一、用户诉求（非技术语言）

> 作者希望：**我写小说时，每一次改动、每一处和他人的协作动作（评论、待办、通知）都必须清清楚楚、可追踪、可回溯、可查账。改坏了能回到过去的某个点，评论区别人提的意见不能因为正文一改就丢，通知不能漏，出了争议能查清是谁在什么时候动了什么。**

### 1.1 要解决的核心痛点

- 正文改动一多就乱，改错了想回去，却发现历史被覆盖，找不回上一个版本。
- 自己输入的内容、粘贴的内容、AI 生成的内容混在一起，想单独撤掉某一块却撤不掉。
- 评论是"贴在正文上的"，正文一编辑，评论位置就跑偏甚至消失，提的意见跟着丢了。
- 待办事项散落各处，谁负责、做到哪一步、关联哪段正文，没有统一的地方看。
- @ 和指派没有集中的消息入口，容易漏掉；出了事查不到操作记录。

### 1.2 期望的完整体验

```text
作者在写作工作台写作
  → 每次输入/粘贴/AI 生成/回滚 自动形成一组可追踪的"改动集"
  → 每条改动可单独接受或拒绝，AI 的改动与手工改动分开管理
  → 需要时主动存一个"不可变版本快照"
  → 随时查看版本历史、对比差异、切回旧版本（回滚不删历史）
  → 划词就能评论，记录选区与原文；可回复/解决/重新打开/转待办
  → 正文编辑后评论位置自动跟随；找不到原文时标记"已失联"而非删除
  → 待办统一管理：标题、负责人、关联对象、状态流转
  → 所有 @、指派、任务结果、系统异常进应用内通知中心
  → 敏感操作（修订处理、版本回滚、权限、迁移）全程留痕可查
```

## 二、功能边界

### 2.1 包含（In Scope）

| # | 能力 | 说明 |
|---|------|------|
| 1 | 修订集管理 | 一次连续输入、一次粘贴、一次 AI 生成或一次回滚形成一个修订集；每个操作独立记录接受或拒绝结果 |
| 2 | 修订合并规则 | 连续输入可按时间/段落/操作类型合并；AI 结果不得与作者手工输入合并 |
| 3 | 版本快照 | 作者主动创建版本；首次接受 AI 修订前、回滚前、迁移/批量导入前自动创建不可变快照 |
| 4 | 版本对比与回滚 | 查看版本历史、对比两版本差异；回滚基于目标快照生成新修订集，不删除后续历史 |
| 5 | 划词评论 | 划选正文即可评论，记录选区、原文、章节版本和作者 |
| 6 | 评论交互 | 回复、解决、重新打开、转为待办；锚点随正文编辑映射更新 |
| 7 | 评论失联处理 | 原文被删或无法定位时标记"已失联"，保留原文与引用，可手动重新关联，不自动删除 |
| 8 | 待办管理 | 创建待办，设标题、说明、负责人、关联章节/评论/修订；状态 `未开始 → 进行中 → 完成`，另有 `已取消` |
| 9 | 通知中心 | @、指派、任务结果、系统异常统一进应用内通知中心；可标记已读 |
| 10 | 审计留痕 | 修订处理、版本回滚、权限变更、迁移等敏感操作写入审计日志 |

### 2.2 不包含（Out of Scope）

- ❌ 多人实时同时编辑同一文档（评论/待办/指派/@ 用于组织作者与 AI 的协作，不代表本期支持多人协同编辑）。
- ❌ 邮件、短信、社区等站外通知（通知以应用内通知中心为准）。
- ❌ 将评论、待办、修订、通知混入正文 JSON（正文只存内容，协作元数据放在独立关系模型）。
- ❌ 跨设备实时同步协作状态（跨设备冲突统一走服务端版本校验与三方合并，见 M1）。

## 三、功能流程

### 3.1 修订集形成

```text
作者在编辑器操作
  → 一次连续输入 / 一次粘贴 / 一次 AI 生成 / 一次回滚
  → 系统按来源与基准版本形成一组有序改动（修订集）
  → 每条改动独立记录接受或拒绝结果
  → AI 结果与作者手工输入分开成组，不混在一起
```

### 3.2 版本快照与回滚

```text
触发快照：作者主动创建 / 首次接受任一 AI 修订前 / 执行回滚前 / 数据迁移或批量导入前
  → 生成不可变快照（同一修订集只创建一个自动快照）
  → 作者随时查看版本历史、对比两个版本差异
  → 执行回滚：基于目标快照生成新的回滚修订集
  → 作者确认后回滚修订集才成为当前正文（回滚不删除后续历史）
```

### 3.3 划词评论

```text
作者划选正文
  → 创建评论：记录选区、原文、章节版本、作者
  → 正文编辑时锚点通过映射自动更新位置
  → 原文被删/无法定位 → 标记"已失联"，保留原文与引用
  → 评论操作：回复 / 解决 / 重新打开 / 转为待办
```

### 3.4 待办流转

```text
创建待办（标题、说明、负责人、关联章节/评论/修订）
  → 状态机：未开始 → 进行中 → 完成（另有 已取消）
  → 状态变化自动产生通知与审计记录
```

### 3.5 通知与审计

```text
@ / 指派 / 任务结果 / 系统异常
  → 写入应用内通知中心（记录关联对象与已读时间）
  → 关联对象被删除时保留可读的历史说明
敏感操作（修订处理、版本回滚、权限、迁移）
  → 写入审计日志，可回答"谁在什么时候做了什么"
```

## 四、验收标准（DoD）

| # | 标准 | 验证方式 |
|---|------|---------|
| 1 | 修订集形成 | 一次连续输入/粘贴/AI 生成/回滚各形成一个修订集，操作有序 |
| 2 | 修订独立接受/拒绝 | 每条改动可单独接受或拒绝，结果可审计 |
| 3 | AI 与手工不混组 | AI 生成结果不与作者手工输入合并成同一修订集 |
| 4 | 版本快照触发 | 主动创建 + 首次接受 AI 修订前 + 回滚前 + 迁移前均产生不可变快照；同一修订集只建一个自动快照 |
| 5 | 版本对比 | 两个版本差异可查看，含节点与正文变更明细 |
| 6 | 版本回滚 | 回滚基于目标快照生成新修订集，不删除后续历史；作者确认后才成为当前正文 |
| 7 | 划词评论 | 划选正文可创建评论，记录选区/原文/章节版本/作者 |
| 8 | 评论交互 | 可回复、解决、重新打开、转为待办 |
| 9 | 评论失联 | 原文被删时标记"已失联"，保留原文与引用，可重新关联，不自动删除 |
| 10 | 待办状态机 | 状态流转 `未开始 → 进行中 → 完成` 与 `已取消` 正确，状态变化产生通知与审计 |
| 11 | 通知中心 | @、指派、任务结果、系统异常均入库；已读状态正确；关联对象删除后保留可读说明 |
| 12 | 审计留痕 | 修订处理、版本回滚、权限、迁移等敏感操作可查操作者、时间与内容 |

## 五、异常与边界处理

| 场景 | 处理 |
|------|------|
| 评论锚点无法重定位 | 标记"已失联"，保留原文与引用，提供重新关联，不自动删除 |
| 版本回滚前有未保存变更 | 提示先保存，返回 409 不执行 |
| 版本对比版本不存在 | 返回 404 |
| 回滚目标版本不存在 | 返回 404 |
| 待办重复完成 | 保持最终状态，只记录一次审计语义 |
| 通知关联对象被删除 | 保留可读的历史说明，不丢弃通知 |
| 待办被取消后再次流转 | 按状态机约束，非法流转拦截并提示 |
| 双模式切换锚点失联 | 标记失联并保留原文，不静默删除评论或修订 |

## 六、数据字段说明（概念模型）

### 6.1 修订集（revision set）

| 字段 | 类型 | 说明 |
|------|------|------|
| `revision_set_id` | string | 修订集唯一标识 |
| `chapter_id` | string | 所属章节 |
| `base_version` | number | 生成时的章节版本 |
| `actor_type` | enum | `author`/`ai`/`import`/`rollback` |
| `actor_id` | string | 作者、Agent 或系统任务标识 |
| `operations` | array | 有序插入、删除和格式操作 |
| `status` | enum | `pending`/`partially_resolved`/`resolved` |
| `created_at` | datetime | 创建时间 |

### 6.2 评论（comment）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 评论唯一标识 |
| `chapter_id` | string | 所属章节 |
| `anchor` | object | 选区起止位置、原文、前后文、章节版本、锚点状态 |
| `content` | text | 评论内容 |
| `author` | string | 评论作者 |
| `status` | enum | `open`/`resolved`/`reopened` |
| `anchor_status` | enum | `attached`/`orphaned` |

### 6.3 待办（todo）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 待办唯一标识 |
| `title` | string | 待办标题 |
| `description` | text | 待办说明 |
| `assignee` | string | 负责人 |
| `linked_object` | object | 关联章节/评论/修订 |
| `status` | enum | `open`/`in_progress`/`done`/`cancelled` |

### 6.4 通知（notification）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 通知唯一标识 |
| `type` | enum | `mention`/`assign`/`task_result`/`system` |
| `linked_object` | object | 关联对象 |
| `read_at` | datetime | 已读时间（空为未读） |

### 6.5 版本快照（version snapshot）

| 字段 | 类型 | 说明 |
|------|------|------|
| `version_no` | number | 版本号 |
| `created_at` | datetime | 创建时间 |
| `created_by` | string | 创建者 |
| `note` | string | 版本备注 |
| `change_type` | enum | `manual`/`auto` |

## 七、相关依赖与约束

- **依赖**：M0（鉴权、工程基座）、M1（正文保存、WAL、版本号推进、409 冲突处理）。评论锚点依赖 ProseMirror 映射；AI 修订集依赖 M3 AI 创作模块生成候选修订。
- **约束**：
  - 修订、评论、待办、通知保存在独立关系模型，不混入正文 JSON。
  - 回滚不删除后续历史，基于目标快照生成新修订集；作者确认后才成为当前正文。
  - 待办状态机固定 `open → in_progress → done`，另有 `cancelled`；状态变化产生通知与审计。
  - @ 与指派只创建应用内通知，不隐式修改业务对象权限。
  - 锚点无法重定位时标记失联并保留原文，不静默删除评论或修订。
  - 模式切换通过同一转换链路重定位评论和修订锚点。
- **前置**：M1 已完成正文保存与版本号机制；M3 AI 创作生成候选修订集，M2 只管理接受/拒绝。
