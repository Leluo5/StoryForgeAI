## 一、方案概述

本功能为创作端 **AI 创作基座**：让作者的 AI 创作任务可追踪、可重试、不重复产生有效结果。核心是「AI 任务生命周期 → BullMQ 队列执行 → SSE 进度推送 → AI 输出转待审修订集」四层，全部落在 NestJS `/api/v1` 资源体系，沿用 M0/M1/M2 的 SessionGuard + CsrfGuard + ZodValidationPipe + `ok()` 响应包装模式，并复用 M2 的修订集（`actor_type='ai'`/`ai_set=true`）作为 AI 结果的落地载体。

### 1.1 方案选型

| 决策点 | 选择 | 备选 | 理由 |
|--------|------|------|------|
| 任务队列 | BullMQ（Redis） | 数据库轮询 / 进程内 | 长任务可靠队列；重试/退避/去重内建；系统设计 §9.1 明确 |
| 进度推送 | SSE（Server-Sent Events） | WebSocket / 轮询 | 单向服务端推送足够；自动重连 + Last-Event-ID 补取；§9.1 明确 |
| 任务状态持久化 | `ai_tasks` 表（DB） | 仅内存 | DB 是重连/重启恢复依据，SSE 只推送不承载状态 |
| 事件补取 | `ai_task_events` 表 + 事件序号 | 仅内存缓冲区 | 重连后按序号补取遗漏事件，重启不丢事件 |
| AI 结果落地 | M2 修订集（`actor_type='ai'`） | 直接写正文 | AI 只生成待审修订，作者接受前正文不变 |
| 幂等去重 | `idempotency_key` + 唯一约束 | 应用层判重 | 同键最多一个有效结果修订集，重复调用自动去重 |
| 外部模型 | 可插拔 Provider（含 Mock/Coze） | 硬编码 | M3a 用 Mock 打通闭环，M3b 接入 Coze；502/503 可重试 |
| 契约复用 | `@storyforge/contracts`（Zod） | 双端各写 | 单一 schema 双端复用，M1/M2 已验证 |
| 鉴权 | SessionGuard + 服务层 author 过滤 | 独立 AuthorGuard | 沿用 M1/M2 模式 |

## 二、数据模型（对齐需求澄清 §六）

全部主键 `uuid`（`gen_random_uuid()` 默认），时间戳 `timestamptz`，列名 snake_case，沿用 M1/M2 手写 SQL 迁移模式。

### 2.1 AI 任务 `ai_tasks`（迁移 `ai-task-base`）

| 列 | 类型 | 约束 | 说明 |
|----|------|------|------|
| `id` | uuid | PK | 任务标识（`task_id`） |
| `idempotency_key` | varchar(128) | 非空 | 幂等键（同键最多一个有效结果） |
| `work_id` | uuid | REFERENCES works(id) ON DELETE CASCADE | 所属作品 |
| `chapter_id` | uuid | REFERENCES chapters(id) ON DELETE CASCADE | 所属章节 |
| `tool` | varchar(40) | 非空 | 工具标识（如 `continue`） |
| `agent_id` | uuid | 可空 | 执行 Agent（M3a 预留，M3b 接入） |
| `input_summary` | jsonb | 非空 | 输入摘要（作品/章节/选区/参数） |
| `base_version` | integer | CHECK >= 0 | 基准章节版本 |
| `status` | varchar(16) | CHECK IN ('queued','running','succeeded','failed','cancelled') | 任务状态 |
| `event_seq` | integer | DEFAULT 0 | 已推送的最大事件序号 |
| `result_revision_set_id` | uuid | REFERENCES revision_sets(id) ON DELETE SET NULL | 成功后的结果修订集 |
| `error` | jsonb | 可空 | 失败原因（结构化） |
| `attempts` | integer | DEFAULT 0 | 已尝试次数 |
| `created_by` | uuid | REFERENCES authors(id) ON DELETE CASCADE | 发起作者 |
| `created_at` | timestamptz | DEFAULT now() | 创建时间 |
| `updated_at` | timestamptz | DEFAULT now() | 最后变更 |

**约束**：`UNIQUE(idempotency_key)`（同幂等键唯一任务，去重依据）。
**索引**：`idx_ai_tasks_work ON ai_tasks(work_id, created_at DESC)`、`idx_ai_tasks_status ON ai_tasks(status, updated_at)`。

### 2.2 任务进度事件 `ai_task_events`（迁移 `ai-task-base`）

| 列 | 类型 | 约束 | 说明 |
|----|------|------|------|
| `id` | uuid | PK | 事件标识 |
| `task_id` | uuid | REFERENCES ai_tasks(id) ON DELETE CASCADE | 所属任务 |
| `event_seq` | integer | 非空 | 事件序号（单调递增，SSE 补取依据） |
| `type` | varchar(24) | CHECK IN ('queued','running','progress','succeeded','failed','cancelled') | 事件类型 |
| `payload` | jsonb | 非空 | 阶段描述/进度百分比/结果摘要/错误原因 |
| `created_at` | timestamptz | DEFAULT now() | 事件时间 |

**约束**：`UNIQUE(task_id, event_seq)`（事件序号唯一，补取不重复）。
**索引**：`idx_ai_task_events_task ON ai_task_events(task_id, event_seq ASC)`。

## 三、API 设计（`/api/v1`）

统一沿用：`SessionGuard` + `CsrfGuard` + `ZodValidationPipe` + `ok(request, data)` 包装 + 写请求带幂等键。错误码：401/403/404/409/422/429/502/503。

### 3.1 AI 任务

- `POST /api/v1/works/:workId/chapters/:chapterId/ai-tasks` — 发起 AI 创作任务（`tool`、`input_summary`、`idempotency_key`）。校验章节归属与权限；若同幂等键已有任务：已有有效结果 → 返回该结果（幂等，不重复执行）；否则 409。响应 `{ task }`。
- `GET /api/v1/works/:workId/chapters/:chapterId/ai-tasks` — 列出章节任务（分页 + status 过滤）。
- `GET /api/v1/works/:workId/ai-tasks/:taskId` — 单任务详情（状态 + 已推送事件序号 + 结果摘要）。
- `POST /api/v1/works/:workId/ai-tasks/:taskId/retry` — 重试（仅 `failed`/`cancelled` 可重试；保留原幂等键；若已有有效结果直接返回）。响应 `{ task }`。
- `POST /api/v1/works/:workId/ai-tasks/:taskId/cancel` — 取消（仅 `queued`/`running` 可取消；`cancelled` 幂等）。响应 `{ task }`。

### 3.2 SSE 进度推送

- `GET /api/v1/works/:workId/ai-tasks/:taskId/events` — **SSE 端点**（text/event-stream）。连接后：
  1. 先推送当前任务状态（`type=snapshot`，含 status/event_seq/result_revision_set_id/error）。
  2. 若请求头 `Last-Event-ID` 或查询参数 `since` 指定序号，先按序号补取 `ai_task_events` 中遗漏事件。
  3. 之后实时推送新事件（由队列 Worker / 服务写入后通过事件总线推送）。
  4. 心跳注释（每 15s `: ping`）保持连接；连接关闭自动清理订阅。

### 3.3 结果修订集（复用 M2）

- 任务成功后结果落入 M2 修订集，作者接受/拒绝/批量接受走 M2 现有端点（`/revision-sets/:id/operations/:opIndex/accept|reject`），无新增端点。
- AI 结果修订集特征：`actor_type='ai'`、`ai_set=true`、`base_version`=任务基准版本、`operations`=候选输出转换的有序操作集。

## 四、核心逻辑

### 4.1 任务发起与幂等（`ai-task.service.ts`）

```ts
// 发起任务：幂等键去重 + 创建任务 + 入队
async createTask(authorId, workId, chapterId, input): Promise<{ task: AITask }> {
  // 1. 悲观锁章节行 + 归属校验（复用 M2 assertOwnedChapter 模式）
  // 2. 幂等键检查：已存在 →
  //      - 已有有效结果（status='succeeded' 且 result_revision_set_id 非空）→ 直接返回该任务（不重复执行）
  //      - 仍在执行 → 返回 409（任务已存在，勿重复提交）
  //      - 失败/取消 → 返回 409（可调用 retry）
  // 3. 创建 ai_tasks(status='queued', event_seq=0, base_version=chapter.version)
  // 4. 写事件 event_seq=1, type='queued'
  // 5. 入队 BullMQ（jobId=task.id，幂等键去重由 UNIQUE(idempotency_key) 兜底）
  // 6. 审计 action='ai_task_create'
  // 7. 返回 { task }
}
```

### 4.2 任务执行（`ai-task.processor.ts` + BullMQ Worker）

```ts
// Worker 消费队列
async processTask(job) {
  // 1. 任务状态 queued → running，写事件 event_seq=N, type='running'
  // 2. 读取基准章节（document + version），组装输入摘要（作品/章节/选区/参数）
  // 3. 调用模型 Provider.generate(...)（可插拔，Mock 或 Coze）
  //     - 成功 → 候选输出
  //     - 失败/超时 → 抛错（BullMQ 退避重试；超限标记 failed，保存 error，写事件）
  // 4. 服务端将候选输出转换为修订集（actor_type='ai', ai_set=true, base_version=任务基准版本）
  //     - 转换前校验章节 version === base_version：若已变化 → 标记 result_stale（基于旧版本），不直接套用
  // 5. 写事件 type='succeeded'（payload 含 revision_set_id + 结果摘要 + stale 标记）
  // 6. 任务 status='succeeded'，result_revision_set_id 落库
  // 7. 审计 action='ai_task_succeeded'
  // 8. 推送事件（事件总线 → SSE 订阅者）
}
```

```ts
// 策略：以基准版本 document 为基线，计算候选输出与基线的差异，生成有序操作集
function toRevisionOperations(baseDocument, candidateDocument): RevisionOperation[] {
  // 1. 规范化文档（复用 @storyforge/editor-schema canonicalizeDocument）
  // 2. 文本级 diff（按块/段）→ 插入/删除/替换操作
  // 3. 格式操作（标题/加粗/斜体等）→ 独立标记
  // 4. 返回有序操作集（每个含 index/step/status='pending'，对齐 M2 存储格式）

```

### 4.4 SSE 事件总线与补取（`ai-task.sse.ts`）

```ts
// 事件总线：进程内 EventEmitter，key = `task:${taskId}`
// 写入事件时广播给该任务的所有 SSE 订阅者

// SSE 连接处理
async handleEvents(request, taskId, response) {
  // 1. 校验任务归属（作品 + 作者）
  // 2. 设置 SSE 头（text/event-stream, no-cache, keep-alive）
  // 3. 推送 snapshot 事件（当前 status/event_seq/result/error）
  // 4. 读取 since 序号（Last-Event-ID 或 ?since=）
  //     → 从 ai_task_events 补取 event_seq > since 的事件（按序号升序推送）
  // 5. 订阅事件总线，实时转发新事件
  // 6. 心跳 15s；客户端断开后清理订阅
}
```

### 4.5 任务取消与重试（`ai-task.service.ts`）

```ts
// 取消：仅 queued/running 可取消；先移除队列（BullMQ job.remove()），再置 cancelled，写事件
async cancelTask(authorId, workId, taskId): Promise<{ task }> {
  // 1. 归属校验 + 悲观锁任务行
  // 2. status ∈ {queued, running}？否则 422（已完成/已失败不可取消，cancelled 幂等返回）
  // 3. job.remove()（若仍排队）；running 任务标记 cancelled（Worker 协程检查点退出）
  // 4. status='cancelled'，写事件 type='cancelled'
  // 5. 审计 action='ai_task_cancel'
}

// 重试：仅 failed/cancelled 可重试；保留原幂等键
async retryTask(authorId, workId, taskId): Promise<{ task }> {
  // 1. 归属校验 + 悲观锁任务行
  // 2. status ∈ {failed, cancelled}？否则 422
  // 3. 若已有有效结果修订集 → 返回该任务（不重复执行）
  // 4. status='queued'，error=null，重新入队（新 job，attempts 重置或累计）
  // 5. 写事件 type='queued'；审计 action='ai_task_retry'
}
```

### 4.6 幂等去重语义

| 场景 | 行为 |
|------|------|
| 同幂等键首次调用 | 正常创建任务 |
| 同幂等键重复调用（任务 succeeded） | 返回已有任务 + 其结果修订集（不重复执行） |
| 同幂等键重复调用（任务 queued/running） | 409（进行中，勿重复提交） |
| 同幂等键重复调用（任务 failed/cancelled） | 409（可调用 retry） |
| Worker 崩溃后重试（同任务新 job） | 任务状态保留；UNIQUE(idempotency_key) 兜底防止重复任务 |
| 模型失败重试（退避） | 新 job 重新执行；同幂等键最多一个有效结果修订集 |

| 场景 | 异常 | 状态码 | 响应体 |
|------|------|--------|--------|
| 未登录 | UnauthorizedException | 401 | `{ error, request_id }` |
| 无作品权限/章节不属作品 | NotFoundException | 404 | `{ error, request_id }` |

| 外部模型失败 | 任务 failed + 502/503 | 502/503 | `{ error, details: { task_id, retryable } }` |
| 幂等键重复并发 | 唯一约束兜底 | 409 | `{ error, details: { task_id } }` |

## 九、部署与运行

1. **Redis 依赖**：`infra/docker-compose.yml` 新增 `redis:7` 服务（端口 6380），`REDIS_URL=redis://127.0.0.1:6380`。
2. **CI 调整**：`.github/workflows/ci.yml` 启动 redis 服务；测试环境注入 `REDIS_URL`。
3. **队列 Worker**：`main.ts` 启动时初始化 BullMQ Worker（同进程）；生产可拆独立进程，本期同进程即可。
4. **幂等键生成**：前端在发起任务前生成 `idempotency_key`（UUID v4），重试沿用。
5. **Mock 模型**：`ai-model.provider.ts` 提供 Mock Provider（固定候选输出 + 可配置延迟/失败），保证测试确定性；Coze Provider 留接口待 M3b 接入。
