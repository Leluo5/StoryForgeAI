## 一、方案概述

本功能是创作端的**素材与灵感底座**：把文章/论文/小说/灵感四类资料统一录入，走 Coze 智能体（LLM）做结构化拆分，建立跨条目关联，提供统一检索与复用。核心是「录入 → 识别 → 拆分 → 关联 → 检索」五段管线。

### 1.1 方案选型

| 决策点 | 选择 | 备选 | 理由 |
|--------|------|------|------|
| 存储 | JSON 文件（`data/knowledge/*.json`） | SQLite | 延续项目 JSON 存储惯例；单创作者本地；条目数可控 |
| 结构化引擎 | 后端调 Coze 智能体 | 前端调 | 隐藏 Token；集中错误处理；可复用已有 coze_client |
| 类型识别 | LLM 自动判定 + 手动指定 | 纯启发式 | 自动判定为主，不确定时人工兜底 |
| 关联引擎 | 向量相似度（本地 TF-IDF 兜底） | 纯关键词 | 需 LLM 嵌入时走 Coze；无外部搜索服务 |
| OCR | 后端调视觉能力 | 前端 OCR 库 | 统一走 Coze 视觉模型，避免前端依赖 |
| 大纲提取 | 拆文后自动触发子任务 | 手动触发 | 满足 DoD #11 自动触发 |

## 二、数据模型（对齐需求澄清 §六）

### 2.1 知识条目 `knowledge_entry`（双层存储：`data/knowledge/<id>.json` + `<id>.md`）

存储形态为「Markdown 正文 + JSON 元数据外壳」双层结构（本轮语法升级落地）：

- `<id>.json`：元数据 + structured（强结构）+ tags + links + content_hash + 时间戳。
- `<id>.md`：正文（Markdown 语法，人可读、可 diff、可富媒体）。
- `index.json`：轻量元数据索引（不含 structured 正文）。

加载合成：`load_entry` 读 JSON + 读 `.md`，正文塞回 `raw_content` 键，对 parser/linker/接口层透明。

```json
{
  "id": "k_01xxx",
  "type": "novel",
  "title": "雾都疑案·拆文",
  "source": "upload",
  "structured": { "...按类型见 2.2..." },
  "tags": ["悬疑", "侦探"],
  "links": ["k_02xxx"],
  "content_hash": "sha256…",
  "created_at": "2026-11-10T10:00:00",
  "updated_at": "2026-11-10T10:05:00"
}
```

正文 Markdown 能力（`knowledge_markdown.py` 纯函数层）：

- `normalize_body(text)`：普通文本 → Markdown 友好形态（章节标题 → `##`、编号列表 → `-`）。
- `render_body_html(text)`：Markdown → 安全 HTML 片段（`extra` + `nl2br`，含 XSS 底线），供详情接口附带 `body_html`。
- `POST /api/knowledge/markdown/render`：渲染预览（不落库，前端实时预览用）。

### 2.2 结构化结果 `structured`（按 type）

| type | 结构 |
|------|------|
| article | `{ paragraphs[], key_points[], summary, tag_list[] }` |
| paper | `{ research_question, research_method, core_conclusion, limitation, design_insight }` |
| novel | `{ characters[], plot_lines[], narrative_style[], world_setting, outline }` |
| inspiration | `{ raw_text, enriched_text, related_ids[] }` |

`novel.outline` 四维度大纲结构：

```json
{
  "chapters": [{ "title": "第一章", "summary": "...", "order": 1 }],
  "plot_nodes": [{ "id": "pn_1", "label": "初遇", "type": "main|branch|turn" }],
  "character_relations": [{ "a": "林远", "b": "周福", "relation": "敌对", "camp": "..." }],
  "core_storylines": { "main": "...", "branches": ["..."], "hidden": ["..."] }
}
```

### 2.3 索引与检索（含全文检索增强）

- `data/knowledge/index.json`：条目元数据索引（id/type/title/tags/created_at），供列表与四维度检索，避免全量扫描。
- 检索四维度：关键词（raw_content+structured 全文）、类型（type）、标签（tags）、时间（created_at 范围）。

**全文检索倒排索引**（`data/knowledge/search_index.json`，本轮检索增强落地）：

- 结构：`{ "postings": { token: { total, entries: { entry_id: freq } } }, "entry_tokens": { entry_id: { token: freq } } }`。
- 分词：中文单字 + 英文/数字词 + 相邻 bigram（复用 linker 分词思路，无外部依赖，对齐本地单创作者轻量基调）。
- 维护点：`create_entry` / `save_entry` → `_upsert_search_entry` 增量更新；`delete_entry` → `_remove_search_entry` 移除；`rebuild_search_index` 全量重建（损坏/缺失兜底）。
- 查询优化：`_search_candidate_ids` 倒排预筛候选 id 集（命中规则=关键词任一分词 token 命中即入候选），候选集是「子串命中」的**超集**，再对候选集做 `_match_keyword` 原子串精排，保证结果与改造前完全一致（不误报不漏报），仅避免全量 `load_entry` 扫描。
- 健壮性：索引缺失/损坏时 `_search_candidate_ids` 返回 None，`query_index` 回退全量扫描（语义不变，仅性能降级）。

### 2.4 知识库→小说创作角色同步（F5→P3 跨模块导入）

知识库 novel 条目是小说创作角色库的角色来源之一，经 `RoleImportEngine`（`modules/novel_creation/role_import.py`）跨模块导入。源字段 → 目标字段映射：

| 知识库源字段 | 小说角色目标字段 | 说明 |
| --- | --- | --- |
| `characters[].名字` | `Role.name` | 直接映射 |
| `characters[].身份` | `Role.identity` | 直接映射 |
| `characters[].性格` | `Role.personality` | 直接映射 |
| `outline.character_relations[]`（当前角色参与的关系边） | `Role.background` + `Role.relations[]` | 聚合为人物关系描述；每条写入 `relations[{target_name, relation_type}]` |
| 无直接来源 | `Role.appearance` | 导入时标红 `kb_no_appearance`，待用户补填 |

> 解耦约束：`RoleImportEngine` 依赖注入 `kb_store`/`role_store`，`role_store` 不 import 知识库符号。导入候选经 `kb_store.query_index(type_="novel")` + `load_entry` 提取，映射后 `import_roles` 创建角色并写导入历史（`data/projects/role_import_history.json`，保留 200 条）。

## 三、API 设计

### 3.1 `POST /api/knowledge/entries` — 统一录入

**请求体**：

```json
{
  "source": "paste|upload|ocr|manual",
  "type": "auto|article|paper|novel|inspiration",
  "title": "可选",
  "raw_content": "文本内容（paste/manual）",
  "file_id": "可选（upload/ocr 时先上传）"
}
```

**响应 200**：`{ "id": "k_01xxx", "type": "novel", "structured": {...}, "tags": [...], "status": "preview" }`

> 返回 `preview` 供前端编辑确认，确认后调 3.2 入库。

### 3.2 `POST /api/knowledge/entries/<id>/commit` — 确认入库

**请求体**：`{ "structured": {...修正后...}, "tags": [...], "links": [...] }`

**响应 200**：`{ "id": "k_01xxx", "status": "saved" }`

### 3.3 `POST /api/knowledge/ocr` — 图片 OCR 识别

**请求体**：multipart `{ "file": <binary> }`

**响应 200**：`{ "text": "识别出的文本" }`

### 3.4 `GET /api/knowledge/entries` — 统一检索

**查询参数**：`keyword` / `type` / `tag` / `start_time` / `end_time` / `page` / `page_size`

**响应 200**：`{ "total": n, "items": [{ id, type, title, tags, created_at }] }`

### 3.5 `GET/PUT/DELETE /api/knowledge/entries/<id>` — 详情 / 编辑 / 删除

- `GET`：完整条目（含 structured）。
- `PUT`：`{ "structured", "tags", "title", "links" }` → 更新 + 重建关联。
- `DELETE`：删除条目，并清理其他条目 `links` 中对它的引用。

### 3.6 `POST /api/knowledge/entries/<id>/link` — 建立关联

**请求体**：`{ "target_id": "k_02xxx", "type": "reference|inspiration|conflict" }`

**响应 200**：`{ "id": "k_01xxx", "links": ["k_02xxx"] }`

### 3.7 `POST /api/knowledge/outline/extract` — 大纲自动提取（拆文后触发）

**请求体**：`{ "novel_id": "k_01xxx" }`

**响应 200**：`{ "novel_id": "k_01xxx", "outline": { "chapters": [...], "plot_nodes": [...], "character_relations": [...], "core_storylines": {...} } }`

## 四、核心逻辑

### 4.1 类型识别

```python
def detect_type(raw_content, manual=None):
    if manual in ("article", "paper", "novel", "inspiration"):
        return manual
    # 调 Coze 智能体判定；不确定时抛 TypeUncertain → 前端弹确认框
    return llm_detect(raw_content)
```

### 4.2 拆分引擎（`knowledge_parser.py`）

```python
def parse_entry(entry):
    if entry["type"] == "article":  return parse_article(entry["raw_content"])
    if entry["type"] == "paper":    return parse_paper(entry["raw_content"])
    if entry["type"] == "novel":    return parse_novel(entry["raw_content"])
    if entry["type"] == "inspiration": return parse_inspiration(entry["raw_content"])
```

- 各 `parse_*` 走 Coze 智能体，结构化提取失败 → **降级为原文存储**（需求澄清 §五「拆分失败」）。
- `parse_novel` 成功后**自动触发** `extract_outline(novel_id)`（DoD #11）。

### 4.3 大纲提取引擎（`knowledge_outline.py`）

```python
def extract_outline(novel_id):
    entry = load_entry(novel_id)
    outline = llm_extract_outline(entry["raw_content"])  # 四维度
    entry["structured"]["outline"] = outline
    save_entry(entry)  # 与拆文数据同条目关联绑定
    return outline
```

- 失败：保留拆文结果，返回 `{ "error": "outline_failed" }`（前端提示重试）。
- 无法提取（无章节结构）：返回 `{ "error": "no_chapters" }`（前端提示手动补充）。

### 4.4 关联引擎（`knowledge_linker.py`）

```python
def link_inspiration(inspiration_id):
    # 1) 在已有条目中检索相似度
    candidates = search_similar(inspiration["raw_text"])
    # 2) 建立关联
    for c in candidates[:3]:
        add_link(inspiration_id, c["id"])
    # 3) 基于已有知识上下文补充完善灵感
    enriched = llm_enrich(inspiration["raw_text"], candidates)
    inspiration["structured"] = {"raw_text": ..., "enriched_text": enriched, "related_ids": [...]}
```

- 无匹配：`related_ids=[]`，仅存独立灵感（需求澄清 §五）。
- 相似度：优先 LLM 嵌入，无嵌入服务时 TF-IDF + 余弦兜底。

### 4.5 统一检索

```python
def search_entries(keyword=None, type=None, tag=None, start=None, end=None, page=1, size=20):
    index = load_index()  # data/knowledge/index.json
    results = [e for e in index if match(e, keyword, type, tag, start, end)]
    return {"total": len(results), "items": paginate(results, page, size)}
```

### 4.6 并发与去重

- 录入走**队列化**：同一 `raw_content` 哈希在 `index.json` 中查重，重复返回已有条目（防重复条目）。
- 超大文本：按 8000 字分块，逐块送 LLM，前端进度提示。

**分块落地说明**（本轮优化，对齐 DoD #14「不同篇幅适配」）：

- `parse_entry` 对 article/paper/novel 走 `_parse_chunked`：文本 > 单次 LLM 上限（`_STRUCT_PROMPT_LIMIT=6000`）时分块逐块解析，再按类型 `_merge_*` 合并。
- 合并规则：数组字段拼接（article.paragraphs/key_points、novel.plot_lines），字符串字段按块拼接（summary、paper 五要素、world_setting），标签/人物/叙事风格保序去重（`_dedup` 兼容 dict 元素）。
- 单块路径（≤ 上限）与直接调 `parse_*` 完全等价（零回归）；LLM 失败仍降级原文存储。

## 五、异常处理（对齐需求澄清 §五）

| 场景 | 处理 | 方案落点 |
|------|------|---------|
| 文件格式不支持 | 前端提示支持清单，拒绝上传 | 3.3 上传前校验 MIME |

| 灵感无匹配知识 | 提示「仅存为独立灵感」 | 4.4 `related_ids=[]` |
| 检索无结果 | 空态 + 建议放宽 | 4.5 返回空 `items` |
| 超大文本 | 分块 + 进度 | 4.6 分块 |
| 并发录入 | 队列化防重复 | 4.6 哈希查重 |
| 大纲提取失败 | 保留拆文 + 提示重试 | 4.3 `outline_failed` |
| 大纲无法提取 | 提示手动补充 | 4.3 `no_chapters` |

## 九、Markdown 导入导出技术方案（Extension，2026-11-12）

> 本扩展为 F5 增量能力：新增 `knowledge_markdown_io.py` 引擎（导出 + 导入），挂 `routes.py` 蓝图，
> 前端交付独立可挂载「Markdown 导入导出」面板组件（对齐需求澄清 §8.4 决策）。不改既有存储与检索。

### 9.1 方案选型

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 导出引擎 | 纯函数 + `zipfile` | 正文已在 `<id>.md` 双层存储，导出即读 `.md` 重组；ZIP 用标准库 |
| 导入解析 | 纯函数解析（复用 `knowledge_markdown.py` 思路，不引入新依赖） | 解析标题/正文/格式元素，与现有 `normalize_body`/`render_body_html` 同一语法栈 |
| 编码检测 | `charset-normalizer` 兜底 `chardet` | 自动检测 UTF-8/GBK 等；无外部服务依赖 |
| 文件名规范 | `re.sub` 清洗非法字符 + `strftime` 时间戳 | 对齐需求澄清 MD-4 |
| 判重 | 标题 + `sha256(raw_content)` | 对齐需求澄清 §8.4 决策；仅同名不同内容视为待确认 |
| 进度 | 分块处理 + 前端 `fetch` 回调 | 大文件避免界面阻塞（对齐 MD-12） |

> 解耦：`knowledge_markdown_io.py` 不 import `knowledge_store` 符号，通过 `store` 参数注入（对齐角色导入引擎的依赖注入约定）。

### 9.3 API 设计（挂 knowledge 蓝图，前缀 `/api/knowledge`）

| 方法/路径 | 用途 | 说明 |
| --- | --- | --- |
| `POST /api/knowledge/markdown/export` | 单条/批量/分类导出 | 入参 `{mode:"single"\|"batch"\|"by_type"\|"by_tag", entry_ids?:[], type?:string, tag?:string}`；`single` 返回 `{content, file_name}`（直接下载）；`batch/by_type/by_tag` 返回 ZIP 字节流（`send_file`) + 统计 |
| `POST /api/knowledge/markdown/import/preview` | 导入预览 | 入参 `{files:[{file_name, content}|{file_name, base64}], target_type}`；返回 `{items:[import_preview_item]}`（含冲突标记，不落库） |
| `POST /api/knowledge/markdown/import` | 确认导入 | 入参 `{items:[import_preview_item], target_type, conflict_strategy}`；返回 `{total, success, failed, failed_items, created, updated}` |
| `POST /api/knowledge/markdown/import/validate` | 单文件格式校验 | 入参 `{file_name, content}`；返回 `{valid, reason}`（扩展名/编码/损坏校验） |

> 导入采用「文件内容经前端 `FileReader` 读取为字符串/base64 上传」而非 multipart 流式——知识库单创作者本地场景，文件规模可控，简化前端进度与冲突判定。大文件分批上传由前端切块调用。

### 9.4 核心逻辑

**导出主流程**：
```python
def handle_export(mode, entry_ids, type_, tag, store):
    if mode == "single":
        entry = store.load_entry(entry_ids[0])
        return {"content": build_export_markdown(entry), "file_name": build_filename(entry["title"])}
    # batch/by_type/by_tag：收集条目 → export_entries → build_zip
    entries = collect(store, mode, entry_ids, type_, tag)
    files = export_entries(entries)  # 逐条渲染，失败记录
    zip_bytes = build_zip(files)
    return {"zip": zip_bytes, "stats": {...}}
```

**导入主流程**：
```python
def handle_import(items, target_type, strategy, store, progress_cb):
    result = import_files(items, target_type, strategy, store, progress_cb)
    # 每条：decode → parse_markdown_text → detect_conflict → 策略分发
    #   overwrite: 更新已有条目 raw_content
    #   rename:    新 id 新文件名（title 加后缀 _imported）
    #   skip:      不处理，计入 skipped（失败统计 reason=conflict_skip）
    return result
```

### 9.5 异常处理（对齐需求澄清 §8.7）

| 场景 | 处理 | 方案落点 |
|------|------|---------|
| 扩展名不支持 | `validate` 返回 `{valid:false, reason:"bad_extension"}` | 9.3 validate |
| 文件损坏/解析失败 | 失败明细 `reason:"parse_error"`，不中断整批 | 9.4 import_files |
| 编码异常 | `decode_bytes` 自动 utf-8→gbk→报错 `encoding_error` | 9.2 decode_bytes |
| 目标条目不存在 | 导出跳过并记 `failed_items[{id, reason:"not_found"}]` | 9.4 collect |
| 同名不同内容 | 冲突策略三选一 | 9.4 detect_conflict |
| 大文件 | 分块 + `progress_cb` 回调 | 9.2 import_files |
| 导出无匹配 | 返回 `{total:0, items:[]}` + 前端提示 | 9.4 collect |

### 9.9 风险与待定

| 风险 | 说明 | 对策 |
|------|------|------|
| 前端文件规模 | 单文件过大上传耗时 | 分块 + 进度提示；知识库单创作者本地场景规模可控 |
| 编码误判 | charset 检测在极端编码下可能误判 | utf-8 优先强制，失败才回退 gbk，减少误判 |
| 正文含 HTML 注释 | 导出注入元数据注释可能污染正文 | 元数据注释置于文件头部，导入解析时剥离 `<!-- ... -->` 注释 |
