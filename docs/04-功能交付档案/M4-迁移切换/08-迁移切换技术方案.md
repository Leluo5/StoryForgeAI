## 一、目标

将旧架构「作品级 LLM 参数」（Agent 模型配置的完整校验 + 生成）迁移到新 NestJS 架构，补齐新架构 `model_config` 仅支持 `temperature`/`max_tokens` 的缺口。

**迁移后**：Agent 模型配置支持完整 LLM 参数（temperature / top_p / max_tokens / system_prompt / stream / frequency_penalty / stop 等），校验规则与旧语义对齐。

## 二、现状与约束分析

### 2.1 旧实现（agent_management/types.py）

| 参数 | 校验规则 | 默认值 |
|---|---|---|
| `model` | 字符串 | `""` |
| `temperature` | 数字，`0 ≤ x ≤ 2` | 0.7 |
| `top_p` | 数字，`0 ≤ x ≤ 1` | 1.0 |
| `max_tokens` | 整数（非 bool），`1 ≤ x ≤ 32768` | 2048 |
| `system_prompt` | 字符串 | `""` |
| `stream` | 布尔 | `false` |
| `frequency_penalty` | 数字 | 0.0 |
| `stop` | 数组 ≤4 项，每项字符串 ≤64 字符 | `[]` |

### 2.2 新架构现状

- `agent.model_config` 为 jsonb，**仅** `{ temperature, max_tokens }`（`agent.service.ts` L115）。
- **缺**：`top_p` / `system_prompt` / `stream` / `frequency_penalty` / `stop` 的完整校验与默认值。

### 2.3 硬约束

1. **校验对齐**：全部参数校验规则与旧语义一致（范围、类型、非 bool）。
2. **jsonb 存储**：`model_config` 仍是 jsonb，不拆列。
3. **向后兼容**：既有 `model_config` 仅含 `temperature`/`max_tokens` 的记录仍能读取，缺省字段补默认。

## 三、设计决策（多方案对比）

### 决策 1：model_config 结构 —— 松散 jsonb vs 类型化 jsonb

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 松散 jsonb（现状） | 灵活 | 无校验、易写脏数据 | ✗ |
| **B. 类型化 jsonb（Zod schema 校验）** | **写入时强校验、类型安全** | 需 schema | **✅ 推荐** |

**推荐 B**：定义 `modelConfigSchema`（Zod），Agent 创建/更新时对 `model_config` 整体校验，写入 jsonb。读取时合并默认值。

### 决策 2：校验位置 —— controller vs service

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. controller（`ZodValidationPipe`） | 入口即拦 | 仅 HTTP 层，内部调用不校验 | ○ 折中 |
| **B. service 内校验 + controller schema** | **双重保障、内部调用也校验** | 略冗余 | **✅ 推荐** |

**推荐 B**：controller 用 `ZodValidationPipe`（`createAgentRequestSchema` 含 `model_config`），service 保存前再做一次 `modelConfigSchema.parse`（兜底内部调用路径），确保任何入口都不写脏数据。

## 四、模块设计

### 4.1 模块结构

```
apps/api/src/agent/
├── model-config.ts                 # modelConfigSchema + 默认值 + 类型
├── agent.service.ts                # 扩展：model_config 校验 + 默认合并
└── agent.service.test.ts           # 扩展：model_config 校验测试
```

`packages/contracts/src/agent-config.ts` 扩展 `modelConfigSchema` + 导出类型。

### 4.2 model_config 完整 schema（对齐旧语义）

```ts
export const modelConfigSchema = z.object({
  model: z.string(),
  temperature: z.number().min(0).max(2).default(0.7),
  top_p: z.number().min(0).max(1).default(1.0),
  // max_tokens：整数 1-32768。
  // 评审修正 R2：移除不可达的 `.refine(v => typeof v !== 'boolean')` —— Zod 的 z.number()
  // 对 JSON 布尔 true/false 直接判 fail（invalid_type），refine 永不可达。
  // 改用 invalid_type_error 提供明确报错语义（boolean 输入已被 z.number() 拦截）。
  max_tokens: z.number({ invalid_type_error: 'max_tokens 须为整数' })
    .int().min(1).max(32768).default(2048),
  system_prompt: z.string().default(''),
  stream: z.boolean().default(false),
  frequency_penalty: z.number().default(0.0),
  stop: z.array(z.string().max(64)).max(4).default([])
});
export type ModelConfig = z.infer<typeof modelConfigSchema>;
```

### 4.3 核心逻辑（agent.service.ts 扩展）

#### 校验与默认合并（save 前）

```ts
private normalizeModelConfig(raw: unknown): ModelConfig {
  // refine 兜底：JSON 反序列化的 bool 可能被识别为 number，显式拒绝
  const cfg = modelConfigSchema.parse(raw);
  return cfg; // 缺省字段由 Zod default 补齐
}
```

Agent 创建/更新时：
```ts
agent.model_config = this.normalizeModelConfig(input.model_config);
```

#### 读取向后兼容（既有记录仅含 temperature/max_tokens）

读取时 `modelConfigSchema.parse` 自动补齐 `top_p`/`system_prompt`/`stream`/`frequency_penalty`/`stop` 默认值，旧记录无需迁移即可读。

## 五、边界与安全

| 项 | 处理 |
|---|---|
| 范围校验 | temperature 0-2、top_p 0-1、max_tokens 1-32768、stop ≤4 项每项≤64 |
| 类型校验 | max_tokens 拒绝 bool（Zod refine）；number 经 `.number()` 非 string |
| 双重校验 | controller `ZodValidationPipe` + service `parse` 兜底 |
| 向后兼容 | Zod default 补齐缺省字段，旧 `model_config` 记录可读 |
| jsonb 存储 | `model_config` 仍 jsonb，不拆列 |
| 归属校验 | 沿用 agent 服务（authorId → agent 归属） |

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| bool 被 Zod number 接受 | `refine(v => typeof v !== 'boolean')` 显式拒绝 |
| 旧记录缺字段致 parse 失败 | Zod `.default()` 补齐，parse 永不因缺省失败 |
| 内部调用绕过 controller 校验 | service 内 `parse` 兜底，确保内部路径也校验 |
| jsonb 脏数据 | 写入前统一 `normalizeModelConfig`，无绕过入口 |
