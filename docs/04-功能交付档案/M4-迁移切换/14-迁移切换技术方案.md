## M4-T12 数据迁移校验

### 目标
独立复跑迁移校验，确认 PG 数据与旧 JSON 全量一致，作为 cutover 的前置门禁。

### 方案
独立校验脚本 `legacy-verify.ts`（T11 已含骨架），产出结构化报告：

| 校验维度 | 方法 | 通过标准 |
|---|---|---|
| **关联** | `legacy_id_map` 覆盖全部引用 | 覆盖率 = 100% |
| **字段（评审修正 R6）** | 主键映射域**全量**比对：`work_id`/`agent_id`/`character_id`/`chapter_id` 逐条比对 | 100% 一致 |
| **字段（抽样）** | 非主键字段抽样：`title`/`content` 长度、`model_config` 键集 | 抽样内 100% 一致 |

> **抽样口径（评审修正 R6）**：主键映射域（`work_id`/`agent_id`/`character_id`/`chapter_id`）**全量**比对；
> 非主键字段抽样 **10%**，且使用**固定随机种子**（种子值写入报告，保证可复现）。

- **执行**：`tsx apps/api/src/database/legacy-verify.ts --source ./data`
- **输出**：`docs/05-测试与验收报告/M4-T12-数据校验报告.md`（逐域行数 + 差异清单 + 随机种子值）
- **门禁**：校验不通过**禁止**进入 T13 cutover。

### 参数与退出码（评审修正 R1）

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `--source <dir>` | 是 | — | 旧 `data/` 目录路径 |
| `--report <path>` | 否 | `docs/05-测试与验收报告/M4-T12-数据校验报告.md` | 报告输出路径 |
| `--strict` | 否 | 关 | 任一差异即 exit 1（供 CI 门禁 / 人工执行） |

| 退出码 | 语义 |
|---|---|
| `0` | 校验通过（各维度全部一致） |
| `1` | 存在差异（报告已产出，须人工裁决后方可继续） |
| `2` | 执行错误（参数缺失、连接失败、脚本异常） |

### 验收
1. 校验报告逐域行数一致；2. 孤儿数为 0；3. 幂等插入 0；4. 差异项有人工裁决记录。

## M4-T13 唯一写入方切换（cutover）

### 目标
将唯一写入方从旧 JSON 切换为 PG，完成架构切换。这是**不可逆操作**，需灰度 + 明确回滚代价。

### 评审修正 R2（实质缺陷修正）

原方案设计的「P2 双写比对 + `LEGACY_WRITE_ENABLED` 回滚开关」**在新架构无实现基础**，故重写：

1. **取消「双写」**：新架构（NestJS / TypeScript）从未写过 `data/*.json`，JSON 的唯一写入方是旧 Flask 进程。因此新侧不存在「写 JSON」的代码路径，双写在结构上不成立。改为**冻结旧写入 + 只读比对**：写入方自 P0 起即唯一落 PG。
2. **取消「秒级回滚开关」**：`LEGACY_WRITE_ENABLED` / feature flag 在 `apps/api/src/` 中无任何实现（已核实）。回滚**不是开关**，而是下述人工回切流程。
3. **「不可逆」与「秒级回滚」的自相矛盾已消除**：本任务不再宣称秒级回滚，改为明示回切代价（见下）。

### 方案：冻结旧写入 + 用户级灰度读 + 单写入方

| 阶段 | 动作 | 回切 |
|---|---|---|
| **P0 冻结** | 停机窗口内停旧 Flask 进程 + 旧后台任务；确认 `data/` 末次写入时间不再变化 | — |
| **P1 灰度读** | 用户级灰度：白名单用户前端指向新 API，其余仍指向旧 API；新侧读 PG、旧侧只读 JSON，**抽样比对读结果一致性** | 白名单清空（回到旧 API） |
| **P2 全量切新端点** | 前端全量指向新 API；旧服务降为**只读**（不接受写入）；写入方唯一落 PG | 前端路由开关切回旧 API |
| **P3 关停旧服务** | 停旧 Flask 服务，旧 JSON 冻结为快照（T14 清理前保留） | **人工回切**（见下） |
| **P4 稳定观察** | 观察流量、错误率、数据一致性 | **人工回切**（见下） |

### 回切流程与代价（替代原「回滚开关」）

**回切动作**（须人工授权，非自动）：
1. 从 P3 前保留的 `data/` 快照恢复旧 JSON（T11 的 `--restore` 语义）
2. 重启旧 Flask 服务，前端路由开关切回旧 API
3. 停止新侧写入

**回切代价（须明示）**：P2/P3 期间**新增于 PG 的数据在回切后不可用**——旧 JSON 未承接这部分写入，回切即丢失。因此：
- 回切仅适用于 **P2 早期 / P4 观察期初期**（新增数据量小）
- P4 后期回切代价过高，应改为**前向修复**而非回切
- 回切须经**回切授权人**确认，不得由执行人自行决定

### 灰度分流定义（评审修正 R5）

- **灰度主体**：前端路由开关（React 侧按用户白名单选择新 API 或旧 API）
- **灰度粒度**：**用户级**（非请求级）——新旧是两套独立进程，无统一流量入口，请求级分流无实现基础
- **写入约束**：灰度期间无论用户指向哪侧，**写入均落 PG**（旧侧只读），避免双写

### P0 执行步骤（评审修正 R7）

| 步骤 | 动作 | 校验方式 |
|---|---|---|
| 1 | 公告停机窗口（提前 1 个工作日） | 公告记录归档 |
| 2 | 停旧 Flask 进程 | 进程不存在 |
| 3 | 停旧后台任务（定时任务 / 队列消费者） | 任务列表为空 |
| 4 | 确认 `data/` 末次写入时间不再变化 | 快照比对 `mtime` |
| 5 | 记录停机时刻 + 执行人 + 回切授权人 | 写入验收报告 |

### 关键约束
- P0 前必须完成 T11 迁移 + T12 校验通过。
- P0 起写入方唯一为 PG；旧 JSON 在 P3 后仅作快照保留（T14 清理前）。
- 回切非自动、非秒级，须人工授权并明示数据丢失代价。

### 验收
1. P1 灰度读抽样一致（差异为 0 或已人工裁决）；2. P2 后写入唯一落 PG（旧 JSON 无新增）；3. P3 后旧 JSON 快照校验无变更；4. 回切流程文档化且经演练；5. P4 观察期错误率达标；6. 停机时刻与执行人已留痕。

## M4-T14 旧代码清理归零

### 目标
旧架构代码归零，新架构成为唯一实现。

### 评审修正 R3 / R4（事实修正）

- **R3**：`app.py` 是旧 **Flask** 主入口（1570+ 行），非 Nest 入口。Nest 入口为 `apps/api/src/main.ts`（保留）。
- **R4**：删除清单须**整文件删除**，非「分支级删除」。判断依据：新架构为 TypeScript，**不可能 import Python 模块**，因此 `work_manager.py` / `coze_client.py` 100% 属旧链路，无需「迁移复用分支」——若新侧确需复用其逻辑，须**先迁到 TS 再删旧文件**（该迁移已归入 M4-T2～T11 各任务，不在本任务执行）。

### 方案：分批删除 + 残留检查

**删除清单（T13 P4 稳定后执行）**：
- `app.py`（旧 **Flask** 主入口，1570+ 行；含 `app.register_blueprint` 注册块一并删除）
- `modules/`（**整目录**，7 个蓝图：含 `modules/agent_management/`、`modules/novel_creation/routes.py` 的 `run_70_workflow` 等）
- `work_manager.py`、`coze_client.py`（**整文件**，非分支）
- `modules/common/storage.py` 的 JSON 持久化路径（随 `modules/` 整删）
- `data/*.json` 的**运行时读取代码**（删除读取逻辑；`.json` 文件本身作为快照备份保留至归档）

**保留项**：
- `apps/api/src/main.ts`（Nest 入口，非删除对象）
- 新架构 TS 代码与旧 Python 代码**无 import 关系**，删除旧文件不影响新侧编译

**残留检查**：
- `grep -r "modules/" apps/` 确认新架构无旧引用（应为 0 命中）
- `git grep` 确认旧符号（`_agents.json` 等）无残留引用
- `pnpm ci` 全绿（lint / typecheck / build / test）
- `tsx apps/api/src/main.ts` 启动正常，核心流程可跑通

**执行顺序**：先删 `modules/`（无新侧引用，可直接删）→ 再删 `app.py` → 最后删 `work_manager.py`/`coze_client.py`。每删一批跑 `pnpm ci`。

### 验收
1. `modules/`、`app.py`、`work_manager.py`、`coze_client.py` 均删除且无新架构引用；2. `pnpm ci` 全绿；3. 残留检查 0 命中；4. 应用启动正常、核心流程可用。

## 执行依赖与顺序

```
T11 迁移脚本
  → T12 数据校验（门禁；exit 0 方可继续）
    → T13 cutover（P0 冻结 → P1 灰度读 → P2 全量切新 → P3 关停旧 → P4 观察）
      → T14 旧代码清理（T13 P4 稳定后）

```

**硬门禁**：
- T12 不过 → 不切 T13
- T13 P4 未稳定 → 不清理 T14
- T14 未归零 → 不收尾 T15

## 风险与应对（T12–T15 共性）

| 风险 | 应对 |
|---|---|
| cutover 数据不一致 | T12 门禁（`--strict` exit 1 阻断）+ P1/P2 读比对 |
| 清理漏删导致旧链路复活 | grep 残留检查 + `pnpm ci` 门禁 |
| 回切预案失效 | P2 前完成回切流程演练；回切代价（丢失 PG 新增）须书面确认 |
| 回切时机误判 | P4 后期不做回切，改前向修复（回切代价过高） |
| 路线图状态失真 | T15 逐项核对 + 文档版本一致 |
| 收尾回归不全 | 全量 e2e + 验收报告留痕 |
