## 一、目标

将旧架构 F6 聊天室房间模型（`modules/story_thread.py` 内存注册表 + `modules/plot/routes.py` sync-room）迁移到新 NestJS 架构，作为 M4 前置的最优先对象（牵动 plot 同步 + novel_creation 协作多线）。

**迁移后**：聊天室房间数据由 PG 持久化（替代内存注册表），SSE 流式推衍（替代长连接轮询），plot ↔ room 双向联动在新侧闭环。

---

## 二、现状与约束分析

### 2.1 旧实现（story_thread.py）

| 能力 | 旧实现 | 问题 |
|---|---|---|
| 存储 | 全局字典 `_rooms`（进程内存） | 进程重启丢数据；多进程不共享 |
| 并发 | 实例级 `threading.RLock`（同房间串行、跨房间并行） | 单进程内有效；多进程/多实例失效 |
| 容量 | `MAX_ROOMS = 10`，满抛 409「聊天室容量已满」 | 需保留（DoD #10 硬约束） |
| 会话 | 内存态不持久化（F6 指标「多线程隔离 100%」） | 与 PG 持久化目标冲突，需重新设计隔离语义 |

### 2.2 硬约束（F6 技术方案 §4.4 / DoD #10）

1. **容量上限**：同时最多 10 个聊天室，超出抛 409。
2. **多线程隔离 100%**：不同房间互不干扰。
3. **step 一步一断**：每次推衍只走一步，显式 `continue` 续跑。
4. **随机系统种子**：`random_seed` 保证房间内确定性。

### 2.3 新架构约束

- 新架构为 **NestJS + PostgreSQL 16**，多实例部署下内存注册表不可靠。
- 已有 `ai-task` 模块提供 SSE 流式模式（`ai-task.sse.ts`）：事件总线 + PG 事件表 + Last-Event-ID 断线重连。
- **无现成 chat-room 模块**（`Glob apps/api/src/**/*chat*` 无结果），需全新创建。

## 三、设计决策（多方案对比）

### 决策 1：房间存储 —— 纯内存 vs PG 持久化

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 纯内存注册表（复刻旧） | 实现简单、隔离自然 | 多实例不一致、重启丢状态 | ✗ 不符合新架构部署 |
| B. PG 表 + 内存缓存 | 持久化、可多实例 | 复杂度高，需缓存一致性 | ○ 折中 |
| **C. PG 表持久化 + SSE 流** | **跨实例可靠、可断线重连** | 需处理并发（行锁） | **✅ 推荐** |

**推荐 C**：房间状态持久化到 `chat_room` 表，推衍步骤流式经 SSE（复用 ai-task 事件总线模式）。容量上限用 PG 行数校验（`COUNT(*)` 事务内），并发用行锁（`SELECT ... FOR UPDATE`）保证同房间串行。

### 决策 2：隔离粒度 —— 房间级行锁 vs 进程内锁

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 进程内 RLock（复刻旧） | 简单 | 多实例失效 | ✗ |
| **B. PG 行锁（`FOR UPDATE`）** | **跨实例可靠、同房间串行** | 需事务管理 | **✅ 推荐** |

**推荐 B**：房间写操作（step/continue）在事务内 `SELECT ... FOR UPDATE` 锁房间行，保证同房间串行、跨房间并行（不同行锁互不阻塞），满足多线程隔离 100%。

### 决策 3：推衍流式 —— 轮询 vs SSE

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 前端轮询（旧长连接语义） | 简单 | 不实时、浪费请求 | ✗ |
| **B. SSE（复用 ai-task.sse.ts）** | **实时、断线重连、不丢事件** | 需事件表 | **✅ 推荐** |

**推荐 B**：复用 `AiTaskEventBus` 事件总线模式，新建房间级事件总线（key = `room:${roomId}`），推衍步骤写入 `chat_room_event` 表并广播，SSE 连接推送。

### 4.3 核心逻辑（ChatRoomService）

#### 容量上限（DoD #10）

```ts
async createRoom(authorId, workId, dto): Promise<ChatRoomEntity> {
  return this.dataSource.transaction(async (tx) => {
    // 归属校验：work ∈ author，否则 404
    await this.assertOwnedWork(tx, authorId, workId);
    // 容量校验：COUNT(chat_room WHERE work_id) < 10，否则 409
    const count = await tx.getRepository(ChatRoomEntity).count({ where: { work_id: workId } });
    if (count >= MAX_ROOMS) throw new ConflictException('聊天室容量已满');
    // 创建（id 由 DTO 或生成）
    return tx.getRepository(ChatRoomEntity).save({ ...dto, work_id: workId, status: 'idle' });
  });
}
```

#### step（一步一断，写操作行锁）

> **评审修正（R1）**：LLM 调用**移出长事务**——避免长事务持锁阻塞同房间操作。改为「短事务锁读状态 → 释放锁 → 调 LLM → 短事务写回状态+事件」，并发安全由「写回前校验 `status === 'running'` 且 `step_index` 未变」乐观兜底。

```ts
async step(authorId, workId, roomId, dto): Promise<ChatRoomEventEntity> {
  // 阶段1：短事务锁读状态（FOR UPDATE 快锁快放，不持锁等 LLM）
  const { room, expectedStep } = await this.dataSource.transaction(async (tx) => {
    const room = await tx.getRepository(ChatRoomEntity).createQueryBuilder('room')
      .setLock('pessimistic_write')
      .where('room.id = :roomId', { roomId })
      .andWhere('room.work_id = :workId', { workId })
      .getOne();
    if (!room) throw new NotFoundException('聊天室不存在');
    await this.assertOwnedWork(tx, authorId, workId);
    if (room.status !== 'running' && room.status !== 'idle') {
      throw new ConflictException('房间未就绪，不可推衍');
    }
    return { room, expectedStep: room.step_index };
  });
  // 阶段2：事务外调 LLM（不持锁，可并发，长耗时不阻塞）
  const stepResult = await this.deriveStep(room, dto);
  // 阶段3：短事务乐观写回（step_index 未变才写，否则重试/冲突）
  return this.dataSource.transaction(async (tx) => {
    const fresh = await tx.getRepository(ChatRoomEntity).createQueryBuilder('room')
      .setLock('pessimistic_write')
      .where('room.id = :roomId', { roomId })
      .andWhere('room.work_id = :workId', { workId })
      .getOne();
    if (!fresh || fresh.step_index !== expectedStep) {
      throw new ConflictException('房间状态已变化，请重试');
    }
    // 一步一断：step_index += 1，状态 running → paused（等待 continue）
    fresh.step_index += 1;
    fresh.status = 'paused';
    fresh.history.push({ step_no: fresh.step_index, content: stepResult, ...dto });
    await tx.getRepository(ChatRoomEntity).save(fresh);
    return this.appendEvent(tx, roomId, 'step', stepResult);
  });
}
```

#### continue（续跑下一步）

`continue` 同 step 结构：校验房间 `status === 'paused'`（非 paused 抛 409「房间未暂停」），`step_index + 1`，重新走一步。与 step 的区别是前置状态校验。

#### stream（SSE）

仿 `ai-task.sse.ts` 完整流程：归属校验 → SSE 头（`text/event-stream` + no-cache + keep-alive + X-Accel-Buffering）→ 推 snapshot（房间状态基线）→ `since`/`Last-Event-ID` 补取 `chat_room_event` 遗漏 → 订阅房间事件总线实时转发 → 15s 心跳 → close 清理。`key = room:${roomId}`。

## 五、边界与安全

| 项 | 处理 |
|---|---|
| 归属校验 | 所有操作先校验 `room.work_id ∈ work.author_id`，否则 404（仿 ai-task.sse.ts `assertOwnedTask`） |
| 容量并发 | `COUNT` 在事务内，配合客户端生成 `room_key` 幂等键（**评审修正 R4**：`(work_id, name)` 唯一会误拒同名房间，改为 `(work_id, room_key)` 唯一；`name` 可重复，`room_key` 唯一防并发重复创建） |
| 行锁 | 写操作 `FOR UPDATE`；读操作普通查询 |
| 输入校验 | 全部经 `ZodValidationPipe`（对齐既有端点） |
| 鉴权 | `SessionGuard` + `CsrfGuard`（写操作） |
| 事件幂等 | `event_seq` 单调递增（DB 序列），SSE 断线按 `Last-Event-ID` 补取不重复 |
| 超时 | LLM 推衍调用加超时（模型 provider 统一），超时标记房间 `failed` + 事件 |

## 七、验收标准

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 容量上限 | 第 11 个房间创建返回 409「聊天室容量已满」（单元测试覆盖） |

| 风险 | 应对 |
