## 一、目标

编写**一次性数据迁移脚本**，将旧 JSON 文件数据映射写入 PostgreSQL，完成数据层切换。迁移须**幂等、可校验、可回滚**，并在 dry-run 下验证映射正确性。

**迁移后**：新架构读写 PG 即得旧数据全量；旧 JSON 不再被读写（M4-T13 cutover）。

## 二、现状与约束分析

### 2.1 旧数据 → 新表映射

| 旧文件 | 主要结构 | 目标新表 |
|---|---|---|
| `data/works/*.json` | 作品/卷/章节 | `work` / `volume` / `chapter` |
| `data/projects/*.json` | 项目（含 LLM 参数） | `author` / `work`（项目≈作品） |
| `_agents.json` | 智能体（含 `versions[]`） | `agent` / `agent_version`（M4-T5） |
| `_roles.json` | 角色 | `character` |
| `_relations.json` | 关系 | `character_relation` |
| `_tools.json` | 工具（含 `is_default`） | `tool_agent`（部分唯一索引） |
| `_groups.json` | 分组（override + manual） | `agent_group_override` |
| `_role_map.json` | 角色版图 | `character_view` / `character_view_node` |
| `_knowledge_base.json` | 知识库条目 | `knowledge_entry` / `knowledge_entry_embedding` |
| `_workflows.json` | 工作流 | `workflow` |
| `_author.json` | 作者 | `author` |
| 其他（`_plot*.json` 等） | 剧情/树 | `plot_tree` / `plot_node` / `plot_group` / `plot_link` |

### 2.2 硬约束

1. **幂等**：脚本可重复执行，不产生重复数据（按业务键去重）。
2. **可回滚**：迁移前备份 `data/`，失败回滚备份；不破坏既有 PG 数据。
3. **可校验**：迁移后行数/字段/引用完整性校验一致。
4. **禁 synchronize**：脚本仅 `INSERT`/`UPSERT`，不改表结构（结构由 25 条迁移保证）。
5. **关联完整性**：外键顺序正确（author → work → chapter 等），父记录先迁。

## 三、设计决策（多方案对比）

### 决策 1：迁移执行方式 —— 独立脚本 vs TypeORM 迁移

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. TypeORM 迁移文件（up 里迁数据） | 随 `migration:run` 统一 | 结构变更与数据混在一起，down 破坏性 | ✗ |
| **B. 独立幂等脚本（`migrate-legacy-data.ts`）** | **与结构迁移解耦、可单独重跑、dry-run** | 需独立运行 | **✅ 推荐** |

**推荐 B**：独立脚本 `apps/api/src/database/migrate-legacy-data.ts`，`tsx` 直接运行，支持 `--dry-run`/`--source`/`--backup`。不注册进 `data-source.ts` migrations（结构迁移与数据迁移分离）。

### 决策 2：主键策略 —— 沿用旧 ID vs 重生成 UUID

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 沿用旧 ID（UUID 化映射）** | **关联关系不丢**（旧 ID → 稳定新 ID） | 需 ID 映射表 | **✅ 推荐** |
| B. 重生成 UUID | 简单 | 关联断裂，需大量外键重算 | ✗ |

**推荐 A**：建立 **`legacy_id_map`**（旧 ID → 新 UUID），保证跨表关联（如 chapter→work、character→work）迁移后仍完整。旧 ID 若是 UUID 直接沿用，非 UUID 则哈希生成稳定 UUID。

## 四、模块设计

### 4.1 模块结构

```
apps/api/src/database/
├── migrate-legacy-data.ts        # 主脚本（CLI 入口）
├── legacy-mappers/               # 各数据域映射器
│   ├── work.mapper.ts            # works → work/volume/chapter
│   ├── agent.mapper.ts           # _agents → agent/agent_version
│   ├── character.mapper.ts       # _roles/_relations → character/character_relation
│   ├── knowledge.mapper.ts       # _knowledge_base → knowledge_entry/embedding
│   ├── workflow.mapper.ts        # _workflows → workflow
│   └── id-map.ts                # legacy_id_map（旧ID→新UUID）
├── legacy-verify.ts             # 迁移校验（行数/引用完整性）
├── migrate-legacy-data.test.ts
└── legacy-mappers/*.test.ts
```

### 4.2 CLI 接口

```bash
# dry-run：不写库，只报告将写入的行数与映射
tsx apps/api/src/database/migrate-legacy-data.ts --dry-run --source ./data

# 正式执行（自动备份 data/）
tsx apps/api/src/database/migrate-legacy-data.ts --source ./data --backup ./data.backup-<ts>

# 回滚：恢复备份（脚本提供 --restore）
tsx apps/api/src/database/migrate-legacy-data.ts --restore ./data.backup-<ts>
```

### 4.3 核心流程（主脚本）

```ts
async function migrate(opts: MigrateOptions) {
  // 1. 备份旧数据（--backup）
  if (!opts.dryRun) await backupLegacyData(opts.source, opts.backup);
  // 2. 幂等清理（按业务键去重，防重复执行）
  await ensureIdempotentClean(opts); // 软删标记或按 source 标记清除上次迁移数据
  // 3. 逐域迁移（顺序：author → work → volume → chapter → agent → character → ...）
  const domains = [authorMapper, workMapper, chapterMapper, agentMapper,
                    characterMapper, relationMapper, toolMapper,
                    knowledgeMapper, workflowMapper, groupMapper, roleMapMapper];
  for (const mapper of domains) {
    const result = await mapper.run(opts); // dryRun 时只统计
    log(`[migrate] ${mapper.name}: ${result.inserted} inserted, ${result.skipped} skipped`);
  }
  // 4. 校验（行数/引用完整性）
  const verify = await legacyVerify(opts);
  if (!verify.ok && !opts.dryRun) throw new Error(`迁移校验失败: ${verify.errors}`);
  return verify;
}
```

### 4.4 ID 映射（id-map.ts）

```ts
export async function resolveNewId(tx, domain: string, legacyId: string): Promise<string> {
  const existing = await tx.getRepository(LegacyIdMapEntity).findOne(
    { where: { domain, legacy_id: legacyId } });
  if (existing) return existing.new_id;
  // 旧 ID 若是合法 UUID 直接沿用，否则确定性哈希 UUID
  const newId = isUuid(legacyId) ? legacyId : uuidFromHash(`${domain}:${legacyId}`);
  await tx.getRepository(LegacyIdMapEntity).save({ domain, legacy_id: legacyId, new_id: newId });
  return newId;
}
```

`LegacyIdMapEntity`（`legacy_id_map` 表）：`domain` / `legacy_id` / `new_id`，`(domain, legacy_id)` 唯一。**该表迁移后保留**，用于审计与追溯。

### 4.5 幂等保证

- 各 mapper 写入前按业务键（如 `coze_id`、`legacy_id`）查 `legacy_id_map`，已迁则 `skipped`。
- 全脚本可重复执行：重复运行只补漏，不重复插入。
- `ensureIdempotentClean`：可选清除上次迁移标记的数据（带 `migrated_from` 标记字段），防污染。

### 4.6 校验（legacy-verify.ts）

| 校验项 | 方法 |
|---|---|
| 行数 | 旧 JSON 条数 vs 新表行数（按域对比） |
| 字段 | 抽样字段比对（key 字段一致） |
| 引用完整性 | 外键孤儿检测（如 chapter.work_id 必须存在于 work） |
| 幂等 | 二次 dry-run 插入数为 0 |

## 五、边界与安全

| 项 | 处理 |
|---|---|
| 数据备份 | 迁移前自动备份 `data/`（`--backup`），失败 `--restore` 恢复 |
| 幂等 | `legacy_id_map` 去重 + 业务键查重，可重复执行 |
| 引用完整性 | 父域先迁（author→work→chapter），`legacy_id_map` 保关联 |
| 禁 synchronize | 脚本仅 INSERT/UPSERT，不改结构 |
| dry-run | 不写库，只报告行数与映射（评审前必跑） |
| 事务 | 每域一个事务，失败回滚该域，不污染已完成域 |
| 失败处理 | 校验失败抛错，主脚本退出非 0，CI 可感知 |
| 大文件 | 分批写入（chunk），防单事务过大 |

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| 大文件单事务过大 | 分批 chunk 写入，防死锁/超时 |
| 旧 ID 非 UUID | 确定性哈希生成稳定 UUID + `legacy_id_map` 映射 |
| 关联断裂 | 父域先迁 + `legacy_id_map` 保引用 |
| 迁移脚本自身 bug | dry-run 先验证 + 单域事务回滚 + 备份可恢复 |
| 数据脏（重复/缺失） | 幂等去重 + 校验报告暴露差异，人工裁决 |
| 结构未就绪 | 前置检查 25 条迁移已应用，否则拒绝执行 |
| 迁移期间写入 | cutover 前冻结写入（M4-T13），迁移期间只读旧数据 |

## 九、执行顺序（迁移批次）

```
1. 前置检查（结构迁移已应用）
2. --dry-run（报告映射）
3. 备份 data/
4. author → work → volume → chapter（作品域）
5. agent → agent_version → tool_agent（智能体域）
6. character → character_relation → character_view（角色域）
7. knowledge_entry → embedding（知识库域）
8. workflow → agent_group_override（工作流/分组域）
9. legacy_id_map 全量落库
10. 校验（行数/字段/引用完整性）
```
