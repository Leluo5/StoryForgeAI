## 二、关键实现决策

| # | 决策点 | 落地 |
|---|---|---|
| 1 | 校验结构 | **类型化 jsonb**（方案决策 1 推荐 B）。契约 `modelConfigSchema` 强校验，`model_config` 仍为 jsonb 不拆列 |
| 2 | 校验位置 | **controller `ZodValidationPipe` + service `normalizeModelConfig` 兜底**（方案决策 2 推荐 B）。任何入口（含内部调用）都不写脏数据 |
| 3 | schema 命名 | 复用已有 `modelConfigSchema`（V1）而非方案 §4.1 提议的另建 schema；`modelConfigV2Schema` 保留为别名，避免重复定义与两处漂移 |
| 4 | `model` 字段 | **`.optional()` 而非方案 §4.2 的必填**。理由：新架构 model 由 `agent.model_id` 承载，`model_config.model` 冗余；optional 时 Zod 缺省不输出该键，兼容旧迁移数据 |
| 5 | max_tokens 类型 | **`.number({ invalid_type_error })` + `.int()`**（评审修正 R2）。Zod `z.number()` 对 JSON 布尔直接判 `invalid_type`，`.refine` 永不可达，已移除 |
| 6 | 向后兼容 | **Zod `.default()` 自动补齐**，旧 `{temperature, max_tokens}` 记录读取即补全，**无需数据迁移** |
| 7 | web 表单 | 表单仅编辑 `temperature`/`max_tokens`，提交时展开 `DEFAULT_MODEL_CONFIG` 完整字段，避免契约层缺字段 422 |

## 五、实现过程中的关键问题与解决

### 问题 1：CI 门禁「异常久」的排查

**现象**：完整 CI 长时间无响应，疑似挂死。

**定位**：逐阶段执行定位——contracts build（~5s）、lint（~1min）、typecheck（~1min）、node test（4.1s）均正常；耗时集中在**全量单测（串行 1463s / 24.4 分钟）**，此为 `--no-file-parallelism` 串行全量单测的固有耗时，非挂死。

**叠加根因**：先前多次强杀 vitest 导致 `pg_terminate` 未执行，测试连接残留持有 `pg_advisory_xact_lock`，后续测试**等待锁而挂起**，表现为「卡死」。

**解决**：清理残留连接后全量单测正常完成（207 文件 / 1948 测试全绿）。CI 真实时长 ≈ 25-30 分钟，瓶颈为串行全量单测。

### 问题 2：web 表单提交触发契约层 422

**现象**：契约 `modelConfigSchema` 升级为全字段 `.default()` 后，web 表单仅提交 `temperature`/`max_tokens`，TS 类型 `ModelConfig` 要求字段齐全。

**解决**：`agent-client.ts` 导出 `DEFAULT_MODEL_CONFIG`，表单提交时展开完整默认字段（服务端 `parse` 仍会补默认，双保险）。
