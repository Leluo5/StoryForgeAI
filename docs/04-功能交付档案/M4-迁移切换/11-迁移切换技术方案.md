## 一、目标

将旧知识库侧独有的端点迁移到新架构：
1. **`detect-type`**：文本自动判定知识条目类型（复用 `classify.ts` 11 类判定）。
2. **`similar`**：向量相似条目检索（复用 `embedding.provider.ts`）。
3. **`markdown-render` / `markdown-export`**：条目 Markdown 渲染与导出。

**迁移后**：知识库完整能力（判定 / 相似检索 / Markdown）在新侧可调用，不依赖旧 Flask。

## 二、现状与约束分析

### 2.1 旧端点语义（knowledge_base/routes.py）

| 旧端点 | 关键语义 |
|---|---|
| `POST /detect-type` | 输入文本 → 判定条目类型（11 类：character/scene/item/organization/event/technology/concept/location/quote/note/other） |
| `GET /entries/<id>/similar` | 向量相似条目（经 embedding 检索，返回 Top-N + 相似度） |
| `POST /markdown/render` | 条目 → Markdown 渲染 |
| `POST /markdown/export` | 批量导出条目为 Markdown |
| `POST /<id>/extract-outline` | 抽取条目大纲 |

### 2.2 新架构现状

| 能力 | 现状 |
|---|---|
| 条目 CRUD（create/list/get/update/softDelete/restore/permanent/restructure/flags/summary） | ✅ `entries.controller.ts` 10 端点 |
| 类型判定 | ✅ `classify.ts` `classifyEntryType`（11 类，规则判定），**无 HTTP 入口** |
| 向量检索 | ✅ `embedding.provider.ts` / `embedding.llm.ts`（provider + mock），`knowledge-entry-embedding.entity.ts` 已建 |

| 大纲抽取 | ❌ 缺口（依赖 LLM） |

### 2.3 硬约束

1. **判定规则对齐**：11 类判定与旧 `classify` 一致（规则表见知识库条目分类规则）。
2. **向量检索**：经 embedding provider（mock 兜底），相似度阈值过滤。
3. **归属校验**：条目属作品/作者，经 `authorId` 归属校验。

## 三、设计决策（多方案对比）

### 决策 1：detect-type 判定 —— LLM vs 规则

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. LLM 判定（prompt） | 准确、可处理模糊 | 成本、延迟、不确定 | ○ 折中 |
| **B. 规则判定（复用 classify.ts）+ LLM 兜底** | **快、确定、零成本；模糊时兜底** | 规则覆盖有限 | **✅ 推荐** |

**推荐 B**：优先 `classifyEntryType` 规则判定（零成本确定）；规则置信度低时走 LLM 兜底（`embedding.llm.ts` 同款 LLM 调用）。与既有 `classify.ts` 保持一致。

### 决策 2：similar 检索 —— embedding provider vs 关键词

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. embedding 向量（复用）** | **语义相似、已建 entity** | 需 embedding 就绪 | **✅ 推荐** |
| B. 关键词全文检索 | 简单 | 语义弱 | ✗ |

**推荐 A**：复用 `knowledge-entry-embedding.entity.ts` + `embedding.provider.ts`，余弦相似度检索 Top-N，阈值过滤。

## 四、模块设计

### 4.1 模块结构

```
apps/api/src/knowledge/
├── entries.classify.controller.ts   # detect-type 端点（薄封装 classifyEntryType）
├── entries.similar.controller.ts    # similar 检索端点（经 embedding provider）
├── entries.markdown.controller.ts   # markdown render/export 端点
├── markdown.service.ts              # Markdown 渲染/导出（纯函数 + 序列化）
└── markdown.service.test.ts
```

`entries.module.ts` 注册新 controller；注入 `embedding.provider`、`KnowledgeEntriesService`。

### 4.2 端点

| 方法 | 路径 | 服务/能力 | 说明 |
|---|---|---|---|
| POST | `/ai-knowledge/detect-type` | `classifyEntryType` | 文本 → 11 类判定 + 置信度 |
| GET | `/ai-knowledge/entries/:entryId/similar` | embedding 检索 | 相似条目 Top-N（query 参：`top_k`） |
| POST | `/ai-knowledge/markdown/render` | `markdownService.render` | 条目 → Markdown |
| POST | `/ai-knowledge/markdown/export` | `markdownService.export` | 批量导出 Markdown |

### 4.3 detect-type（规则 + LLM 兜底）

```ts
async detectType(authorId: string, input: { content: string }): Promise<ClassifyResult> {
  // 1. 规则判定（classifyEntryType，零成本）
  const rule = classifyEntryType({ content: input.content });
  // 2. 规则未命中 → LLM 兜底（embedding.llm.ts 同款调用）
  // 评审修正 R4：不硬编码 confidence 阈值 —— 既有 classify.ts 的 ClassifyResult 未必含 confidence 字段。
  // 触发条件对齐既有语义：规则判定结果为 'other'（未命中 11 类）时走 LLM 兜底。
  // 若编码时确认 ClassifyResult 含 confidence，可改用阈值判定，但须与 F5 知识库判定语义一致。
  if (rule.type === 'other') {
    const llm = await this.classifyByLlm(input.content);
    return llm;
  }
  return rule;
}
```

### 4.4 similar（向量检索）

```ts
async similar(authorId: string, entryId: string, topK = 5): Promise<SimilarResult[]> {
  const entry = await this.entriesService.getEntry(authorId, entryId); // 归属校验 + 向量就绪
  const vec = await this.embeddingProvider.embed(entry.content);
  // 余弦相似度检索同库条目（排除自身），Top-N + 阈值过滤
  return this.searchByCosine(authorId, vec, entryId, topK, 0.7);
}
```

### 4.5 markdown（渲染/导出）

纯函数序列化：条目字段（标题/类型/标签/正文/关联）→ Markdown。导出返回多条目合并 Markdown（`_markdown_io` 移植）。

## 五、边界与安全

| 项 | 处理 |
|---|---|
| 11 类对齐 | 复用 `classify.ts`，不另立类型表 |
| 相似度阈值 | 默认 0.7 过滤低质结果；`top_k` 上限（防大结果集） |
| embedding 未就绪 | mock provider 兜底（既有机制），不报错 |
| 归属校验 | 条目属作品/作者（`getEntry` 内含） |
| Markdown 注入 | 输出经转义，避免原始内容注入（XSS/Markdown 注入） |
| 鉴权 | `SessionGuard` + 写操作 `CsrfGuard` |
| 输入校验 | `ZodValidationPipe` + schema（`top_k` 1-50、`content` 非空） |

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| 规则判定覆盖不足 | 低置信度走 LLM 兜底（决策 1） |
| embedding 模型不可用 | mock provider 兜底（既有机制），返回降级结果 + 标记 |
| 相似检索性能 | 向量列存 PG（既有 entity），`top_k` 上限限制结果集 |
| Markdown 注入 | 输出转义，避免 XSS/Markdown 注入 |
| 既有服务签名 | 编码前核对 `entries.service.ts` 方法签名（getEntry 归属校验） |
