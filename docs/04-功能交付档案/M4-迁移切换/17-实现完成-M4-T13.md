## 二、编码中发现的缺陷与修复（T13 真实数据触发）

### 2.1 workflow 同名唯一约束冲突（真实数据缺陷）

- **现象**：真实 `data/workflows/_global/*.json` 有 **15 个同名「章节流」**（旧 JSON 按 `id` 区分，允许同名），而 `ai_workflows` 表有 `UNIQUE(author_id, name)`（`uq_ai_workflows_author_name`），迁移第 2 条即冲突。
- **根因**：T11 fixture 数据无重名，掩盖了该唯一约束问题；真实数据暴露。
- **修复**（`workflow.mapper.ts` 新增纯函数 `dedupeWorkflowName`）：同作者同名追加 `" (2)"`、`" (3)"`… 后缀，保留全部 15 条且 `id` 不变；`legacy-verify.ts` 的 workflow 字段比对同步复用该函数重算期望 name，保证迁移/校验一致。
- **新增测试**：`migrate-legacy-data.test.ts` 新增 `M4-T13 dedupeWorkflowName` describe（3 用例：15 个同名去重 / 不同名不受影响 / 跳过已占用后缀）。

### 2.2 legacy_id_map 覆盖率语义修正

- **现象**：正式校验发现覆盖率 94.5%（9 条未映射主键），全部是 **DB 迁移前已存在的开发期预置数据**（works 5 / agents 2 / characters 2 的 fixture id），非本次迁移产物。
- **根因**：`verifyIdMapCoverage` 原实现要求「全表主键 ⊆ map」，对迁移前已存在的开发期数据过度严格；fixture 测试库干净未暴露。
- **修复**（`legacy-verify.ts` `verifyIdMapCoverage`）：语义改为**迁移产物可追溯**——主门禁检查 `legacy_id_map` 每条映射的 `new_id` 必须存在于目标表（迁移产物完整落库）；目标表主键但无映射（开发期预置）仅计入参考，不阻断。
- **测试对齐**：`legacy-verify.test.ts`「有差异时退出码 1」用例改为删除**目标表行**（character 实体）模拟迁移产物不可追溯（旧用例删除 map 记录在新语义下不再是差异）。

## 三、回切预案（方案 14 人工回切流程）

cutover 为**不可逆操作**，旧代码保留（T14 前不删），回切须**人工授权**：

1. 从 `data.backup-20261127155909/` 快照恢复旧 JSON（`migrate-legacy-data.ts --restore <备份目录>` 语义）。
2. 重启旧 Flask 服务，前端路由开关切回旧 API。
3. 停止新侧写入。

**回切代价（须明示）**：P2/P3 期间**新增于 PG 的数据在回切后不可用**——旧 JSON 未承接这部分写入。因此回切仅适用于切换初期（新增数据量小）；后期应改为**前向修复**而非回切。回切须经**回切授权人**确认，不得由执行人自行决定。
