## 四、评审意见（修正项）

### 🔴 R1（必改）：T2 step 的 LLM 调用在长事务内

**问题**：T2 §4.3 `step` 在 `this.dataSource.transaction` 内调用 `deriveStep(room, dto)`（LLM 推衍），LLM 请求耗时可达数秒至数十秒，**长事务持锁**会阻塞同房间后续操作，且连接/事务资源占用高。

**建议**：改为「锁 → 读状态 → **释放锁** → 调 LLM → 再开短事务写回状态+事件」。即 LLM 调用移出事务，仅状态读取与写入在事务内；并发安全由「写回前校验 `status === 'running'` 且 `step_index` 未变」兜底（乐观并发）。若需严格串行，可保留 `FOR UPDATE` 但将 LLM 调用前置到事务外。

### 🟡 R2（建议改）：T2 `event_seq` 多实例递增冲突

**问题**：T2 §4.2 `chat_room_event.event_seq` 单调递增，但多实例部署下应用层递增可能并发冲突（两实例同时取 `max+1`）。

**建议**：改用 **PG 序列**（`serial` 或 `BIGSERIAL`）作为 `event_seq` 生成源，或房间级 `(room_id, event_seq)` 用序列保证唯一。SSE 断线游标逻辑不变。

### 🟡 R3（建议改）：T3 pull 去重依赖 step_no 不复用

**问题**：T3 §4.2 pull 去重按 `(room_id, step_no)`，若房间 `history` 被清空重建（或房间重建后 `step_index` 归零），同一 `step_no` 会被误判为已存在而跳过。

**建议**：去重键改为 `origin` 全标记 `sync-room:${roomId}:${step_no}`，并在 `plot_node.origin` 唯一约束下判重；或 pull 时先校验房间 `created_at`，仅回写该时间之后的步骤。

### 🟡 R4（建议改）：T2 `(work_id, name)` 唯一约束可能误伤同名房间

**问题**：T2 §5 建议「`(work_id, name)` 唯一防并发重复创建」，但 F6 允许同名房间（用户可命名相同），唯一约束会误拒合法创建。

**建议**：容量防重改用「事务内 `COUNT` + 应用层幂等键（客户端生成 `room_key`）」，不强制 `name` 唯一；`name` 可重复但 `room_key` 唯一。

### 🟡 R5（建议改）：T3 push 与 pull 的事务粒度未明确

**问题**：T3 §4.2 push 注入 `updateContext` + 返回节点、pull 回写节点，但未明确事务边界（是单事务还是分步）。

**建议**：明确 push 为「读节点 + 更新 context」单短事务；pull 为「读 history + 批量回写」单事务（`batchCreateNodes` 内已含事务，复用其原子性）。文档补充事务边界说明。
