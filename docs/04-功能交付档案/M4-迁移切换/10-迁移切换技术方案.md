## 一、目标

将旧链路 `modules/plot/role_map_ai.py` 的「角色关系图谱自动生成（AI 建图）」能力，迁移到新架构的 character-relation 模块，满足以下完成标准：

1. 新架构 character-relation 模块新增 **AI 建图服务**：输入已入库角色列表 → LLM 生成关系边 → 写入 `character_relations` 表。
2. **复用 LLM 调用**，走新 AI 链路（`ai_task` 队列）。
3. 建图结果经 `character-relation-type.seed.ts` 的归一规则表校验（**关系类型归一**）。

### 1.1 用户三项决策（已确认，硬约束，不可偏离）

| # | 决策 | 含义 |
|---|---|---|
| **D1** | 建图输入源 = 仅基于已入库角色建边 | 角色已存在（`character` 表），LLM 只生成关系边 `relations[]`，**不抽取角色** |
| **D2** | 执行链路 = ai-task 队列（新 scope） | 复用 M4-T7 队列 + processor 分支模式 |
| **D3** | 落点 = 写 `character_relations`，不新建角色 | `origin='ai'`，缺失对端角色跳过该边（**不报错**） |

> **这三项决策推翻了旧版方案的「三阶段 extract→preview→commit + draft 表 + 写角色表」设计**。新方案为 **「单步生成 + 直接落库」** 模式：
> - 无 `preview` / `commit` 二阶段
> - 无 draft 表
> - 不写 `character` 表（不新建角色）

## 三、设计决策：多方案对比

### 3.1 决策 A：新 scope 命名与 tool 标识

| 方案 | scope | tool | 说明 |
|---|---|---|---|
| **A1（推荐）** | `character_map` | `character_map_generate` | 语义清晰，与既有 `character`（角色资料）、`role_profile`（F11）区分；tool 走 `ai_tools` 权威校验 |
| A2 | `character` | `character_map_generate` | 复用 `character` scope，但与角色资料任务混同，processor 分支难区分 |
| A3 | `role_map` | `role_map_generate` | 沿用旧链路命名，但与 `character` 域命名不一致 |

**推荐 A1**：`scope='character_map'` + `tool='character_map_generate'`。理由：新 scope 有独立 context 类型与 processor 分支，语义隔离清晰；`ai_tasks.scope` CHECK 重建模式已有先例（M4-T7），成本低。

### 3.2 决策 B：LLM provider 适配方式

| 方案 | 说明 |
|---|---|
| **B1（推荐）** | 新增 **`CharacterMapModelProvider` 接口**（或 `generateCharacterMap` method），专用于 character 域建图 |
| B2 | 复用 `AiModelProvider.generate` 加新 method（重载） |
| B3 | 强行复用章节域 `AiModelContext`（不合适：baseDocument 是 ProseMirror，与建图输入结构不兼容） |

**推荐 B1**：新增独立接口，输入/输出契约清晰，避免污染章节域。参考 `CharacterAvatarModelProvider` 的独立 provider 模式。

### 3.3 决策 C：建图执行 handler 的落库策略

| 方案 | 说明 |
|---|---|
| **C1（推荐）** | 单步生成 + 直接落库：LLM 返回 → 归一匹配 → 批量写 `character_relation`（`origin='ai'`） |
| C2 | 保留旧方案「extract→preview→commit」三阶段（**已被用户决策推翻**） |
| C3 | 写入 draft 表暂存，人工确认（**已被用户决策推翻**） |

**推荐 C1**：完全对齐用户三项决策（D1/D2/D3），单事务写库，失败整体回滚（任务标 failed）。

### 4.2 scope 与 tool

- **scope**：`'character_map'`（加入 `aiTaskScopeSchema`、`AiTaskEntity.scope` 类型、processor `ProcessContext` 联合、`startRunning` 分支、`process` 分支、`markFailed` 可选清理）

### 4.3 LLM 契约

**输入**（已入库角色列表，由 handler 从 `character` 表读取）：

```ts
interface CharacterMapInput {
  characters: Array<{
    id: string;        // 角色 UUID
    name: string;      // 角色名（LLM 引用用）
    identity: string | null;  // 身份/简介（提供语义上下文）
  }>;
  relationTypes: Array<{ code: string; label: string; group_label: string; directed: boolean }>; // 归一类型上下文
}
```

**输出**（LLM 返回，仅关系边，不含角色）：

```ts
interface CharacterMapRelation {
  from: string;          // 角色 name 或 id 引用
  to: string;            // 角色 name 或 id 引用
  relation_type: string; // 归一类型 code 或 label
  note?: string;         // 关系备注（写入 label 或 tag）
  directed?: boolean;    // 可选覆盖，默认取类型 directed
}
interface CharacterMapOutput {
  relations: CharacterMapRelation[];
}
```

**Provider 接口**：

```ts
interface CharacterMapModelProvider {
  generateCharacterMap(input: CharacterMapInput): Promise<CharacterMapOutput>;
}
```

### 4.4 CharacterMapService

```ts
class CharacterMapService {
  /** 入队建图任务（D2）：走 ai-task 队列，scope='character_map' */
  async enqueue(authorId, workId, { idempotencyKey? }): Promise<{ task: AiTask; created: boolean }>;

  /** 进度查询：复用 ai-task SSE/事件，按 taskId 查状态 */

```

- `enqueue` 内部调 `createCharacterMapTask(authorId, workId, { tool: 'character_map_generate', inputSummary, idempotencyKey })`
- 幂等键建议：`character_map:generate:{workId}`（同一作品同一时刻仅一个建图任务，重复触发返回既有任务）
- 作品归属校验（work_id + author_id）→ 404

### 4.5 CharacterMapTaskHandler（建图执行）

```
handle({ taskId, authorId, workId, tool, inputSummary }):
  1. 读取已入库角色列表（D1）：character 表 where work_id，过滤未归档（status != archived）
     - 不足 2 个角色 → 直接成功（无意义建边，写 summary { skipped: 'insufficient_characters' }）
  2. 读取归一类型表：character_relation_types where work_id（首次需 seedCharacterRelationTypes）
  3. 调 CharacterMapModelProvider.generateCharacterMap(input) → CharacterMapOutput
  4. 解析 relations[]（对每边）：
     a. 解析 from/to 引用 → 角色 id（按 name 或 id 精确匹配；匹配不到 → 跳过该边，D3）
     b. 自环（from.id === to.id）→ 跳过
     c. 无向边去重：computePairKey(a, b)，重复 → 跳过
     d. 类型归一：relation_type → 匹配 code 或 label → type 实体；匹配不到 → fallback 第一个类型（复刻 confirmRelationItem）
     e. 调用 CharacterRelationService.create(authorId, workId, {
          source_id, target_id, type_id, directed, label, tag, origin: 'ai'
        })  —— 幂等重复返回 created=false，不报错
  5. 返回 summary { generated, created, skipped, typeFallbacks }
```

**异常语义**：
- LLM 失败 → 抛 `AiModelError`（retryable）→ processor 重试 → 最终 failed
- 单边落库失败（非幂等类）→ 整体抛错 → 事务回滚 → 任务 failed（**不静默吞**）
- 缺失对端角色 / 自环 / 重复 → **跳过不报错**（D3 硬约束）

## 五、边界与安全

| 边界 | 约束 |
|---|---|
| 作品归属 | 所有读/写均在 `work_id` + `author_id` 校验内，跨作品访问 → 404 |
| 角色未归档 | 建图输入过滤 `status != archived`；落库 `create` 内部再校验 |
| 缺失对端角色 | **跳过该边，不报错**（D3）；计入 `summary.skipped` |
| 自环 | `from === to` 跳过（`character_relations_not_self` CK 兜底） |
| 无向边去重 | `computePairKey` + `UNIQUE (work_id, pair_key, type_id)`，幂等返回 `created=false` |
| 类型归一 | code/label 匹配，匹配不到 fallback 第一个类型（不阻塞建图） |
| LLM 失败 | 抛 `AiModelError` retryable，processor 重试后 failed |
| 单边落库失败 | 整体回滚（非幂等异常不静默） |
| 幂等键 | 同一作品同一时刻仅一个建图任务 |
| 工具启用 | `ai_tools` 权威校验，未启用 → 409 `AI_TOOL_DISABLED` |
| 写入方式 | 仅 `origin='ai'`，**不新建角色**（D3），不改 `character` 表 |

|---|---|
| LLM 返回格式不稳定 | 严格解析：from/to 引用解析失败跳过该边；relation_type 缺失 fallback；整体解析异常 → 任务 failed |
| 建图重复触发 | 幂等键 `character_map:generate:{workId}` 去重 |
| 大量角色/边 | 单事务批量写；角色数上限告警（如 >100 提示，不阻塞） |
| 类型 seed 未执行 | handler 先 `seedCharacterRelationTypes` 幂等 seed |
| 与现有 character scope 混淆 | 独立 scope `character_map` + 独立 handler，processor 分支明确 |
| 方案 13 文档偏差 | 本方案注明，后续文档同步修正（§35/§182/§235） |
| 旧链路残留 | 迁移完成并验证后，旧 `role_map_ai.py` 标记废弃（后续任务处理） |
