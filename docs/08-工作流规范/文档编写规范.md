# 文档编写规范

> 版本：v1.0 · 状态：生效（2026-11-10）
> 适用范围：`docs/` 全部文档、项目根 `README.md`、各功能交付档案
> 维护：08-工作流规范｜关联：[文档中心](../README.md)、[开发规范](../02-技术与架构/开发规范/README.md)
> 权威性：格式与质量以本规范为准；编写流程与角色分工以 SpecForge 工作流（`项目工作流`）为准。

---

## 一、总则

### 1.1 目的

统一本项目（StoryForgeAI —— Coze 作品展示与在线体验平台）所有文档的**分类归属、格式表现、内容深度、流转流程与验收标准**，使任何人在任何时间打开任意一篇文档，都能快速回答三个问题：

1. 这篇文档解决什么问题、给谁看；
2. 结论是什么、依据在哪里；
3. 结论是否仍然有效、过期后由谁更新。

### 1.2 强制性级别

| 级别 | 关键词 | 含义 | 违反后果 |
| --- | --- | --- | --- |
| **MUST** | 必须 | 不可协商的硬性要求 | P0 问题，禁止合并发布 |
| **SHOULD** | 应当 | 默认执行，偏离需在文档内注明理由 | P1 问题，本轮迭代修复 |
| **MAY** | 可以 | 可选做法，用于统一风格 | P2 问题，下次维护修正 |

### 1.3 四项基本原则（MUST）

| 原则 | 要求 |
| --- | --- |
| **单一事实来源（SSOT）** | 同一信息只允许一处权威正文，其他文档通过链接引用，禁止复制粘贴 |
| **结论先行** | 每篇文档开头先给结论 / 摘要，再展开论证；每节先给判断，再给依据 |
| **可执行** | 规则必须具体到"谁在什么场景做什么、做到什么程度"，禁止"遵循最佳实践"这类空话 |
| **可验证** | 命令可复制执行、路径可点击到达、数据标注时点与来源、结论附证据链接 |

### 1.4 语言规范（MUST）

- 正文使用**简体中文**；技术标识（`Flask`、`requests`、`Coze`、`PAT Token`、`SSE`、`JWT`）保留英文原文。
- 中英文之间加半角空格；中文标点用全角，数字与单位用半角（`3000 毫秒`、`-731.2 KB`）。
- 禁止口语化、网络用语、情绪化表达。
- 禁止使用 Emoji 作为状态标记；统一使用文字标签（见 3.8）。
- 面向用户的操作步骤使用第二人称"你"，面向研发的规范使用陈述句，禁止混用。

### 1.5 冲突与例外

- 本规范与 SpecForge 工作流在**流程**上冲突时，以 SpecForge 工作流为准；在**格式**上冲突时，以本规范为准。
- 历史日志（`09-历史日志/`）与归档（`docs-archive/`）为历史证据，**不适用**本规范的格式条款，只读不改。
- 例外必须显式声明：在文档头注明"豁免条款 + 理由 + 责任人"，不得静默违反。

## 二、文档分类与定位

### 2.1 分类总览（MUST）

| 编号 | 文档类型 | 存放位置 | 主要读者 | 生命周期 |
| --- | --- | --- | --- | --- |
| 1 | 产品文档 | `01-产品与设计/` | 全员 | 长期，随产品迭代 |
| 2 | 设计文档 | `01-产品与设计/设计系统/` | 前端、设计 | 长期，随视觉迭代 |
| 3 | 技术文档 | `02-技术与架构/` | 研发 | 长期，随架构演进 |
| 4 | 架构决策记录（ADR） | `02-技术与架构/架构决策记录/` | 研发 | 永久，只增不改 |
| 5 | 规划与路线 | `03-规划与路线/` | 产品、研发 | 长期，按里程碑更新 |
| 6 | 功能交付档案 | `04-功能交付档案/` | 产品、研发、测试 | 功能上线后冻结 |
| 7 | 测试与验收报告 | `05-测试与验收报告/` | 研发、测试 | 验收后冻结 |
| 8 | BUG 修复报告 | `06-BUG修复档案/` | 研发 | 永久，只增不改 |
| 9 | 运维 / 上线手册 | `07-上线与运维/` | 运维、研发 | 长期，随流程更新 |
| 10 | 工作流规范 | `08-工作流规范/` | 全员 | 长期，严格版本化 |
| 11 | 历史日志 | `09-历史日志/` | 全员（追溯用） | 永久，只读 |

> 当前项目 `docs/` 下已有的文档按上表归类；`superpowers/` 是工作流产出物的即时存放区（若有），功能上线后归档到 `04-功能交付档案/`。

### 2.2 技术文档

**定位**：描述系统"是什么、怎么分层、为什么这样设计、改动时动哪里"。

**MUST 包含**：背景与约束 → 分层/模块清单 → 关键数据流 → 接口与数据结构 → 风险与回滚 → 关联文件路径。

**禁止**：粘贴大段业务代码、写产品需求、复制其他文档正文。

**示例**：[技术栈](./02-技术与架构/技术栈.md)、[目录结构](./02-技术与架构/目录结构.md)。

### 2.3 产品文档

**定位**：描述"为谁解决什么问题、做什么不做什么、如何判断做成了"。

**MUST 包含**：问题与背景 → 目标用户 → 价值主张 → 范围（含明确不做的部分）→ 核心流程 → 验收标准 → 衡量指标。

**禁止**：出现技术实现细节（框架、表结构、接口名）——这些归技术文档。

**示例**：[项目概述](./01-产品与设计/项目概述.md)。

### 2.4 设计文档

**定位**：描述视觉与交互的"可复用规则"，而非单页稿。

**MUST 包含**：设计原则 → 设计令牌（颜色/字号/间距）→ 组件与状态 → 动效规则 → 无障碍要求 → 与代码的落地映射。

**说明**：本项目为原生 CSS 变量浅/深主题，设计文档应覆盖主题令牌与三种交互模式（`chat`/`form`/`mixed`）的视觉规则。

### 2.5 功能交付档案

**定位**：一个功能从需求到上线的完整证据链。

**MUST 包含**：需求与验收标准 → 技术方案 → 任务拆解 → 实施记录（含验证）→ 上线结论。四者缺一不可，缺失时须注明原因与责任人。

**结构规则**：每个功能一个子目录，三份固定分册（`01-需求澄清.md` / `02-技术方案.md` / `03-任务规划.md`）；超过 1000 行或 60 KB 时，按 3.14 拆为"索引 + 分册"，不得继续单篇膨胀。

**本项目功能清单**（已归档）：

| 功能编号 | 功能名 | 子目录 |
| --- | --- | --- |
| F1 | 资源拉取与批量导入 | `04-功能交付档案/F1-资源拉取与批量导入/` |
| F2 | 作品管理与访问码控制 | `04-功能交付档案/F2-作品管理与访问码控制/` |
| F3 | 在线体验 | `04-功能交付档案/F3-在线体验/` |
| F4 | 站点设置 | `04-功能交付档案/F4-站点设置/` |

### 2.6 API 文档

**定位**：调用方无需读源码即可完成集成。

**MUST 包含**：用途 → 鉴权方式 → 请求参数（类型/必填/默认值）→ 返回结构 → 错误码 → 调用示例 → 幂等与限流 → 版本与兼容说明。

**规则**：
- 本项目后端为单应用 Flask，API 契约在 `docs/02-技术与架构/API文档/` 中有一处权威描述；
- 参数表必须标注类型（`string` / `number` / `boolean` / `object` / `array` / `file`）；
- 错误码必须与 [开发规范 · 错误处理](../02-技术与架构/开发规范/01-基础约定与后端规范.md#33-错误处理) 一致（400/401/404/500/502），禁止自定义 `-1`。

### 2.7 测试与验收报告

**定位**：用可复核的证据回答"是否达标"。

**MUST 包含**：测试范围 → 环境与版本（commit / Python 版本 / 依赖版本）→ 用例与结果表 → 缺陷清单 → 结论（通过 / 有条件通过 / 不通过）→ 证据（日志、截图）链接。

**禁止**：只写"测试通过"而没有用例、数据或证据链接。

### 2.8 BUG 修复报告

**定位**：可防复发的完整闭环记录。

**MUST 包含**：复现步骤（未复现不得进入修复）→ 影响范围 → 根因 → 修复方案（最小改动）→ 单元测试 → 手动验证步骤 → 涉及文件清单。

### 2.9 变更日志

**定位**：已上线功能的增量变更记录，用于审计与回滚。

**MUST 包含**：变更编号 → 日期 → 变更类型（Tweak / Extension / Refactor）→ 影响面 → 变更前后对比 → 验证结论 → 回滚方式。

**命名**：`YYYY-MM-DD-<功能>-变更<NN>.md`；小改动可直接追加到原文档并标注变更标记。

### 2.10 运维手册

**定位**：让任意一名研发在无人交接的情况下完成部署、验证与回滚。

**MUST 包含**：前置条件与环境 → 编号执行步骤 → 每步校验命令与预期输出 → 回滚步骤 → 应急联系人与升级路径。

**规则**：所有命令必须可直接复制执行；涉及密钥只写变量名，禁止写明文。

**本项目特有**：部署涉及 `start.bat` / `start.sh` 一键启动，及 `data/global_config.json` 与 `data/works/*.json` 的备份/迁移；PAT Token 与管理密码不得明文出现。

### 2.11 架构决策记录（ADR）

**定位**：记录"当时为什么这样选"，防止后来者反复推翻。

**MUST 包含**：状态（提议 / 已采纳 / 已废弃 / 被替代）→ 背景与约束 → 决策 → 备选方案及取舍 → 后果（正面/负面）→ 关联决策。

**规则**：ADR 一经采纳不再改写结论，只能新增"被替代"记录并链接新 ADR。

### 2.12 规划与路线

**定位**：目标、顺序与依赖的唯一权威来源。

**MUST 包含**：目标与衡量指标 → 里程碑与范围 → 依赖与阻塞 → 风险与应对 → 验收标准。

**规则**：多份规划文档并存时，必须在卷首声明权威口径与生效日期。

### 2.13 工作流规范

**定位**：团队协作的可执行流程。

**MUST 包含**：触发条件 → 输入 → 步骤 → 产出物 → 边界（禁止事项）→ 检查清单。

**示例**：[本规范](./文档编写规范.md)。

### 2.14 分类判定

按以下顺序判定，命中即停：

1. 是否描述"用户要什么"？→ 产品文档
2. 是否描述"系统怎么实现"？→ 技术文档 / ADR / 功能交付档案
3. 是否是某次验证的证据？→ 测试与验收报告
4. 是否是某次故障的闭环？→ BUG 修复报告
5. 是否是上线执行步骤？→ 运维手册
6. 是否是团队协作规则？→ 工作流规范
7. 是否是过程留痕？→ 历史日志

## 三、格式标准

### 3.1 文件与命名（MUST）

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 类别目录 | `NN-中文类别名` | `02-技术与架构` |
| 单篇文档 | 中文名，体现核心内容与用途 | `项目结构.md` |
| 功能档案分册 | `NN-中文分册名.md`（NN 固定序号） | `01-需求澄清.md` |
| 分册组 | `<主题>/README.md` + `NN-中文分册名.md` | `F1-资源拉取与批量导入/01-需求澄清.md` |
| 索引文件 | 固定 `README.md` | `docs/README.md` |
| 变更日志 | `YYYY-MM-DD-<功能>-变更<NN>.md` | `2026-11-10-在线体验变更01.md` |
| ADR | `NNNN-中文决策名.md` | `0001-PAT令牌迁移环境变量决策.md` |

**禁止**：英文短语文件名、空格、`_` 连接、大小写混排、无意义缩写（`tmp`、`new`、`doc1`）。

**技术缩写白名单**：`API`、`BUG`、`ADR`、`CI`、`PAT`、`SSE`、`SPA`、`JSON`、`HTTP`、`LLM`、`XSS`、`Coze`。白名单之外一律中文。

### 3.2 文档头（MUST，长期维护型文档）

技术文档、产品文档、设计文档、工作流规范、运维手册必须在 H1 之后紧跟一行或多行引用块，包含：

```markdown
> 版本：v1.0 · 状态：生效（YYYY-MM-DD）
> 适用范围：……
> 维护：……｜关联：[xxx](./xxx.md)
```

功能交付档案分册额外增加一行（关联需求/方案/任务分册）：

```markdown
> 对应需求：[01-需求澄清.md](./01-需求澄清.md)
```

测试报告、BUG 报告、变更日志、ADR、历史日志可省略版本行，但必须注明**日期**与**结论/状态**。

### 3.3 标题层级（MUST）

- 每篇文档**有且仅有一个 H1**，内容为文档标题，不以编号开头。
- H2 使用中文序号：`## 一、总则`；H3 使用阿拉伯序号：`### 1.1 目的`；H4 使用 `#### 1.1.1`。
- **禁止 H5 及更深**；超过三层时改用列表或拆分为分册。
- **禁止跳级**（H1 → H3）；标题之间必须有正文，不允许两个标题紧邻。
- 标题不超过 30 字，结尾不加标点（问句除外）。

### 3.4 段落（SHOULD）

- 一段只讲一个观点，控制在 5 行以内。
- 结论先行：先写判断，再写原因与证据。
- 禁止"如上所述""众所周知""显而易见"等无信息量衔接语。
- 长句拆短：单句不超过 60 字；并列超过 3 项改用列表。

### 3.5 列表（MUST）

| 场景 | 规则 |
| --- | --- |
| 无序枚举 | 使用 `-`，禁止 `•`、`●`、`*` 混用 |
| 有序步骤 | 使用 `1.` 连续编号，每项一个动作 |
| 嵌套 | 最多 3 级，缩进 2 空格 |
| 句式 | 同级各项句式结构一致（都是动宾短语或都是完整句） |
| 标点 | 短语项不加句号；完整句项加句号，同级统一 |
| 键值对 | 3 组以上改用表格 |

### 3.6 代码块（MUST）

- 必须标注语言：`python`、`javascript`、`css`、`html`、`jinja`、`json`、`bash`、`powershell`、`text`、`markdown`。
- 禁止行号、禁止硬制表符、缩进统一 4 空格（Python）或 2 空格（JS/CSS）。
- 单块不超过 60 行；超长代码改为"关键片段 + 文件链接"。
- 代码块前后各一句话说明"这段是什么、关键点在哪"。
- 示例必须来自真实代码或可运行的最小例；伪代码必须显式标注 `// 伪代码`。
- 命令块必须可直接复制执行，包含必要的 `cwd` 说明。

### 3.7 行内代码（MUST）

以下内容一律使用行内代码：文件名、目录路径、命令、变量名、函数名、配置键、状态码、表名、环境变量。

```markdown
修改 `work_manager.py` 的 `get_work_public()`，错误码参考 `401`。
```

### 3.8 引用块与状态标记（MUST）

- 引用块用于：提示、警告、决策、来源、已落地状态。
- 首行必须带标签：`【必读】`、`【注意】`、`【禁止】`、`【决策】`、`【已落地】`、`【来源】`。
- 引用块不超过 3 段；内部禁止嵌套代码块（模板示例除外）。
- 状态文字统一为：**已落地**、**待确认**、**计划中**、**已废弃**、**冻结**；禁止使用 Emoji。

```markdown
> 【禁止】在生产环境将 PAT Token 硬编码在 `data/global_config.json` 中。
```

### 3.9 表格（MUST）

- 必须有表头与分隔行；列数不超过 6 列，超出时拆分或改列表。
- 单元格内容不超过 2 行，禁止在单元格内换行、嵌套列表或代码块。
- 说明性文字放最后一列；数值列右对齐，文本列左对齐。
- 表格前必须有一句引导语；数据表必须标注**单位与口径**。
- 禁止空单元格，缺数据写 `—` 并说明原因。

### 3.10 图片与图示（SHOULD）

- 存放于文档同级 `assets/` 目录，命名 `功能-序号-描述.png`。
- 必须写 alt 文本，图下加说明：`*图 1：数据流*`。
- 格式优先 `SVG`（架构图/流程图）或 `PNG`（截图）；单图不超过 500 KB。
- 禁止外链图床；禁止用截图代替可复制文本（代码、命令、错误码）。
- 架构与流程优先用 Mermaid 或 SVG 描述，保证可 diff、可检索。
- 截图必须脱敏：PAT Token、密码、手机号、真实作品 ID 一律打码。

### 3.11 链接（MUST）

- 站内引用用相对路径，链接文字必须是目标文档标题或明确的语义描述。
- 禁止"点击这里""详见此处"等无指向文字。
- 外链必须 `https://`，并在文末"参考来源"列出标题与访问日期。
- 锚点使用小写英文连字符；链接必须可解析，死链视为 P0。
- **禁止**使用 `file:///` 绝对路径链接；一律改用相对路径（跨目录用 `../`、`../../`）。

### 3.12 数字、单位与时间（MUST）

| 对象 | 规则 |
| --- | --- |
| 百分比 | 保留 1 位小数（`-35.7%`） |
| 日期 | `YYYY-MM-DD`（`2026-11-10`） |
| 时间 | `HH:mm`，默认时区 `Asia/Shanghai` |
| 文件大小 | `KB` / `MB`，保留 1 位小数 |
| 版本号 | `v主.次`（`v1.0`）；代码依赖写完整语义版本（`2.3.0`） |
| 延迟 | 毫秒（`ms`），如 Coze 流式响应首包 `< 500 ms` |

### 3.13 强调与字体（MUST）

- Markdown 不携带字体信息，渲染效果由平台统一控制；**禁止**使用 HTML `style`、`font`、`color` 标签改字体或字号。
- 粗体只用于结论、禁令、关键术语；每段不超过 2 处，禁止整段加粗。
- 不使用斜体表示强调（斜体仅保留给书名、引用原文）。
- 代码、命令、路径必须用行内代码，不用粗体代替。

### 3.14 导航头与分册结构（MUST）

分册首部固定两行：

```markdown
> 所属：[《母文档》分册索引](./README.md)｜第 i / n 篇
> 上一篇：[…](./xx.md)｜下一篇：[…](./yy.md)
```

分册索引（`README.md`）必须包含：

1. 来源说明（原文规模、归档链接、返回总索引链接）；
2. `## 篇章导航` 表（编号 / 篇章 / 内容概要 / 原文章节）；
3. `## 阅读路径`（顺序阅读、按需跳读、回溯原文）。

**拆分阈值**：单篇 ≥ 1000 行或 ≥ 60 KB 必须拆分；分册篇幅以 40–250 行为宜；索引不超过 150 行。

### 4.3 完整性（MUST）

- 禁止遗留 `TODO`、`待补充`、`TBD`；确需延后时必须写"负责人 + 截止里程碑 + 影响说明"。
- 每个结论必须有依据（代码位置、测试结果、数据、决策记录）。
- 功能交付档案的"需求 → 方案 → 任务 → 实施 → 验证"链条必须闭合。
- 删除内容时保留变更记录，禁止静默删改结论。

### 4.4 准确性（MUST）

- 命令、路径、接口名、字段名必须与当前代码一致；以 `main` 分支为准。
- 数据必须标注时点与来源。
- 不使用"大概""可能""应该"描述事实；不确定的内容写"待确认"并标注责任人。
- 版本、依赖、错误码引用必须写明出处章节或链接。
- 引用外部资料必须标注作者/组织、标题、链接与访问日期。

### 4.5 术语统一（MUST）

| 术语 | 定义 | 禁止同义词 |
| --- | --- | --- |
| 作品 | 从 Coze 拉取并导入的展示单元（bot / workflow / dataset） | 智能体、条目（泛指时） |
| 访问码 | 控制作品体验入口的口令（可选） | 密码（与管理员密码区分） |
| 体验者 | 浏览并在线体验作品的访客 | 用户、游客（泛指时） |
| 管理员 | 管理后台操作者 | 站长 |
| PAT Token | Coze 个人访问令牌（Personal Access Token） | token、密钥（泛指时） |
| 交互模式 | 作品体验方式：`chat` / `form` / `mixed` | 类型、方式 |
| SSE | 服务器发送事件（Server-Sent Events） | 流式、EventSource |

- 新术语必须先在本文档 §8.2 核心术语表登记，再在文档中使用。
- 首次出现采用"中文（English，缩写）"格式，如"个人访问令牌（Personal Access Token，PAT Token）"。

### 4.6 篇幅与拆分（MUST）

- 单篇超过 1000 行或 60 KB 必须拆分。
- 分册正文逐字保留原文，只新增导航头与"（续）"标题链，不改写、不删减。
- 拆分前原文必须归档到 `docs-archive/`。

### 4.7 代码与命令示例（MUST）

- 示例优先取自真实代码，并标注文件路径。
- 命令示例必须给出完整可执行形式（含包管理器、参数、预期输出）。
- 示例中的 PAT Token、密码、访问码一律替换为占位符：`<PAT>`、`<PASSWORD>`、`<ACCESS_CODE>`。
- 禁止粘贴超过 60 行的整文件；用"关键片段 + 文件链接"替代。

### 4.8 安全与脱敏（MUST）

- 禁止写入任何 PAT Token、管理密码、访问码明文、私钥、证书。
- 敏感配置只写变量名与配置位置，不写值（如 `data/global_config.json` 的 `admin_password` 字段名，不写实际密码）。
- 截图与日志摘录必须脱敏；无法脱敏时改用文字描述。
- 外部链接必须为公开可访问地址，禁止内网地址与带 token 的 URL。

## 五、编写流程

### 5.1 生命周期（MUST）

```text
需求触发 → 分类与落点 → 撰写 → 作者自检 → 同行评审 → 发布（入索引） → 维护更新 → 归档 / 废弃
```

任何环节不得跳步；**未在 `docs/README.md` 登记索引的文档视为未发布**。

### 5.2 角色与职责

| 角色 | 职责 |
| --- | --- |
| 作者 | 确定分类与落点、按模板撰写、完成自检、响应评审意见 |
| 评审人 | 事实正确性（技术/产品负责人）、结构完整性、格式合规性 |
| 发布人（文档维护人） | 更新索引与导航、校验链接、合并发布 |

单人项目可兼任多个角色，但**自检与评审至少分离一人**；本项目为单人维护，可自评自审，但必须保留评审痕迹（见 6.4）。

### 5.3 作者自检清单（MUST）

发布前作者必须自查并勾选以下 10 项：

- [ ] 分类正确、落点目录正确（§2.14）
- [ ] 文档头完整（版本/状态/适用范围/维护/关联）
- [ ] 唯一 H1、无跳级、无 H5
- [ ] 无 `file:///` 绝对链接、无死链
- [ ] 代码块均标注语言、无行号
- [ ] 表格有表头、≤6 列、无空单元格
- [ ] 无 TODO/TBD/待补充
- [ ] 无敏感信息明文（PAT/密码/访问码）
- [ ] 术语统一（§4.5）
- [ ] 篇幅 ≤1000 行且 ≤60 KB

### 5.4 同行评审要点（SHOULD）

- 技术/产品事实是否正确（对照代码与验收标准）；
- 结论是否可执行、可验证；
- 是否与既有文档冲突（SSOT 检查）；
- 引用链接是否可解析。

### 5.5 发布（MUST）

- 更新 `docs/README.md` 索引（新增/变更条目）；
- 更新所属功能档案 `README.md` 导航（功能级文档）；
- 校验全部链接（可执行脚本或人工检查）；
- 在 `09-历史日志/` 记录发布事件（可选，重大文档必记）。

### 5.6 维护更新（MUST）

- 仅维护人可改动已发布文档；
- 改动后同步更新文档头版本号与日期；
- 涉及代码/配置变更时，按 §5.7 更新触发表同步相关文档；
- 禁止静默删改结论；删除内容必须保留变更记录。

### 5.7 更新触发表（MUST）

| 代码/配置变更 | 必须同步文档 |
| --- | --- |
| 新增/移除功能 | `01-产品与设计/项目概述.md` |

**硬约束**：代码变更提交时，文档同步必须同 commit 或紧随其后的 commit 完成；未同步视为未完成。

### 5.8 归档与废弃（MUST）

- 废弃文档移入 `docs-archive/`（保留原文，可追溯）；
- 归档前在 `docs/README.md` 标注状态为"已归档"，并记录归档日期与去向；
