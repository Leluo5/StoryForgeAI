## 一、分支模型

| 分支 | 用途 | 规则 |
|------|------|------|
| `main` | 稳定可发布 | 禁止直接 push；只接受 `merge` 或 `rebase` |
| `develop` | 集成分支 | 功能完成合入；保持可运行 |
| `feature/<模块>-<短描述>` | 新功能 | 从 `develop` 切出，完成后合回 |
| `fix/<bug-短描述>` | 缺陷修复 | 从 `develop` 切出，修复后合回 |
| `docs/<描述>` | 纯文档改动 | 不涉及代码 |

- 禁止在 `main`/`develop` 上直接提交代码改动。
- 分支命名小写、用 `-` 分隔（`feature/knowledge-markdown-io`）。
- 功能分支保持短生命周期（≤ 5 个提交），避免长期分叉。

## 二、Conventional Commits

提交信息采用 **[Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/)** 规范：

```
<type>(<scope>): <subject>

[body]
```

| type | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(knowledge): 增加 Markdown 导入导出` |
| `fix` | 缺陷修复 | `fix(knowledge): 修复 identical+rename 边界统计` |
| `docs` | 文档变更 | `docs(dev-standards): 拆分开发规范为多分册` |
| `refactor` | 重构（无行为变化） | `refactor(common): 统一错误响应契约` |
| `test` | 测试变更 | `test(markdown-io): 补充 rename 边界回归` |
| `chore` | 构建/工具/杂项 | `chore: 更新 .gitignore` |
| `perf` | 性能优化 | `perf(coze): 缓存 token 校验` |

**规则**：
- `type` 必填，`scope` 建议（模块名），`subject` 用中文、≤ 50 字符、不加句号。
- 破坏性变更在 `body` 加 `BREAKING CHANGE:`。
- 一个提交只做一件事；禁止 `feat` 混入 `docs`。
- 关联 issue 用 `Refs: #<id>`。

## 三、提交前检查

每次 commit 前（或 `git add` 后）自查：

| 检查项 | 要求 |
|--------|------|
| 无敏感信息 | 不含 PAT Token、access_code、密钥（见 [04-安全与数据规范](./04-安全与数据规范.md)） |
| 无调试残留 | 无 `print()` / `console.log()` / `debugger` / 注释掉的死代码 |
| 无临时文件 | 无 `*.tmp`、`*.bak`、`node_modules/`、`__pycache__/` |
| 测试通过 | 全量 `pytest`（或受影响用例）绿 |
| 规范合规 | 符合本规范 01/02/04/05 分册 |
| 文档同步 | 涉及代码变更时同步需求/方案文档（见第五节） |

**提交前命令（PowerShell）**：

```powershell
git add -A
git status  # 检查暂存内容
git diff --cached --stat  # 确认改动范围
```

## 四、AI 协作协议

> 【必读】本项目大量开发由 AI 助手（Trae / 商汤「商量」等）完成，需在提示词与协作中明确约束。

| 场景 | 约束 |
|------|------|
| 任务分派 | 单次任务 ≤ 2 小时、单一职责；明确「完成标准」与「验收文件」 |
| 上下文 | AI 开工前必须读取 `docs/` 目录下相关文档（项目工作流 §二） |
| 越界拦截 | AI 在需求阶段不写代码、设计阶段不写实现、编码阶段不改需求（边界守卫） |
| 代码生成 | 严格遵循本规范 01/02 分册（命名/错误处理/安全） |
| 文档同步 | 改代码必同步文档；AI 完成后主动更新对应分册与验收标准 |
| 验证 | AI 完成代码后必须跑测试并附测试输出，禁止口头声明通过 |
| 提交 | AI 不主动 commit；由用户确认后按第二节规范提交 |

## 五、文档同步规范

### 5.1 同步触发（代码改动必查）

| 代码改动类型 | 必同步文档 |
|-------------|-----------|
| 新增/修改 API 端点 | `技术方案.md`（接口设计）、`使用文档.md`（如有） |
| 新增/修改数据字段 | `技术方案.md`（数据模型）、需求澄清（验收标准） |
| 新增/修改前端组件 | `技术方案.md`（前端设计）、`使用文档.md` |
| 修改错误码/契约 | `技术方案.md`（异常处理）、`04-安全与数据规范.md` |
| 修复 BUG | `docs/BUG修复文档/` 下新建修复报告 |

### 5.2 同步要求

- **增量更新**，不推倒重写；保留版本号与变更历史。
- 功能文档路径：`docs/04-功能交付档案/<功能名>/`（01-需求澄清 / 02-技术方案 / 03-任务规划 / 04-使用文档）。
- 文档与实现不一致时，代码任务完成前必须完成文档同步，或明确标注「延后原因 + 里程碑」。
- 涉及「已知边界」的修复，必须在文档 FAQ 或异常边界章节同步描述，避免二次踩坑。

## 六、代码审查约定

- 合并前由非作者审查（或 AI 审查辅助），重点：命名、错误处理、安全（XSS/注入/越权）、测试覆盖。
- 单次 MR 变更 ≤ 500 行（超出需说明拆分理由）。
- 审查发现 `[MUST]` 违规 → 打回；`[SHOULD]` → 记录并限期整改。
