## 二、背景与约束

### 2.1 问题

M3c-2 角色版图需要把「角色已归档」提示精确落到正文的**具体段落**。此前章节级方案存在两类缺陷：

1. **漏报**：原设计只按成长事件关联章节派生标记，正文提到该角色但未建成长事件的章节完全没有提示。
2. **噪声**：若改为整章提示，一个长章节里只有一句提到角色，作者也难以定位。

要做到段落级提示，必须先能稳定识别「同一个段落」。而现有正文模型存在客观限制：

- 正文权威格式是 ProseMirror JSON，存于 `chapters.document`；
- 段落节点**没有任何稳定标识**，只能靠数组下标或文本内容定位；
- 章节有 `version` 与 `content_hash`，粒度是整章。

### 2.2 约束

| 约束 | 内容 |
| --- | --- |
| 正文唯一源 | ProseMirror JSON 是唯一正文，Markdown 只是编辑与导出视图，不建立第二份正文（[系统设计 §6.1](../../superpowers/specs/2026-11-15-writing-workbench-system-design.md)） |
| 业务元数据边界 | 评论、待办、修订、通知等业务元数据保存在独立关系模型，不混入正文 JSON |
| 正文不可破坏 | 归档与恢复不得改写、删除、锁定正文文字 |
| 可逆与幂等 | 恢复后正文逐字一致；重复操作无副作用 |
| 兼容存量 | 已交付章节的正文与历史版本快照必须继续可读、可对比 |

---

## 三、决策

**在 ProseMirror 块级文本节点上引入稳定属性 `pid`，定位为「排版稳定性标识」，不作为业务元数据。**

核心决策点：

1. **范围**：至少 `paragraph`，`heading`、`blockquote` 按实际需要声明；`pid` 由 `editor-schema` 的 Schema 声明，契约层允许并校验格式与唯一性。
2. **语义边界**：`pid` 不携带角色、关系、归档、归属等任何业务含义；归档状态全部存放在独立的锚点与归属表中。
3. **哈希边界**：`canonicalizeDocument` 与 `content_hash` 计算时忽略 `pid`，避免纯标识变化被误判为正文变更。
4. **生成规则**：新建段落、回车拆分、粘贴、AI 建树写入、Markdown 导入、跨作品导入时统一分配；合并段落保留锚点所属一侧的 `pid`；保存与契约解析时校验唯一性。
5. **存量兼容**：历史正文采用「读取时惰性补 `pid`、保存时固化」，历史版本快照保持只读、不回溯改写。
6. **恢复零写入**：角色恢复只改变锚点状态，正文 JSON 不产生任何写入。

### 3.1 边界示意

```text
正文 JSON（唯一正文源）
  └─ paragraph { pid: "…" , content: [文本] }   ← pid 仅为排版身份
业务元数据（独立关系模型）
  ├─ character_text_anchors(chapter_id, paragraph_pid, status)
  └─ plot_node_character_owners(node_id, character_id, is_exclusive)
```

## 四、备选方案及取舍

| 方案 | 描述 | 取舍理由 |
| --- | --- | --- |
| **A. 正文块级 pid（采纳）** | 段落携带稳定 `pid`，锚点表以 pid 关联 | 段落身份稳定、可跨编辑重定位；代价是正文契约变更与存量回填，需回归依赖正文的模块 |
| **B. 独立锚点表 + 文本指纹** | 不碰正文，锚点存段落序号 + 文本哈希 + 摘录 | 不违 §6.1 原则；但作者一改字指纹即失效，漂移率高，段落增删后定位不准 |
| **C. 实时全文扫描** | 不落库，每次打开章节扫描角色名与别名 | 实现最轻；但重复扫描成本高，同名普通词误报难控，且无法承载「剔除误报」的持久状态 |

**选择 A 的理由**：段落级提示的价值取决于定位稳定性，B 在真实改稿场景下会大面积失效，C 无法表达作者对误报的处置。A 的代价是可控且可验证的工程回归，不是语义失控。

## 五、后果

### 5.1 正面

- 段落级锚点具备稳定身份，编辑后可通过 pid + 文本校验判断是否失效，失效时降级为整章提示。
- 归档与恢复都能做到正文零写入，满足「恢复前后正文逐字一致」。
- `content_hash` 忽略 pid 后，版本快照、修订 diff、审批流不会被纯标识变化污染。

### 5.2 负面 / 成本

- **正文契约变更**：`editor-schema`、`packages/contracts`、Markdown 双向转换、编辑器节点创建逻辑都需改动。
- **跨模块回归**：M1 章节保存与版本快照、M2 变更协作与审批 diff、M3a AI 整篇替换、M3c-1 剧情自动建树写正文、撤销重做、导入导出，均需回归验证。
- **存量回填**：历史正文需要惰性补 `pid`，任何遗漏都会让旧段落暂时无法被锚定。
- **原则例外**：这是对「业务元数据不混入正文」的一次有意例外，必须长期守住「`pid` 无业务语义」这条线，否则边界会被逐步侵蚀。

## 七、验证方式

1. **契约与唯一性**：同一文档内 `pid` 唯一；跨作品导入后全部重新分配，无重复。
2. **哈希中立**：仅改变 `pid` 不改变 `content_hash`；正文文字变化必须改变 `content_hash`。
3. **往返一致**：ProseMirror ↔ Markdown 双向转换不丢节点、不丢文字；导出丢弃 pid、导入重新生成。
4. **存量兼容**：历史章节打开、保存、版本对比、修订 diff 全部正常，旧快照仍可读取。
5. **归档端到端**：归档 → 命中段落显示标记 → 剔除误报 → 编辑后降级整章 → 恢复后标记消失且正文逐字一致。
6. **回归清单**：M1/M2/M3a/M3c-1 依赖正文的相关用例全部通过。
