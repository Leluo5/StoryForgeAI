# StoryForgeAI 开发规范

> 版本：v1.0 · 状态：生效（2026-11-10）
> 项目：StoryForgeAI —— Coze（扣子）作品展示与在线体验平台
> 类型：技术文档
> 维护：02-技术与架构｜关联：[文档中心](../README.md)、[项目概述](../01-产品与设计/项目概述.md)
> 适用范围：本项目后端（Python/Flask）与前端（原生 JS/CSS/HTML）代码

---

## 一、总则

1. **规范目的**：保证代码风格统一、命名一致、错误处理可预期、Git 工作流可追踪，让 AI 协作与人工维护都高效。
2. **强制约束**：下列规则均为**硬性要求**，每条附正确/错误对比。禁止出现「遵循最佳实践」这类无明确动作的表述。
3. **优先级**：本规范冲突时，按 `后端规范 > 前端规范 > Git 工作流 > 安全规范` 顺序执行。

## 二、后端规范（Python / Flask）

### 2.1 代码风格

| 规则 | 正确示例 | 错误示例 |
|------|---------|---------|
| 缩进 | 4 空格（禁 Tab） | `\t` 缩进 |
| 行宽 | ≤ 100 字符 | 长行无断行 |
| 引号 | 统一双引号 `"` | 混用单双引号 |
| 命名（函数/变量） | `snake_case`：`get_work_public()` | `camelCase`、`GetWork()` |
| 命名（常量） | `UPPER_SNAKE_CASE`：`DEFAULT_TIMEOUT` | `defaultTimeout` |
| 命名（类） | `PascalCase`：`WorkManager` | `work_manager` |
| 导入顺序 | 标准库 → 第三方 → 本地，每组空行 | 随意混排 |
| 编码 | 文件头部声明 `# -*- coding: utf-8 -*-`（如含中文） | 缺失声明 |

### 2.2 函数设计

- 单一职责：一个函数只做一件事，超 30 行需考虑拆分。
- 参数 ≤ 5 个；超过时用 dict / dataclass 聚合。
- 必须包含 docstring（模块级、公开函数级），说明入参、返回、异常。
- 返回类型保持一致：成功返回 `data`，失败返回 `(None, error_msg)` 或抛异常，**不要混用**。

### 2.3 错误处理

```python
# ✅ 推荐：集中错误处理，明确错误信息
try:
    resp = coze_client.get_bots(pat)
except CozeAPIError as e:
    return jsonify({"error": f"Coze 调用失败: {e.message}"}), 502
```

- 禁止裸 `except:` 吞掉所有异常（应捕获具体异常）。
- 所有 API 返回错误必须统一结构：`{"error": "<可读信息>"}`，HTTP 状态码区分语义（400 参数 / 401 鉴权 / 404 未找到 / 500 服务器 / 502 上游）。
- 日志用 `app.logger` 或标准 `logging`，禁止 `print()` 调试残留。

### 2.4 路由与接口规范

- 路由函数保持**薄**（只做参数解析 + 调用 service + 序列化响应），业务逻辑下沉到 `coze_client` / `work_manager`。
- RESTful 语义：
  - `GET /api/works` 列表、`GET /api/works/<id>` 详情
  - `POST /api/admin/login` 创建会话
  - `PUT /api/admin/config` 更新配置
  - `DELETE /api/admin/works/<id>` 删除
- 参数校验：所有用户输入（含 query/body）必须校验类型与边界，非法输入返回 400。
- 敏感字段（PAT Token、access_code）**只进不出**：任何对外响应必须经 `get_work_public()` 过滤。

### 2.5 SSE 流式接口约定

- 响应头：`Content-Type: text/event-stream`，`Cache-Control: no-cache`。
- 事件格式：`data: {json}\n\n`，每事件独立换行。
- 结束时发送 `event: done` 或 `data: {"done": true}`。
- 必须处理客户端断开（`GeneratorExit` / `try-finally` 释放连接）。
- 禁止在 SSE 中发送非 JSON 文本（会破坏前端解析）。

## 三、前端规范（原生 JS / CSS / HTML）

### 3.1 JavaScript

| 规则 | 正确示例 | 错误示例 |
|------|---------|---------|
| 作用域 | IIFE 包裹，`'use strict'` | 全局变量泄漏 |
| 命名（变量/函数） | `camelCase`：`currentWorkId` | `snake_case`、`CurrentWork` |
| 命名（常量） | `UPPER_SNAKE_CASE`：`PARAM_TYPES` | `paramTypes` |
| 命名（DOM id/class） | `kebab-case`：`work-card` | `workCard` |
| 比较 | 全等 `===` / `!==` | `==` / `!=` |
| 声明 | `const` 优先，需重新赋值才用 `let` | 随意 `var` |
| 分号 | 统一使用 | 混用或省略 |

### 3.2 前端状态管理约定（重要）

- 全局状态**只经** `state` 对象读写（见 [app.js](static/js/app.js)），禁止散落临时全局变量。
- 视图切换统一走 `renderView(viewName)`，禁止直接 `display` 切换绕过。
- DOM 操作集中：创建元素用 `createElement` / `innerHTML` 模板，**所有动态内容必须转义**（防 XSS）。

```javascript
// ✅ 转义动态内容
el.textContent = work.name;   // 不要用 el.innerHTML = work.name
```

### 3.3 API 请求封装

- 所有请求必须走 `api.request()` 统一封装（自动加 `Content-Type`、统一错误抛出）。
- 错误处理：`catch` 中调用统一 `showToast/error` 反馈，禁止空 `catch{}`。
- 请求前设置 `isStreaming`/loading 状态，请求后（含 `finally`）必须复位，防止 UI 卡死。

### 3.4 CSS

- 统一用 **CSS 变量**管理主题色（浅/深），颜色值集中定义，禁止散落硬编码颜色。
- 类名 `kebab-case`，命名带语义（如 `.work-card__title`），避免深层嵌套选择器。
- 响应式：关键布局断点（<768px 移动端）必须验证，禁止固定宽度撑破。
- 避免 `!important` 滥用；确需覆盖时注释原因。

### 3.5 HTML / 模板

- 语义化标签（`header/main/section/nav`），避免纯 `div` 堆砌。
- 所有交互元素（按钮/输入）需 `aria-label` / `type` 明确。
- 模板中 `{{ }}` 变量输出必须经 Jinja2 自动转义，禁 `|safe` 用于用户内容。

## 四、Git 工作流

### 4.1 分支模型

| 分支 | 用途 | 说明 |
|------|------|------|
| `main` | 生产/稳定 | 始终可运行 |
| `dev` | 集成开发 | 功能开发汇入 |
| `feature/<名称>` | 新功能 | 从 `dev` 拉出 |
| `fix/<名称>` | BUG 修复 | 从 `dev` 拉出 |

### 4.2 Commit Message 规范

采用 **Conventional Commits**：

```text
<type>(<scope>): <subject>
```

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 BUG |
| `refactor` | 重构（不改行为） |
| `docs` | 文档 |
| `style` | 格式（不改逻辑） |
| `test` | 测试 |
| `chore` | 构建/依赖 |

示例：
```text
feat(admin): 支持 AI 识别截图生成参数结构
fix(work): 修复访问码验证后 token 未持久化问题
docs: 更新项目概述与技术栈文档
```

- subject ≤ 72 字符，动词开头，现在时。
- 一次 commit 只做一件事（一个 type + 一个 scope）。

### 4.3 提交前检查

- 无 `print()` / `console.log()` 调试残留。
- 无未使用的 import / 变量。
- 无敏感信息（PAT Token、密码）进入提交。
- 运行 `python -m py_compile app.py` 确认语法通过。

## 五、安全规范（硬约束）

| # | 规则 | 要求 |
|---|------|------|
| 1 | 管理鉴权 | 所有 `/api/admin/*` 必须校验会话；`require_admin` 装饰器不得为空壳实现 |
| 2 | 密码存储 | 禁止明文；改用 `werkzeug.security` 哈希或环境变量 |
| 3 | PAT Token | 禁止落盘明文；迁移至环境变量 / 密钥服务；响应层必须过滤 |
| 4 | XSS | 前端渲染用户内容必须 `textContent` / 转义，禁 `innerHTML` 直插 |
| 5 | 注入 | 参数类型转换用白名单（`PARAM_TYPES`），禁止 eval/exec |
| 6 | 访问码 | 校验失败统一返回 401，不泄露是否存在；限制尝试次数 |
| 7 | SSE | 禁止把上游错误原文直接透传给前端（可能含敏感信息） |

## 六、AI 协作协议

1. **先读文档再动手**：改动前必读 `项目概述.md` / `技术栈.md` / `目录结构.md` / 本规范。
2. **一次只做一件事**：一条指令只对应一个功能/修复，禁止混改。
3. **改动范围最小**：只改任务相关代码，不做无关重构、不顺手改格式。
4. **改代码必同步文档**：功能变更后更新对应文档，否则视为未完成。
5. **测试**：新增功能/修复后运行基本验证（启动服务 + 手动走一遍关键流程）。
6. **验收标准**：每条需求有明确「完成标准」，无验收标准不得开始编码。
